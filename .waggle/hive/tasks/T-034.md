## 1. Goal

Three gaps in how dispatch picks a guard's model, each of which costs the queen a manual step or a Keeper card today:

1. **Confirming guards do not alternate.** D-205: a fix round gets one confirming guard, alternating between the two guard models round to round, and after a single confirming guard finds a must-fix, the other model confirms the next round. A plain guard run resolves its model from policy alone (`Resolve` with the builder's model avoided), so every confirming guard gets the round 1 first guard model. On T-029 the confirming guard ran on opus, the round 1 model, and D-205 alternation was not met (D-228). Dispatch has no model flag by design (`cmd/waggle/dispatch.go`: no flag lowers a model or forces), so the queen cannot fix it from the command line.
2. **`--second` refuses an ancestor builder base.** `checkSecond` (`guard.go`) requires the latest builder run, the latest first guard run and the second guard to share one `base_oid`. On T-029 the builder ran at `217e81e` and the first guard at `60a9d57`, two commits later on main (the round 2 Colima evidence), so the fable `--second` refused (D-228). The builder's code did not change between the two bases; only hive records did.
3. **The no-cross-model hint names the wrong level.** When the second guard finds no model, the error from `pick` (`policy.go`, the `ErrNoCrossModel` format string) says `map a model not already used, for example runtimes.adapters.<adapter>.alternates.<level>`, where `<level>` is the guard's own level. On this hive before D-224 (opus, sonnet, haiku; builder and guard minimum standard; no alternates) it said `alternates.standard`. Following it moves the wrong guard: `pick` tries a level's alternate before moving up a level, so a standard alternate becomes the first guard on every ticket. On a fresh ticket the second guard would then resolve opus, but the first guard model changes for every Tier 3 review, and on T-027, whose first guard had already run on opus, the re-resolved pair no longer matched the record and `checkSecond` would still have refused (D-224 rationale). The level that keeps the first guard where it is and gives the second guard a model was `frontier`, the level the first guard's model sits at.

## 2. Design

### 2.1 Item 1: the previous round's guard model, and alternation

**Where the history is (Q-T034-1, recommended (a)).** Dispatch already writes one `result.json` per run under `.waggle/worktrees/runs/<ticket>-<role>-<seq>/` with `branch`, `model`, `head_oid`, `verdict` and `second`, and `checkSecond` already trusts these records (D-188). Review markers on base (D-248) carry `verdict` and `head` but no model, and the model appears only in the queen's file name convention (`T-<nnn><suffix>-<model>.md`), so base reviews cannot order rounds or name models without new formats. The design below uses the run records.

**Rounds.** A round is the guard runs on one branch head. For a guard run under review of head `H` on branch `B`:

- A **usable guard record** has `second: false`, `branch` equal to `B`, a non-empty `verdict` and `end` equal to `done` (a run that parsed a verdict but ended in violations or another failure is not a round the queen commits). Records of another branch (phase suffix) or another ticket are skipped, as are unreadable, oversize (over `maxBrief`, as today), symlinked or malformed records. `<seq>` compares as a number (`guard-10` after `guard-9`), as the current reader does.
- The **previous round's guard** is the usable guard record with the highest `<seq>` whose `head_oid` is not `H`.
- **This round's first guard** (used by `--second`, 2.2) is the usable guard record with the highest `<seq>` whose `head_oid` is `H`.
- The **builder record** is the builder record of this ticket with the highest `<seq>` whose `branch` is `B` and `second` is false, whatever its `end` (a failed builder run may still have pushed commits, so its model is avoided too).

Both guard lookups need `H`, which `guardTarget` resolves in a later `seq` step than `Resolve` today. For a guard run only, the builder moves the guard's model steps (`Resolve`, `checkSecond`, `Settings`) after the `guardTarget` step; none of them depends on the backend or the claim. For a builder or forager run the step order stays exactly as today, so its resolution, inputs, errors and the order in which errors appear do not change (AC2).

**Test seam.** The record lookups and the resolution of 2.1 and 2.2 live in one unexported helper in `guard.go` that takes the runs directory, the policy, the `TaskContext` (with `GuardMustFix` already set), the branch, the head and the `--second` flag, and returns the selection, the warnings and the error. `run.go` calls it; AC3 to AC5 test it on data with no session fixture.

**Alternation in the policy.** `TaskContext` gains one field, `AvoidModels []string` (guard role only): models the guard must not use besides the policy's builder model. For a guard with `AvoidModels` set, `Resolve` avoids the policy's builder model and every entry, with the same D-179 downward walk bounded by the roster guard minimum (D-180) that the second guard uses today. Extending the walk to a plain confirming guard departs from D-179's "the first guard and every other role are unchanged"; Q-T034-5 puts that to the Head Keeper. For the hive's shape (builder sonnet, first guard opus, `alternates.frontier: fable`) that gives: previous opus, now fable; previous fable, now opus. After a builder step-up (builder opus, first guard fable, second guard sonnet by D-179): previous fable, now sonnet; previous sonnet, now fable. A previous model that is no longer one of this round's two guard models (the builder stepped up, or the config changed) is avoided to no effect, so the guard gets the policy's first guard model.

**The builder record's model (opus brief guard M1).** With a downward walk open to plain guards, the policy's builder model at the guard's base is not enough: a builder dispatched at must-fix count 1 (sonnet) whose round then reaches count 2 makes the policy name opus as builder, and a plain guard avoiding opus and a previous fable would walk down to sonnet, the model that built the head. So every guard run that finds a builder record puts its `model` in `AvoidModels`, and after resolution dispatch refuses with exit 3 (`ExitEnv`) before launch if the selected model still equals it: `guard would use <model>, the model of builder run <record name>`. For `--second` this is today's rule 5 with its existing text (`--second would use ...`). When no builder record exists (records cleaned, another host), a plain guard avoids only the policy's builder model, as today; `--second` refuses (2.2 rule 1). The no-builder-record plain case is stated as accepted in section 5.

**What dispatch does on a plain guard run.** In every case `AvoidModels` starts with the builder record's model when there is one.

- Previous round found: `AvoidModels` also gets its `model`. If `Resolve` then returns `ErrNoCrossModel` (no model differs from the builder's models and the previous one, so alternation is impossible), dispatch resolves again with only the builder record's model in `AvoidModels` and adds the warning `confirm_model_repeated: <model> also reviewed <short previous head>; no other guard model is available (D-205)` to `result.json`. Any other error stands.
- No previous round found, and the base shows an earlier must-fix round for this phase (`Inputs.MustFix` is above 0): the record history is missing (cleaned with `--runs`, or another host). Behavior is Q-T034-2; recommended (a): resolve as a round 1 first guard and add the warning `confirm_model_unknown: no guard run record for <branch> before <short head>; the model did not alternate (D-205)`.
- No previous round and `MustFix` is 0: a round 1 first guard, resolved as today, no warning.

This alternates on every round, whatever the previous verdict, since D-205 says round to round; a polish round after a pass (D-210) alternates too. Which tiers alternate (D-205 is written for Tier 3; D-100 keeps Tier 2 at one guard) is Q-T034-5; the brief is written for its recommended option (a): alternation and the previous round lookup apply only when the request's tier is Tier 3 or unknown (`req.Tier` nil, treated as Tier 3 as the policy does), and a Tier 0 to Tier 2 plain guard resolves as today apart from the builder record rule above. Known limit: a polish round after an all-pass history whose records were cleaned has `MustFix` 0, so it gets no warning (stated, accepted; the queen can see it from the review file names).

### 2.2 Item 2: `--second` base ancestry and its first guard

**First guard model (Q-T034-3, recommended (a)).** Once plain confirming guards alternate, a two-confirmation round (D-205: signals, deletes, leases or claims, or over 100 lines) can have its plain guard on the round 1 second guard's model. Today `Resolve` re-resolves the first guard from policy for `--second`, so it would pick that same model and `checkSecond` would refuse every such round. Under (a) dispatch sets `AvoidModels` on a `--second` run to the builder record's `model` and the `model` of this round's first guard record (2.1); `SecondGuard` stays set, and `Resolve` uses `AvoidModels` in place of its policy re-resolution of the first guard when it is non-empty (a caller with no record keeps today's behavior). `checkSecond` keeps its equality checks against both recorded models.

**`checkSecond`, new rules.** In order, each refusal exit 3 (`ExitEnv`) with the message shown:

1. No builder record (2.1: latest `builder` record with `second: false`, now also on branch `B`), or no first guard record for this round (2.1, head `H`): `--second needs a builder run and a first guard run of <ticket> on head <short H> in .waggle/worktrees/runs`. This is stricter than today, which takes the latest guard record on any head.
2. A recorded `base_oid` that is not 40 or 64 lowercase hex: `--second: run record <name> has no valid base_oid`. No record value reaches git unchecked.
3. The second guard's base differs from the first guard's `base_oid`: `--second: base <base> differs from the first guard's base <first>; pass --base <first>` (or, under Q-T034-4 (a), the default makes this case rare; an explicit `--base` that differs still refuses).
4. The builder's `base_oid` equals the first guard's, or is an ancestor of it: accepted. Checked with `git merge-base --is-ancestor <builder base> <first guard base>` through `Git.Run` (hooks and fsmonitor off). Exit 0 accepts. Exit 1 refuses with `--second: builder base <b> is not an ancestor of the first guard's base <f>; rerun the builder and both guards on one base`. Any other failure (an object missing after rewritten history or a gc, a non-commit) refuses with `--second: cannot check builder base <b> against <f>: <git error>`. A missing object is never treated as an ancestor.
5. The resolved model equals either recorded model: refused as today.

**Rewritten history.** If main was force-pushed and the builder's base is no longer reachable from the first guard's base, rule 4 refuses (exit 1 from git, or a missing object). If the builder ran after the first guard (its base is a descendant of the guard's base), rule 4 refuses too, and rule 1 already catches a builder run that moved the head. If the builder rebased the branch, its new record carries the new base; the old guard records are on another head and stop counting for this round.

**Why the second guard keeps the first guard's base exactly.** The second guard reads its brief and review files from its base, and `roundMustFix` counts must-fix rounds there, which drives the builder step-up in the policy. A base newer than the first guard's (for example one carrying the first guard's own review) could change the builder model the policy avoids (the D-188 concern). Equality with the first guard keeps both guards on one input set; ancestry is allowed only for the builder, whose run produced the code under review, not its policy inputs. A builder model the policy at the newer base would have stepped up is still caught by rule 5 (fail closed).

**Default base for `--second` (Q-T034-4, recommended (a)).** Under (a), `--second` with no `--base` takes the `base_oid` of the latest usable guard record on branch `B` (2.1, any head, since `H` is not known yet; hex checked by rule 2) as its base instead of `<remote>/main`. `run.go` sets `req.Base` to that OID before the base step, so `ResolveBase` resolves it as an explicit base and `offBranch` checks it against main as it does for an explicit `--base`. If `ResolveBase` fails on that OID (the commit is gone after rewritten history or a gc), dispatch exits 3, not 2, with `--second: first guard base <oid> from run record <name> does not resolve`, since the queen passed no flag. If no usable guard record exists, `req.Base` stays empty, the default base applies, and rule 1 refuses later. Rule 1 still checks that this round's first guard record reviewed the head `guardTarget` resolves. The queen commits each guard's review to main between the two guards, so today main has usually moved past the first guard's base by the time `--second` runs, and the queen's template says never to rerun with other flags to get past a refusal: each such refusal is a Keeper card.

### 2.3 Item 3: the hint

What it says now (`pick`, the `ErrNoCrossModel` format string): `<sentinel>: role guard task "<id>" level <guard level> shares [<avoided models>] with the builder or first guard (map a model not already used, for example runtimes.adapters.<adapter>.alternates.<guard level>)`.

What is wrong: for a second guard (and a `--second` run under 2.2) the guard level is the one level where a new alternate cannot help unless the first guard is also on it. `pick` walks from the guard level up and tries each level's primary, then its alternate. An alternate added at any level from the guard level up to, but not including, the level where the first guard's model was picked is tried before the first guard's model, so it becomes the first guard and the second guard still has nothing. For a plain first guard (only the builder's model avoided) the guard level is right, and that text stays as it is (`TestGuardCrossModel` and the all-`m` case of `TestSecondGuard` pin it, unchanged).

The rule (second guard only, built in `Resolve` where the D-179 walk has failed; `pick`'s text is unchanged). Let `F` be the first guard's model (re-resolved, or the first guard record's model in `AvoidModels` under Q-T034-3) and `Lf` the lowest level from the guard level up where `F` is mapped as primary or alternate. The level to name is the first of these with no alternate mapped: `Lf`; each level above `Lf`, going up; each level below the guard level down to the roster guard minimum, going down (the D-179 walk reaches those). Exact text:

- A level `L` found: `<sentinel>: role guard task "<id>" level <guard level>: builder "<builder model>", first guard "<F>" (map a third model at runtimes.adapters.<adapter>.alternates.<L>, which keeps the first guard on <F>)`.
- None found: `<sentinel>: role guard task "<id>" level <guard level>: builder "<builder model>", first guard "<F>" (every alternate that keeps the first guard on <F> is taken; map a third model under runtimes.adapters.<adapter>.levels)`.

- No `Lf` (under Q-T034-3 `F` comes from a record, so it can be mapped only below the guard level, after a guard walked down, or not at all, after a config change): `<sentinel>: role guard task "<id>" level <guard level>: builder "<builder model>", first guard "<F>" (the first guard's model is not mapped at or above level <guard level>; map a third model under runtimes.adapters.<adapter>.levels)`.

When `AvoidModels` holds the builder record's model as well, the text names it as the builder model if it differs from the policy's (`builder "<record model>"`); the level rule is unchanged.

`<sentinel>` is `ErrNoCrossModel` through `%w`, so `errors.Is` holds and its text (`no model differs from the builder's and the first guard's`) leads. Models print with `%q`. Worked cases: this hive before D-224 (no alternates, builder sonnet, first guard opus picked at frontier) names `alternates.frontier`; `walkPolicy("opus", "haiku", "")` (builder opus, first guard fable on the frontier alternate, guard minimum standard) names `alternates.standard`, because frontier's slot is taken and the walk reaches standard. Those are the two assertion changes the lease rule allows.

## 5. Threat model (D-203)

Attacker: a dispatched builder working inside its lease (it controls its commits, its branch head and when the queen dispatches a guard on it), a dispatched guard (it controls its final message and so its parsed verdict), and ordinary repo state (main moving, branches rebased, records cleaned). Trusted: the queen and her flags, the config at base, review files on base, and the run records dispatch writes under `.waggle/worktrees/runs/`, which no worker lease covers. A finding whose attacker needs to write or plant a run record, push to the base branch, change config at base, or pass dispatch flags of its choosing is a note, not a must-fix, because that capability can already pick any model directly (D-188 trusts the same records).

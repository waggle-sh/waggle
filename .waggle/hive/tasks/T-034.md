## 1. Goal

Three gaps in how dispatch picks a guard's model, each of which costs the queen a manual step or a Keeper card today:

1. **Confirming guards do not alternate.** D-205: a fix round gets one confirming guard, alternating between the two guard models round to round, and after a single confirming guard finds a must-fix, the other model confirms the next round. A plain guard run resolves its model from policy alone (`Resolve` with the builder's model avoided), so every confirming guard gets the round 1 first guard model. On T-029 the confirming guard ran on opus, the round 1 model, and D-205 alternation was not met (D-228). Dispatch has no model flag by design (`cmd/waggle/dispatch.go`: no flag lowers a model or forces), so the queen cannot fix it from the command line.
2. **`--second` refuses an ancestor builder base.** `checkSecond` (`guard.go`) requires the latest builder run, the latest first guard run and the second guard to share one `base_oid`. On T-029 the builder ran at `217e81e` and the first guard at `60a9d57`, two commits later on main (the round 2 Colima evidence), so the fable `--second` refused (D-228). The builder's code did not change between the two bases; only hive records did.
3. **The no-cross-model hint names the wrong level.** When the second guard finds no model, the error from `pick` (`policy.go`, the `ErrNoCrossModel` format string) says `map a model not already used, for example runtimes.adapters.<adapter>.alternates.<level>`, where `<level>` is the guard's own level. On this hive before D-224 (opus, sonnet, haiku; builder and guard minimum standard; no alternates) it said `alternates.standard`. Following it makes things worse: `pick` tries a level's alternate before moving up a level, so a standard alternate becomes the first guard on every ticket and the second guard still refuses (D-224 rationale). The level that works was `frontier`, the level the first guard's model sits at.

## 2. Design

### 2.1 Item 1: the previous round's guard model, and alternation

**Where the history is (Q-T034-1, recommended (a)).** Dispatch already writes one `result.json` per run under `.waggle/worktrees/runs/<ticket>-<role>-<seq>/` with `branch`, `model`, `head_oid`, `verdict` and `second`, and `checkSecond` already trusts these records (D-188). Review markers on base (D-248) carry `verdict` and `head` but no model, and the model appears only in the queen's file name convention (`T-<nnn><suffix>-<model>.md`), so base reviews cannot order rounds or name models without new formats. The design below uses the run records.

**Rounds.** A round is the guard runs on one branch head. For a guard run under review of head `H` on branch `B`:

- The **previous round's guard** is the guard record of this ticket with the highest `<seq>` among those with `second: false`, `branch` equal to `B`, a non-empty `verdict` and `head_oid` not equal to `H`. Records with `second: true`, no verdict (failed, timed out, `no_verdict`), another branch (phase suffix) or another ticket are skipped, as are unreadable, oversize (over `maxBrief`, as today) or malformed records. `<seq>` compares as a number (`guard-10` after `guard-9`), as the current reader does.
- **This round's first guard** (used by `--second`, 2.2) is the record with the highest `<seq>` among those with `second: false`, `branch` equal to `B`, a non-empty `verdict` and `head_oid` equal to `H`.

Both lookups need `H`, which `guardTarget` resolves in a later `seq` step than `Resolve` today. The builder moves the guard's model steps (`Resolve`, `checkSecond`, `Settings`) after the `guardTarget` step; none of them depends on the backend or the claim, and nothing between them changes for a builder or forager run (AC2). The builder and forager resolution, its inputs and its errors do not change.

**Alternation in the policy.** `TaskContext` gains one field, `AvoidGuard string` (guard role only): a model the guard should not use besides the builder's. For a guard with `AvoidGuard` set, `Resolve` avoids both the builder's model and `AvoidGuard`, with the same D-179 downward walk bounded by the roster guard minimum (D-180) that the second guard uses today. For the hive's shape (builder sonnet, first guard opus, `alternates.frontier: fable`) that gives: previous opus, now fable; previous fable, now opus. After a builder step-up (builder opus, first guard fable, second guard sonnet by D-179): previous fable, now sonnet; previous sonnet, now fable. A previous model that is no longer one of this round's two guard models (the builder stepped up, or the config changed) is avoided to no effect, so the guard gets the policy's first guard model.

**What dispatch does on a plain guard run.**

- Previous round found: `AvoidGuard` is its `model`. If `Resolve` then returns `ErrNoCrossModel` (only one model differs from the builder's, so alternation is impossible), dispatch resolves again without `AvoidGuard` and adds the warning `confirm_model_repeated: <model> also reviewed <short previous head>; no other guard model is mapped (D-205)` to `result.json`. Any other error stands.
- No previous round found, and the base shows an earlier must-fix round for this phase (`Inputs.MustFix` is above 0): the record history is missing (cleaned with `--runs`, or another host). Behavior is Q-T034-2; recommended (a): resolve as a round 1 first guard and add the warning `confirm_model_unknown: no guard run record for <branch> before <short head>; the model did not alternate (D-205)`.
- No previous round and `MustFix` is 0: a round 1 first guard, resolved as today, no warning.

This alternates on every round, whatever the previous verdict, since D-205 says round to round; a polish round after a pass (D-210) alternates too. Known limit: a polish round after an all-pass history whose records were cleaned has `MustFix` 0, so it gets no warning (stated, accepted; the queen can see it from the review file names).

### 2.2 Item 2: `--second` base ancestry and its first guard

**First guard model (Q-T034-3, recommended (a)).** Once plain confirming guards alternate, a two-confirmation round (D-205: signals, deletes, leases or claims, or over 100 lines) can have its plain guard on the round 1 second guard's model. Today `Resolve` re-resolves the first guard from policy for `--second`, so it would pick that same model and `checkSecond` would refuse every such round. Under (a) dispatch sets `AvoidGuard` on a `--second` run to the `model` of this round's first guard record (2.1); `SecondGuard` stays set, and `Resolve` uses `AvoidGuard` in place of its policy re-resolution when it is non-empty (a caller with no record keeps today's behavior). `checkSecond` keeps its equality checks against both recorded models.

**`checkSecond`, new rules.** In order, each refusal exit 3 (`ExitEnv`) with the message shown:

1. No builder record for the ticket (latest `builder` record, `second: false`, as today), or no first guard record for this round (2.1, head `H`): `--second needs a builder run and a first guard run of <ticket> on head <short H> in .waggle/worktrees/runs`. This is stricter than today, which takes the latest guard record on any head.
2. A recorded `base_oid` that is not 40 or 64 lowercase hex: `--second: run record <name> has no valid base_oid`. No record value reaches git unchecked.
3. The second guard's base differs from the first guard's `base_oid`: `--second: base <base> differs from the first guard's base <first>; pass --base <first>` (or, under Q-T034-4 (a), the default makes this case rare; an explicit `--base` that differs still refuses).
4. The builder's `base_oid` equals the first guard's, or is an ancestor of it: accepted. Checked with `git merge-base --is-ancestor <builder base> <first guard base>` through `Git.Run` (hooks and fsmonitor off). Exit 0 accepts. Exit 1 refuses with `--second: builder base <b> is not an ancestor of the first guard's base <f>; rerun the builder and both guards on one base`. Any other failure (an object missing after rewritten history or a gc, a non-commit) refuses with `--second: cannot check builder base <b> against <f>: <git error>`. A missing object is never treated as an ancestor.
5. The resolved model equals either recorded model: refused as today.

**Rewritten history.** If main was force-pushed and the builder's base is no longer reachable from the first guard's base, rule 4 refuses (exit 1 from git, or a missing object). If the builder ran after the first guard (its base is a descendant of the guard's base), rule 4 refuses too, and rule 1 already catches a builder run that moved the head. If the builder rebased the branch, its new record carries the new base; the old guard records are on another head and stop counting for this round.

**Why the second guard keeps the first guard's base exactly.** The second guard reads its brief and review files from its base, and `roundMustFix` counts must-fix rounds there, which drives the builder step-up in the policy. A base newer than the first guard's (for example one carrying the first guard's own review) could change the builder model the policy avoids (the D-188 concern). Equality with the first guard keeps both guards on one input set; ancestry is allowed only for the builder, whose run produced the code under review, not its policy inputs. A builder model the policy at the newer base would have stepped up is still caught by rule 5 (fail closed).

**Default base for `--second` (Q-T034-4, recommended (a)).** Under (a), `--second` with no `--base` takes the first guard record's `base_oid` (latest `second: false` guard record with a verdict on branch `B`, hex checked by rule 2) as its base instead of `<remote>/main`; `ResolveBase` then resolves it as an explicit base. Rule 1 still checks that record reviewed the head `guardTarget` resolves. The queen commits each guard's review to main between the two guards, so today main has usually moved past the first guard's base by the time `--second` runs, and the queen's template says never to rerun with other flags to get past a refusal: each such refusal is a Keeper card.

### 2.3 Item 3: the hint

What it says now (`pick`, the `ErrNoCrossModel` format string): `<sentinel>: role guard task "<id>" level <guard level> shares [<avoided models>] with the builder or first guard (map a model not already used, for example runtimes.adapters.<adapter>.alternates.<guard level>)`.

What is wrong: for a second guard (and a `--second` run under 2.2) the guard level is the one level where a new alternate cannot help unless the first guard is also on it. `pick` walks from the guard level up and tries each level's primary, then its alternate. An alternate added at any level from the guard level up to, but not including, the level where the first guard's model was picked is tried before the first guard's model, so it becomes the first guard and the second guard still has nothing. For a plain first guard (only the builder's model avoided) the guard level is right, and that text stays as it is (`TestGuardCrossModel` and the all-`m` case of `TestSecondGuard` pin it, unchanged).

The rule (second guard only, built in `Resolve` where the D-179 walk has failed; `pick`'s text is unchanged). Let `F` be the first guard's model (re-resolved, or `AvoidGuard` under Q-T034-3) and `Lf` the lowest level from the guard level up where `F` is mapped as primary or alternate. The level to name is the first of these with no alternate mapped: `Lf`; each level above `Lf`, going up; each level below the guard level down to the roster guard minimum, going down (the D-179 walk reaches those). Exact text:

- A level `L` found: `<sentinel>: role guard task "<id>" level <guard level>: builder "<builder model>", first guard "<F>" (map a third model at runtimes.adapters.<adapter>.alternates.<L>, which keeps the first guard on <F>)`.
- None found: `<sentinel>: role guard task "<id>" level <guard level>: builder "<builder model>", first guard "<F>" (every alternate that keeps the first guard on <F> is taken; map a third model under runtimes.adapters.<adapter>.levels)`.

`<sentinel>` is `ErrNoCrossModel` through `%w`, so `errors.Is` holds and its text (`no model differs from the builder's and the first guard's`) leads. Models print with `%q`. Worked cases: this hive before D-224 (no alternates, builder sonnet, first guard opus picked at frontier) names `alternates.frontier`; `walkPolicy("opus", "haiku", "")` (builder opus, first guard fable on the frontier alternate, guard minimum standard) names `alternates.standard`, because frontier's slot is taken and the walk reaches standard. Those are the two assertion changes the lease rule allows.

## 5. Threat model (D-203)

Attacker: a dispatched builder working inside its lease (it controls its commits, its branch head and when the queen dispatches a guard on it), a dispatched guard (it controls its final message and so its parsed verdict), and ordinary repo state (main moving, branches rebased, records cleaned). Trusted: the queen and her flags, the config at base, review files on base, and the run records dispatch writes under `.waggle/worktrees/runs/`, which no worker lease covers. A finding whose attacker needs to write or plant a run record, push to the base branch, change config at base, or pass dispatch flags of its choosing is a note, not a must-fix, because that capability can already pick any model directly (D-188 trusts the same records).

Must-fix: any path where a guard's model equals the builder's model as the policy or the builder record names it; a `--second` run whose model equals this round's first guard's; a plain guard whose model does not alternate when the previous round's record exists and a second guard model is mapped, without the `confirm_model_repeated` warning; records of another ticket (including a number prefix such as `T-0230`), another branch, a `second: true` run or a run with no verdict counted as a round; a record value passed to git without the hex check; a missing object or any git error treated as ancestry; `--second` accepted on a non-ancestor builder base or a second base other than the first guard's; any change to builder or forager resolution, to a round 1 first guard's model, or to `pick`'s plain guard hint; a read past today's caps; a panic on a malformed record; files changed outside the lease rule.

Note, not must-fix: a planted or edited run record steers model choice (needs host write outside every lease, as D-188); records lost to `clean --runs` or another host give round 1 resolution with a warning (Q-T034-2), or none for an all-pass history (2.1 known limit); the queen can dispatch guards in an order D-205 does not intend (trusted).

Guard prompt sentence (repeat verbatim): "Threat bar (D-203): a finding whose attacker needs to write or edit a run record under .waggle/worktrees/runs, push to the base branch, change the base config, or pass dispatch flags of its choosing is a note, not a must-fix; must-fix is for what a builder through its commits and branch head, a guard through its final message, or ordinary repo state (main moving, a rebase, cleaned records) can trigger, and for any guard model that equals the builder's or this round's first guard's."

D-193: nothing in this ticket sends a signal, calls `sweep()`, reaps a process or deletes files or git state. The `run.go` edits are in the `seq` steps before the session starts (step order, `TaskContext` fields, base default, warnings). New tests are data tests (fabricated `result.json` directories in a temp dir, fabricated policies) and local git fixtures for commit graphs (`merge-base --is-ancestor`), plus the existing local-mode guard run fixture. The full `go test -race ./...` runs on the host. If a fix round adds a signal or a sweep, D-193 applies to it.

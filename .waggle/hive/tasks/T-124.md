## 1. Goal

Make Waggle the tool an agent lead uses to claim the issue it is about to work on, so that every other person and agent team sees the claim where they already look: on the GitHub issue. Level 1 ships GitHub only; the claim format stays tracker-neutral, and Linear is the first ticket after the dogfood (D-412). Start from the convention many repos already write in `AGENTS.md` ("assign yourself before you start, skip assigned issues") and add the part that convention cannot do: a claim that wins a race, expires on its own, and says which paths it will touch. The existing gate becomes an optional second step that checks a PR stayed inside its claim.

The Head Keeper's own words (D-410): "Agent leads (queens) need to claim issues that they are working on so other users and agent teams even know those are 'claimed' in the first place. That's the real problem I have."

## 2. Where we start

**What exists.** Claims are git refs, `refs/waggle/claims/ticket-<n>` (`internal/comb/backend.go:188`), one JSON `Lease` per ref (`backend.go:114-126`): ticket, keeper, role, gate, directories, claimed and expiry times, branches. `AcquireLeaseWithTrailers` (`git.go:540`) is a compare-and-swap per ticket with an optimistic directory overlap check across tickets (`git.go:614`); a same-owner claim renews, an expired one is taken over. Ticket ids are invented (`T-001`, `^(T-)?[0-9]{1,6}$`, `backend.go:194`). Default lifetime is 120 minutes and `waggle dispatch` renews during a run (`internal/dispatch/claim.go:64`). `internal/forge` talks to GitHub for PRs, reviews and comments; nothing writes an issue assignee, label or issue comment. `internal/relay` holds a pure parser for `/waggle claim` PR comments (T-065, partial, not usable).

**What the outside inputs found.** The outside analysis: "the repo has been public since about November 20, and has 2 stars (one is the owner), 0 forks, 0 outside issues or PRs", and the D-235 criterion "stands at 0 of 3". A binding gate takes seven steps, two of them in GitHub settings. The claims follow-up: duplicate PRs were "the most common PR-level failure reason: 23% (142 PRs) of the failures classified" in a study of 33k agent PRs, and "Waggle does not solve this today for anyone not running its CLI. Claims use invented ids (`T-001`), live in git refs that the GitHub UI never shows". Its gap statement: "one claim that is atomic, expires on its own, states which paths it will touch, works from any agent tool, and shows up on the issue where other teams already look. Nobody ships that combination."

**The risk the follow-up names and this plan accepts.** "It is thin. A team can get most of it with one line in `AGENTS.md` and `gh issue edit --add-assignee`." Level 1 must beat that line on day one with three things the line cannot do: refusal on a race, expiry, and scope overlap. And "GitHub and Linear are both one feature away", so the window is months. Build small, test fast.

## 3. Level 0: the AGENTS.md convention

A claim is three visible things on the issue, and nothing else:

1. **Assignee:** the human (or bot) account the lead works under.
2. **Label:** `claimed` (Q-T124-2).
3. **One sticky comment** in claim format v1 (section 4.1): holder, lead name, expiry, declared paths, state.

The rule an agent follows, with nothing installed but `gh` (or any tracker's UI, since the convention names nothing GitHub-specific):

- Before starting, read the issue. Skip it if it carries an active claim (label present and a v1 comment whose `expires` is in the future and whose `state` is `active`).
- To claim: assign yourself, add the label, post the claim comment. Wait a few seconds, re-read the comments. If an earlier active claim by someone else is there, edit yours to `state: lost`, remove your assignment and skip.
- While working, edit `expires` forward before it passes.
- When done (merged, abandoned or handed off), edit `state: released`, remove the label and your assignment.

T-125 writes this as a copyable `AGENTS.md` section and as the spec. T-126 makes the README lead with it: problem, the three things, the snippet, then "add Waggle to make it atomic, expiring and scoped". Bee vocabulary (keeper, queen, forager, builder, guard, scout, hive, honey) moves to one glossary page; the README keeps plain terms (task, issue, claim, paths, gate, approver), as D-236 decided and the outside analysis asked again ("A gate-only user needs four" terms).

## 4. Level 1: open core claims

Free and open source (Apache-2.0, as today): the CLI, a GitHub Action and an MCP server (D-411). All three speak one claim format and one protocol.

### 4.1 The claim record

The sticky comment is the record. Proposed v1 (Q-T124-1), readable by a person and by an agent without Waggle:

```text
Claimed by @octocat for lead `expo-queen` until 2026-11-26 18:00 UTC.
Paths: internal/parser/, docs/parser.md

    waggle-claim: v1
    id: 7f3c9a2e41d0
    holder: octocat
    lead: expo-queen
    claimed: 2026-11-26T16:00:00Z
    expires: 2026-11-26T18:00:00Z
    paths: internal/parser/, docs/parser.md
    state: active
```

- The machine block is an indented `key: value` block whose first line is `waggle-claim: v1`. It renders as code on GitHub and in any Markdown tracker, needs no HTML comment (so a later tracker's handling of HTML comments, Linear's included, is not something this plan relies on) and is easy to write by hand. Nothing in the block names GitHub: the format is tracker-neutral (D-412).
- `id` is a random claim id. Identity is the claim id, not the login: our four queens all work under one GitHub login, so a renewal or release must match `id`, or one queen would renew another's claim.
- `expires` is absolute UTC and lives only in the comment. A heartbeat edits it.
- `state` is `active`, `released`, `expired` or `lost`. Old comments are edited, not deleted, so the issue keeps the history (later readable by Nectar).
- `paths` are repo-relative directories or files, normalized by the same rules as `NormalizeDirectories` (`backend.go:272`), up to `leases.max_directories_per_claim`.
- Issue reference forms for the CLI: `#123` (this repo's GitHub remote) and `gh:owner/repo#123`. The grammar reserves `linear:ENG-123` now, so adding Linear later changes no format: until T-129 lands, Level 1 parses it and refuses with "Linear support follows the dogfood". The `linear:` prefix is required, because a Linear team key `T` would make `T-123` ambiguous with today's ticket ids.

### 4.2 Atomic claims: write, re-read, earliest valid claim wins

Neither GitHub nor Linear offers compare-and-swap on an issue, and GitHub accepts several assignees without complaint. The protocol makes the comment list the arbiter:

1. Read the issue's comments. If an active claim by another claim id exists, refuse and name the holder, lead and expiry.
2. Post a new claim comment.
3. Wait a settle delay (proposed 3 seconds, to absorb read-after-write lag), then re-read all comments.
4. Collect valid claims: v1 format parses, `state: active`, `expires` after the server's current time minus a grace (5 minutes, for clock skew), and the author is allowed to claim (section 10). Order by the server's `created` time, then by comment id.
5. If ours is first, we hold it: set the assignee and the label. If not, edit ours to `state: lost` and refuse, naming the winner.
6. Every heartbeat re-reads the list. If a claim earlier than ours is valid (a double holder slipped through lag), ours yields: edit to `lost`, unassign if no other active claim names us, stop and report.

"Now" is always the server's time, read from the API response's `Date` header, never the local clock. A client refuses to heartbeat a claim that has already expired by server time, and a claimant treats a claim as expired only after `expires` plus the grace, so an honest holder can never revive a claim someone else already took. Before claiming over an expired claim, the claimant edits that comment to `state: expired`.

### 4.3 Leases, heartbeat and expiry

- Default lifetime 120 minutes (today's `default_ttl_minutes`), heartbeat at half of it. `waggle dispatch`, the MCP server (while its client is connected) and `waggle heartbeat --every` renew. A queen that runs `waggle claim` and walks away gets an expiring claim, which is the point.
- `waggle sweep` (and the Action on a schedule, every 15 minutes) edits expired claims to `state: expired`, removes the label and the assignee it set. It never touches a claim it cannot parse; it reports it.
- A claim older than `claims.max_age` (proposed 7 days) still renews but is flagged in `waggle claims` and in the sweep's summary, so a lead that heartbeats forever is visible. No automatic release.

### 4.4 Declared scope and overlap

A claim declares paths. At claim time Waggle reads the active claims on the same repo's open issues (one search for the label, then the comments of each hit) and refuses a claim whose paths overlap another active claim's paths, naming the issue and holder. This is the one property only Waggle has (claims follow-up: "a tracker can tell you issue 12 is taken, but not that issues 12 and 15 will both rewrite `internal/parser`"). It reuses the overlap rules of `DirsOverlap` and the case-folded check. Like today's refs (`backend.go:110-113`, the concurrency invariant), overlap across issues has a race window; it is a warning-grade refusal, and Level 2 is the authority. Paths are optional: a claim with no paths is a plain claim and overlaps nothing.

### 4.5 `waggle next`

`waggle next [--label ready] [--query <q>] --lead <name> [--paths ...]` lists open issues matching the filter in the repo's configured priority order (section 8, T-142), skips claimed ones and ones whose declared paths (from the issue body's `Paths:` line, if any) overlap held claims, and claims the first. On a lost race it tries the next, up to five. This closes the plan-to-dispatch race the claims follow-up cites ("Shared-backlog agents must re-check the claim board at dispatch time"), and it is the command a queen needs most.

### 4.6 GitHub first, Linear after the dogfood (D-412)

One `Tracker` interface in the core (T-127), with one adapter in Level 1: T-128, GitHub. The adapter lists open issues by label or query, reads comments with server times, posts and edits a comment, sets and clears assignee and label, reads the caller's identity and the server time, and answers "may this author claim" (on GitHub, a user's repository permission). The interface and the claims core stay tracker-neutral: no GitHub type crosses into `internal/claims/`, and the author check is an adapter method, so a second adapter adds files without touching the core.

The Linear adapter (T-129) is the first ticket after the 14-day dogfood and depends on it (D-412). It adds the Linear tracker, turns on the reserved `linear:` reference form, adds `priority.source: linear` (T-142's order), the workspace-admin owners default (T-141) and the Linear read for Level 2 (T-137). On Linear the label and assignee are the workspace's own and the claim comment is a Linear comment. The `/claim` comment path stays GitHub only even then: a Linear comment cannot trigger a GitHub Action, and a Linear webhook needs a hosted receiver, which is the App (section 7). On Linear, leads will claim through the CLI or MCP. Linear auth is settled in the T-129 brief (it was Q-T124-3).

### 4.7 Entry points

- **CLI:** `waggle claim <issue> [--paths a,b] [--lead name] [--ttl 2h]`, `waggle release <issue>`, `waggle heartbeat <issue> [--every 10m]`, `waggle claims` (list), `waggle next`, `waggle sweep`, each with `--json`. Today's `waggle claim T-<id> --dirs ... --gate ...` is unchanged (section 6).
- **GitHub Action** (`claims/`, a composite Action pinned by SHA like `gate/`): handles `/claim [paths]`, `/release` and `/heartbeat` issue comments, and runs the scheduled sweep. It never checks out or runs PR code. One workflow file, no ruleset, no admin setting, works on GitHub Free private repos.
- **A `/claim` comment:** for humans, and for contributors and agents without push access or without the CLI. This replaces the relay's PR-comment design for issues; T-065 and T-070 stay as they are.
- **MCP server:** `waggle mcp`, stdio, tools `claim`, `release`, `heartbeat`, `next`, `list`, `show`. It uses the caller's own `gh` token (section 10); a Linear key comes with T-129.
- **`waggle init --claims`:** writes the `AGENTS.md` section, the claims workflow and the config keys, and prints the label to create. Two commands to a working install.

## 5. Level 2: the gate as an opt-in scope check

The existing gate learns one new, opt-in source for a PR's claim: the issue the PR closes or names (`Closes #123`, a `claim-123` branch, or a `Waggle-Issue:` trailer). With `gate.claims_source: issue` the gate reads that issue's active claim through the tracker and checks the PR's changed paths against the claim's `paths`, in report-only mode first (a sticky PR comment, the check passes), with the existing modes to turn it binding. Default off. Today's T-id lease check, protected paths and decisions log are unchanged. Built as T-137, after the dogfood starts, since dogfood does not need it.

## 6. The comb becomes an optional cache; today's claims

**Source of truth.** For an issue claim, the issue is the record and the comment list is the arbiter. Issue claims never write `refs/waggle/claims/`.

**Optional cache (T-136).** `waggle claims --cache` mirrors active issue claims into `refs/waggle/cache/<tracker>/<key>` for offline `waggle status` and for repos that want the claim set in git. The cache never decides a claim; on any mismatch the issue wins and the cache entry is rewritten. Anyone who can push refs can write the cache, which is why it is never trusted.

**Today's `refs/waggle/claims/ticket-<n>`: coexistence, no migration.** T-id claims keep working exactly as now, with the same code, the same gate check and the same `force-release`. That code is kept and frozen (D-411): bug and security fixes only. `waggle status` shows both kinds side by side (T-136). There is nothing to migrate for outside users (the outside analysis found none), and v0.1.x releases stay installable. Our own hive keeps T-id refs for its gate until Level 2 is binding here; during the dogfood the Waggle queen also mirrors each new ticket to a GitHub issue and claims that, accepting two claims per task for two weeks. Whether the hive later moves fully to issue claims is a decision for after the dogfood, not part of this plan.

## 8. Governance: who sets vision, roadmap and priority

The Head Keeper's ruling (item 55, e1759): "Yes, add it to the brief." It answers who sets the vision, the roadmap and backlog priority in a Waggle repo. Agents claim and build; people decide what matters.

1. **Vision and roadmap are human-owned.** The repo's owners own them: a `governance.owners` list in the repo's Waggle config (Q-T124-10 settles the file), defaulting to the repo's admins when the list is absent (GitHub: collaborators with admin permission; Linear workspace admins arrive with T-129). `governance.steering_paths` names the vision and roadmap files (default `VISION.md`, `ROADMAP.md` and the Waggle config file itself, so the owners list protects itself). Agents propose a change by PR or by issue and never merge it; an owner's approval at the PR's exact head is what counts (Q-T124-13). Level 0 says this in the `AGENTS.md` section (T-125). Level 2 checks it: the gate's existing protected-path approver check, fed from `governance.owners`, reports a steering-path PR without an owner approval (T-137, report-only by default).
2. **Priority comes from the tracker.** Waggle stores no priority of its own. One configured source per repo: a priority label, a GitHub Projects order or milestones in Level 1 (Q-T124-11), and Linear priority and cycles once T-129 lands. `waggle next` picks the top unclaimed, non-overlapping item in that order (section 4.5). T-142 reads the order; T-131 consumes it.
3. **Who may reprioritize is set in config.** `governance.reprioritizers` defaults to the owners and can name leads per area (by path prefix or by label), so a lead may reorder its own area's backlog. An agent reprioritizing an issue it holds or has claimed is a violation: `waggle sweep` and the Action's scheduled run flag it with a comment on the issue, a line in `waggle claims` and the sweep's summary. Waggle never reverts a priority change; an owner does. Attribution is the hard part (Q-T124-12): our queens share one login, and a GitHub Projects reorder reaches only org-level `projects_v2_item` webhooks, which a repo workflow cannot receive, so until the App (T-140) a Projects reorder is seen by snapshot, not by actor. T-141 adds the config; T-143 adds the check.
4. **Quorum is the optional, later answer.** For open projects with many contributors, Quorum's `sqrt(Nectar)` ballots on roadmap and priority (T-054) can replace the owners list as the priority source, as an opt-in `governance.mode: quorum`. It stays frozen under D-411 and gets no ticket in this program. `governance.mode: owners` is the only mode built now.
5. **Our repos.** Backlogs move from `TODO.md` files to GitHub issues with visible priority (D-412), and the queens pull from there with `waggle next` (T-144, before the dogfood; Q-T124-14 picks where each backlog lives). The Waggle hive keeps `ROADMAP.md` and the task files as its plan of record, owner-merged as today's Tier 2 rule already requires; its open tickets get mirrored issues as section 6 describes. The scout role's "Owns `ROADMAP.md`" becomes "drafts `ROADMAP.md`; owners merge" (T-144, Tier 3).

## 10. Threat model (D-203)

**Boundary.** Issue text, comments and labels on a public repo are attacker-written. The tracker (GitHub in Level 1) is trusted for comment authorship, server time, ordering and permissions. A claim is a coordination signal, not a security control: it stops honest agents and people from colliding, and Level 2 is the only place a claim becomes binding.

**Who can forge a claim.** Anyone can post a comment shaped like a v1 claim on a public issue. A claim counts only if its author may claim: by default a user with triage or write permission on the repo (read from the GitHub permission API), or the Action's bot account acting on a `/claim` from such a user. On a public repo a maintainer can set `claims.comment_policy: anyone` so outside contributors `/claim` through the Action, with a shorter lifetime (Q-T124-7). Forged comments from others are ignored and listed by `waggle claims` as "ignored: author may not claim".

**Who can steal a claim.** Posting over an active claim loses the arbitration. Editing or deleting another person's comment needs repo write; that person can already unassign, relabel or close the issue, so this is a note, not a must-fix. A claimant who forges an earlier `created` time cannot: the order uses the server's time, not the block's `claimed` field. A holder that heartbeats forever holds its own issue, which it already could by assignment; `claims.max_age` makes that visible.

**Who can race.** Two leads that post within the settle delay both see both comments on re-read and agree on the earliest. Read-after-write lag beyond the delay can let both believe they hold the issue until the next heartbeat re-read, at most half a lifetime; the later one yields (section 4.2 step 6). Overlap across issues has the same window as today's refs; Level 2 catches the files. Clock skew is handled by server time plus the grace.

**Tracker unreachable.** If GitHub is unreachable, `claim` and `next` fail closed (no claim written, a clear error) and `waggle claims` says the list is unknown, never empty.

**Linear (T-129, after the dogfood).** Not in Level 1 (D-412). Carried into the T-129 brief so it inherits this model: every workspace member may claim (workspace membership is the trust boundary); editing another's comment needs workspace edit rights; Linear is trusted for ordering and authorship like GitHub; a Linear personal API key acts as its user with that user's workspace access, so it is a full-access secret, read from `LINEAR_API_KEY` only, never logged, never in a comment, never passed to a fork's workflow; the same fail-closed rule applies.

**What an MCP client can do.** Exactly the six tools, with the identity of the token the server runs with: claim, heartbeat and release its own claims (matched by claim id), list and read. There is no tool to release or edit someone else's claim, run a shell, change the gate or read files. Issue titles, bodies and comments returned to the model are untrusted text: the server returns fields, caps each at 4 KiB, and marks them as issue content. A prompt-injected client can claim issues it should not; `claims.max_active_per_lead` (proposed 5) caps that, and every claim is visible and expires.

**The Action.** Runs on `issue_comment` and `schedule` with `issues: write` and nothing else, never on PR code, from its own pinned tree (as `gate/` does, D-270). A comment body is parsed with caps by a pure parser.

**Priority and steering.** Priority labels, milestones and Projects order on GitHub need triage or above (and Linear priority, once T-129 lands, needs workspace membership), so an outside commenter cannot reorder `next`. A forged `governance` block in a PR is a steering-path change and needs an owner (section 8). Priority text in an issue body is ignored.

**Notes, not must-fix (D-203).** An attacker with repo admin, with the holder's token, or able to post as the Action's bot can do anything a claim could stop. The comb cache is untrusted by design.

## 14. Open questions

**Q-T124-1. Claim comment format and where expiry lives.**
1. **Recommended:** one visible comment with a plain sentence and an indented `waggle-claim: v1` key-value block; `expires` lives only in that block and a heartbeat edits it. Readable and writable by hand (Level 0), and tracker-neutral: it renders the same on GitHub now and in Linear when T-129 lands (D-412).
2. The same sentence with the machine block in a hidden HTML comment. Cleaner to read, but hand-writing is harder and ties the format to trackers that hide HTML comments, which Linear may not.
3. Expiry kept outside the comment (a cache ref or the Action's state), the comment showing only the holder. Keeps comment edits rare, but a reader without Waggle cannot tell a live claim from a dead one.

**Q-T124-2. Label name.**
1. **Recommended:** `claimed`, configurable as `claims.label`. Plain, works with no tool, matches the convention's wording. The comment, not the label, decides, so a repo's existing `claimed` label does no harm.
2. `waggle:claimed`. No clash with existing labels, but it names the tool on every issue and reads oddly at Level 0.
3. `in progress`. Common already, but many repos use it for other meanings.

**Q-T124-3. Withdrawn under D-412.** It asked how the CLI and Action authenticate to Linear, which assumed Linear on day one. Level 1 ships no Linear code, so the question moves to the T-129 brief, written during the dogfood, with the same options (personal API key in `LINEAR_API_KEY`, recommended; an OAuth app with a localhost callback; key now and OAuth with the App later). The id is kept so earlier references stay valid.

**Q-T124-4. Does Level 1 ship in the current binary or a new one?**
1. **Recommended:** the current `waggle` binary and repo. `waggle claim` routes issue references to the new code; the T-id path is untouched. One install, one release pipeline, and the gate can read issue claims later without a second tool.
2. A new small binary (for example `claim`) in the same repo. A lighter first impression, but two releases, two install lines and duplicated config.
3. A new repo. Cleanest brand reset, loses the release, docs and test tooling we have.

**Q-T124-5. How the MCP server is distributed.**
1. **Recommended:** `waggle mcp`, a stdio subcommand of the same binary, with a one-line config snippet per client and a listing in the public MCP registries. No new runtime, same checksummed release.
2. Option 1 plus a thin npm package that downloads the pinned release, for clients that expect `npx`. More reach, one more package to keep.
3. A hosted remote MCP endpoint. Needs hosting and auth; belongs with the App.

**Q-T124-6. The dogfood bar.**
1. **Recommended:** the eight lines in section 9, over 14 days on GitHub (D-412), with at least one backlog shared by two leads (the l19-hq issues).
2. A lighter bar: zero duplicate pickups and expiry clearing, nothing else measured.
3. The section 9 bar without a shared backlog, each queen on its own repo. Easier to run, but it tests almost nothing the convention does not already do.

**Q-T124-7. Who may claim on a public repo.**
1. **Recommended:** writers by default; `claims.comment_policy: anyone` lets a maintainer open `/claim` through the Action to everyone, with a 24 hour cap on outside claims. Safe default, and OSS repos can open it.
2. Anyone by default. Friendlier to outside contributors, but any account can hold any issue on any public install until expiry.
3. Writers only, no option. Simplest, closes the door the follow-up says agent-friendly OSS repos would use.

**Q-T124-8. When the D-235 clock restarts and what counts.**
1. **Recommended:** eight weeks from the day T-139 starts outreach; three outside repos counted by public `claims/` Action references, public v1 claim comments from a Waggle client, or users telling us.
2. Eight weeks from the day T-135 merges, whether or not the dogfood bar is met. A fixed date, but it can burn weeks on a fix.
3. Option 1 with six weeks. Faster answer, given the follow-up's "months, not years" window.

**Q-T124-9. Review depth for the claims program.**
1. **Recommended:** two guards on different models for the code that decides who holds a claim, who may reprioritize or what merges (T-127, T-133, T-137, T-141, T-143), one guard for the adapters, CLI, MCP and ordering tickets (T-128, T-130 to T-132, T-134 to T-136, T-142, and T-129 after the dogfood), with a second only after a must-fix. Keeps the double read where arbitration lives and follows the outside analysis ("one guard per review unless code touches the gate verdict"). Needs a D-205 change card for the program.
2. Keep D-205 as written: two guards for every Tier 3 first review, which is nearly every ticket here. Safest, slowest.
3. One guard everywhere during the program, a second only on a must-fix. Fastest; weakest on the arbitration code.

**Q-T124-10. Where the owners list lives.** The ruling names `waggle.yml`; this repo's Waggle config today is `.waggle/control/config.yaml`.
1. **Recommended:** a `governance:` block in whichever config the repo has. `waggle init --claims` writes a root `waggle.yml` for a claims-only install (no `.waggle/` tree to meet first); a hive repo keeps `.waggle/control/config.yaml`; the loader reads exactly one and fails if both exist. The config file is a default steering path, so the owners list needs an owner to change.
2. One file everywhere, `.waggle/control/config.yaml`. One loader path, already Tier 3 here, but a claims-only user meets a hidden directory first.
3. Owners from `CODEOWNERS`, no Waggle key. GitHub-native, but it would say nothing on Linear when T-129 lands, breaking the tracker-neutral rule (D-412), and enforcement needs branch protection, the admin step Level 1 avoids.

**Q-T124-11. Priority source and order.**
1. **Recommended:** one source per repo, `priority.source: label | project | milestone`, default `label`. Label: `priority: p0` to `p3`. Project: one named project's view order. Milestone: earliest due date, then label. Unprioritized issues come last, ties go to the oldest issue, and `next --prioritized-only` skips the unprioritized. Label first because it is visible on the issue, works on GitHub Free and has an attributable actor. The key's value set is open, so T-129 adds `linear` (current cycle first, then Urgent to Low, then No priority, the default on Linear) without a config change (D-412).
2. Read every source and merge by fixed precedence (project, then milestone, then label). Fewer settings, but one item can carry conflicting signals and nobody can tell why `next` picked it.
3. Labels only in Level 1, Projects order and milestones after the dogfood. Smallest build, but it leaves Projects users out of the first release.

**Q-T124-12. Detecting an agent reprioritizing its own claimed issue.** Our queens share one GitHub login, and the Head Keeper may act under it too.
1. **Recommended:** a claim records its issue's priority at claim time (`priority:` in the v1 block). A change while the claim is active is a violation when the actor is the claim holder's login and is not a reprioritizer for that area; it is flagged "unattributed" when the actor login is shared by an owner and a lead, or when the source has no actor (Projects order). Our queens move to one machine-user login, which ends the shared case. Cost: none on GitHub. A Linear seat for the same login is a T-129 question, not a Level 1 cost (D-412).
2. Snapshot only: any change while a claim is active is flagged for an owner to confirm, actor ignored. Works with shared logins, but flags every legitimate owner change.
3. Actor only, no machine user. Simplest, but with our shared login every change looks like an owner's, so our own repos would never flag one.

**Q-T124-13. What "agents never merge" vision and roadmap changes means.**
1. **Recommended:** an owner approves the PR at its exact head; who presses merge is not checked. The gate's protected-path approver check already does this, and it matches today's Tier 2 rule here. GitHub records only the merging login, which our queens share.
2. An owner must press merge, checked by `merged_by` not being a lead's login. Stricter, but it needs the machine-user login of Q-T124-12 option 1 and fails silently without it.
3. Convention only: the `AGENTS.md` rule, no check. Nothing to build, nothing to see when it is broken.

**Q-T124-14. Where our backlogs move.** All on GitHub issues (D-412); the question is how they are split.
1. **Recommended:** each repo's `TODO.md` moves to that repo's GitHub issues with `priority:` labels, and the l19-hq issues hold the shared backlog. Each `TODO.md` becomes a one-line pointer. No seat cost, and it exercises the default path outside users will take.
2. Everything into the l19-hq issues as one backlog, with a repo label per item. One place to look, but `Closes #N` cannot close an issue in another repo without the full `owner/repo#N` form, and the Level 2 check reads the PR's own repo first.
3. Only the four dogfood repos move now; the rest after the bar is met. Less churn, but queens in other repos keep picking from files nobody else can see.

## 1. Goal

Make Waggle the claims layer for the task lists agent teams already use. **Backlog.md (or a GitHub issue, or a Waggle hive task) says what the work is. Waggle says who holds it now, until when, and what it touches** (D-416). An agent lead claims a task before it starts; every other person and agent team sees that claim on the GitHub issue, where they already look; a second lead going for the same task, or for overlapping paths, is refused with the holder's name; and a claim nobody renews clears itself.

The Head Keeper's own words (D-410): "Agent leads (queens) need to claim issues that they are working on so other users and agent teams even know those are 'claimed' in the first place. That's the real problem I have."

Waggle does not become a tracker. It reads task ids, status, dependencies and priority from the source that owns them and never writes a Backlog.md file or a priority. The only things it writes are its claim refs and a one-way mirror onto GitHub issues.

## 2. Where we start

**The claim store exists.** Claims are git refs under `refs/waggle/claims/` (`internal/comb/backend.go:188`), one ref per ticket, `ticket-<n>`, each pointing at a commit whose tree holds one JSON `Lease` (`backend.go:114-126`). Writes are `git push --atomic --force-with-lease=<ref>:<expected oid>` (`git.go:805-816`): an empty expected oid creates, a stored oid renews or takes over. `force-release` deletes a claim and appends an audit ref in one atomic push (`force.go:486-494`). Ticket ids are Waggle's own (`^(T-)?[0-9]{1,6}$`, `backend.go:194`), default lifetime is 120 minutes (`internal/config/config.go:35`), and `waggle dispatch` renews during a run (`internal/dispatch/claim.go:64`). `waggle-sh/waggle` holds 21 live claim refs today. Nothing writes an issue assignee, label or comment.

**One trap for this plan.** Every reader lists the whole prefix and reports any ref that is not `ticket-<n>` as malformed (`backend.go:195`, `git.go:946-963`): `waggle status`, `waggle doctor` and dispatch's force path (`internal/dispatch/force.go:292`) would all warn on the first new claim. The claim-time overlap check already ignores such refs, so nothing blocks, but the noise is real. T-136 fixes it before any new ref is written (section 6).

**Backlog.md, as it is.** Markdown task files in git with a CLI, an MCP server and a web board (7.5k stars, MIT). Its format, read from its source:

- The folder is `backlog/` or `.backlog/` (a folder holding `config.yml` or `config.yaml` wins; otherwise whichever exists, `backlog/` first), or a custom folder named by `backlog_directory` in a root `backlog.config.yml` that also sets `project_name`.
- Active tasks are `<folder>/tasks/<prefix>-<n> - <Title>.md`; drafts sit in `drafts/`; finished tasks move to `completed/` or `archive/tasks/`. Subtasks use decimal ids (`task-4.1`).
- YAML front matter: `id` (for example `BACK-260` or `task-12`; the prefix is `task_prefix` in config, default `task`), `title`, `status` (one of config `statuses`, default `To Do`, `In Progress`, `Done`), `assignee` (a list), `labels`, `milestone`, `dependencies` (a list of task ids), `priority` (one of config `priorities`, default `high`, `medium`, `low`, normalized to lower case), `ordinal` (a number for board order), `parent_task_id`, `references`.
- Its own sort is priority rank (config order, then no priority), then task id compared numerically.
- It has no lease, no atomic claim and no expiry. Its `assignee` field is a line in a file, changed by a commit.

**What the inputs found.** The claims follow-up: duplicate PRs were the most common PR-level failure in a study of agent PRs (23 percent of the failures it classified), and "nobody ships" a claim that is atomic, expires, states its paths, works from any tool and shows on the issue. The pressure test ran a 20-way race on one new ref against a bare repo: exactly one push won. It also found what "atomic" does not cover: anyone with push access can overwrite or delete any claim with `--force`, nested refs (`T-123` and `T-123/w1`) cannot coexist in git, a push to a custom ref starts no workflow, GitHub recommends at most 6 pushes a minute per repo, and two-way sync is where projects like git-bug pay forever. Its verdict on Backlog.md: "Read its files as a task source. Do not invent `.backlog/T-123.md`."

**The risk this plan accepts.** The follow-up: "It is thin. A team can get most of it with one line in `AGENTS.md` and `gh issue edit --add-assignee`." Waggle must beat that line on day one with refusal on a race, expiry and scope overlap. The platforms are one feature away, so build small and test fast.

## 3. Level 0: the AGENTS.md convention

A claim shows on an issue as three things:

1. **Assignee:** the GitHub login the lead works under, when GitHub can assign it.
2. **Label:** `claimed` (Q-T124-2).
3. **One sticky comment** naming the holder, the lead, the paths, when the claim expires and when it was last checked (section 4.5).

The rule an agent follows with nothing installed but `gh`: read the issue first and skip it if it shows a live claim or an assignee; to claim, assign yourself, add the label and post the comment; keep it current while you work; when done (merged, abandoned or handed off), remove all three. T-125 writes this as a copyable `AGENTS.md` section, including the Backlog.md form (read `backlog/tasks/`, claim through Waggle, never edit another lead's task). Level 1 is what makes the same three things atomic, expiring and scoped.

T-126 makes the README lead with it: the problem, "Backlog.md says what, Waggle says who and until when", the snippet, then the install. Bee vocabulary moves to one glossary page; the README keeps plain terms (task, issue, claim, paths, gate, approver), as D-236 decided.

## 4. Level 1: the claims layer

The rulings that frame it stand: open core (D-411: the CLI and the GitHub Action are free and open source, Apache-2.0, a hosted App later), existing code kept and frozen (D-411), GitHub first and Linear after the dogfood (D-412), and the companion position (D-416).

### 4.1 Task ids from any source

A claim is keyed on an **opaque task key**. An adapter turns each source's own id into a key; the claim store never parses one. Three sources in Level 1:

| Source | Id it reads | Key | Ref |
| --- | --- | --- | --- |
| Backlog.md | front matter `id`, never the file name (a rename does not orphan a claim) | `bl-<id>`, lower case: `BACK-260` becomes `bl-back-260`, `task-4.1` becomes `bl-task-4.1` | `refs/waggle/claims/bl-back-260` |
| GitHub issue in this repo | the issue number | `gh-<n>` | `refs/waggle/claims/gh-123` |
| Waggle hive task | `T-<n>` | `ticket-<n>`, today's form | `refs/waggle/claims/ticket-124` |

Rules for keys: lower case always (loose refs on a case-insensitive checkout would fold `BACK-1` and `back-1` into one file), characters `[a-z0-9._-]` only, no `..`, no trailing `.` or `.lock`, at most 100 bytes. A source id that does not fit becomes `h-<first 20 hex of sha256(source ":" id)>`, and the record keeps the original id. Ids never come from "next integer in a file": Backlog.md allocates its own ids, issues have numbers, and hive ids are allocated by the queen as today. A Linear key (`ln-<identifier>`) arrives with T-129 and changes nothing here.

Hive tasks keep today's ref name and today's `lease.json` record, so the frozen gate keeps reading them. They are claimed, renewed and released by today's code (`waggle claim`, `waggle dispatch`); the new layer reads them for listing, overlap, `next` and the mirror and never writes them (section 6).

### 4.2 One flat claim per task

- **One ref per task, flat name, no children.** `refs/waggle/claims/<key>` and nothing under it. The lead holds the claim; its workers are a display field (`workers`, up to 8 short names). If the work splits cleanly, split the task in its source.
- **The record**, a `claim.json` in the claim commit's tree: `v` (1), `key`, `source` (`backlog`, `github`), `task` (the source's own id), `title` (capped at 120 bytes), `holder` (a GitHub login), `lead` (the lead's name, for example `expo-queen`), `workers`, `paths` (optional, section 4.3), `scoped_at`, `claimed_at`, `renewed_at`, `expires_at`, `issue` (the mirrored issue number, if any), `branch` (optional). Times are UTC at second precision. T-125 writes the spec; T-127 owns the parser.
- **Atomic create.** `git push --atomic --force-with-lease=<ref>: origin <commit>:<ref>`: the push fails if the ref exists. The loser is told who holds it.
- **Takeover only after expiry plus grace,** with the expected old value: `--force-with-lease=<ref>:<oid it read>`. A takeover is a child commit of the expired claim, so its history stays. Two takers race on the old oid and one wins.
- **Batch renew.** `waggle renew --mine` renews every claim the caller holds in one atomic push, each ref with its own expected old value. If any ref moved (taken over after a lapse, or deleted), the push is retried without it and that claim is reported lost. A lead renews every 30 minutes by default, so two leads with ten claims each make 4 pushes an hour, far under GitHub's 6 a minute.
- **Release, and release on merge.** `waggle release <key>` deletes the ref with its expected old value and, in the same atomic push, appends an entry to `refs/waggle/claim-log` (key, holder, reason, time), the same pattern `force-release` uses for its audit ref. Reasons: `released`, `merged`, `backed-off`, `taken-over`, `expired`. A merged PR that names the task (a `Waggle-Task: <key>` trailer, or `Closes #<n>` for an issue task) is released by the sweep (section 4.5) without a command.
- **Lease timing** (Q-T124-16): default 2 hours, renewed every 30 minutes; maximum 24 hours, enforced when written and when read (a reader treats a record whose `expires_at` is more than 24 hours after `renewed_at` as expiring at `renewed_at` plus 24 hours); a 10-minute grace after `expires_at` before anyone may take over or sweep. A claim in its grace window still counts as held for `next` and overlap.
- **"Do I still hold this?"** `waggle claims --check <key>` exits 0 only if the caller's claim is live and its oid is the one it last wrote. Dispatch and the queen run it before every push to a PR branch and before opening a PR; a lost claim stops the work instead of racing the new holder.

### 4.3 Scope, and the overlap check after claiming

Scope is optional at claim time: whoever writes a task usually does not know its paths until a forager has looked. A claim starts with `paths: []` and gains paths with `waggle scope <key> --paths a,b`. Paths follow today's lease rules (literal repo-relative paths, no globs, at most 5, never `.waggle/`, compared on segment boundaries and with ASCII case folding), reusing comb's exported normalizer read-only.

Git makes each ref atomic but not the set, so overlap is checked **after** the write:

1. Write the claim (or the scope change) as above.
2. Re-list: one `ls-remote` of `refs/waggle/claims/*`, fetching only claim commits not already cached by oid.
3. Compare this claim's paths with every other live claim, hive leases included.
4. If an overlapping claim wins, back off: a claim made with paths deletes itself (expected old value, log reason `backed-off`); a scope change reverts to the previous scope and the claim stays. **A live hive lease (`ticket-<n>`) always wins.** It has no `scoped_at`, today's code never reads new-kind claims and so never backs off, and it is checked by the gate at merge. Between two new-kind claims, the winner is the smaller `scoped_at`, then the smaller key in byte order, so every reader of the same snapshot picks the same winner.
5. Report the holder of the winning claim.

Two writers whose pushes and re-lists interleave can each miss the other. The next renew runs the same check against a fresh list, so a double hold between two new-kind claims lasts at most one renewal interval, and one against a hive lease ends when the new-kind claim backs off at that renew (a hive lease written after the new claim still wins, since today's `waggle claim` checks only other `ticket-` refs); and `claims --check` before a push catches either sooner. The gate (Level 2) is the only fence a PR cannot get past; in the dogfood the sweep reports any PR from a lead that did not hold the claim.

### 4.4 `waggle next`

`waggle next [--claim] [--source backlog|github|hive] [--label l] [--paths a,b] [--json]` gives the top task nobody holds:

- **One `ls-remote`** returns the default branch head and every claim oid. One fetch brings that head and any claim commit not cached. Backlog.md files and hive task files are read from that fetched tree, never the working tree, so a three-day-old branch cannot hand out finished work. One paginated GitHub API call lists open issues.
- **Candidates.** Backlog.md: tasks in `tasks/` (not drafts, completed or archive) whose `status` is the config's `default_status` (or its first status), and whose `dependencies` are all finished (in `completed/` or at the last status). Hive: task files with `- **Stage:** ready` (T-106). GitHub: open issues with no assignee (an assignment Waggle made for a claim that has since expired does not count), not labeled `blocked`, and not Waggle window issues (those mirror a file task, section 4.5).
- **Skips** anything with a live or in-grace claim, and anything whose known paths overlap a live claim. Known paths are the hive task's lease line or an issue body's `Paths:` line; a task with no known paths is never skipped for overlap.
- **Order** (Q-T124-11): each source's own priority maps to one bucket: issue label `priority: p0` is 0; `p1` and Backlog.md `high` are 1; `p2` and `medium` are 2; `p3` and `low` are 3; none is 4. A Backlog.md config with its own `priorities` list maps by position. Within a bucket, sources come in config order (`claims.sources`, default `backlog, github, hive`), then each source's native order: Backlog.md `ordinal` (a Waggle choice: Backlog.md's own priority sort ignores it and ties on id), then id compared numerically as Backlog.md does; issues oldest first; hive tasks by id.
- **`--claim`** claims the first candidate; on a lost race or a back-off it tries the next, up to five. This closes the gap between picking and claiming that a separate `next` and `claim` leave open.

### 4.5 The issue mirror, one way, and the reconcile sweep

The ref is the truth. The issue is a window onto it, written by Waggle and never read back for claim state.

- **The CLI writes the issue at claim time,** in the same command as the claim, best effort: claim, scope change, release, back-off and takeover each re-render the issue. A mirror failure never fails the claim; it prints a warning and the sweep repairs it. Renewals do not touch the issue unless the shown expiry would be more than 30 minutes wrong.
- **An issue task** (`gh-<n>`) gets the assignee (only when GitHub can assign that login; the comment carries the truth either way), the `claimed` label and one sticky comment, found by its hidden marker `<!-- waggle:claim v1 key=gh-123 -->` and edited in place. The comment renders the full current state, never a delta: holder, lead, workers, paths, expiry, "as of" time and the claim commit's short oid. On release it reads "released (merged in #456)" and the label goes; the assignee is removed only if Waggle set it. Waggle never edits an issue body that it did not create.
- **A Backlog.md or hive task** gets a window issue on its first claim (Q-T124-18; the CLI opens it for a Backlog.md claim, and the sweep for a hive claim, since today's code writes those): title `[BACK-260] <title>`, label `waggle-task`, marker `<!-- waggle:task key=bl-back-260 -->`, and a body rendered from the task file at the default branch head under a banner: "Mirrored from `backlog/tasks/back-260 - Title.md` at `<sha>`. Edit the file. Edits made here are overwritten." Later claims reuse it. If the task's `references` already name exactly one issue in this repo, that issue is the window and its body is left alone. The window closes when the task reaches its last status or leaves `tasks/`. Comments on a window stay free for discussion; nothing in them flows back.
- **The reconcile sweep,** `waggle sweep`, runs every 15 minutes on Level 19's own runner host (the AWS worker box that runs our review jobs), from a timer, with a fine-grained token for the dogfood repo's contents and issues (Q-T124-19). It is not a GitHub-hosted scheduled workflow: those are delayed under load (19 minutes on average in one 2026 incident), a custom ref push triggers none, and a 5-minute cron would cost about 8,600 Actions minutes a month on a private repo. Each run makes one `ls-remote`, one fetch and a few API calls. **It writes only new-kind claim refs:** it never deletes, releases or takes over a `ticket-<n>` ref, which stays with today's code, `dispatch` and `force-release`; for hive claims it only renders window issues and reports. **Its memory between runs** is `refs/waggle/sweep-state`, written only by the sweep with an expected old value: the time of its last run and the claim oids it saw then. It is a hint, not claim state: if it is missing or damaged, the sweep looks back 24 hours (the maximum lease) for merged PRs and skips vanished notices for that run, so a bad state ref costs at most a missed or false notice. Each run:
  1. deletes claims past expiry plus grace (expected old value, log reason `expired`) and clears their issues;
  2. releases claims whose PR merged since the last run in its state ref (log reason `merged`);
  3. re-renders every mirrored issue from the refs and files, which repairs drift, a lost CLI write and any edited window body;
  4. marks a claim that vanished without a log entry (an oid in its state ref whose ref is gone and whose key has no log entry since): its sticky comment reads "claim vanished without a release" with the last oid seen, and `waggle claims --mine` shows it as lost to its holder;
  5. reports, without acting: holders over their cap, records with an over-long lease, and PRs whose author's lead did not hold the named task.

Rate budget: the sweep and the CLI together stay under 6 pushes a minute and about 100 API calls an hour for a repo with tens of live claims.

### 4.6 Command surface

All in the current `waggle` binary (Q-T124-4): `waggle claim <key>` (a `T-<n>` argument still goes to today's code byte for byte; any other key goes to the new layer), `waggle scope`, `waggle renew --mine`, `waggle release`, `waggle claims [--mine] [--check <key>] [--json]`, `waggle next`, `waggle sweep`. Keys can be typed as the source shows them (`BACK-260`, `#123`, `T-124`) and are mapped by the adapters. Config lives in a `claims:` block (sources, Backlog.md folder override, lease timing, holder cap, labels, sweep interval) in the repo's Waggle config file (Q-T124-10 settles the file name for a claims-only repo; the dogfood repo is set up by hand from T-125's doc).

## 5. Level 2: the gate as an opt-in scope check (after the dogfood)

The gate learns one new, opt-in source for a PR's claim: the task the PR names, by a `Waggle-Task: <key>` trailer or `Closes #<n>`. With `gate.claims_source: claims` it reads that claim from the ref and checks the PR's changed paths against the claim's `paths`, report-only first (a sticky PR comment, the check passes), with the existing modes to make it binding. Default off. Today's T-id lease check, protected paths and decisions log are unchanged. T-137 builds it after the dogfood, since the dogfood measures cooperation, not enforcement.

## 6. The comb and today's claims

## 8. Governance: who sets vision, roadmap and priority

The Head Keeper's ruling (D-415, item 55, e1759): "Yes, add it to the brief." Agents claim and build; people decide what matters.

1. **Vision and roadmap are human-owned.** The repo's owners own them: a `governance.owners` list in the repo's Waggle config (Q-T124-10), defaulting to the repo's admins. `governance.steering_paths` names the vision and roadmap files (default `VISION.md`, `ROADMAP.md` and the Waggle config file itself). Agents propose by PR or issue and never merge; an owner's approval at the PR's exact head is what counts (Q-T124-13). T-125 says this in the `AGENTS.md` section; T-137 can check it with the gate's existing protected-path approver check, report-only.
2. **Priority comes from the tracker.** Waggle stores no priority. For a Backlog.md task the tracker is its file (`priority`, `ordinal`), changed by a commit that owners review as any other; for an issue it is the `priority:` label; Linear priority arrives with T-129. `waggle next` follows that order (section 4.4).
3. **Who may reprioritize is set in config.** `governance.reprioritizers` defaults to the owners and can name leads per area (by path prefix or label). An agent reprioritizing a task it holds is a violation: the sweep flags it on the issue and in `waggle claims` (T-143). For Backlog.md the actor is the commit author, which our shared queen login blurs (Q-T124-12). Waggle never reverts a priority change; an owner does.
4. **Quorum is the optional, later answer** for open projects with many contributors (`governance.mode: quorum`). It stays frozen under D-411. `governance.mode: owners` is the only mode built now.
5. **Our repos.** The dogfood repo's `TODO.md` becomes Backlog.md task files, created with Backlog.md's own CLI, plus its existing GitHub issues (T-144, Q-T124-14). The Waggle hive keeps `ROADMAP.md` and its task files as its plan of record. The scout role's "Owns `ROADMAP.md`" becomes "drafts `ROADMAP.md`; owners merge" (T-144, Tier 3).

T-141 (config) and T-143 (the check) build after the dogfood starts and do not gate it.

## 10. Trust model and threat model (D-203)

**Claims are cooperative.** A claim stops honest agents and people from colliding. It is not a lock against anyone who can push: the pressure test overwrote, deleted and replaced claims with `--force` and plain pushes, and GitHub has no per-ref permissions outside branches and tags. Holder names are self-asserted. The docs (T-125, T-126) say this plainly, in those words.

**Cheap protections, all in Level 1:**

- **Holder caps.** At most 5 live claims per holder by default (`claims.max_per_holder`); the CLI refuses a sixth, and the sweep reports a holder over the cap that wrote past the CLI.
- **A short maximum lease.** 24 hours, enforced on write and on read, so a far-future `expires_at` from a bad clock or a bad actor counts as 24 hours.
- **A grace window.** 10 minutes after expiry before takeover or sweep, which absorbs clock skew and short GitHub outages.
- **A claim log and a "claim vanished" notice.** Every Waggle release writes a log entry in the same atomic push; a claim that disappears without one is shown as vanished on its issue and to its holder.
- **Worker credentials never write claim refs.** The lead holds the claim; workers run with tokens that cannot push `refs/waggle/` where the host allows it, as today's dispatch rule already requires.
- **The sweep deletes only by rule** (expired past grace, or its PR merged), only new-kind claims (never a `ticket-<n>` ref), and every deletion is logged.
- **Later, the App is the only writer for outsiders and `/claim`** (section 7).

**Failure modes and their answers.** Clock skew: the grace window and read-side cap. Zombie holder (a laptop sleeps past its lease and wakes): `claims --check` before every push. GitHub outage: no claim, no start; the grace covers short gaps. Mirror lag or a lost mirror write: the CLI writes first and the sweep repairs. Mirror racing itself: every render is full state, so the last writer is always right after the next sweep. Stale task files on old branches: `next` reads the default branch only.

**Boundary.** Issue titles, bodies, comments and labels, and Backlog.md files merged by others, are attacker-written on a public repo. They are read as data with caps (titles at 120 bytes, bodies rendered into a window only as quoted text) and never as instructions. The sweep runs from its own pinned build with a token limited to one repo's contents and issues; it never checks out or runs PR code. Priority labels and milestones need triage or above, and Backlog.md priority changes need a merged commit, so an outside commenter cannot reorder `next`.

**Notes, not must-fix (D-203).** An attacker with repo admin, with a lead's push token, or with the sweep's token can do anything a claim could stop.

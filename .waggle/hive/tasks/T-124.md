## 1. Goal

Make Waggle the tool an agent lead uses to claim the issue it is about to work on, so that every other person and agent team sees the claim where they already look: on the GitHub issue. Level 1 ships GitHub only; the claim format stays tracker-neutral, and Linear is the first ticket after the dogfood (D-412). Start from the convention many repos already write in `AGENTS.md` ("assign yourself before you start, skip assigned issues") and add the part that convention cannot do: a claim that wins a race, expires on its own, and says which paths it will touch. The existing gate becomes an optional second step that checks a PR stayed inside its claim.

The Head Keeper's own words (D-410): "Agent leads (queens) need to claim issues that they are working on so other users and agent teams even know those are 'claimed' in the first place. That's the real problem I have."

## 2. Where we start

**What exists.** Claims are git refs, `refs/waggle/claims/ticket-<n>` (`internal/comb/backend.go:188`), one JSON `Lease` per ref (`backend.go:114-126`): ticket, keeper, role, gate, directories, claimed and expiry times, branches. `AcquireLeaseWithTrailers` (`git.go:540`) is a compare-and-swap per ticket with an optimistic directory overlap check across tickets (`internal/comb/git.go:626`); a same-owner claim renews, an expired one is taken over. Ticket ids are invented (`T-001`, `^(T-)?[0-9]{1,6}$`, `backend.go:194`). Default lifetime is 120 minutes and `waggle dispatch` renews during a run (`internal/dispatch/claim.go:64`). `internal/forge` talks to GitHub for PRs, reviews and comments; nothing writes an issue assignee, label or issue comment. `internal/relay` holds a pure parser for `/waggle claim` PR comments (T-065, partial, not usable).

**What the outside inputs found.** The outside analysis: "the repo has been public since about November 20, and has 2 stars (one is the owner), 0 forks, 0 outside issues or PRs", and the D-235 criterion "stands at 0 of 3". A binding gate takes seven steps, two of them in GitHub settings. The claims follow-up: duplicate PRs were "the most common PR-level failure reason: 23% (142 PRs) of the failures classified" in a study of 33k agent PRs, and "Waggle does not solve this today for anyone not running its CLI. Claims use invented ids (`T-001`), live in git refs that the GitHub UI never shows". Its gap statement: "one claim that is atomic, expires on its own, states which paths it will touch, works from any agent tool, and shows up on the issue where other teams already look. Nobody ships that combination."

**The risk the follow-up names and this plan accepts.** "It is thin. A team can get most of it with one line in `AGENTS.md` and `gh issue edit --add-assignee`." Level 1 must beat that line on day one with three things the line cannot do: refusal on a race, expiry, and scope overlap. And "GitHub and Linear are both one feature away", so the window is months. Build small, test fast.

## 3. Level 0: the AGENTS.md convention

A claim is three visible things on the issue, and nothing else:

1. **Assignee:** the human (or bot) account the lead works under.
2. **Label:** `claimed` (Q-T124-2).
3. **One sticky comment** naming the holder, the lead, the declared paths and how long the claim lasts. Its exact format is set by the Level 1 design (Q-T124-1, held).

The rule an agent follows, with nothing installed but `gh` (or any tracker's UI, since the convention names nothing GitHub-specific):

- Before starting, read the issue. Skip it if it carries an active claim.
- To claim: assign yourself, add the label, post the claim comment.
- While working, keep the claim current.
- When done (merged, abandoned or handed off), release the claim, remove the label and your assignment.

How a claim shows it is active, how it expires and how two claimants settle a race come with the Level 1 design; T-125 writes the convention to match it.

T-125 writes this as a copyable `AGENTS.md` section and as the spec. T-126 makes the README lead with it: problem, the three things, the snippet, then "add Waggle to make it atomic, expiring and scoped". Bee vocabulary (keeper, queen, forager, builder, guard, scout, hive, honey) moves to one glossary page; the README keeps plain terms (task, issue, claim, paths, gate, approver), as D-236 decided and the outside analysis asked again ("A gate-only user needs four" terms).

## 5. Level 2: the gate as an opt-in scope check

## 8. Governance: who sets vision, roadmap and priority

The Head Keeper's ruling (item 55, e1759): "Yes, add it to the brief." It answers who sets the vision, the roadmap and backlog priority in a Waggle repo. Agents claim and build; people decide what matters.

1. **Vision and roadmap are human-owned.** The repo's owners own them: a `governance.owners` list in the repo's Waggle config (Q-T124-10 settles the file), defaulting to the repo's admins when the list is absent (GitHub: collaborators with admin permission; Linear workspace admins arrive with T-129). `governance.steering_paths` names the vision and roadmap files (default `VISION.md`, `ROADMAP.md` and the Waggle config file itself, so the owners list protects itself). Agents propose a change by PR or by issue and never merge it; an owner's approval at the PR's exact head is what counts (Q-T124-13). Level 0 says this in the `AGENTS.md` section (T-125). Level 2 checks it: the gate's existing protected-path approver check, fed from `governance.owners`, reports a steering-path PR without an owner approval (T-137, report-only by default; T-137 is held for the Level 1 design, and the steering-path half does not depend on the claim format).
2. **Priority comes from the tracker.** Waggle stores no priority of its own. One configured source per repo: a priority label, a GitHub Projects order or milestones in Level 1 (Q-T124-11), and Linear priority and cycles once T-129 lands. `waggle next` picks the top unclaimed item in that order. T-142 reads the order; T-131 consumes it (held for the Level 1 design).
3. **Who may reprioritize is set in config.** `governance.reprioritizers` defaults to the owners and can name leads per area (by path prefix or by label), so a lead may reorder its own area's backlog. An agent reprioritizing an issue it holds or has claimed is a violation, flagged with a comment on the issue and a line in the claims listing; which scheduled run does the flagging (today's proposal: the sweep and the Action, both held) follows the Level 1 design. Waggle never reverts a priority change; an owner does. Attribution is the hard part (Q-T124-12): our queens share one login, and a GitHub Projects reorder reaches only org-level `projects_v2_item` webhooks, which a repo workflow cannot receive, so until the App (T-140) a Projects reorder is seen by snapshot, not by actor. T-141 adds the config; T-143 adds the check.
4. **Quorum is the optional, later answer.** For open projects with many contributors, Quorum's `sqrt(Nectar)` ballots on roadmap and priority (T-054) can replace the owners list as the priority source, as an opt-in `governance.mode: quorum`. It stays frozen under D-411 and gets no ticket in this program. `governance.mode: owners` is the only mode built now.
5. **Our repos.** Backlogs move from `TODO.md` files to GitHub issues with visible priority (D-412), and the queens pull from there with `waggle next` (T-144, before the dogfood; Q-T124-14 picks where each backlog lives). The Waggle hive keeps `ROADMAP.md` and the task files as its plan of record, owner-merged as today's Tier 2 rule already requires; its open tickets get mirrored issues as section 6 describes. The scout role's "Owns `ROADMAP.md`" becomes "drafts `ROADMAP.md`; owners merge" (T-144, Tier 3).

## 10. Threat model (D-203)

This section keeps only what does not depend on Level 1 mechanics. **The claim threat model** (who can forge, steal or race a claim, arbitration, expiry, caps on active claims, behavior when the tracker is unreachable, and the comb's trust) **comes with the Level 1 design** and its follow-up brief.

**Boundary.** Issue text, comments and labels on a public repo are attacker-written. A claim is a coordination signal, not a security control: it stops honest agents and people from colliding, and Level 2 is the only place a claim becomes binding.

**Entry points.** The MCP server exposes claim tools only, with the identity of the token it runs with (the caller's own `gh` token): no tool runs a shell, changes the gate, reads files or acts on someone else's claim. Issue titles, bodies and comments returned to the model are untrusted text: the server returns fields, caps each, and marks them as issue content. A prompt-injected client can still claim issues it should not, so the Level 1 design must bound and expose that. The Action never checks out or runs PR code, runs from its own pinned tree (as `gate/` does, D-270) with the least permissions its job needs, and parses comment bodies with caps by a pure parser.

**Priority and steering.** Priority labels, milestones and Projects order on GitHub need triage or above (and Linear priority, once T-129 lands, needs workspace membership), so an outside commenter cannot reorder `next`. A forged `governance` block in a PR is a steering-path change and needs an owner (section 8). Priority text in an issue body is ignored.

**Linear (T-129, after the dogfood).** Not in Level 1 (D-412). Carried into the T-129 brief: workspace membership is the trust boundary; Linear is trusted for authorship and ordering as GitHub is; a Linear personal API key acts as its user with that user's workspace access, so it is a full-access secret, read from `LINEAR_API_KEY` only, never logged, never in a comment, never passed to a fork's workflow.

**Notes, not must-fix (D-203).** An attacker with repo admin, with a lead's token, or able to post as the Action's bot can do anything a claim could stop.

**Q-T124-11. Priority source and order.**
1. **Recommended:** one source per repo, `priority.source: label | project | milestone`, default `label`. Label: `priority: p0` to `p3`. Project: one named project's view order. Milestone: earliest due date, then label. Unprioritized issues come last, ties go to the oldest issue, and `next --prioritized-only` skips the unprioritized. Label first because it is visible on the issue, works on GitHub Free and has an attributable actor. The key's value set is open, so T-129 adds `linear` (current cycle first, then Urgent to Low, then No priority, the default on Linear) without a config change (D-412).
2. Read every source and merge by fixed precedence (project, then milestone, then label). Fewer settings, but one item can carry conflicting signals and nobody can tell why `next` picked it.
3. Labels only in Level 1, Projects order and milestones after the dogfood. Smallest build, but it leaves Projects users out of the first release.

**Q-T124-12. Detecting an agent reprioritizing its own claimed issue.** Our queens share one GitHub login, and the Head Keeper may act under it too.
1. **Recommended:** a claim records its issue's priority at claim time (where in the claim record is set by the Level 1 design). A change while the claim is active is a violation when the actor is the claim holder's login and is not a reprioritizer for that area; it is flagged "unattributed" when the actor login is shared by an owner and a lead, or when the source has no actor (Projects order). Our queens move to one machine-user login, which ends the shared case. Cost: none on GitHub. A Linear seat for the same login is a T-129 question, not a Level 1 cost (D-412).
2. Snapshot only: any change while a claim is active is flagged for an owner to confirm, actor ignored. Works with shared logins, but flags every legitimate owner change.
3. Actor only, no machine user. Simplest, but with our shared login every change looks like an owner's, so our own repos would never flag one.

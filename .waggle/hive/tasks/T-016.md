## 1. Goal

A hive changes the Waggle build it runs only through a logged upgrade (D-041), and product template changes reach a hive's installed copies only through this command, in a hive PR (D-042). Replace the manual phase C procedure in T-011 section 10 with one command.

## 2. Behavior sketch (to be confirmed in section 5)

Dry run by default, `--apply` executes, same convention as `waggle uninstall`.

1. **Preconditions,** checked before any write, exit 1 with no change on failure: cwd is the work tree root; clean tree; `.waggle/control/config.yaml` exists (legacy layout gets T-011's 6.5 message); `run.sock` absent; every marked block parses; the running binary has a usable version (release tag, or `vcs.revision` with `vcs.modified=false`). An `unpinned` build is refused.
2. **Plan,** one line per action:
   - `[pin] <old> -> <new>`, read from `waggle.pin` and from the running build.
   - `[rewrite]` each file in `layout.Managed` whose bytes differ from this build's template, with a unified diff under `--diff`. `[same]` otherwise.
   - `[remove]` each managed file present in the hive that this build's templates no longer ship (D-083; T-020's `roles/architect.md` is the first case). See 2.1 for how a file is known to be managed. Never `[remove]` a seeded file or anything outside 2.1's set.
   - `[skip] seeded` for `config.yaml`, `WAGGLE.md`, `local.yaml`, except the single `waggle.pin` line in `config.yaml`.
   - `[edit]` the marked blocks in `.gitignore` and `CLAUDE.md` or `AGENTS.md` when this build's block body differs.
   - `[shims]` regenerate `.claude/agents/waggle-*.md` through the runtime adapter, and remove any `waggle-*.md` shim carrying `# waggle:generated` whose role file was removed above (T-011 section 7: a shim without that line is never touched).
3. **Apply:** write in that order; never commit; never touch `refs/waggle/*`.

### 2.1 How a file is known to be managed

The mechanism is T-011's, nothing new. A file is managed, and so eligible for `[rewrite]` or `[remove]`, when **one** of these holds:

- Its path is an entry of `layout.Managed`, or lies directly inside a directory entry of it (today `roles/` is the only directory entry, so every `*.md` directly under `.waggle/control/roles/` is managed, whatever its name). Hand-added files there are not allowed in the first place (D-042, T-011 section 6.2), so a role file the target templates do not ship is stale output, not hive content.
- It is the gate workflow and carries T-011's `waggle:managed` line. Without that line it is a project file: `[skip]` with a warning, as `waggle uninstall` does. (After T-018 phase C the workflow leaves `layout.Managed` and is owned by the forge's CI shim; follow the merged state.)
- It is a shim under `.claude/agents/waggle-*.md` with the `# waggle:generated` first frontmatter line.

Everything else is seeded, project-owned, or hive record (`.waggle/hive/**`), and `upgrade` never removes it. The set of files a build ships is the template set compiled into the running binary (`init.go`'s template-to-path map), so "no longer ships" means "in the hive under a managed location, absent from this build's map".
4. **Log:** print a ready `waggle decide` input (kind `technical`, title `Upgrade hive pin to <new>`, choice naming old and new pin) and the hint to run it in the same hive PR. See 5.4.
5. **Last line:** `Review with git status, then open a hive PR. This changes .waggle/control/ (Tier 3) and needs Head Keeper approval.`

Exit codes 0 ok, 1 refused, 2 usage, 3 git or I/O. `runUpgrade(args []string, stdout, stderr io.Writer) int`, no `os.Exit` inside.

## 3. Tests (outline)

Real `git init` repos with `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`; build info injected through the same func T-011 6.3 uses.

1. Dry run changes nothing and lists every managed file.
2. `--apply` with an unchanged pin is a no-op (all `[same]`).
3. A hand-edited managed file is restored and reported.
4. Seeded files keep their bytes except the one `waggle.pin` line.
5. Each precondition failure exits 1 with no change; `unpinned` build refused.
6. Project content outside marked blocks is byte-identical after apply.
7. A role file under `.waggle/control/roles/` that the build's templates do not ship is listed as `[remove]` in the dry run, deleted by `--apply`, and its `# waggle:generated` shim goes with it. A gate workflow without the `waggle:managed` line and a shim without `# waggle:generated` are never removed. A rerun after apply reports no `[remove]` lines.

## 4. Out of scope

- Enforcing the pin in `waggle gate` (T-014 or its follow-up: fail managed files that differ from the pinned templates).
- Fetching or building a target version. The Head Keeper builds the target outside the working tree, as in T-011 section 10.
- Upgrading from the legacy (pre-T-011) layout.

## 5. Open design points (for the Keeper before this becomes a full brief)

- **5.1 Which binary runs it.** Resolved by D-063, which clarifies D-042: the **target** build (the new known-good version) runs `upgrade`, renders its templates into the hive PR, and becomes the pin when that PR merges. The old pinned build never renders templates; it is recorded only as the "from" value. Section 2 already assumes this.
- **5.2 Seeded-file migrations.** If a release changes the `config.yaml` schema, seeded files need migrating, but they belong to the hive. Recommended for v0.1: report-only (print the keys the new build expects and does not find), Head Keeper edits by hand in the same PR. Versioned migration functions later, keyed by a `schema` field.
- **5.3 Downgrades and ordering.** Pins can be tags or bare commits, and a host repo does not contain Waggle's history, so commits cannot be ordered. Recommended: refuse a semver tag downgrade unless `--allow-downgrade`; for commit pins, print from and to without an ordering check.
- **5.4 Who writes the decision.** `waggle decide` cannot verify approval (T-006 section 8). Recommended: `upgrade` prints the input JSON, and the Head Keeper runs `waggle decide` in the same hive PR. Alternative: `upgrade --apply` calls `decisions.Append` itself, which blurs "a decision was made" with "a command ran".
- **5.5 Pin edit inside a seeded file.** `config.yaml` is Head Keeper-owned, yet the pin line must change. Recommended: a narrow line edit that requires exactly one `pin:` key under `waggle:` and refuses otherwise, rather than re-serializing the file through T-004's parser.
- **5.6 Hive-only changes to managed files.** T-007 wants a `gate decisions` step in our hive's workflow, and `upgrade` would overwrite it (T-011 section 14). Recommended: no per-hive exceptions; such a step goes into the template or not at all. Needs a Keeper call before T-007 dispatches.
- **5.7 Shim regeneration.** Shims are gitignored per-Keeper output (T-011 section 7). Recommended: `upgrade` regenerates the running Keeper's shims; other Keepers rerun `waggle init --force` or a future `waggle shims`. Removal of a stale shim (2.1) follows the same rule: this Keeper's shim goes with the upgrade, other Keepers' shims go when they rerun.
- **5.8 Removed managed files.** Resolved by D-083: `upgrade` deletes managed files the target build's templates no longer ship, per section 2 `[remove]` and 2.1. Raised by T-020 Q-T020-3, whose phase C stops if `roles/architect.md` survives the upgrade.

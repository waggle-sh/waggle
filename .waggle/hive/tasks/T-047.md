## 3. Q1: where the file lives and what the URL is

`docs/setup.md`, as one file (Q-T047-1). URL form `https://raw.githubusercontent.com/waggle-sh/waggle/refs/tags/<tag>/docs/setup.md`.

- The `refs/tags/` form cannot be shadowed by a branch with the tag's name. The form resolves on a public repo (checked: `cli/cli`, `refs/tags/v2.60.0`, 200). AWS uses the same shape with `refs/heads/main`.

- A raw URL serves markdown as plain text with no rendering, which is what an agent needs.
- One file, not AWS's two: a second troubleshooting file is a second fetch at a second URL with the same trust. Failures go in a section of the same file.

An agent-driven install is trustworthy only once a person has made `verify-leases-and-tiers` and PRs required on the default branch. After that, an agent holding your git credentials can still write its own claim, so write claims yourself, from credentials the agent does not hold.

The last sentence is README line 24 and `docs/gate.md` L3 in user words. GitHub rulesets target branches and tags, so this brief assumes they cannot restrict `refs/waggle/*`. Not verified; the doc makes no claim about it.

### 8.2 Attackers and what they can do

**Trusted for this ticket:** the Head Keeper's tags and release publishing; GitHub's TLS and its serving of the repo. **Attackers considered:** an outside PR author (after the flip) changing `docs/setup.md`, a builder inside this lease, text in the target repo or logs that an agent reads, a person who posts a lookalike prompt, and the installing agent itself.

**A tampered doc is code execution with the user's credentials,** since an agent runs what it says. That is the same damage as a tampered `install.sh`, but it reads as prose, it needs no shell pipe, and an agent may follow it with less scrutiny than a user gives a script. So review of this file is review of code (8.4).

### 8.3 What the pins do and do not protect

| Control | Protects against | Does not protect against |
| :--- | :--- | :--- |
| Tag in the URL | A later commit on `main` changing what an already pasted prompt runs. A merged bad PR reaching users before a new tag. | Anyone who can move or delete the tag. **This repo has no tag ruleset today** (`gh api .../rulesets` lists only `main`, 2026-11-01; T-036 2.10 left it on its own card), so the Head Keeper card of Q-T047-7 matters. |
| `SHA256SUMS` check | A corrupt or truncated download, and a swapped asset whose sums line was not also swapped. | **Someone who can edit the release can change both files.** Sums and archive come from the same release. It proves consistency, not origin. The digest cannot go in the doc, because the assets are built from the commit the doc is in. |
| Step 5 pin check | A binary that would pin the Action to a commit other than the tag's. It keeps the workflow honest whatever the release asset is. | A deliberately forged binary, which can print any ref and do anything else when run. The check runs after the binary has already run once. |
| Workflow SHA pin | CI following a moved tag: the Action is pinned by commit (`init.go:133-158`; T-036 section 5). | The one time the doc and binary run on the user's machine. |
| GitHub artifact attestations | Would prove provenance. **Not there yet:** `release.yml` has no attest step; D-275 adds them at G5, and T-036 left their availability on a private repo unverified. The doc must not mention them until they exist. | |

**Neither pin defends against the repo's own maintainers, and neither makes the gate bind.** Stated plainly in the doc's top section by 8.1.

### 8.4 What a future change to the doc needs

Tier 3 by content, whatever the path says. First review: two guards on different models, each reading for: a new network endpoint, a new download or a pipe into a shell, reading or printing a credential, a broader permission, a removed or softened MUST NOT, and any change to the human step. A change reaches users only through a new tag and a README prompt update. **Tags are never moved:** a fix is a new tag. Mechanism: Q-T047-5.

### 8.5 Must-fix and notes for guards

**Must-fix:** any command in the doc that does not parse against the real CLI; the doc telling an agent to merge, create a rule, write a claim, pass `--force` or `--admin`, pipe to a shell or handle a credential; a step without a success criterion; a human step moved to the agent; a stop rule from 4.3 missing, above all the non-GitHub check, the `[skip]` check and the failed-check explanation; a URL that follows `main`; any wording saying the setup, the checksum or the tag makes the gate stronger against the installing agent; the doc or README claiming a run that section 9 has no evidence for; a file outside the lease rule; a test that writes, pushes or calls `main()` with anything but `-h`.

**Note, not must-fix:** an attack that needs write access to tags or releases on this repo, or the maintainer's own account; a forged binary that passes a sums line its forger also wrote; an agent that ignores the MUST NOT lines (it already holds the credentials, which the doc says); a lookalike prompt on another site; `README.md` Install wording this ticket does not edit.

**Guard prompt sentence (repeat verbatim):** "Threat bar (D-203): a finding whose attacker needs write access to this repo's tags or releases, the maintainer's account, or an agent already disobeying the doc while holding the user's credentials is a note, not a must-fix; must-fix is for any instruction in docs/setup.md that a reader or agent following it faithfully would use to harm the user's repo, leak a credential or switch on the gate without a person, any command that does not parse against the real CLI, and any claim that the setup makes the gate stronger against the agent installing it."

## 10. The AWS pattern: what we take and drop

**Kept:** inputs in one message, skipped when supplied. Autodetected OS. "MUST NOT ask for credentials". The agent runs commands, explains each and pauses only at named human steps.

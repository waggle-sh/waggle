## 1. Goal

The Head Keeper (the first login in `gate.approvers`, `docs/gate.md` section 6) runs `waggle force-release T-<id>` to see a stuck or malformed claim, then runs it again with the exact object id they saw and a reason to delete it. The delete and an audit entry land together on `refs/waggle/audit/force-releases` (D-010), so the claim is gone, its history is kept, and anyone can review who cleared what and why with `git log --first-parent refs/waggle/audit/force-releases`.

Two cases this serves:

1. **Malformed claim.** A ref under `refs/waggle/claims/` that does not decode (bad JSON, a blob instead of a commit, a non-canonical name). Today it refuses claim and release for that task and the remedy is a raw `git push origin :<ref>` with no record (`internal/dispatch/claim.go:103`).
2. **Stuck claim.** A well-formed, unexpired claim whose owner is unreachable, with a TTL of up to 7 days (`docs/multi-keeper.md` section 4). Only the owner may release it (`ReleaseLease` returns `ErrNotOwner`), so another Keeper's work on overlapping directories waits until expiry.

## 2. Scope by phase

### 2.1 Phase A: command, authorizer wiring, decision card rule

1. **Command shape.** `waggle force-release <task> [--ref <full ref>] [--oid <object id>] [--reason <text>] [--owner <id>] [--repo <dir>] [--json]`. Exactly one of `<task>` or `--ref` names the target. `<task>` builds the ref with `comb.RefName`. `--ref` takes the full name `status` or a dispatch error printed, which may be non-canonical, as `ForceRelease.Ref` allows (`internal/comb/force.go:84-86`).
2. **Two steps, no default (the decision card rule, RFC-0003 section 3.5).**
   - **Inspect** (no `--oid`): reads the target with `GitBackend.RefOID` (`force.go:225-246`, which syncs in remote mode) and classifies it with `ReadClaim` (`internal/comb/claim_read.go:18`). It prints the ref, the full object id, and either the owner, gate, directories and expiry of a valid claim or the malformation reason. It then prints the exact second command, with `--oid` filled in and `--reason` left for the caller to write. It writes nothing and exits 0. It runs the authorizer first and still prints the facts when the caller is not authorized, with a line saying who is (so another Keeper can hand the facts to the Head Keeper).
   - **Execute** (`--oid` given): `--reason` is required (1 to 512 bytes, the rules of `validateReason`, `force.go:142-160`). `--oid` must be the full hex id; there is no `HEAD`, no prefix, no `latest` and no `--yes` or `--force` flag. The delete is the library's compare-and-swap against that id (`force.go:88-93`), so a claim renewed, taken over or replaced since inspection fails with exit 4 and `re-inspect: the claim changed since you looked`.
   - No interactive prompt. The comb authorizer must not prompt (`force.go:47-49`), and a prompt is not a decision record. The two-step form is the card: the inspect output is what the decision is about, and the execute line is the typed choice.
3. **Authorizer wiring.** A `baseHeadKeeper` authorizer in `internal/dispatch/force.go`:
   - reads `.waggle/control/config.yaml` at the base commit (`ResolveBase` with the configured remote, then `blobAt`), never the working tree, as `basePolicy` does for protected paths (`internal/dispatch/task.go:124`). A local edit to the config, by a person or an agent, does not change who the Head Keeper is, which matches the gate reading `gate.approvers` from the PR base (`docs/gate.md` section 11);
   - takes `gate.approvers[0]` as the only authorized login (Q-T072-1);
   - compares it with the caller's id by ASCII case folding, the same rule as the gate's `isHeadKeeper` (`cmd/waggle/gate_approve.go:136-138`). The comb's `StaticHeadKeepers` is exact-match (`force.go:61-81`) and is not used here (Q-T072-3);
   - takes the caller's id from `--owner`, else `config.LoadKeeperID` (`internal/config/local.go:32`), which already refuses the placeholder once `forge.remote` is set;
   - with no `gate.approvers` at base, denies everyone with `no first approver in gate.approvers at <base>; nobody can force-release`, exit 4. It never falls back to allow.
   The check is advisory against anyone with raw push access, as D-009 records and `force.go:51-56` says. The help and docs say so plainly.
4. **Refusals before any write.** Exit 2 for usage (both or neither of `<task>` and `--ref`, a short `--oid`, `--reason` without `--oid`, `--oid` without `--reason`). Exit 4 for a refused release (`ErrNotHeadKeeper`, `ErrConcurrentUpdate`, `ErrInvalidForceRelease`). Exit 3 for git, config or remote trouble. An absent ref is outcome `no_claim`, exit 0, with no audit entry, like `waggle release` (`internal/dispatch/release.go` `no_claim`). Inside a dispatch worktree the command refuses with exit 4 (Q-T072-4).
5. **Output.** Text: one line per fact on inspect; on execute, `force-released <ref> (was <12 hex>, owner <id> | malformed: <reason>); audit <12 hex>`. With `--json`, one object in the house shape (`jsonVersion`, `command`, `ok`, `task`, `outcome` of `inspected`, `released` or `no_claim`, plus `ref`, `oid`, `owner`, `malformed_reason`, `audit_oid`, `warnings`). Field names follow D-297: `keeper_id` stays a key, prose says owner. The reason is never echoed to stdout in JSON or text (it can hold personal notes); it is stored only in `force-release.json`.
6. **Decision card rule for the queen.** A force-release is a `delete` card (RFC-0003 section 3.5, `.waggle/control/roles/queen.md:10`). The queen never runs the execute step and never applies a default. She may run the inspect step, puts its output and the exact execute command on an `AskUserQuestion` card of kind `delete`, and the Head Keeper runs the execute step from their own shell. In this hive that line goes into `.waggle/control/roles/queen.md`, a Tier 3 file, as a Head Keeper action (section 12). Phase B carries the same line into the scaffold template for other hives.
7. **Audit and Nectar.** Nothing new is written beyond what `ForceRelease` writes. The audit chain already keeps the released claim commit as its second parent (`force.go:16-27`, `:452-455`), and Nectar backfill already reads it as a claim source (`internal/comb/backfill.go:18, 68`), so a forced release keeps the task's attribution (core item 5 is not narrowed).

## 3. Flow, end to end

1. Ben's agent run dies with T-102 claimed for 3 days. Ana needs `internal/pricing`. Her claim is refused: `overlaps T-102 ... held by ben`.
2. Ana runs `waggle force-release T-102`. It prints the claim and says only `ana` (first in `gate.approvers`) may release it. Ana is the Head Keeper, so it also prints `waggle force-release T-102 --oid 4c21eb3...a0bd --reason "<why>"`.
3. Ana tries to reach Ben, then runs the execute line with a reason. The claim ref is deleted and the audit entry written in one atomic push (`force.go:263-270`).
4. `git log --first-parent refs/waggle/audit/force-releases` shows `waggle: force-release refs/waggle/claims/ticket-102 by ana` and the reason. Ben's claim chain is the entry's second parent.
5. Ana claims her task. Ben's open PR now fails the gate with `no claim for T-102` until someone claims T-102 again with his branch, which is the existing L4 and takeover behavior.

## 6. Exit codes and output

`0` inspected, released, or `no_claim`. `2` usage. `3` git, config or remote trouble (including an unreadable base config, fail closed). `4` refused: not the Head Keeper, no `gate.approvers`, stale `--oid`, invalid request, or run inside a dispatch worktree. These match `waggle claim` and `waggle release` (`internal/dispatch/request.go:22-25`).

## 7. Threat model (D-203)

**Boundary.** The caller's id comes from a gitignored local file or a flag, so it is a claim, not a proof (D-009). The base config is read from the remote's default branch, which a PR cannot change before merge.

**Defended.**
- *Agent clears a rival's claim through the CLI:* only the first approver's id passes; the dispatch worktree refusal stops a dispatched agent that inherits the Keeper's `local.yaml`; a queen card is never auto-applied.
- *Agent edits its local config to name itself:* the authorizer reads base, not the worktree.
- *Race with a renewal or takeover:* compare-and-swap on the inspected id; exit 4 and re-inspect.
- *Lost history:* the audit entry keeps the released claim reachable.
- *Terminal injection from a malformed claim:* every claim field printed goes through `clean` (`cmd/waggle/claim.go:97`), as other claim output does.

**Not defended (stated in help and docs).** Anyone with push access can delete a claim ref with raw git and leave no audit (D-009, `force.go:272-277`). An agent with the Head Keeper's shell and id can pass `--owner`. In team mode a raw delete leaves the PR failing the gate, a denial of service, not a forged claim (`force.go:274-277`).

## 11. Open questions

- **Q-T072-1: Who may force-release: `gate.approvers[0]` only, every listed approver, or a separate allow-list?**
  Recommended: `gate.approvers[0]` only. It is the gate's existing Head Keeper rule (`docs/gate.md` section 6), it lives in a Tier 3 file as D-009 requires, and it adds no config key. Every approver would let any reviewer delete another Keeper's claim. A separate list adds a `gate:` key that breaks older gates (L10). A team that wants a second force-releaser reorders `gate.approvers` through an admin-bypass merge, which is already logged. This keeps core item 3 whole: any Keeper's stuck claim can be cleared by one named person.

- **Q-T072-2: Should the build add a config key (for example `gate.force_releasers`) so D-009's "allow-list of keeper IDs" is literal?**
  Recommended: no. D-009's Keeper choice is an allow-list in a Tier 3 file matched against `keeper_id`; `gate.approvers` at base is that list, of length one for this purpose. A new key under `gate:` would make every pinned older gate exit 3 (L10). If the Head Keeper wants more than one force-releaser later, it is a new top-level section (ignored by older builds, `internal/config/config.go` top-level rule) in a follow-up, not this ticket.

- **Q-T072-3: Exact match (the comb's `StaticHeadKeepers`) or ASCII case folding (the gate's `isHeadKeeper`)?**
  Recommended: case folding, implemented in `internal/dispatch`, leaving `StaticHeadKeepers` untouched. GitHub logins are case-insensitive and `gate.approvers` is compared folded everywhere else, so exact match would refuse the real Head Keeper over a capital letter. `StaticHeadKeepers` stays for library callers that want exact matching.

- **Q-T072-4: How does the CLI stop a dispatched agent, which inherits the Keeper's `local.yaml`, from force-releasing?**
  Recommended: refuse when the repo root is inside the dispatch worktree directory (`layout.Worktrees`), exit 4, and say the command is for a person at the main clone. There is no worker environment marker today (no `WAGGLE_` variable is set for workers in `internal/dispatch/run.go`), and adding one would change the Cell environment allowlist, which is outside this lease. A TTY requirement was considered and rejected: it breaks the Head Keeper's own scripts and an agent tool can allocate a pseudo-terminal. The refusal is advisory, like the rest (D-009).

- **Q-T072-5: D-038 deferred case-folded overlap checks to "the next Comb ticket", and `docs/multi-keeper.md:99` pairs them with force-release. Does T-072 take them?**

## 1. Goal

G4 makes the gate installable in a repo that is not this one. Today the template's gate step runs only where the base revision holds waggle's own source (`$BASE_SHA:cmd/waggle/gate.go`) and is skipped with a notice everywhere else (T-033), the template ships an `echo` relay job with write permissions, a user has to install the whole hive to get the gate, and nothing tells a user whether the gate is a required check. After this ticket:

1. A composite Action at `gate/action.yml`, pinned by commit SHA, builds and runs `waggle gate verify` in any repo (2.2).
2. The template runs that Action when the base lacks the gate source, pinned to the commit of the build that rendered it, so `waggle.pin` and the Action move together (2.3, 2.4).
3. `waggle init --gate-only` writes the workflow, a small config and `DECISIONS.md`, and nothing else; `waggle upgrade` keeps such a repo gate-only, and a later full `init` says what it needs (2.5, 2.6).
4. The relay stub, the shell tier step and the `waggle dispatch release` alias go (2.7, 2.8).
5. `waggle version` reports a release version stamped at build time, for the release binaries the Head Keeper's workflow builds (2.4, 2.10).
6. Phase B: `waggle doctor` answers the two setup questions: can this clone push claim refs, and is `verify-leases-and-tiers` a required check (with strict up-to-date) on the default branch (2.9).

Product and hive stay apart: everything above is product code. Release signing, tags, the release workflow, repo settings and this hive's own workflow are Head Keeper commits (2.1, 2.10, 2.11).

### 2.2 The Action (`gate/action.yml`), under Q-T036-1 (a)

A composite Action. Inputs, each passed to steps only through `env:`, never as `${{ inputs.* }}` inside `run:`: `base-sha`, default `${{ github.event.pull_request.base.sha }}`; `head-sha`, default `${{ github.event.pull_request.head.sha }}`; `token`, default `${{ github.token }}`.

Steps, each run step with `shell: bash` and `set -euo pipefail`:

1. `actions/setup-go@<setup-go-sha> # v5.x` under Q-T036-5 (a) (`@v5` under (b)) with `go-version:` set to the `go` line of `go.mod` (today `"1.23"`) and `cache: false`. Not `go-version-file`: whether `setup-go` accepts a path outside the workspace is unverified (section 10), and a fixed value with a text test that it equals `go.mod`'s line (AC-A3) avoids the question.
2. **Build from the Action's own tree.** `cd "$GITHUB_ACTION_PATH/.."`, then `go build -o "$RUNNER_TEMP/waggle-gate/waggle" ./cmd/waggle`, with step env `CGO_ENABLED: "0"`, `GOTOOLCHAIN: local` (a `toolchain` line can never fetch another toolchain), `GOPROXY: "off"` (waggle has no module dependencies; if one is added, this fails closed until the Action is changed), `GOFLAGS: -mod=readonly`, `GOWORK: "off"`. The parent of the action path is waggle's tree at the pinned SHA (section 10). Never the workspace, never the PR head. No token in this step's env.
3. **Claim refs.** `git fetch --prune origin '+refs/waggle/claims/*:refs/waggle/claims/*'`. Forced and pruned, so a template step that fetched first, or a claim released and rewritten in between, cannot make this step fail or leave a stale claim. The caller must check out with `fetch-depth: 0`; the gate already exits with "is the clone shallow? use fetch-depth: 0" otherwise (`gate_verify.go:205`).
4. **Gate.** Env `BASE_SHA`, `HEAD_SHA`, `GITHUB_TOKEN` from the inputs; run `"$RUNNER_TEMP/waggle-gate/waggle" gate verify --base "$BASE_SHA" --head "$HEAD_SHA"`. The gate's exit code is the step's; the event file, `GITHUB_REPOSITORY` and `GITHUB_ACTIONS` reach it from the runner as in T-035 2.2.

The Action carries no trigger or permission (Actions cannot); the T-035 hand-off (`pull_request` with `edited`, `pull_request_review: [submitted, dismissed]`, job `if:`, `pull-requests: read`, the concurrency group, the token) lives in the calling workflow, which the template already has. The G5 recipes repeat it for hand-written workflows.

### 2.4 The Action ref and the version

`{{GATE_REF}}` is a new placeholder filled by both `init` and `upgrade` from the same build info `resolvePin` reads:

1. A clean `vcs.revision` (40 hex, `vcs.modified=false`): that commit. This is what a release binary built from a tag checkout (2.10), a `go build` in a clean clone and the hive's own pin builds carry. If `resolvePin` returns a tag for the same build (a Go 1.24 or later toolchain stamps `Main.Version` from a tag; 1.23, which `go.mod` names, does not), the ref is still the revision and the tag appears only in the comment. The commit must be on GitHub (a build from an unpushed commit or a private fork renders a ref that fails at job setup); the recipes say to run `upgrade` from a release binary.
2. No clean revision but `resolvePin` returns a release tag (a `go install ...@vX.Y.Z` module build has no VCS data): the tag, and `init` and `upgrade` write `[warn]   gate Action pinned by tag <tag>, not by commit; replace it with the tag's commit SHA` to `Out` (never stderr), before the plan's last line. `cmd/waggle/upgrade_test.go:75-82` requires an empty stderr and that stdout ends with the last line on a tag-only build.
3. Neither (`unpinned`): a full `init` writes every other file and skips the gate workflow with `[warn]   .github/workflows/waggle-gate.yml not written: this build has no commit or release tag to pin the gate Action to`; `init --gate-only` refuses before any write with the same reason (a gate-only repo without its workflow is no gate); `upgrade` already refuses an unpinned build.

So a repo's Action SHA is its `waggle.pin` revision, both written in one `waggle upgrade` commit. This closes T-035 2.1's version skew for the template path: the gate that reads a repo's config is the build that wrote its schema. Release binaries built with Go 1.23 pin a 40-hex revision, not a tag, so the downgrade rule (`upgrade.go:356`, tags only) does not apply to them; the G5 release notes say so.

`cmd/waggle/main.go`: `const version = "0.1.0-bootstrap"` becomes `var version = "0.1.0-dev"`, set by the release build with `-ldflags "-X main.version=<tag without v>"`; the `version` case calls a small extracted function that prints `waggle v<version>` to a writer, so a test can call it. It feeds only that output, never the pin.

### 2.5 `waggle init --gate-only`, and moving a gate-only repo to a full hive

`InitOptions.GateOnly` (flag `--gate-only`). In a repo without Waggle files it writes exactly three files and nothing else:

- `.github/workflows/waggle-gate.yml` (managed, from the same template, with 2.4's rule; an unpinned build refuses);
- `.waggle/control/config.yaml` (seeded) from `templates/gate-config.yaml.tmpl`: SPDX line, a two-line comment in plain terms (D-236), `version: 1`, `waggle: pin: {{PIN}}` with the same pin comment as today, `forge: provider: github` and `remote: origin` (claims are pushed there and the gate fetches them from it), and `gate: protected_paths: ""` and `approvers: ""` each with a one-line comment. It must parse with `config.Parse`. It carries no `runtimes:` block: the gate never reads one;
- `.waggle/hive/DECISIONS.md` (seeded, never overwritten) from `templates/gate-decisions.md.tmpl`, whose bytes a scaffold test asserts equal to `decisions.Render(nil)`, the header `waggle decide` writes. A template rather than a product import of `internal/decisions` keeps one mechanism for all three files and the import graph D-092 left.

No roles, roster, devcontainer, `WAGGLE.md`, `local.yaml`, runtime shims, `.gitignore` or `CLAUDE.md`/`AGENTS.md` block, and no `tasks/`, `reviews/` or `media/` directories. The gate-only file list is separate from `templateFiles`, so a full `init` and every test that walks `templateFiles` see the same list as today. `--forge` other than `github` is refused before any write (the gate needs GitHub Actions); `--runtime`, `--profile`, `--delivery` and `--comb-mode` are ignored; `--force` rewrites only the workflow; the legacy-layout and symlink checks run over the three paths. `main.go` prints `Initializing Waggle gate (gate-only)...` and a next step naming the three files to commit and `verify-leases-and-tiers` as the check to require. Without `local.yaml`, `waggle claim` needs `--owner` (D-240); the recipes say so.

**`--gate-only` in a repo that already holds a full hive** finds the workflow and config present and skips them (seeded, or managed without `--force`); it creates `.waggle/hive/DECISIONS.md` only when that file is missing (a full `init` never creates it; `waggle decide` does). Nothing else is written.

**A full `init` over a gate-only footprint.** `InitRepo` ends with `config.LoadPolicy` for runtime `claude-code` (`init.go:310-313`), and `ParseRuntimes` fails without a `runtimes:` block (`internal/config/runtimes.go:34-37`); the seeded config is never overwritten (`init.go:266-268`). So before any write, a full `init` with runtime `claude-code` checks the existing seeded config by `topKeys`: when it exists and lacks `runtimes`, `init` refuses with `.waggle/control/config.yaml has no runtimes: block (a gate-only config); add the runtimes: block a full init writes, or rerun with --runtime none` and writes nothing. With `--runtime none` it proceeds: no policy load, the full file set for runtime `none`, the gate-only config and `DECISIONS.md` kept. After that the repo has a roster, so it is no longer a gate-only footprint, and `upgrade` with its default `--runtime claude-code` refuses at step 6 for the same reason (`upgrade.go:528-531`, existing behavior, an `ErrRefused` before any write) until the block is added or `--runtime none` is passed. The upgrade path to shims is therefore: add the block by hand, then `upgrade`. Rejected: shipping a `runtimes:` block in the gate-only config, which puts hive runtime settings in every gate user's Tier 3 file.

### 2.6 `waggle upgrade` and `uninstall` on a gate-only repo, under Q-T036-4 (a)

Today `planUpgrade` creates every managed file a repo lacks, refreshes the marked blocks and regenerates shims, so a gate-only repo would get the whole hive on its first upgrade. A repo where `.waggle/control/roster.json` and `.waggle/control/roles/` are both absent (`os.Lstat`, `fs.ErrNotExist`) is a gate-only footprint: `upgrade` plans the pin line and the gate workflow only, prints one `[note]    gate-only repo: only waggle.pin and the gate workflow are upgraded`, compares top-level config keys against `gate-config.yaml.tmpl` instead of `config.yaml.tmpl`, and skips steps 2 to 6 for every other file: no managed render, stale removal, block, policy load or shim step runs, whatever `--runtime` says (so the default `claude-code` never reaches `resolvePolicy` there). Every precondition stays. Any other repo upgrades as today. `uninstall` on a gate-only repo removes `.waggle/` and the workflow and touches nothing else (AC-A8); a full hive's uninstall output is unchanged (`uninstall_test.go:127, 218`).

### 2.7 Relay stub and shell tier step

Relay mode is cut from v0.1 (repositioning note section 4). The `relay-claim` job only echoes, holds `contents`, `pull-requests` and `issues: write`, and interpolates `${{ github.event.comment.user.login }}` into `run:`. ### 2.9 Phase B: `waggle doctor`, cut to two checks

`waggle doctor [--repo <dir>] [--no-write]`, `runDoctor(args, stdout, stderr, getenv) int`, no `os.Exit`. Loads `config.Load` from `<repo>/.waggle/control/config.yaml`. T-018's nine-finding walk, the `init` hook and its phase B notes N3 to N10 stay open there.

**Claim refs (`probe.go`, every forge with a remote).** `ProbeClaimRefs(ctx, dir, remote string, write bool) Finding`, ID `claim-refs`, required. Git runs through a package variable defaulting to `gitRun` (scrubbed env, no shell), which tests replace. Steps:

1. `git ls-remote --symref <remote> HEAD` for the tip OID, validated with `oidPattern`; failure is `unknown` ("cannot read <remote>").
2. With `write` false: `skipped` ("not tested; run waggle doctor without --no-write"), no further git call.
3. `git cat-file -e <oid>^{commit}`: `git push` needs the object locally, and a clone that has not fetched since the remote moved fails with `bad object` and `!` porcelain lines (verified, section 10). Absent: `unknown`, Not enforced "push access to refs/waggle/* was not tested", Fix "run git fetch <remote>, then waggle doctor"; no push. Doctor never fetches on its own.
4. Doctor prints `Testing pushes to <remote> with two temporary refs under refs/waggle/probe/ (deleted afterwards).` to stdout, then `git push --atomic --porcelain <remote> <oid>:refs/waggle/probe/<16 hex>-a <oid>:refs/waggle/probe/<16 hex>-b` (16 hex from `crypto/rand`; the object is local and already on the remote, so nothing uploads), then `git push --atomic --porcelain <remote> :<a> :<b>`.
5. Outcomes: both succeed, `ok`; "does not support --atomic" in the push error, `missing` (claims push with `--atomic`, `comb/git.go:757`); any other push failure or a `!` porcelain line, `missing` ("this remote does not accept pushes to refs/waggle/*"); delete fails, `missing` with both ref names and the exact command `git push <remote> :<a> :<b>` in Fix (claims are released by deleting refs).

Never `--force` or a `+` refspec, never a retry. No git stderr or remote text is printed; findings carry fixed phrases and the ref names only.

**Required gate (`probe_github.go`, `github.Probe`).** Findings `required-gate` (required) and, by `merge_strategy`: `up_to_date` gives `up-to-date` (required); `native_queue` gives `up-to-date` `skipped` ("Not used: merge_strategy is native_queue") and a `merge-queue` finding, not required, `unknown`, Not enforced "this build does not check the merge queue rule", Fix "check that a merge queue rule is active on <branch>". ## 5. Threat model (D-203)

**Attackers:** (1) the PR author, as in T-035 section 5: they control the PR head, its commits, branch name, body and retargeting, and can add or delete any file in the head, `cmd/waggle/gate.go` and `go.mod` included; (2) for the release chain, someone who can create or move tags or replace release assets in `waggle-sh/waggle` without being the Head Keeper (a leaked collaborator token), or who tampers with a download in transit; (3) for doctor, the remote and GitHub's API answering with hostile text. **Not controlled by them:** the Head Keeper's account, the base revision and its workflow, config and `go.mod`, GitHub's runner, its Action download and the Go toolchain manifest, and the commit SHA a user pinned.

**Must-fix:**
- *Pinning.* The template rendering anything but a 40-hex `GATE_REF` when the build has a clean revision; a branch name ever used as the ref; the Action building or running anything from `$GITHUB_WORKSPACE`, the PR head or the merge commit instead of its own tree; the path choice (`present`) keyed on anything but the base tree; a `uses:` in the Action or template not in the form Q-T036-5 rules.
- *Download and build.* Any binary download in CI under Q-T036-1 (a); a build without `GOTOOLCHAIN=local` or `GOPROXY=off`; a `go-version` that differs from `go.mod`'s line; under (b), a checksum fetched from a mutable location or a mismatch that does not fail.
- *Token.* The token in the Action's build step env, in `with:` of `setup-go`, in argv, in output or interpolated into `run:`; any `write` permission left in the template; `pull_request_target` anywhere; `${{ inputs.* }}` or `${{ github.event.* }}` inside a `run:` block of the Action or template.
- *Footprint.* `init --gate-only` writing or editing anything but its three files (`CLAUDE.md`, `AGENTS.md`, `.gitignore`, shims included), or writing anything from an unpinned build; a full `init` over a gate-only config writing anything before it refuses; `upgrade` on a gate-only repo creating hive files or loading the policy; a full hive's `upgrade` or `init` output changing other than as section 6 lists.
- *Doctor.* A push without the notice line first, with `--no-write`, or without the local object check; a fetch by doctor; `--force`, a `+` refspec or a retry; a probe ref name not from `crypto/rand`; remote stderr, GitHub message text or the token in output; a `missing` or `unknown` finding that renders `ok`; a read failure that turns into `ok`.
- Files changed outside the phase's lease rule.

**Note, not must-fix:** tag moves do not reach a SHA-pinned Action; a user who pins `@vX.Y.Z` by hand, or a module build under 2.4 rule 2, follows a moved tag, which the tag ruleset (2.10) and the recipes address, and a `go install` of a moved tag fails the checksum database check. `SHA256SUMS` shares the release's trust domain (Q-T036-1, Q-T036-6). The Action trusts `actions/setup-go` and GitHub's Go manifest (attacker 2 cannot reach either). Job-level env such as `GOFLAGS` comes from the calling workflow, which is base-trusted except for Q-T036-7's edited-workflow hole, the one real bypass, recorded there. A `GATE_REF` that does not resolve fails every run of the job at setup, base-source path included, which fails closed (2.3, Q-T036-8). A required context with no integration binding can be satisfied by any app or status posting that name, which needs write access; doctor does not check the binding (cut). An install PR fails its own gate and needs an admin merge. The doctor push probe writes to a remote the user names, after the notice line. `dispatch.Release` left unused.

**Guard prompt sentence (repeat verbatim):** "Threat bar (D-203): a finding whose attacker needs the Head Keeper's account, the base revision or its workflow, GitHub's runner, Action download or Go toolchain manifest, or a commit SHA the user pinned is a note, not a must-fix; must-fix is for what a PR author can do through the PR head, branch, body and retargeting, for any path where CI runs code that a SHA pin does not cover or exposes the token beyond the gate step, for any write by init, upgrade or doctor outside what this brief names, and for files outside the phase's lease rule."

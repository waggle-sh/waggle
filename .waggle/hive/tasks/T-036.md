## 1. Goal

G4 makes the gate installable in a repo that is not this one. Today the template's gate step runs only where the base revision holds waggle's own source (`$BASE_SHA:cmd/waggle/gate.go`) and is skipped with a notice everywhere else (T-033), the template ships an `echo` relay job with write permissions, a user has to install the whole hive to get the gate, and nothing tells a user whether the gate is a required check. After this ticket:

1. A composite Action at `gate/action.yml`, pinned by commit SHA, builds and runs `waggle gate verify` in any repo (2.2).
2. The template runs that Action when the base lacks the gate source, pinned to the commit of the build that rendered it, so `waggle.pin` and the Action move together (2.3, 2.4).
3. `waggle init --gate-only` writes the workflow, a small config and `DECISIONS.md`, and nothing else; `waggle upgrade` keeps such a repo gate-only (2.5, 2.6).
4. The relay stub, the shell tier step and the `waggle dispatch release` alias go (2.7, 2.8).
5. `waggle version` reports a release version stamped at build time, for the release binaries the Head Keeper's workflow builds (2.4, 2.10).
6. Phase B: `waggle doctor` answers the two setup questions: can this clone push claim refs, and is `verify-leases-and-tiers` a required check (with strict up-to-date) on the default branch (2.9).

Product and hive stay apart: everything above is product code. Release signing, tags, the release workflow, repo settings and this hive's own workflow are Head Keeper commits (2.1, 2.10, 2.11).

### 2.2 The Action (`gate/action.yml`), under Q-T036-1 (a)

A composite Action. Inputs, each passed to steps only through `env:`, never as `${{ inputs.* }}` inside `run:`:

- `base-sha`, default `${{ github.event.pull_request.base.sha }}`; `head-sha`, default `${{ github.event.pull_request.head.sha }}`; `token`, default `${{ github.token }}`.

Steps, each run step with `shell: bash` and `set -euo pipefail`:

1. `actions/setup-go` (pinned per Q-T036-5) with `go-version-file: ${{ github.action_path }}/../go.mod` and `cache: false`.
2. **Build from the Action's own tree.** `cd "$GITHUB_ACTION_PATH/.."`, then `go build -o "$RUNNER_TEMP/waggle-gate/waggle" ./cmd/waggle`, with step env `CGO_ENABLED: "0"`, `GOTOOLCHAIN: local` (a `toolchain` line can never fetch another toolchain), `GOPROXY: "off"` (waggle has no module dependencies; if one is added, this fails closed until the Action is changed), `GOFLAGS: -mod=readonly`, `GOWORK: "off"`. The runner downloads the whole repository at the pinned ref for a `owner/repo/path@ref` Action, so the parent of `action_path` is waggle's tree at that SHA. Never the workspace, never the PR head. No token in this step's env.
3. **Claim refs.** `git fetch --prune origin '+refs/waggle/claims/*:refs/waggle/claims/*'`. Forced and pruned, so a template step that fetched first, or a claim released and rewritten in between, cannot make this step fail or leave a stale claim. The caller must check out with `fetch-depth: 0`; the gate already exits with "is the clone shallow? use fetch-depth: 0" otherwise.
4. **Gate.** Env `BASE_SHA`, `HEAD_SHA`, `GITHUB_TOKEN` from the inputs; run `"$RUNNER_TEMP/waggle-gate/waggle" gate verify --base "$BASE_SHA" --head "$HEAD_SHA"`. The gate's own exit code is the step's; the event file, `GITHUB_REPOSITORY` and `GITHUB_ACTIONS` reach it from the runner as in T-035 2.2.

The Action carries no trigger or permission (Actions cannot); the T-035 hand-off (`pull_request` with `edited`, `pull_request_review: [submitted, dismissed]`, job `if:`, `pull-requests: read`, the concurrency group, the token) lives in the calling workflow, which the template already has. The G5 recipes repeat it for hand-written workflows.

      - name: Waggle gate (Action)
        if: steps.src.outputs.present == 'false'

Under Q-T036-2 (a) this hive keeps the base-source path (its base always has the gate source); every other repo takes the Action path.

### 2.4 The Action ref and the version

`{{GATE_REF}}` is a new placeholder filled by both `init` and `upgrade` from the same build info `resolvePin` reads:

1. A clean `vcs.revision` (40 hex, `vcs.modified=false`): that commit. This is what a release binary built from a tag checkout, a `go build` in a clean clone and the hive's own pin builds carry. If `resolvePin` returns a tag for the same build (a toolchain that stamps `Main.Version`), the ref is still the revision; the tag appears only in the comment.
2. No clean revision but `resolvePin` returns a release tag (a `go install ...@vX.Y.Z` module build has no VCS data): the tag, and `init` and `upgrade` print `[warn]   gate Action pinned by tag <tag>, not by commit; replace it with the tag's commit SHA`.
3. Neither (`unpinned`): `init` writes every other file and skips the gate workflow with `[warn]   .github/workflows/waggle-gate.yml not written: this build has no commit or release tag to pin the gate Action to`; `upgrade` already refuses an unpinned build.

So a repo's Action SHA is its `waggle.pin` revision, both written in one `waggle upgrade` commit. This closes T-035 2.1's version skew for the template path: the gate that reads a repo's config is the build that wrote its schema. A hand-written workflow pinned to an older Action that meets a newer config key exits 3 (D-239), which fails closed; the G5 recipes say to move both together.

`cmd/waggle/main.go`: `const version = "0.1.0-bootstrap"` becomes `var version = "0.1.0-dev"`, set by the release build with `-ldflags "-X main.version=<tag without v>"`; `waggle version` prints as today (`waggle v<version>`). It feeds only that output, never the pin.

### 2.5 `waggle init --gate-only`

`InitOptions.GateOnly` (flag `--gate-only`). It writes exactly three files and nothing else:

- `.github/workflows/waggle-gate.yml` (managed, from the same template, with 2.4's rule);
- `.waggle/control/config.yaml` (seeded) from the new `templates/gate-config.yaml.tmpl`: SPDX line, a two-line comment in plain terms (D-236), `version: 1`, `waggle: pin: {{PIN}}` with the same pin comment as today, `forge: provider: github` and `remote: origin` (claims are pushed there and the gate fetches them from it), and `gate: protected_paths: ""` and `approvers: ""` each with a one-line comment. It must parse with `config.Parse`;
- `.waggle/hive/DECISIONS.md` (seeded, never overwritten) with the bytes of `decisions.Render(nil)`, the header `waggle decide` writes.

No roles, roster, devcontainer, `WAGGLE.md`, `local.yaml`, runtime shims, `.gitignore` or `CLAUDE.md`/`AGENTS.md` block, and no `tasks/`, `reviews/` or `media/` directories. The gate-only file list is separate from `templateFiles`, so a full `init` and every test that walks `templateFiles` see the same list as today. `--forge` other than `github` is refused before any write (the gate needs GitHub Actions); `--runtime`, `--profile`, `--delivery` and `--comb-mode` are ignored; `--force` rewrites only the workflow; the legacy-layout and symlink checks run over the three paths. In a repo that already holds a full hive, `--gate-only` finds every file present and writes nothing; a full `init` after `--gate-only` adds the rest of the hive. `main.go` prints `Initializing Waggle gate (gate-only)...` and a next step naming the three files to commit and `verify-leases-and-tiers` as the check to require. Without `local.yaml`, `waggle claim` needs `--owner` (D-240); the recipes say so.

### 2.6 `waggle upgrade` and `uninstall` on a gate-only repo, under Q-T036-4 (a)

Today `planUpgrade` creates every managed file a repo lacks, refreshes the marked blocks and regenerates shims, so a gate-only repo would get the whole hive on its first upgrade. A repo where `.waggle/control/roster.json` and `.waggle/control/roles/` are both absent (`os.Lstat`, `fs.ErrNotExist`) is a gate-only footprint: `upgrade` plans the pin line and the gate workflow only, prints one `[note]    gate-only repo: only waggle.pin and the gate workflow are upgraded`, compares top-level config keys against `gate-config.yaml.tmpl` instead of `config.yaml.tmpl`, and plans no block, shim, roster, role or devcontainer change and no stale-file removal. Every precondition stays. Any other repo upgrades as today. `uninstall` on a gate-only repo removes `.waggle/` and the workflow and touches nothing else (AC-A8).

### 2.9 Phase B: `waggle doctor`, cut to two checks

`waggle doctor [--repo <dir>] [--no-write]`, `runDoctor(args, stdout, stderr, getenv) int`, no `os.Exit`. Loads `config.Load` from `<repo>/.waggle/control/config.yaml`. If `forge.remote` is empty it prints `Local-only repo: no forge checks. After adding a remote and setting forge.remote, run waggle doctor.` and exits 0 with no network call. Otherwise it builds the forge through a package variable `newForge = forge.New` (tests replace it), runs `Probe`, prepends the claim-refs finding, renders with `forge.Render`, and exits 0 when every required finding is `ok` or `skipped`, 1 when any is `missing` or `unknown`, 2 on usage, 3 when config, forge construction or the default-branch read fails before a report exists. T-018's nine-finding walk, the `init` hook and its phase B notes N3 to N10 stay open there.

**Claim refs (`probe.go`, every forge with a remote).** `ProbeClaimRefs(ctx, dir, remote string, write bool) Finding`, ID `claim-refs`, required. Git runs through a package variable defaulting to `gitRun` (scrubbed env, no shell), which tests replace. Steps: `git ls-remote --symref <remote> HEAD` for the tip OID (validated with `oidPattern`; failure is `unknown`, "cannot read <remote>"); with `write` false, `skipped` ("not tested; run waggle doctor without --no-write"); otherwise doctor prints `Testing pushes to <remote> with two temporary refs under refs/waggle/probe/ (deleted afterwards).` first, then `git push --atomic --porcelain <remote> <oid>:refs/waggle/probe/<16 hex>-a <oid>:refs/waggle/probe/<16 hex>-b` (16 hex from `crypto/rand`; the OID is already on the remote, so nothing uploads), then `git push --atomic --porcelain <remote> :<a> :<b>`. Outcomes: both succeed, `ok`; "does not support --atomic" in the push error, `missing` (claims push with `--atomic`, `comb/git.go:757`); any other push failure or a `!` porcelain line, `missing` ("this remote does not accept pushes to refs/waggle/*"); delete fails, `missing` with both ref names and the exact command `git push <remote> :<a> :<b>` in Fix (claims are released by deleting refs). Never `--force` or a `+` refspec, never a retry. No git stderr or remote text is printed; findings carry fixed phrases and the ref names only.

**Required gate (`probe_github.go`, `github.Probe`).** Findings `required-gate` (required) and `up-to-date` (required when `merge_strategy` is `up_to_date`; `skipped`, "Not used: merge_strategy is native_queue", otherwise). `Report.Auth` is `g.auth`, `Claims` as `none` reports it. Reads through `g.t` (gh or `GITHUB_TOKEN`, D-061): `GET /repos/{o}/{r}` for `default_branch` (checked with `checkBranch`, then `url.PathEscape`); `GET /repos/{o}/{r}/rules/branches/{b}?per_page=100&page=n`, at most 10 pages (an 11th is a read failure). A `required_status_checks` rule whose `parameters.required_status_checks[].context` equals `GateCheck` (default `verify-leases-and-tiers`, exact match) makes `required-gate` ok, and `up-to-date` ok when any such rule has `strict_required_status_checks_policy: true`, else `missing`. With no matching ruleset rule, the classic fallback reads `GET /repos/{o}/{r}/branches/{b}/protection/required_status_checks`: 200 is evaluated the same way over `contexts` and `checks[].context` with `strict`; 404 whose message is exactly `Branch not protected` or `Required status checks not enabled` is `missing`; any other 403 or 404 is `unknown` ("needs repo admin to read branch protection"). Any other status, a transport error or bad JSON after the default branch was read makes the affected findings `unknown`, never exit 3. Every `missing` or `unknown` carries Not enforced and Fix lines (`Render` refuses otherwise). Status codes may appear in Summary; GitHub message text never does.

### 2.10 Release binaries (Head Keeper; no product code beyond 2.4)

Requirements for `.github/workflows/release.yml`, which the queen drafts in a control PR for a Head Keeper commit after phase A merges: trigger `push: tags: ['v*.*.*']`; workflow permissions `contents: read`, job permissions `contents: write` only; `actions/checkout` at the tag with `persist-credentials: false` and `fetch-depth: 0`; refuse unless the tag is annotated and its commit is an ancestor of `origin/main`; build `linux` and `darwin` on `amd64` and `arm64` with `CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=${TAG#v}" ./cmd/waggle` from the clean checkout (so `vcs.revision` is the tag commit and 2.4 rule 1 applies); archive each with `LICENSE` and `NOTICE`; write `SHA256SUMS` over the archives; create a **draft** release with `gh release create --verify-tag --draft` that the Head Keeper publishes by hand. ## 3. Questions for the Head Keeper (open)

- **Q-T036-1: what runs the gate in CI in a repo without the gate source?** (a) The Action builds `cmd/waggle` from its own tree at the pinned SHA (2.2); no binary is downloaded in CI. (b) The Action downloads the release binary for its version and checks it against the release's `SHA256SUMS` (and, after G5, a GitHub artifact attestation). **Recommended: (a).** A SHA pin then covers everything that runs, through git's content addressing, with no checksum source to trust. Checksums committed in the Action are not an option: the binary embeds the template, the template names the Action SHA, and that SHA would have to name the binary's checksum, which is a hash cycle. Under (b) `SHA256SUMS` sits in the same release as the binary, so it protects against corruption, not against a swapped asset, and the private repo blocks anonymous downloads until G5. Cost of (a): about 30 to 60 seconds of setup and build per gate run against a few seconds for a download. Reversible: the Action's inputs stay the same if its internals later switch to (b).
- **Q-T036-2: what does this hive's own workflow run after the re-render?** (a) The template keeps the base-source build when the base holds `cmd/waggle/gate.go` and runs the Action otherwise (2.3). (b) The Action only; the hive runs the gate at its pin. **Recommended: (a).** It keeps the T-035 pattern where gate changes reach the hive at merge, keeps `upgrade` honest for the hive, and costs about 8 template lines. Cost: the hive never exercises the Action path; 2.11 items 5 and 8 cover that. (b) saves those lines but delays every gate fix here to a pin move. Reversible.
- **Q-T036-3: where does the Action live?** (a) `gate/` in this repo: one tag and one SHA for code and Action (`uses: waggle-sh/waggle/gate@<sha>`). (b) A separate public repo with `action.yml` at its root, which GitHub Marketplace listing requires. **Recommended: (a).** The repo is private until G5, a second repo would split pins and releases, and (b) can be added at G5 as a thin wrapper if discovery needs Marketplace. Cost: no Marketplace listing at launch. Hard to reverse after G5: the `uses:` path is in users' workflows.
- **Q-T036-4: how does `upgrade` know a repo is gate-only?** (a) The footprint: no `roster.json` and no `roles/` (2.6). (b) A config key such as `waggle.footprint: gate`. (c) A marker comment in the seeded config. **Recommended: (a).** No schema change (a key is the D-239 version-skew problem again and needs `internal/config/` in the lease), nothing new to parse. Cost: a hive whose roster and roles were deleted by hand upgrades as gate-only, which only skips files. Reversible.
- **Q-T036-5: how are GitHub-owned actions pinned in the template and the Action?** (a) By full commit SHA with a version comment, for `actions/checkout` and `actions/setup-go`, with the SHAs supplied by the queen in the ruling (the builder has no network). (b) By major tag (`@v4`, `@v5`), as today; only our Action is pinned by SHA. **Recommended: (a).** A security product should pin what it ships; cost is two lookups now and a manual bump at upgrades. (b) trusts GitHub's tags, the same party that runs the runner. Reversible.
- **Q-T036-6: release signing.** (a) `SHA256SUMS` now; GitHub artifact attestations (build provenance, `gh attestation verify`) added to the release workflow at G5, when the repo is public (private-repo attestations need a higher plan). (b) `SHA256SUMS` only. (c) Keyless cosign signatures over `SHA256SUMS` now. **Recommended: (a).** No key to manage, and CI does not depend on it under Q-T036-1 (a). Cost: about 6 YAML lines at G5 (`id-token: write`, `attestations: write`). Reversible.
- **Q-T036-7: a PR that edits the gate workflow runs its own copy** (T-035 section 5 note, carried to G4). A `pull_request` run takes the workflow from the PR, so a PR can make `verify-leases-and-tiers` pass without running the gate; this predates G4 and the gate cannot see it. (a) Record it in G4; the G5 recipes require code-owner review on `.github/workflows/**` (or an organization ruleset that requires the workflow, where the plan has it); a short spike before G5 checks whether the gate can run under `pull_request_target` (workflow from base, no PR code executed) without losing the review trigger. (b) Move the gate to `pull_request_target` inside G4. (c) A note only. **Recommended: (a).** (b) reverses T-035's `pull_request_target` ban and changes how check runs attach to the head, which needs its own threat model; (c) ships a launch with a known bypass and no stated mitigation. Cost of (a): one recipe paragraph and a spike ticket. Reversible.

## 5. Threat model (D-203)

**Attackers:** (1) the PR author, as in T-035 section 5: they control the PR head, its commits, branch name, body and retargeting, and can add or delete any file in the head, `cmd/waggle/gate.go` and `go.mod` included; (2) for the release chain, someone who can create or move tags or replace release assets in `waggle-sh/waggle` without being the Head Keeper (a leaked collaborator token), or who tampers with a download in transit; (3) for doctor, the remote and GitHub's API answering with hostile text. **Not controlled by them:** the Head Keeper's account, the base revision and its workflow, config and `go.mod`, GitHub's runner, its Action download and the Go toolchain manifest, and the commit SHA a user pinned.

**Must-fix:**
- *Pinning.* The template rendering anything but a 40-hex `GATE_REF` when the build has a clean revision; a branch name ever used as the ref; the Action building or running anything from `$GITHUB_WORKSPACE`, the PR head or the merge commit instead of its own tree; the path choice (`present`) keyed on anything but the base tree; a nested `uses:` in the Action or template not pinned as Q-T036-5 rules.
- *Download and build.* Any binary download in CI under Q-T036-1 (a); a build without `GOTOOLCHAIN=local` or `GOPROXY=off`; under (b), a checksum fetched from a mutable location or a mismatch that does not fail.
- *Token.* The token in the Action's build step env, in `with:` of `setup-go`, in argv, in output or interpolated into `run:`; any `write` permission left in the template; `pull_request_target` anywhere; `${{ inputs.* }}` or `${{ github.event.* }}` inside a `run:` block of the Action or template.
- *Footprint.* `init --gate-only` writing or editing anything but its three files (`CLAUDE.md`, `AGENTS.md`, `.gitignore`, shims included); `upgrade` on a gate-only repo creating hive files; a full hive's `upgrade` or `init` output changing other than as section 6 lists.
- *Doctor.* A push without the notice line first or with `--no-write`; `--force`, a `+` refspec or a retry; a probe ref name not from `crypto/rand`; remote stderr, GitHub message text or the token in output; a `missing` or `unknown` finding that renders `ok`; a read failure that turns into `ok`.
- Files changed outside the phase's lease rule.

**Note, not must-fix:** tag moves do not reach a SHA-pinned Action; a user who pins `@vX.Y.Z` by hand, or a module build under 2.4 rule 2, follows a moved tag, which the tag ruleset (2.10) and the recipes address, and a `go install` of a moved tag fails the checksum database check. `SHA256SUMS` shares the release's trust domain (Q-T036-1, Q-T036-6). The Action trusts `actions/setup-go` and GitHub's Go manifest (attacker 2 cannot reach either). Job-level env such as `GOFLAGS` comes from the calling workflow, which is base-trusted except for Q-T036-7's edited-workflow hole, the one real bypass, recorded there. A required context with no integration binding can be satisfied by any app or status posting that name, which needs write access; doctor does not check the binding (cut). An install PR fails its own gate and needs an admin merge. The doctor push probe writes to a remote the user names, after the notice line. `dispatch.Release` left unused.

**Guard prompt sentence (repeat verbatim):** "Threat bar (D-203): a finding whose attacker needs the Head Keeper's account, the base revision or its workflow, GitHub's runner, Action download or Go toolchain manifest, or a commit SHA the user pinned is a note, not a must-fix; must-fix is for what a PR author can do through the PR head, branch, body and retargeting, for any path where CI runs code that a SHA pin does not cover or exposes the token beyond the gate step, for any write by init, upgrade or doctor outside what this brief names, and for files outside the phase's lease rule."

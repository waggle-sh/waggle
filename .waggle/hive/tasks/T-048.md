## 1. Goal

The gate's main claim needs two corrections before G5, and neither has a template fix.

**The check can be forged.** With test workflows on a probe repo, one workflow per victim head, required check set, approvals 0 to isolate the check (`media/T-046/probe-log.md`, T-048 attack rows):

| Attack | Result |
|---|---|
| POST a passing check of the required name, alone | `BLOCKED`: a post alone does not clear the failure |
| DELETE the failing run | Its check run and suite leave the commit; `BLOCKED` on the missing check |
| Delete, then post, from a plain branch's `on: push` workflow | `CLEAN` |
| From another open PR's workflow | `CLEAN`, and the victim **merged with no admin flag** |
| From the PR's own job of the required name | `CLEAN` |
| Delete, then post, on today's `pull_request` shape | `UNSTABLE`, mergeable: **today's template has it** |

**S12** (fine-grained token, Contents write, no Workflows): a new workflow file was refused; a file identical to one on another branch was pushed, and that copy ran with its own write token and posted a passing check. One case; whether a copy must match path and bytes exactly was not tested further.

**An approval alone cannot turn the check green.** E1: with an approval standing and a passing review run on the head, `APPROVED BLOCKED`, because the earlier failing `pull_request` run stays. E2: a re-run of the failed run clears it. Both on test workflows; the real gate was not run, and the docs say so.

**What these do not cover.** Nothing here ran the real gate binary. S2 and S3 did not run and are not needed: D-355 stands without them. Forks did not run; the attack needs a write token, and "The `GITHUB_TOKEN` has read-only permissions in pull requests from forked repositories" ([EV]) points the same way, not run.

## 2. Decisions this brief makes

1. **The review trigger stays.** E1 shows the approval run cannot clear the failure, but the trigger still does one useful thing with no manual step: a dismissal, or a request for changes, runs the gate, and that run fails, adding a failing run that blocks. Removing it would be a template change and would make a dismissal silent. Its costs go in the docs: a comment-only review also fires a run (P3), so each failed run on the head has to be re-run after an approval. The merge state after a dismissal run was not read on E1; it follows from P4a and E1, and the docs do not state it more firmly than that.
2. **Doctor's closing line must change.** `Everything Waggle relies on is enforced on this repo.` (`report.go:107`) is false against section 1: it can print with every finding `ok` while a pushed workflow can forge the check. New text:

   ```
   No setting above is missing. A credential that can push a workflow file can still forge the required check: see the gate spec, L11.
   ```

   Two guards read this sentence. No exit code changes, no new finding, and `Render`'s other branch stays. Adding a required-review finding is out of scope (section 9).
3. **`README.md` Install step 3, `docs/gate.md:104` and `docs/recipes/README.md:15`** say the install PR "needs an admin merge". That holds only once a rule blocks it (T-047 section 2 noted this). Under O2 the install PR still fails its own gate, so only the admin wording changes.

## 1. Goal

A PR must not be able to change the workflow that gates it, and a listed approver's submit or dismiss must re-evaluate the check with no manual step. Today neither holds.

**Today's `gate.approvers` is broken without a manual re-run.** The template runs one job on `pull_request` and `pull_request_review`. A failing same-named run blocks the merge even with a later passing run: on a test workflow, a passing review run left `APPROVED BLOCKED` where the same state with the check not required read `APPROVED UNSTABLE` (E1; also P4, P9). So a PR that needs an approval fails on `pull_request`, and the approval can never turn it green. All of this is from test workflows on `waggle-sh/gate-probe`, not the real gate; the real run is section 10.2.

The design is the E3 row of the probe log: the required check runs under `pull_request_target` and reads reviews live; a `pull_request_review` workflow with a differently named job only signals; a `workflow_run` workflow with `actions: write` finds the protected run by head SHA and re-runs it. On E3, submit and dismiss each re-evaluated the check with no manual step. A re-run replaces a failing result (E2, E3); a posted check did not (P9). Same-repo only.

**Working model, a hypothesis and not a GitHub rule:** for a required name, the latest check run in each check suite must pass. The fact-check found every reading consistent with it; no GitHub page says it. The 10.2 rows confirm or break it.

## 2. What the evidence does not support (for the queen)

1. **A chain failure is not fail closed in general.** It leaves the check as it was. A red check stays red. A **green check after a dismissal stays green**: a passing run, a dismissal, then a chain that does not complete. So the approver path fails open on every chain failure after a dismissal, including the re-run limits GitHub documents (50 re-runs of a run, 30 days from the first run). Section 3.3 adds one step that holds the check red on failure; Q-T048-3.
2. **The "no same-repo spoof" evidence covers two shapes.** P4a and P4b show a passing same-named run beside a failing run does not clear it, and a PR token cannot PATCH the failing run. So (d) is `yes` for create and patch only. These are untested, and each could make T-046 row (d) `no`:
   - **S1, delete or cancel the protected run.** A same-repo PR's workflow can declare `actions: write` (P4b run 3 shows declaring a write scope works under a read default), and GitHub documents that write access can delete a completed run ([DEL]). Cancel should still block under the working model. If deletion removes the failing check, the PR's own passing job is the only check of that name.
   - **S10, a posted pass landing in the protected suite.** An API-created check run does not get its own suite. On `4028254` the posted run sits in `spoof-api`'s suite, and on `2dab4dd` the chain's in `probe-clone`'s: on both heads, the lowest-numbered suite there (read 2026-11-01). The protected run's suite was not the lowest on either, by luck of ordering. If the protected suite is the lowest, the working model says a posted pass is the latest in that suite and **clears the failure**. Two heads; a guess, but P4b run 3 and P9 do not exclude it, and it would also mean P9 failed for a reason nobody tested.
   - **S2, a branch name that stops the protected run.** "To ensure repository security, branches with names that match certain patterns (such as those which look similar to SHAs) may not trigger workflows with the `pull_request_target` event." ([EV]) If the protected run never starts, no failing run exists to block.
   - **S3, a passing spoof while the protected run is in progress.** P4 tested a completed failure only.
   **What each result means.** If the attacking workflow is in the PR being merged, the PR changes `.github/workflows/`, so (d) then rests on the D-276 code-owner rule (D-346), and `docs/gate.md` L11, the recipes and `waggle doctor` must say so (Q-T048-7). **But the code-owner rule does not cover the same attack from a second open PR:** that PR's workflow runs before any review and can act on the first PR's head, and the first carries no workflow change. If S1 or S10 works from a second PR, (d) is `no` against anyone with push rights, whatever the code-owner setting, and today's template is no better. That goes to the Head Keeper before dispatch (Q-T048-1). `[skip ci]` is settled the good way: it "won't stop a workflow that's triggered `on: pull_request_target` from running" ([SK]).
3. **T-046 section 6 needs three corrections.** `gate/action.yml` does not keep its text: its claim fetch needs credentials once the checkout stops storing them (3.6). `branches_test.go:152-155` does not flip: its env has no `GITHUB_EVENT_PATH`, so after the `readPREvent` change it still exits 1 with the same message; it needs a new case with an event file (3.7). The 30 to 60 line estimate is about a fifth of the real size once docs count (section 13).
4. **The install PR gets no gate run** (section 6). That changes T-047 (section 11).
5. **Forks are unproven and partly documented against us.** T-046 row a3 is still `unknown` for forks, so D-346's O1 needs the fork rows. The review run can wait for a maintainer's approval on a first-time contributor's PR, while `pull_request_target` never does (section 5).

**The fetch step.** P7 on a private repo: with `persist-credentials: false`, `git fetch origin refs/pull/1/head` failed for lack of credentials; with the default it printed `pull head fetch: ok` (run 40704121544). A public repo should fetch anonymously, which is not tested. Both are served by a helper that lives only in this step's environment and reads the token from the environment, so nothing reaches `.git/config` or argv:

```yaml
      - name: Fetch the PR head and claim refs
        env:
          GITHUB_TOKEN: ${{ github.token }}
          PR_NUMBER: ${{ github.event.pull_request.number }}
          GIT_CONFIG_COUNT: "1"
          GIT_CONFIG_KEY_0: credential.helper
          GIT_CONFIG_VALUE_0: '!f() { echo username=x-access-token; echo "password=$GITHUB_TOKEN"; }; f'
        run: |
          git fetch origin 'refs/waggle/claims/*:refs/waggle/claims/*' "+refs/pull/$PR_NUMBER/head:refs/waggle-gate/head"
```

The step then checks `git cat-file -e "$HEAD_SHA^{commit}"` beside the existing base check and fails with `head <sha> is not in the clone`. Not run: probe row S8. `refs/pull/<n>/head` serves same-repo and fork PRs alike; `[PL]` says PR commits are available in the base repo; fork not run (section 5).

**C3, non-default bases (Q-T048-4).** Under this event `GITHUB_SHA` is the last commit on the default branch ([CL], P1). Today's `git worktree add ... "$BASE_SHA"` would build a writer-controlled non-default branch's code in a privileged job. Building from `$GITHUB_SHA` is three changed words and closes it. The gate still reads its config from the PR base (`gate_verify.go:258-296`), as today: for a PR into `release`, whoever controls `release` controls that config, and the required rule normally does not cover that branch anyway.

**C7 unchanged:** only GitHub-written fields go into `env:`; `head.ref` stays banned (`guard_template_test.go:68`).

### 3.2 `waggle-gate-review.yml.tmpl` (signal only, the PR can edit its own copy)

```yaml
name: Waggle Gate Review
on:
  pull_request_review:
    types: [submitted, dismissed]
permissions: {}
jobs:
  review-signal:
    if: github.event.review.state != 'commented'
    runs-on: ubuntu-latest
    steps:
      - run: echo "review recorded"
```

The job name must differ from the required check: E3 was run that way, and a same-named job would put a passing check on the head. The `if:` is new against E3: P3 shows a comment-only review fires the run, and on a public repo any account can leave one. Skipping it stops drive-by reviews from spending re-runs. Assumes the workflow's conclusion is then `skipped` (S6); if not, drop the `if:` and the chain's matching clause, and accept the cost.

### 3.3 `waggle-gate-chain.yml.tmpl` (runs only from the default branch, holds the write scope)

```yaml
name: Waggle Gate Chain
on:
  workflow_run:
    workflows: [Waggle Gate Review]
    types: [completed]
permissions: {}
jobs:
  rerun-gate:
    if: github.event.workflow_run.event == 'pull_request_review' && github.event.workflow_run.conclusion != 'skipped'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions:
      actions: write
      checks: write
    concurrency:
      group: waggle-gate-chain-${{ github.event.workflow_run.head_sha }}
      cancel-in-progress: false
    env:
      GH_TOKEN: ${{ github.token }}
      REPO: ${{ github.repository }}
      HEAD_SHA: ${{ github.event.workflow_run.head_sha }}
    steps:
      - name: Re-run the gate at this head
        run: |
          set -euo pipefail
          ids=$(gh api "repos/$REPO/actions/workflows/waggle-gate.yml/runs?head_sha=$HEAD_SHA&event=pull_request_target" --jq '.workflow_runs[].id')
          test -n "$ids"
          for id in $ids; do
            for _ in $(seq 60); do
              test "$(gh api "repos/$REPO/actions/runs/$id" --jq .status)" = completed && break
              sleep 10
            done
            gh api -X POST "repos/$REPO/actions/runs/$id/rerun"
          done
      - name: Hold the check red if that failed
        if: failure() || cancelled()
        run: |
          gh api -X POST "repos/$REPO/check-runs" -f name=verify-leases-and-tiers -f head_sha="$HEAD_SHA" -f status=completed -f conclusion=failure -f 'output[title]=Gate not re-evaluated' -f 'output[summary]=A review changed and the gate could not re-run. Push a new commit.'
```

No checkout, no third-party action, no PR content on disk. Differences from E3, each unproven until S-rows or section 10: it re-runs every run at the head, not `workflow_runs[0]` (section 4 row 4); it waits for a run in progress; it has the concurrency group; it has the hold step. `workflow_run.pull_requests` is not read, so an empty list on forks does not matter. `head_branch`, `display_title` and `head_commit` are author text and never read.

**Why the hold step.** A failing same-named run blocks, by P4. A posted failure should block too: on `2dab4dd`, a posted failure replaced a posted success in one suite (check runs 125065193198 and 125065728736). What clears it depends on its suite (S5, S10): a new head always does, a re-run may. A PR's posted pass may clear it too, which needs a writer and a chain failure at once: note. It makes a chain failure fail closed against everything but that.

**Zero or several runs** (never `.workflow_runs[0]`): zero fails `test -n` and holds red; several are each re-run (section 4 row 4). The `event=pull_request_target` filter drops a PR's own `pull_request` copy of the gate file. AC2 and AC13.

## 4. Races and failures

"Stale green" means a passing check after a dismissal.

| # | Case | What happens | What the user sees and does |
|---|---|---|---|
| 1 | Review while the gate run is in progress | The API refuses a re-run of a run in progress (from the request; not separately run). The chain waits up to 10 minutes, then re-runs. A run in progress holds the check pending. | Nothing; the result arrives late. |
| 2 | Several reviews close together | One chain runs per head and GitHub keeps the newest pending one. The last chain starts after the last review, so its re-run reads every review. A replaced pending chain never started, so the hold step does not fire. Not run: S9. | Nothing. |
| 3 | New push between review and re-run | The chain re-runs the old head's run; that head may no longer be fetchable and it fails with `head ... is not in the clone`. It does not matter: the rule reads the new head, which has its own `synchronize` run. An approval counts only at exactly the head (`gate_approve.go:155`). | Approver approves the new head. |
| 4 | Several runs at one head (`labeled`, `edited`, close and reopen) | E1 shows a failing run from another event blocks. Whether an older failing run of the **same** event blocks is unknown (S4). So the chain re-runs all of them: the safe answer either way, at a few extra minutes. An older run re-runs with its old base. A failure there blocks, which is the strict side. | If S4 shows old failures block: a label alone cannot clear a red check; a review or a re-run does. `docs/recipes/README.md:30` already says re-run, push or review. |
| 5 | 50 re-runs reached, or 30 days past the first run ([LIM], [RR]) | The POST fails, the job fails, the hold step posts red. | Red check titled `Gate not re-evaluated`. Push a new commit, then get a fresh approval. |
| 6 | Chain fails after an approval | Stays red, or the hold step posts red. | Same as row 5. |
| 7 | Chain fails after a dismissal | Without the hold step: **stale green.** With it: red. | Same as row 5. |
| 8 | No run found for the head (PR older than the install; a branch name that stopped the run) | `test -n` fails, hold step posts red. | Push a commit, or close and reopen. |
| 9 | Chain never starts: Actions outage, or the run is cancelled by a writer before its steps | **Stale green remains.** Today's review run has the same exposure. | Note, L13. A person who dismisses and needs certainty checks the Actions tab. |
| 10 | Between dismissal and the re-run starting | **Stale green until the re-run replaces the result: 28 seconds on E3.** Inside it, a ruleset approval count (`REVIEW_REQUIRED`) is the only block, and an adopter who requires no approval has none. Auto-merge can fire in it. Today's review run has a similar window. | Note, L13. |

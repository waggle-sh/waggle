## 1. Goal

A PR must not be able to change the workflow that gates it, and a listed approver's submit or dismiss must re-evaluate the check with no manual step. Today neither holds.

**Today's `gate.approvers` is broken without a manual re-run.** The template runs one job on `pull_request` and `pull_request_review`. A failing same-named run blocks the merge even with a later passing run: on a test workflow, a passing review run left `APPROVED BLOCKED` where the same state with the check not required read `APPROVED UNSTABLE` (E1; also P4, P9). So a PR that needs an approval fails on `pull_request`, and the approval can never turn it green. All of this is from test workflows on `waggle-sh/gate-probe`, not the real gate; the real run is section 10.2.

The design is the E3 row of the probe log: the required check runs under `pull_request_target` and reads reviews live; a `pull_request_review` workflow with a differently named job only signals; a `workflow_run` workflow with `actions: write` finds the protected run by head SHA and re-runs it. On E3, submit and dismiss each re-evaluated the check with no manual step. A re-run replaces a failing result (E2, E3); a posted check did not (P9). Same-repo only.

**Working model, a hypothesis and not a GitHub rule:** for a required name, the latest check run in each check suite must pass. The fact-check found every reading consistent with it; no GitHub page says it. **A finer alternative:** on `f85a2b0`, the default `latest` filter of `check-runs` returns both a job-created failure (125065897409, has an `external_id`) and a posted failure (125066785619, none) in one suite, and hides only the posted success behind the posted failure. So that view groups by suite, name and origin. Which grouping the merge rule uses is unknown; S5, S10 and 10.2 read it.

### 3.2 `waggle-gate-review.yml.tmpl` (signal only, the PR can edit its own copy)

```yaml
name: Waggle Gate Review
on:
  pull_request_review:
    types: [submitted, dismissed]
permissions: {}
jobs:
  review-signal:
    if: github.event.review.state != 'commented'
    runs-on: ubuntu-latest
    steps:
      - run: echo "review recorded"
```

The job name must differ from the required check: E3 was run that way, and a same-named job would put a passing check on the head. The `if:` is new against E3: P3 shows a comment-only review fires the run, and on a public repo any account can leave one. Skipping it stops drive-by reviews from spending re-runs. Assumes the workflow's conclusion is then `skipped` (S6); if not, drop the `if:` and the chain's matching clause, and accept the cost.

### 3.3 `waggle-gate-chain.yml.tmpl` (runs only from the default branch, holds the write scope)

```yaml
name: Waggle Gate Chain
on:
  workflow_run:
    workflows: [Waggle Gate Review]
    types: [completed]
permissions: {}
jobs:
  rerun-gate:
    if: github.event.workflow_run.event == 'pull_request_review' && github.event.workflow_run.conclusion != 'skipped'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions:
      actions: write
      checks: write
    concurrency:
      group: waggle-gate-chain-${{ github.event.workflow_run.head_sha }}
      cancel-in-progress: false
    env:
      GH_TOKEN: ${{ github.token }}
      REPO: ${{ github.repository }}
      HEAD_SHA: ${{ github.event.workflow_run.head_sha }}
    steps:
      - name: Re-run the gate at this head
        run: |
          set -euo pipefail
          ids=$(gh api "repos/$REPO/actions/workflows/waggle-gate.yml/runs?head_sha=$HEAD_SHA&event=pull_request_target" --jq '.workflow_runs[].id')
          test -n "$ids"
          for id in $ids; do
            for _ in $(seq 60); do
              test "$(gh api "repos/$REPO/actions/runs/$id" --jq .status)" = completed && break
              sleep 10
            done
            gh api -X POST "repos/$REPO/actions/runs/$id/rerun"
          done
      - name: Hold the check red if that failed
        if: failure() || cancelled()
        run: |
          gh api -X POST "repos/$REPO/check-runs" -f name=verify-leases-and-tiers -f head_sha="$HEAD_SHA" -f status=completed -f conclusion=failure -f 'output[title]=Gate not re-evaluated' -f 'output[summary]=A review changed and the gate could not re-run. Push a new commit.'
```

No checkout, no third-party action, no PR content on disk. Differences from E3, each unproven until S-rows or section 10: it re-runs every run at the head, not `workflow_runs[0]` (section 4 rows 4 and 14); it waits for a run in progress; it has the concurrency group; it has the hold step. `workflow_run.pull_requests` is not read, so an empty list on forks does not matter. `head_branch`, `display_title` and `head_commit` are author text and never read.

**Why the hold step, and what clears it.** A failing same-named run blocks, by P4. A posted failure should block too: on `2dab4dd` a posted failure replaced a posted success in one suite (125065193198, 125065728736), not yet read as a merge state (S5). **One statement, used everywhere: a new head always clears it; a re-run, a close and reopen, or a posted pass may, depending on the suite it landed in and how GitHub groups runs; S5 answers which, and L13 takes that answer.** In an adopter's repo it usually lands in the gate's own suite. Under the finer grouping of section 1 only a new head clears it, so a chain flake costs a push and a fresh approval.

**Zero or several runs** (never `.workflow_runs[0]`): zero fails `test -n` and holds red; several are each re-run, and `queue: max` keeps those re-runs from cancelling each other (section 4 row 14). The `event=pull_request_target` filter drops a PR's own `pull_request` copy of the gate file. AC2 and AC13.

## 9. Threat model (D-203)

**Attacker:** a same-repo PR author (an agent with push rights to its own branch or to any unprotected branch, the case the gate exists for; the other-PR and plain-branch forms are in scope, fable's ruling), a fork PR author, and a drive-by account reviewing a public PR.

## 1. Goal

Today the gate checks a commit against the claim of whichever ticket the commit names (`classify`, `gate_commits.go:258-308`, then `claimFor`, `:312-334`), and nothing ties that claim to the PR. A PR on any branch can carry `T-040: ` commits and pass for T-040's live lease. After this ticket a claim records the branches its work may arrive on, and a bound commit passes only when its claim names the PR's head branch. Binding sources (D-234, D-237) do not change; this adds a check after binding.

One ticket per PR (the other D-278 example) was not chosen: it stops mixing tickets but not a PR naming a ticket it does not own, which is the gap.

## 2. Design

### 2.1 A claim records branches (`internal/comb/`)

`Lease` (`backend.go:112-121`) gains `Branches []string` with JSON tag `branches,omitempty`, after `Directories`. Under Q-T039-4 (a) `LeaseVersion` stays 2 (`backend.go:88`): `parseLease` decodes with plain `json.Unmarshal` (`git.go:441-461`), so an older binary reads a claim with `branches` as before and ignores the field, and a claim with no field reads as `nil`.

`ValidateBranches(list []string) error` (exported, next to `validateLeaseFields`) refuses with `ErrInvalidLease`: more than 4 entries (`branches: at most 4`); a duplicate entry (exact bytes); an entry over 255 bytes; an entry that is not one of these two forms:

- **Branch:** a short branch name as `git check-ref-format --branch` accepts it, restricted to ASCII bytes 0x21 to 0x7e minus `~ ^ : ? * [ \`; no `..`, `@{` or `//`; not starting with `-`, `/` or `.`; not ending with `/`, `.` or `.lock`; no `/`-separated component that starts with `.` or ends with `.lock` (`a/.b`, `a/b.lock/c`); not `@`; not starting with `refs/`.
- **Fork branch** (under Q-T039-3 (a) only): `<owner>/<repo>:<branch>`, owner matching `^[A-Za-z0-9][A-Za-z0-9-]{0,38}$`, repo matching `^[A-Za-z0-9._-]{1,100}$` and not `.` or `..`, branch as above. A colon cannot appear in a git ref, so the form is unambiguous. Under Q-T039-3 (b), or after the planned cut (section 9), an entry with a colon is refused.

`validateLeaseFields` calls `ValidateBranches(l.Branches)`. Because `decodeLease` re-validates every stored claim with it (`git.go:477`), a stored claim with a bad list is a malformed claim, which the gate already fails (`claimFor`, `gate_commits.go:321-322`). An empty or nil list is valid (Q-T039-1 decides what the gate does with it). Errors name an entry by its 1-based position and the rule it broke, never by its bytes, in any form (no `%q`): for example `branches entry 2: not a valid branch name: comb: invalid lease`. The reason is that a stored claim's validation error becomes the malformed reason (`decodeLease`, `git.go:477-479`; `ReadClaim`, `claim_read.go:37`) and the gate prints it (`gate_commits.go:321-322`), so an entry in the error would be a claim entry in a gate message (2.4, section 5, AC14). `MaxLeaseBytes` (64 KiB, `git.go:347`) holds 4 entries of 255 bytes with room to spare.

### 2.2 Writers record branches (`internal/dispatch/`, `cmd/waggle/claim.go`)

- **`Request.ClaimBranches []string`** (`request.go`, struct only): the branch list a claim records when the caller names one. `Validate` does not read it.
- **`AcquireClaim`** (`claim.go`): `want.Branches` is, in order: `req.ClaimBranches` when it is not empty; else, on a renewal (same keeper, active claim, `:57`) whose stored claim lists branches, the stored list unchanged; else `[]string{req.Branch}`. A dispatch renewal therefore never adds its own branch (section 4; the Hive effect line gives the later-phase workaround). `AcquireClaim` checks expiry before keeper (`:54-57`), so a same-keeper re-claim after expiry is a takeover and resets the list. `Validate` always sets `req.Branch` (default `t-<nnn>`, `request.go:115-117`), so a fresh dispatch claim records the branch dispatch creates and pushes, phase suffix included (`t-036a`; `checkBranch`, `request.go:144-158`, allows it, and its alphabet is a subset of 2.1's). A takeover never inherits the old list. The renewal note (`:59-62`) also compares `Branches` and prints old and new lists after the directories, in the same `%v` shape.
- **The dispatch renewal** (`run.go:409`): the `comb.Lease` literal gains `Branches: claim.Lease.Branches` (`claim` is in scope, `run.go:263`, set at `:358`; it holds the read-back, or `want` when the read-back fails, `claim.go:70-73`), so the keepalive always repeats what was recorded. This is the only change in `run.go`.
- **`ClaimTask`** (`task.go`): `ClaimTaskRequest` gains `Branches []string`; `ClaimTask` refuses a bad list with `failf(ExitUsage, "%w", err)` from `comb.ValidateBranches` (error code `usage`) before `refuseHardcoded`, and passes the list as `ClaimBranches`.
- **`waggle claim --branch <name>`** (`cmd/waggle/claim.go`): repeatable, up to 4; both usage texts gain `[--branch <name>]...`, and the flag's help text says what it is, not the work branch of `waggle dispatch --branch` or the merged-check branch of `waggle release --branch` (`claim.go:231`): `PR branch this claim accepts; repeatable, up to 4`. Given flags replace the stored list. With none, a fresh claim or takeover records `t-<nnn>` (Q-T039-2 (a)) and a renewal keeps the stored list (a TTL extension does not drop `copilot/<slug>`). The claim JSON body (`claimBodyJSON`, `claim.go:38-47`) gains `branches` (always an array, `nonNil`), a field added under schema version 1 (`claim.go:20-22`); the positional literal at `:203` gains the value. Text output is unchanged apart from the note.

**Copilot cloud agent (D-279).** Copilot picks its branch (`copilot/<slug>`, `tasks/T-037.md` row G3) after the task starts. The human or orchestrator who assigned the task renews the claim with `--branch copilot/<slug>` (and `--branch t-<nnn>` if it also works there) once the PR opens. Until then the gate fails the PR with the 2.4 message, which fails closed. A claim write does not trigger the gate workflow, so after the renewal the failed check must be re-run, or the next push or review must arrive (Copilot pushes already wait for "Approve and run workflows", T-037 row G2). A re-claim after the claim expired is a takeover and drops `copilot/<slug>`, so the recipe repeats every `--branch` on any re-claim after expiry. The T-037 recipe and the D-235 demo card state this; this ticket changes no docs.

### 2.3 The gate knows the PR head (`cmd/waggle/gate_approve.go`, `gate_verify.go`)

- **`readPREvent`** also reads `pull_request.head.repo.full_name` (a null `head.repo` reads as `""`) and `pull_request.base.repo.full_name`; `prEvent` gains `headRepo` and `baseRepo`. Both `pull_request` and `pull_request_review` payloads carry these (fable brief guard N1). Missing fields do not make the event malformed (the approver path must keep working on today's payloads). The event names it accepts do not change.
- **Head identity**, resolved once in `runGateRange` and carried in `scanInput` as one new field (so the approver rescan, which reuses `p.in`, `gate_approve.go:219-221`, sees the same head):
  - `name` is today's branch name (`--branch`, else `GITHUB_HEAD_REF` under Actions, else the event's head ref; `gate_verify.go:133-139`), kept raw.
  - `sameRepo` is true in exactly these cases: an event was read and its `headRepo` and `baseRepo` are both non-empty and equal under ASCII case folding; or no event was read and either the run is outside Actions or the name came from `--branch`. In every other case the head is a fork. So under Actions a `GITHUB_HEAD_REF` with no read event (`pull_request_target`, which D-276 plans a spike for, an unreadable event file, any future trigger) is a fork, and an event that says fork is a fork whatever the name source.
  - `known` is `name != ""`.
- A name that `branchTicket` ignores (over 255 bytes or a control byte) is still known: it binds nothing, as today, matches no claim entry and never takes the 2.4 fallback, so a bound commit fails. It is never echoed.

### 2.4 `claimFor` checks the head (`cmd/waggle/gate_commits.go`)

After a claim reads and decodes (the `default:` case, `:325-331`), and once per ticket (the `s.claims` cache, `:313`), a new unexported function decides:

1. **Head unknown** (`name == ""`). Outside Actions: no check; the first such claim in a run adds one warning `no pull request branch; claim branches not checked (pass --branch)` under `leases` (`gateReport.warn` does not dedupe, `gate_verify.go:60-62`, hence the `commitScan` flag). Under Actions: one failure `<id>: pull request branch unknown`. Under the template a PR author cannot reach this case (the runner sets `GITHUB_HEAD_REF` on `pull_request`; on `pull_request_review` the name comes from the event GitHub writes), so it fires only on a GitHub fault or a gate run outside a PR event (`push`, `merge_group`, `workflow_dispatch`), and fails closed there.
2. **Claim lists branches:** a same-repo head passes when `name` equals a plain entry byte for byte. A fork head passes, under Q-T039-3 (a), only when an entry `<owner>/<repo>:<branch>` has `<owner>/<repo>` equal to `headRepo` under ASCII case folding (an empty `headRepo` matches nothing) and `<branch>` equal to `name`; under (b) never. Otherwise one failure: `<id>: claim does not name this pull request's branch`.
3. **Claim lists no branch** (written before this ticket, or stripped by an older binary's renewal): per Q-T039-1. (a) one failure `<id>: claim names no branch; renew it with waggle claim --branch`. (b) a same-repo head whose name `branchTicket` does not ignore, and that is exactly `t-<d>` or `waggle/T-<d>`, or either followed by a non-digit and anything, where `<d>` is the digit string of the canonical `<id>` (`040` for T-040, so `t-0040` and `t-40` fail), passes with one warning `claim for <id> names no branch; accepted on ticket branch name`; a fork head or any other name gets the (a) failure. These are D-237's names plus dispatch's suffixes without a dash (`t-036a`). (c) one warning, as (b)'s, and it passes for any head.

The failure is filed under `leases` with no path, outside the path loop (`gate_commits.go:220-233`), so the approver filter (`s.filter`, `:223`) never drops it and no approval clears it. The claim still applies its path rules (`cl.ok` stays true), so the report stays complete. Messages carry only the canonical ticket ID: never the head name, the repo names or a claim entry. Base merges reuse their first parent's ticket and its cached result. `classify` does not change.

### 2.5 What remains for the T-037 docs (L1 restated from the merged code)

- Anyone who can push to a branch a claim names can add commits under that claim (same-repo branches are writable by every repo writer unless protected).
- Whoever writes the claim chooses its branch list; an agent that can run `waggle claim` can name its own branch (L3, unchanged).
- Under Q-T039-1 (b), until the sunset: a claim with no list accepts its ticket's same-repo branch names. That covers claims written before the upgrade and claims an older binary renewed (Q-T039-4 (a) strips the list), and the gate accepts expired claims with a warning (`gate_commits.go:327-330`), so such a claim stays in fallback until it is renewed by a new binary or released.
- A re-claim after expiry is a takeover and resets the list to `t-<nnn>`: repeat every `--branch` (2.2). A dispatch renewal keeps the stored list and never adds its own branch.
- A local run without `--branch` skips the check with a warning; a gate run under Actions outside a PR event fails every bound commit.
- Claims can name only ASCII branch names (2.1); a PR from a branch outside that set cannot pass for a claimed ticket.
- After a claim's list changes, the check must be re-run (2.2).

## 3. Questions for the Head Keeper (open)

- **Q-T039-1: what does the gate do with a claim that names no branch?** (a) Fail closed with a renew hint. (b) Fall back to the ticket's own branch names (D-237's `waggle/T-<id>` and `t-<id>`, plus dispatch's `t-<id><suffix>` without a dash, canonical digits only), same-repo heads only, with a warning; any other head fails; with a sunset: a follow-up flips the function to (a) after the hive's pin move and the renewal of every live hive claim, and before the G5 flip. (c) Warn only. Recommended: (b) with the sunset. Every claim on every repo today has no list, and the hive's claims keep having none until the pin moves; (b) keeps those PRs passing on the branches dispatch and D-237 already tie to the ticket, while a feature branch or fork carrying another ticket's commits fails. Stated plainly: (b) protects only the transition. Under Q-T039-4 (a) any older binary's renewal, the pinned hive keepalive included, puts a claim back into fallback, so until the sunset a same-repo branch named for a ticket can carry commits under that ticket's claim whether or not the claim's holder works there. At G5 no outside user has pre-upgrade claims, so (a) costs them nothing by then, which is why the sunset falls before the flip. (a) now is strictest and costs a renewal of every live claim at upgrade and a pin move before the next hive dispatch; (c) leaves the gap open for every claim without a list. Reversible: the flip is one branch of the function.
- **Q-T039-2: is `--branch` optional or required on `waggle claim`?** (a) Optional; with none a fresh claim records `t-<nnn>`, the branch dispatch would use, and a renewal keeps the stored list. (b) Required. Recommended: (a). It matches dispatch, keeps existing `waggle claim` calls and tests working, and a wrong default fails closed at the gate with a message that names the fix. Cost: a human who works on `feature/x` learns about `--branch` from the gate failure. (b) breaks every `waggle claim` call in `claim_test.go` and in T-037's draft recipes. Reversible.
- **Q-T039-3: can a fork PR match a claim?** (a) Only through entries of the form `<owner>/<repo>:<branch>`, matched against the event's `head.repo.full_name`. (b) Never; bound commits from forks always fail leases. Recommended: (a). Public repos take outside PRs from forks, and the claim writer (never the PR author, L3) can name the fork branch; about 28 doubled lines. Cost: the event's repo fields become trusted inputs (GitHub writes them). A fork named for a ticket branch never matches a plain entry under either answer. (b) is the planned cut (section 9). Reversible.
- **Q-T039-4: does the field ship at lease version 2 or 3?** (a) Optional `branches` at version 2. (b) Version 3. Recommended: (a). Older binaries read new claims unchanged (`parseLease` ignores unknown fields), so the pinned hive dispatch and any installed CLI keep working. Cost: an older binary that renews a claim drops the list without saying so (2.5). (b) makes every older binary treat new claims as malformed (`git.go:457-458`), which breaks the hive's pinned dispatch the moment a new binary writes one, and adds `git.go` to the lease. Hard to reverse after G5.

## 5. Threat model (D-203)

**Attacker.** The PR author (agent or person): it controls commits, subjects, trailers, the branch name (any valid ref, up to git's limits), the PR body and, for a fork, the fork's name and branch. It cannot write claim refs, the base revision, the base config, the workflow (including which trigger runs the gate), or the event file and runner variables GitHub writes.

**Trusted.** Claim refs and whoever writes them (L3), the base revision and its config, the workflow, GitHub's event payload and `GITHUB_HEAD_REF`, the Head Keeper.

**Must-fix:** a bound commit that passes the gate while its claim lists branches and none matches the PR head; a fork head that matches a plain entry, or any entry under Q-T039-3 (b); a fork head that takes the Q-T039-1 (b) fallback; a head treated as same-repo under Actions without a read event whose repo names match, other than a `--branch` name with no event; a head the fallback accepts for a ticket other than the claim's, by substring (`xt-040`), with non-canonical digits (`t-0040`) or when `branchTicket` ignores it; a match that folds case on the branch part; an empty head under Actions that passes, or an ignored name that skips the check; the failure dropped by the approver filter or cleared by an approval; the head name, a repo name or a claim entry echoed in a gate message; a claim write path (`AcquireClaim`, the `run.go:409` renewal, `ClaimTask`) that drops or alters the list it was asked to record or keeps, or a takeover that inherits the old list; a stored claim with an invalid list read as valid; more than 4 entries, a duplicate, or an entry over 255 bytes accepted; any change to `classify`'s results or messages; any `LeaseVersion` change under Q-T039-4 (a); an older-format claim (no field) read differently by the comb; a test that sends a signal, sets a session `Timeout` or cancels a running session (D-193); files changed outside the lease rule; any em or en dash added.

**Note, not must-fix:** anything that needs a claim ref written (L3), including a claim that lists the attacker's branch; a repo writer pushing commits onto a branch a claim names (2.5); an older binary dropping the list on renewal, and the fallback that follows under Q-T039-1 (b) until the sunset; a gate run outside a PR event failing every bound commit; a GitHub fault that empties the head (fails closed).

**Guard prompt sentence (repeat verbatim):** "Threat bar (D-203): a finding whose attacker needs to write claim refs, the base revision, the base config, the workflow or GitHub's event payload is a note, not a must-fix; must-fix is for any way a PR author, through commits, subjects, trailers, the branch name, the PR body or a fork, gets a bound commit past a claim that does not name the PR's head branch, and for any claim writer that loses the branch list."

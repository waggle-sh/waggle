## 1. Goal

The head tree collision check (`caseCollisions`) keys every path from `git ls-tree -r` by `collisionKey` and compares whole paths. It never compares a path with a directory. A file `Docs` and a file `docs/a` are two distinct keys (`docs` and `docs/a`), so the check passes, yet on a case-insensitive checkout the file `Docs` and the directory `docs` cannot both exist: the checkout fails or drops one. The same holds for a file `café` (NFC) against a directory `café/` (NFD) on APFS. T-014b review F6 accepted the gap for case; T-074 Q-T074-3 (D-395) kept whole paths only and opened this ticket to close it for case and normalization together.

## 2. Scope

1. **Directory index.** Built once from the head tree, from every path `ls-tree` returned, before any path is judged (section 4).
2. **Directory test.** For each path (file, symlink or gitlink: every `ls-tree -r` entry), after the existing file against file test, look the path's folded name up in the directory index. A hit is a finding (section 3).
3. **Finding text.** A directory finding names the file and the directory (section 3); the existing file against file text is unchanged.
4. **Docs.** `docs/gate.md` section 4, once T-107 has merged (Q-T123-3).

## 3. The exact rule

**Fold.** One name is `collisionKey` of one path component, the same key the file against file check uses (decomposition of Latin-1 Supplement, Latin Extended-A and Hangul, lower casing, single rune equivalents; `gate_fold.go`). The key never produces or removes `/`, so folding a component equals slicing the fold of the whole path.

**What fails.** A tree entry `F` (a file, symlink or gitlink) fails when some proper prefix `D` of another tree entry, cut at a `/`, has `collisionKey(D) == collisionKey(F)`, comparing whole prefixes from the root, not single components. `F` is `docs` or `a/Docs`, `D` is `docs` or `a/docs` (the directory of `docs/x` or `a/docs/x`). A byte-equal `F` and `D` also fail: there is no `prev != p` exemption, because a tree that holds a file and a directory of one byte name cannot be checked out anywhere (git writes such a tree only through a hand-built object).

**Whole head tree.** The rule judges every entry of the head tree, as the file against file check does, not only paths the PR adds or renames. A repo that already holds a file and a directory with one folded name (valid on Linux) therefore fails every PR after the pin moves, including a PR that does not touch either path, until one of them is renamed. Main holds no such pair (section 5). Q-T123-4 asks whether to limit the rule to pairs the PR touches.

**Which path the finding names.** The file `F`, always, in `checkTiers`. Never the directory and never a child of it. A directory is not a tree entry, so it has no path of its own in the report, and naming the file makes the result independent of tree order and of which side an author added in the PR. One finding per path, decided by `ls-tree` order. Pass 2 runs the file against file test first and, on a hit, reports it and does `continue`: no directory finding is added for that path. A directory finding does not `continue`: pass 2 still runs `seen[k] = p` after it. So of two file twins of one folded name that also match a directory, the first in `ls-tree` order gets the directory finding (it has no earlier twin) and the later one gets the file against file finding naming the first (it has an earlier twin), and a path never gets two findings.

**Which directory the text names.** The first directory spelling `ls-tree -r` returned for that folded name, spelled as a prefix of the first path that created it (`Docs` for `Docs/a`, not the child). `ls-tree` order is by bytes and fixed by the tree, so the choice is the same whatever order the index was written in.

**Text.**

- Pure case difference (`strings.ToLower(D) == strings.ToLower(F)`): `path collides with directory <D> on case-insensitive checkouts`.
- Any other pair, including normalization alone and case with normalization together: `path collides with directory <D> on checkouts that treat Unicode normalization forms as one name`.

The word `directory` marks the new case, so the two existing file against file texts stay byte for byte (`TestVerifyASCIIText`, `TestVerifyCaseCollision`).

**Not reported.**

- Two directories with one folded name (`Docs/a` and `docs/b`). A checkout merges them into one directory and loses nothing; if the files inside also fold alike, the file against file check already fails them (Q-T123-2).
- A directory against a file when neither is in the head tree (the base tree is not read; the check runs on the head tree only).
- A file whose name equals a directory only under compatibility forms (NFKC) or outside the table; the limits of `collisionKey` carry over (docs section 4).

## 4. How the folded directory index is built from the head tree

Input: the paths `caseCollisions` already holds from `ls-tree -r -z --name-only --full-tree <head>`, in `ls-tree` order. Paths over `maxTreePath` (4096) are skipped by the index, as the existing loop skips them for the file test (`len(p) > maxTreePath`, which fails them first), so no index work sees more than 4096 bytes per path.

**Signatures (builder and guard test these and nothing else).** In `gate_fold.go`:

- `type dirIndex struct{ ... }`: the trie; fields are the builder's choice.
- `func buildDirIndex(paths []string) *dirIndex`: pass 1; skips empty paths and paths over `maxTreePath`.
- `func (x *dirIndex) dirOf(p string) (dir string, ok bool)`: pass 2 lookup; `ok` is true when the folded name of the whole path `p` is a directory node, and `dir` is the spelled prefix `firstPath[:end]` of that node.
- `func (x *dirIndex) dirCount() int`: the number of directory nodes, one per distinct folded directory.
- `func dirCollisionText(dir, p string) string`: the finding text of section 3, choosing the case or normalization sentence.

`caseCollisions` keeps its signature and calls `buildDirIndex` once, then `dirOf` per path.

Pass 1 (index). For each path, split at `/`. For each proper prefix, in order from the root, compute the fold of that component only and descend a trie keyed by `(parent node id, folded component)`:

- a node that exists is reused; a new node records one entry `{firstPath, end}`: the path that created it and the byte offset where the prefix ends, so the spelled directory is `firstPath[:end]`, a substring that costs no new memory;
- each path costs one descent, one component at a time, so total work is linear in the bytes of the tree, not quadratic in depth.

The trie, not a map of prefix strings, is deliberate: a map of whole folded prefixes costs up to depth times length per path (a 2048 deep, 4096 byte path stores about 4 MB), and a hostile PR chooses the paths. The trie stores one folded component per new directory, so memory is linear in the path bytes.

Pass 2 (judge). Existing loop, in `ls-tree` order: over-length path fails as today; file against file test as today (`continue` after a finding); then the directory test: descend the trie by the path's own folded components for the whole path, and test whether the node reached at the last component exists as a directory node. A hit names `firstPath[:end]` of that node. A directory hit reports the finding and does not `continue`; `seen[k] = p` runs after it, as for a path with no finding. Only a file against file hit or an over-length path skips `seen`.

The two passes are why the result does not depend on whether the file or the directory comes first in `ls-tree` order. A tree with no directory node under any file's folded name does pass 2 with one trie descent per path and one map lookup, the same order of cost as today.

An ASCII only component keeps the ASCII fast path in `collisionKey`; the split uses `strings.IndexByte`.

## 7. Threat model (D-203)

**Boundary.** The head tree is attacker influenced input: a PR author chooses every path name. The gate runs on the Action's own pinned tree (`gate/action.yml`), so the PR cannot change the rule it is checked by.

**Defended.**

- *A PR adds a file whose folded name is a directory so a macOS checkout fails or drops one of them* (`Docs` against `docs/a`, NFC against NFD): the file fails `tiers`.
- *A PR adds the directory over an existing file, or the file over an existing directory:* same, in either order, because the index is built before any path is judged.
- *A deep or wide tree to exhaust memory or time:* paths over 4096 bytes fail before the index sees them; the trie stores one folded component per new directory and each path walks it once, so memory and time are linear in the tree's bytes, and there is no quadratic step. A unit test builds a 2000 deep path and 5000 siblings and finishes inside the test timeout (D11).
- *Hostile bytes (newline, `::warning::`, invalid UTF-8, a lone combining mark) in a path:* `collisionKey` never panics (T-074); the finding text goes through the existing encoder, so a directory name in the text is encoded like the file name.
- *An author who tries to hide one name behind another spelling:* the check folds the same way as the file test, so it holds exactly as far as `collisionKey` holds; no weaker.

**Not defended (stated in docs).** Pairs outside the table, mark reordering, compatibility forms, a directory against a directory, and a merge that skips the gate (L2 in `docs/gate.md`).

**False positives.** A file and a directory fold to one name only when `collisionKey` says they are one name, the same standard the file test uses; a directory against a longer name (`docs` against `docs2/a`, `doc` against `docs/a`) never matches, because the whole prefix is compared. No test or doc relies on a file and directory pair that main holds.

## 11. Open questions

- **Q-T123-1: Which path does a file against directory finding name?**
  Options: (a) the file (or symlink or gitlink) always, with the directory in the text. (b) the entry that comes later in `ls-tree` order, as the file against file check does. (c) the directory, as a prefix path with no child.
  Recommended: (a). A directory is not a tree entry, so (c) names something the report cannot point at, and (b) names a child of the directory in one order and the file in the other, so which path fails would depend on spelling and sort order. (a) gives one stable path to rename and does not depend on which side the PR added.

- **Q-T123-2: Does a directory against a directory with one folded name fail?**
  Options: (a) no: `Docs/a` and `docs/b` pass; the file against file check already catches a clash of files inside them. (b) yes: fail the second directory spelling, naming the first path under it.
  Recommended: (a). A case or normalization insensitive checkout merges the two directories and loses no file, so there is no data loss to prevent, and (b) would fail brownfield trees that git on Linux holds legitimately. (b) is right only if the Head Keeper wants the gate to enforce one spelling per directory.

- **Q-T123-3: Does the `docs/gate.md` section 4 change ride in T-123's build?**
  Options: (a) yes, once T-107 merges: the queen holds the build claim for `docs/gate.md` until T-107 releases it, and one PR carries the code and the docs. (b) no: the build ships the code now and `t-123b` carries the docs after T-107 merges. (c) fold the docs change into T-107's PR as a follow-up commit.
  Recommended: (a). A merge rule and its doc line belong in one PR, and T-107 is already open. (b) is the fallback if T-107 stalls and the Head Keeper wants the rule sooner; (c) widens a Tier 3 PR that is already under review, so it is not recommended.

- **Q-T123-4: Does the rule fail every file and directory pair in the head tree, or only pairs the PR touches?**
  Options: (a) every pair in the head tree, as the file against file check does today: simple, order independent, no base tree read; a repo that already holds such a pair blocks every PR until the pair is renamed. (b) only pairs where at least one of the two paths is added or renamed in the PR: needs the base tree (`ls-tree` of the base, a second read and a diff), so the check no longer reads the head tree alone and the T-074 limit "the base tree is not read" goes; an existing pair stays green until someone touches it. (c) (a), plus a one release grace in which a pair already in the base tree is a warning, not a failure: most code, same base tree read.
  Recommended: (a). Main holds no such pair (section 5), the gate is a pin move away from every repo that adopts it, and a macOS checkout of an existing pair is already broken, so failing it is the point. (b) and (c) add a base tree read and a second code path to a merge rule for a case the repo family does not have. Revisit if a real adopter reports a blocked repo.

- **Scout defaults for the Head Keeper to confirm.** These rules are decided in section 3 without a question of their own. Each is the scout's default; none is ruled.
  1. A byte-equal file and directory pair fails, with no `prev != p` exemption (git writes it only through a hand-built object, and no checkout can hold it).
  2. A symlink (`120000`) and a gitlink (`160000`) count as files, as every `ls-tree -r` entry does.
  3. One finding per path: of file twins that also match a directory, the first in `ls-tree` order gets the directory finding and a later one gets the file against file finding, with no directory finding (a directory finding does not skip `seen[k] = p`).
  Confirm or change each; a change to 1 or 3 alters section 3, section 4 pass 2 and tests D6 and D9.

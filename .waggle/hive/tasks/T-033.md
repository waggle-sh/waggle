## 1. Goal

Three small product fixes the T-032 cycle surfaced, each of which costs the queen a manual step or a wrong count today:

### 2.2 Item 2: which line is a round's verdict (Q-T033-2, ruled (a), D-248)

How review files grow: dispatch writes the guard's final message, unchanged, to `<run>/review.md` (`run.go`); the queen commits that file unchanged as `reviews/T-<nnn><suffix>-<model>.md` and appends a later round by the same model to the end of the same file after one blank line (queen item 3). So a round has no delimiter git or dispatch can see: a round contains blank lines, headings and quoted text of its own, and the queen's blank line looks like any paragraph break. A rule such as "the first `Verdict:` line after a blank line" therefore still counts quoted lines. The fix is a delimiter that only dispatch writes.

- **Round marker.** When a guard run records a verdict (`res.Verdict` is `pass` or `must-fix`), dispatch writes `review.md` as one marker line, one blank line, then the final message: `<!-- waggle-review v1 verdict=<pass|must-fix> head=<head OID> -->`. `<head OID>` is the head under review that `guardTarget` resolved (`req.Head`, the value later recorded as `head_oid`), lowercase hex, 40 or 64 characters. Defensive: when `req.Head` is not 40 or 64 lowercase hex, the writer skips the marker (the review is then written as on a `no_verdict` run). The marker is an HTML comment, so a rendered review hides it, and the queen's "commit unchanged" habit carries it into the hive file at the start of each round. When no verdict was parsed (`no_verdict`, a cut final), `review.md` is the final message with no marker (escaped as below); the queen does not commit those.
- **Escaping.** On every `review.md` write, with or without a marker (`no_verdict` included), any line of the final message that starts, at column 0, with `<!-- waggle-review` is written to `review.md` with one leading space, so a guard that quotes the marker (for example when reviewing this ticket) cannot add a round. `final.md` stays byte for byte the guard's message. Nothing else in the message is changed.
- **Counting** (a new unexported function in `guard.go`, next to `verdictLine` and the marker writer, so writer and reader share one format). For one review file: split it at marker lines. A marker line is a line that, after trailing spaces and `\r` are trimmed, matches `^<!-- waggle-review v1 verdict=(pass|must-fix) head=([0-9a-f]{40}|[0-9a-f]{64}) -->$` exactly. The text before the first marker (all of a file that has none) is legacy and counts by today's rule (`runtime.CountMustFix`, unchanged). After the first marker, only marker lines count: each `verdict=must-fix` marker is one must-fix; `Verdict:` lines after the first marker count for nothing. `ReadInputs` (for `reviews/T-<nnn>.md`) and `roundMustFix` (for each phase file) call this function instead of `runtime.CountMustFix`. Caps (`maxReviews`, `maxBrief`) and file selection do not change.
- **Why legacy keeps today's rule.** Every existing review file has no marker, so its count is unchanged, `TestInputsReview`, `TestResultMustFix`, `TestMustFixCountPerPhase` and `TestCountMustFix` pass unchanged, and no existing assertion moves. The double count in old files stays, but those phases are closed; a phase whose rounds start after the pin move counts only markers. A file that mixes one legacy round and later marker rounds counts both parts by their own rules.
- **Hive effect.** Markers appear only in runs made by a binary past this merge, so in this hive only after the next pin move. Until then the count is today's.
- **Known limits (accepted).** Reviews a subagent writes and the queen commits outside `waggle dispatch` (brief reviews such as `T-033-brief-opus.md`) carry no marker, so they keep legacy counting, top-and-bottom double counts included. A marker-less round appended after a marker round counts 0, since after the first marker only markers count. Brief-review files named with the `T-033-` prefix match `roundMustFix`'s phase prefix, so their must-fix lines count toward the build's step-up; this is pre-existing and not changed here.

## 5. Threat model (D-203)

Attacker: a dispatched builder or guard working inside its lease, and a PR author on a repo that installed the template. The builder controls its commits; the guard controls its final message; the PR author controls the head tree, commits and branch. None can write to the base branch, change hive review files on base directly, or edit `review.md` after dispatch writes it (the queen commits it unchanged; she is trusted). The workflow is a separate case: on `pull_request` GitHub runs the workflow file from the merge commit, so a PR that edits `.github/workflows/` runs its own copy. Its integrity rests on branch protection and the Head Keeper's review of `.github/` changes (hardcoded Tier 3), not on anything this ticket ships; G4's pinned Action is the real fix. A finding that needs a PR to rewrite the workflow file is a note here.

Must-fix: any template, roster text or guard task line that still tells a guard to write a file in the repo; a change to the `Rules:` line that drops or rewords the `do not commit` clause or the last-line verdict clause; a final-message line that becomes a counted marker in `review.md` (the escaping missing, partial or applied after column 0); a marker counted that is not at column 0 or does not match the 2.2 pattern exactly; a `Verdict:` line after the first marker counted; a count for a file with no marker that differs from `runtime.CountMustFix`; `final.md` changed; a marker written when no verdict was parsed; any read past today's caps; in the workflow template: any permission above `contents: read` at workflow level or on the verify job, `pull_request_target`, a build or a presence check that reads the PR head instead of `BASE_SHA`, `|| true` (or any other swallowed exit) on the claim fetch or the gate step, a `gate decisions` step, or a template line 2 other than the managed marker; a file changed outside the lease rule.

Note, not must-fix: the guard can still under-report by omitting its last-line verdict (dispatch records `no_verdict`, as today); the queen can edit a review before committing it (trusted); legacy review files keep their double count; in a repo without waggle's source the template's gate step is skipped with a notice until G4 (no weaker than today's template); the relay stub keeps write permissions until G4 removes it; setup-go reads `go.mod` from the merge commit (2.3 step 6); a PR that edits the workflow file runs its own copy (above).

Guard prompt sentence (repeat verbatim): "Threat bar (D-203): a finding whose attacker needs to push to the base branch, edit the gate workflow file in a PR (the Head Keeper reviews .github/ changes), change committed review files, or edit review.md after dispatch writes it is a note, not a must-fix; must-fix is for what a builder through its commits, a guard through its final message, or a PR author through the head tree can trigger. Write no file in the repo: your review is your final message."

D-193: nothing in this ticket sends a signal, calls `sweep()`, reaps a process or deletes files. The `run.go` edit is the `review.md` write after the session has ended. New tests are data tests (marker writing, escaping and counting on byte slices), git-only fixture tests through `ReadInputs` and `roundMustFix`, the existing guard run fixture (`guardFixture`, which does not reach `sweep()` beyond what D-195 already allows on the host), and scaffold render tests. The full `go test -race ./...` runs on the host. If a fix round adds a signal or a sweep, the D-193 rule applies to it.

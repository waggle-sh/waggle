### 4.1 Roles

- **Keeper.** A human who runs Waggle on their own machine, donating compute and tokens. A Keeper talks only to the Queen and answers decision cards. (source: RFC-0003 section 2)
- **Head Keeper.** The Keeper with final authority over a hive: approves every Tier 3 change, can force-release a stuck claim, and does the admin merge that repairs a corrupt decision log. Identified in v0.1 by an allow-list in a Tier 3 file; formerly called Master Keeper or Controller. (source: D-009, D-031, D-035)
- **queen.** The entry session and the only agent a Keeper talks to. It asks decision cards and relays answers to `waggled`; it never waits on workers or writes code or specs. (source: RFC-0003 section 2, roster)
- **scout.** Planning role: breaks goals into task briefs under 400 lines, sets each task's lease and gate, and owns the roadmap, specs, and these README sections. Never writes feature code. Scouts search ahead and dance directions to the hive. (source: roster, D-065, D-074)
- **forager.** Triage role: reproduces bugs, writes failing tests, maps the lease a ticket needs, and estimates size. Never writes implementation code; safe to run unattended. Foragers bring material back from outside. (source: RFC-0003 section 2, D-074)
- **builder.** Implementation role: reads only its brief and leased files, works inside a Cell, runs tests and a self-review, then reports done. Never touches paths outside its lease. Builder bees make comb. (source: RFC-0003 section 2, roster, D-074)
- **guard.** Review role: checks every acceptance criterion, saves evidence, and returns a verdict (`pass` or `must-fix`), a Risk Tier, and an Intent Packet. Runs on a different model at or above the builder's capability level and never fixes what it finds. (source: RFC-0003 section 2, D-028)
- **waggled.** The host daemon, a deterministic Go loop with no model. It starts Cells, routes worker messages over `.waggle/control/run.sock`, writes the decision log, enforces token caps, and renders derived views. (source: RFC-0003 section 2, T-011)

The role names are D-074's: the role that plans is the scout, the role that triages is the forager, the role that codes is the builder. Records written before T-020 use the older names (architect, scout, forager, with the first two meaning something else); the retired-names table in `CONTRIBUTING.md` (section 6) maps them. The RFC still carries the old names until T-020 phase B; the README seed does not wait for it.

Planned roles. Lead-in sentence: "Planned for v0.2 and not yet specified. RFC-0003 groups them under UX, visuals, hygiene, and deliberation." Then one bullet each, text `Planned (v0.2).`: **weaver**, **nurse**, **studio**, **assembly**. `drone` is not listed: it is retired by D-073 (real drones do no work). Do not invent purposes; the brief that specifies each role replaces its line. (source: RFC-0003 sections 2.2 and 4, D-073)

### 4.2 Terms

Top line: "Any brief that adds a role or term updates these two sections in the same PR."

- **Hive.** A repository with Waggle installed. Waggle keeps its files in `.waggle/` (control plane in `.waggle/control/`, plans and records in `.waggle/hive/`), plus the gate workflow and one marked import line. (source: D-030, T-011)
- **Comb.** The hive's shared coordination state, stored as git refs under `refs/waggle/`. The same code path serves one Keeper on a local repo and hundreds on a shared remote. (source: RFC-0003 section 3.1)
- **Cell.** The sandbox a worker runs in: its own git worktree and dev container, the repo read-only except leased directories, no host credentials, network egress blocked. (source: RFC-0003 section 2, D-061)
- **Swarm.** All the agents working in one hive at a time, across every Keeper. An informal word, not a setting. (source: D-070, README intro, `cmd/waggle` usage banner)
- **Claim.** A Keeper's hold on one ticket, stored as the ref `refs/waggle/claims/ticket-<n>`. Renewals and takeovers add commits to the claim; releasing it deletes the ref. (source: D-001)
- **Lease.** The directories a claim may change, checked when claimed and again, authoritatively, at merge. A lease can never include `.waggle/` or any Tier 3 path. (source: D-002, D-043)
- **Gate.** The review a task passes before it merges. A **Light gate** covers small, isolated Tier 0 or 1 work and may ride a lane; a **Full gate** is its own guard review, required for Tier 2 and above and for anything over about 150 lines or touching schemas, auth, shared modules, dependencies, or steering files. (source: RFC-0003 section 3.3)
- **Risk Tier.** How much review a change needs, set by what it touches: Tier 0 comments and typos, Tier 1 small isolated changes with tests, Tier 2 normal logic and every steering file, Tier 3 control plane, CI, sandbox, and dependencies (Full gate plus Head Keeper approval). Hardcoded floors can be raised by config, never lowered. (source: RFC-0003 section 3.3, D-022)
- **Intent Packet.** The guard's short account of what changed, why, and the blast radius. It goes in the merge commit message with trailers for ticket, risk tier, and verdict. (source: D-017)
- **Decision card.** A structured question the queen puts to a Keeper: at most four options, recommendation first, cost and reversibility stated. Approved answers go into the hive's `DECISIONS.md`. (source: RFC-0003 section 2, T-006)
- **Lane.** An integration branch (`int-<release>-<n>`) where several Light-gate tasks share one guard pass. Leases are still checked commit by commit. (source: RFC-0003 section 3.2)
- **Nectar.** Planned (v0.2): reputation a Keeper earns from merged commits that survive 30 days on `main` without a revert. (source: RFC-0003 section 2.1)
- **Quorum.** Planned (v0.2): hive voting weighted by the square root of Nectar, with a Head Keeper veto. (source: RFC-0003 section 2.1)
- **Capability level.** `frontier`, `standard`, or `fast`. Roles declare a minimum level, never a model name, and hive config maps levels to concrete models. (source: D-028)
- **Own honey.** Building Waggle with Waggle: the Waggle repo is itself a hive that runs a pinned, known-good Waggle build. (source: D-041, D-044)

2. **Rules.**
   - Our hive runs a pinned, known-good Waggle build recorded as `waggle.pin` in `.waggle/control/config.yaml`, never the code under construction. Changing the pin is a deliberate upgrade logged with `waggle decide` (D-041).
   - Template changes reach our hive only through `waggle upgrade`, run from the target build, which becomes the new pin when the hive PR merges. Do not hand-edit hive copies of templates (D-042, D-063).
   - Worker leases never include `.waggle/`; hive files change only through waggle commands or the Head Keeper. Waggle enforces this for every hive (D-043).
   - A change that touches both layers is split: a product ticket first, then a hive upgrade.
   - `DECISIONS.md` records how our hive decided. Anything users rely on also lands in the RFC or product docs (D-045).
3. **Conventions only this repo uses** (not part of Waggle's schema): every brief carries a `Layer: product | hive` line; CODEOWNERS protects `internal/scaffold/templates/` (D-034) and `README.md` (D-065), both via T-015. `CONTRIBUTING.md` is not Tier 2 (D-058).

Things users already know keep their standard industry words (forge, PR, CI, commit, ref), and so do precise mechanisms (Gate, Lease, Claim, Risk Tier, Intent Packet).

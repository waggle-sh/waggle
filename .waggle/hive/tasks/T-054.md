## 1. Goal

Let Keepers cast quadratic votes on roadmap tasks and issue priority, weighted by `sqrt(Nectar)`, with a recorded Head Keeper veto, exactly as RFC-0006 option 1 rules it: rounds with one Nectar snapshot pinned at open, `C` credits per Keeper at `v^2` cost, weight on the tally in integer milli units, ballots in `refs/waggle/quorum/*` signed with SSH keys from a Tier 3 registry, and a tally anyone with a clone can recompute byte for byte.

Today nothing in the code votes: no `quorum` package, ref namespace, config key or command exists (`cmd/waggle/main.go:31-118` has no such case).

## 2. Scope by phase

### 2.1 Phase A: tally core (RFC 4.1, 5.1 to 5.3, 5.5, 5.6, 8 scope)

Pure functions over in-memory values. No git, no file I/O, no clock.

1. **Module.** New `internal/quorum/` with record types for `round.json`, `ballot.json`, `veto.json` and `tally.json` (RFC 6.1, 6.3, 6.4), each with `version: 1`. Canonical encoding: `json.MarshalIndent` with two spaces and a trailing newline, as `lease.json` is written (`git.go:634-639`); slices sorted before encoding (votes by item, ballots by `keeper_id`, items by tally order) so no map order reaches bytes (Q-T054-7).
2. **Item grammar.** `^(T-[0-9]{3,6}|issue-[0-9]{1,9})$` (RFC 4.1), checked before anything else; `T-` items in canonical display form.
3. **Ballot validation.** Whole `v >= 0` per item (no negative votes, RFC 13 question 9 as proposed); every item in the round's set; no duplicate item; `round` matches; `keeper_id` matches the D-016 pattern (`internal/config/local.go:17`); `sum v^2 <= C`; `credits_used` equals that sum. Validation needs no Nectar (RFC 5.2 item 1).
4. **Nectar parsing (RFC 5.3).** Input is the RFC-0005 9.2 JSON bytes, decoded with `json.Decoder.UseNumber`, never through a float. Each `nectar` text parses as an exact decimal into milli-Nectar `m(k)`. Negative, non-finite, exponent form or more than 3 decimals is malformed and stops the tally with the `keeper_id` named. An absent `keeper_id` is 0. `pending`, `matured`, `clawed_back` and `units` are never read. `schema_version` other than 1 is malformed.
5. **Weights and score.** `w_milli(k) = isqrt(m(k) * 1000)` with an integer square root, `score(i) = sum w_milli(k) * v(k, i)` in `uint64` with overflow checked (an overflow is malformed, not a wrap). Order by score descending, ties by the lower task or issue number (RFC 4.3); state the order between a `T-` and an `issue-` with equal number (suggested: `T-` first, Q-T054-7). Raw votes per item summed separately (RFC 5.5).
6. **Veto application.** Given veto records already checked for authority and decision (phase C), remove the named item from the ready order, or with `all` mark the round rejected so the previous order stands (RFC 8 scope). A veto never changes a score, a weight or another item's place.
7. **Malformed reporting.** A typed list of `(ref, reason)` with fixed reason codes, never echoing free text from a ballot (RFC 6.5).

Follow-on: T-071 (signed Head Keeper approval for protected paths, recorded under D-374) starts after this phase A is on main. It is planned after phase A only and does not wait on phase B.

### 2.2 Phase B: ballot store and signatures (RFC 6.1 to 6.4)

1. **Shared object-ref writer in `internal/comb`.** One exported entry point (suggested `WriteObjectRef(ctx, ref, files, parent, expected, msg, now)`) that builds a commit whose tree holds the given blobs (`hash-object`, `mktree`, then `commitTree` with its fixed identity and dates), then writes the ref by compare-and-swap: local `update-ref <ref> <new> <expected>` through the `casLoop` retry rules, or remote `push --atomic --porcelain --force-with-lease=<ref>:<expected>` with resync and the same bounded retry as `pushClaim`. It refuses any ref under `ClaimRefPrefix` (`backend.go:184`) or `ForceReleaseAuditRef` (`force.go:28`), so it can never write a claim. A lost race returns a sentinel the caller can retry on, distinct from `ErrAlreadyClaimed`. A matching reader fetches a given namespace (suggested `+refs/waggle/quorum/*:refs/waggle/quorum/*` with `--prune`, so a deletion on the remote shows as a missing receipt rather than a stale local copy; Q-T054-6).
2. **Registry path.** `layout.Keepers = ControlDir + "/keepers"` (OpenSSH `allowed_signers` format, RFC 6.3).
3. **Ref names (RFC 6.1).** `refs/waggle/quorum/round-<r>/record` and `refs/waggle/quorum/round-<r>/k-<sha256hex(keeper_id)>`; `<r>` an unpadded positive integer. A ref under the namespace that is not one of these two forms is reported, never parsed. A ballot whose ref hash does not match its `keeper_id` is malformed.
4. **Signing and verification.** Through the `ssh-keygen` binary, as `internal/comb` runs `git` (Q-T054-1): `ssh-keygen -Y sign -n <namespace> -f <key>` over the exact `ballot.json` bytes, stored as `ballot.sig`; verification with `ssh-keygen -Y verify -f <registry file> -I <keeper_id> -n <namespace> -s <sig>` against the registry read from the round's base commit with `git cat-file` (the pattern of `baseTierPolicy`, `gate_verify.go:269-301`), written to a temp file, never the worktree copy. Three namespaces: `waggle-quorum-ballot`, `waggle-quorum-round`, `waggle-quorum-veto`. The registry is capped in size (as `config.MaxFileSize` caps the config) and a registry line must carry `namespaces=` limited to those three. Key source for signing: Q-T054-5.
5. **Cast and recast.** `Cast(round, keeper_id, votes)` validates (phase A item 3) before any git call, signs, and writes a child of the Keeper's previous ballot (`prev` = that OID) with expected = that OID, or create-only for a first ballot. On a lost race it re-reads and retries on the new parent. Returns the ballot commit OID as the receipt (RFC 6.4).
6. **Load.** Fetch, list the round's ballot refs, read each tip, verify signature and hash, re-validate, and return counted ballots plus the malformed list. Only the tip of each ballot chain counts (last ballot wins).
7. **Fixture Nectar source.** An interface (suggested `NectarSource.Snapshot(ctx, NectarAt) ([]byte, error)`) and a file-backed implementation used by tests in B and C. It returns RFC-0005 9.2 bytes; the core parses them by phase A item 4.

### 2.3 Phase C: round lifecycle (RFC 4.2, 4.3, 5.4, 6.4, 6.5, 8)

1. **Open.** `Open(items, closes_at, signer)` allocates the next round number by create-only CAS on `round-<r>/record` (a lost race moves to `r+1`). It writes a signed `round.json` with: item set, `C` and `round_days` as read from the base config (defaults 100 and 14, RFC 4.2, 5.1), `base` commit, `opens_at`, `closes_at`, and `nectar_at` = `main_sha`, `now` (the open time), `receipts_sha` (the head of `refs/waggle/receipts/main`, or the zero OID before T-051 phase A has written one) and `rules_version` (RFC 5.4). Items come from an explicit list, or from the `T-` lines under the heading that starts with `## Backlog` in `ROADMAP.md` at the base commit (today the heading is `## Backlog (honey and multi-Keeper)`, `.waggle/hive/ROADMAP.md:22`). Only a registered key of a `gate.approvers` entry in the base config may sign it (Q-T054-3).
2. **Veto.** `Veto(round, item | all, D-<n>, signer)` appends a signed `veto.json` to the round chain. Only the Head Keeper's key may sign (first `gate.approvers` entry at the base commit, matched as `isHeadKeeper` does, `gate_approve.go:136-138`; namespace `waggle-quorum-veto`). A veto by any other key is refused at write and ignored with a reason at close.
3. **Close.** Fetch, load ballots (phase B item 6), read the Nectar snapshot for the pinned `nectar_at` through the source, verify every veto's signature and that `D-<n>` exists in `DECISIONS.md` at the close commit (`internal/decisions.Parse`), tally (phase A), and append a signed `tally.json` holding the item set, `nectar_at`, the Nectar map used as `keeper_id` to milli-Nectar (not the raw report, so `computed_at` never enters the bytes, Q-T054-2), every counted ballot OID, applied and ignored vetoes with reasons, malformed ballots, scores and raw votes. A second close of a closed round is refused.
4. **Verify.** Recompute `tally.json` from refs, registry at base, Nectar at `nectar_at` and `DECISIONS.md` at the stored close commit; succeed only on byte equality. With a receipt OID, report `counted`, `not counted (superseded by <oid>)`, `missing` or `not a ballot of this round`.
5. **Status.** Provisional scores for an open round (same code path as close, nothing written), raw votes, credits left per Keeper, vetoes with decision IDs, malformed ballots.
6. **Ready list (RFC 4.3).** Given a closed tally, the active claims (`ListActiveLeases`) and a `merged(task)` check, return the ordered items that are not vetoed, have no active claim and whose dependencies are met. The ready list is computed live and is not part of `tally.json`, so the tally stays reproducible while claims change. Dependency source and the `merged` rule: Q-T054-4. Phase C ships the function with an injected `merged` check; phase D wires it.

## 7. Threat model (D-203)

**Boundary.** Anyone who can push `refs/waggle/*` can write, rewind or delete any ref under `refs/waggle/quorum/` (`docs/gate.md` L3 applies unchanged). Authenticity comes from signatures checked against `.waggle/control/keepers` at the round's base commit, which is Tier 3: adding a voter or a key needs Head Keeper approval, and a PR cannot add a voter to a round already open.

**What is defended.** A forged or edited ballot fails verification and is never counted. A ballot under another Keeper's ref fails the hash check. A round, close or veto signed by a key that is not a listed approver (or, for a veto, not the Head Keeper) is refused. A veto without its `D-<n>` in the append-only decisions log is ignored and reported. Nectar is pinned at open, so a merge rush during a round moves no weight. A registry change after open does not change the round. Malformed input is reported by ref and reason code, never echoed.

**What is not defended (note, not must-fix).** Deletion: a pusher can delete a ballot ref or rewind the round chain (dropping a veto record or a close). Mitigations: receipts and `verify --receipt`, the tally listing every counted OID, the decision entry that survives in `DECISIONS.md`, and a forge rule protecting the namespace where one exists (section 12 item 7). Late ballots: the closer's fetch is the deadline (RFC 6.4). Identity splitting raises total weight until alias merge exists (RFC 7, phase 3); the registry rule of one human, one `keeper_id` is the control in v0.2. Ballots are public to repo readers, so vote buying is verifiable for a buyer (RFC 7, question 6).

**Must-fix:** any write under `refs/waggle/claims/` or the force-release audit ref from Quorum code; any change to existing claim behavior; a counted ballot with a bad or missing signature, a ref hash mismatch, a cost over `C`, a negative vote or an item outside the set; a veto or close accepted from an unauthorized key; a veto applied without its decision entry; a float anywhere in Nectar parsing or a stored record; `tally.json` bytes that differ across clones, map orders or a later `now`, `main` advance or receipt append; the registry read from the worktree instead of the base commit; the wall clock read inside `internal/quorum`; a git or `ssh-keygen` call before input validation; free text from a ballot echoed in output; a help line that fails `checkPlain`; files outside the phase lease; any em or en dash added.

## 8. Test plan (RFC 12)

Fixture repos are built with `git` in `t.TempDir()` with fixed author and committer dates and fixed times; test keys are generated with `ssh-keygen -t ed25519` in the temp dir. No test reads the wall clock or the network. Each case is a named subtest. Tests that need `ssh-keygen -Y` fail with a clear message when it is absent (they do not skip silently); the guard checks the CI log shows them run.

**Phase A**

- A1: RFC 5.6 golden: Keepers A, B, C, the zero-Nectar D and the fractional E (`w_milli` 3774, contribution 18870); order T-102, T-101, T-103; the all-on-T-101 variant scores 215 and 100.

- A3: ballot validation: over budget, negative, non-integer, unknown item, duplicate item, wrong round, bad `keeper_id`, `credits_used` mismatch; each refused.
- A4: item grammar: `T-1` (too short), `T-0001234567`, `issue-0`, `issue-1234567890`, `t-101`, trailing space; each refused.
- A5: tie break by lower number; `T-` versus `issue-` with equal number per Q-T054-7.
- A6: veto of one item removes it from the order without changing any score; `all` marks the round rejected.
- A7: Sybil: one identity with Nectar 400 versus four with 100 each on the same item: the split scores higher (40 against 20 per vote), documenting the RFC 7 risk until alias merge.
- A8: overflow: a crafted Nectar near the `uint64` limit is malformed, not wrapped.
- A9: encoding: shuffled input orders give byte-identical records.

**Phase B**

- B1: signatures: valid; wrong key; key not in the registry at the base commit; wrong namespace; `ballot.json` edited after signing; a registry line without `namespaces=`; a registry changed after open does not change the round.
- B2: CAS: two writers on one ballot ref race (the `hookBeforeWrite` pattern, `git.go:104-106`); recast chains to the previous ballot; last ballot wins; local and remote mode.
- B3: ref safety: `keeper_id` with `.`, `@`, `+` and the 128-character maximum map to valid refs; hash mismatch is malformed; a non-canonical ref under the namespace is reported, never parsed.
- B4: the writer refuses any ref under `refs/waggle/claims/` and the force-release audit ref; every existing `internal/comb` test passes unchanged.
- B5: validation before git: an invalid ballot runs no `git` and no `ssh-keygen` (a test git binary that fails on any call).
- B6: censorship: a ballot ref deleted on the remote shows its receipt as `missing` after fetch.

**Phase C**

- C1: open: round numbers allocate under a race (two openers get `r` and `r+1`); `--from-roadmap` reads only `T-` lines under `## Backlog` at the base commit; a non-approver key is refused; `nectar_at` holds all four inputs.
- C2: veto: applied with a matching decision entry; ignored and reported without one; `all` keeps the prior order; a veto signed by another approver is refused.
- C3: determinism: close in one clone, verify in another: same `tally.json` bytes; a `main` advance, a later `now`, a receipt appended after `receipts_sha` and a changed `computed_at` do not change it.
- C4: verify fails on a tally edited by one byte, a dropped counted ballot and a vetoed item restored.
- C5: ready list: a vetoed item, an item with an active claim and an item with an unmet dependency are skipped; an expired claim does not hold an item.
- C6: second close refused; close of an unknown round is exit 1 at the CLI layer (phase D maps it).

**Phase D**

- D1: config: `quorum.credits` and `quorum.round_days` parse; unknown key under `quorum:` is a load error with its line; absent block gives 100 and 14; zero or negative refused.
- D2: end to end in a fixture repo: open, three votes, a recast, a veto with its decision entry, close, verify from a second clone, `status --next`.
- D3: Nectar parity: a fixture repo scored through `internal/nectar` gives the weights section 6 expects.
- D4: exit codes 0, 1, 2, 3 for each command; `--json` prints only JSON on stdout.
- D5: `vote -h` and `quorum -h` pass `checkPlain`.

Every phase: `go build ./...`, `go vet ./...`, `go test -race ./...` pass; `gofmt -l .` prints nothing; no added line holds an em or en dash.

## 11. Findings and questions

Findings from reading the code and the RFCs together:

- **F1: T-051's `Input` may not pin what Quorum needs.** RFC 5.4 replays Nectar at a pinned `main_sha`, `now` and `receipts_sha`. The T-051 draft's `Input` carries "the repo, the `main` ref, the receipts, the rules version and `Now`" (T-051 section 2.2 item 1). If "the `main` ref" and "the receipts" are live heads rather than OIDs, a close after `main` moves cannot replay. **Recommended:** the queen amends T-051 phase B before it dispatches so `Input` takes a main commit OID and a receipts commit OID, and its B11 golden asserts every `nectar` serializes without exponent form and with at most 3 decimals (RFC 13 question 1).
- **F2: RFC-0005 line 230 says splitting loses weight.** Its gameability table reads "Quorum weight is `sqrt(Nectar)` (T-053), so splitting loses weight." RFC-0006 section 7 is right: `sqrt` is concave, so four identities with 100 each outweigh one with 400. **Recommended:** fix the RFC-0005 sentence in its next edit; A7 pins the real behavior.
- **F3: an unknown top-level config section is ignored, not rejected.** `internal/config/config.go:8-9` and `config_test.go:255` show older builds skip unknown top-level sections; only unknown keys inside a known section fail (`:164`, `:185`, `:218`). The T-051 draft's section 12 item 5 says an older gate "exits 3" on a `nectar:` block; by this code it would not. Same for `quorum:`. **Recommended:** the queen corrects T-051 item 5; the pin-order advice can stay as a habit.
- **F4: the RFC-0006 ruling is not recorded yet.** `DECISIONS.md` names T-054 only in D-366's ticket list (`:7084`), and `docs/RFC-0006-quorum.md:4-6` and `:294` still say proposed and "Not decided".
- **F5: RFC-0006 places alias merge and collusion flags in two phases.** Section 10 lists collusion flags in `status`, and section 12 tests alias merge for T-054, while section 11 puts both in phase 3. See Q-T054-8.

Questions, each with a recommendation:

- **Q-T054-1: signing tool. Head Keeper decision (security; also a dependency change).** (a) Shell out to `ssh-keygen -Y sign|verify` with the registry in `allowed_signers` format. (b) Add `golang.org/x/crypto/ssh` and verify in Go. **Recommended: (a).** It matches how Waggle already runs `git` as a binary, reads the RFC's registry format natively, and adds no `go.mod` change (Tier 3). Cost: every Keeper and the CI runner need an OpenSSH `ssh-keygen` with `-Y`; `waggle quorum` reports a clear error when it is missing.
- **Q-T054-2: what `tally.json` stores from Nectar.** (a) The parsed map of `keeper_id` to milli-Nectar, plus `nectar_at`. (b) The raw 9.2 report bytes. **Recommended: (a).** RFC-0005 9.2's `computed_at` may be the wall clock, so storing the raw report would make two honest closes differ.
- **Q-T054-3: approver and Head Keeper identity versus `keeper_id`. Head Keeper decision (security).** `gate.approvers` holds forge logins; the registry holds `keeper_id`s. (a) A registry principal is an approver when its `keeper_id` equals an approvers entry, case-insensitively, as `isHeadKeeper` compares (`gate_approve.go:136-138`). (b) Add an explicit login column to the registry. **Recommended: (a)** for v0.2. In this hive the `keeper_id` on claims is already the forge login; a repo where they differ cannot open rounds until (b) lands as a follow-up.
- **Q-T054-4: dependencies for the ready list (RFC 4.3).** (a) The opener records each item's dependencies in `round.json` (from the `Depends on:` line of `.waggle/hive/tasks/T-<id>.md` at base, T-IDs only, editable with a `--depends` flag); a dependency is met when a first-parent commit on `main` binds to it and it has no active claim. (b) Skip dependencies in the MVP. **Recommended: (a).** It is deterministic and recorded. (b) narrows RFC 4.3 and the "what gets picked up next" half of VISION item 6: **CUT? needs Head Keeper typed reason.** Caveat for (a): a multi-phase task counts as merged after its first phase lands; the ready list prints the dependency so a planner can see it.
- **Q-T054-5: signing key source.** (a) `--key <path>`, default `git config user.signingkey` when `gpg.format` is `ssh`, else usage error. (b) Always require `--key`. **Recommended: (a).** It reuses the key a Keeper already signs commits with and fails loudly otherwise.
- **Q-T054-6: forced fetch of the namespace.** (a) Forced fetch with `--prune`, so local state matches the remote and a deleted ballot shows as missing. (b) Non-forced, as T-051 does for receipts, reporting a rewind. **Recommended: (a).** Ballot refs are rewritten by design (recasts) and authenticity rests on signatures, not history; receipts and the counted-OID list make deletions visible. A voter re-pushes from their own clone (RFC 6.4).
- **Q-T054-7: ordering and encoding details.** Tie between `T-n` and `issue-n`: `T-` first. Records: two-space indent, trailing newline, sorted lists. **Recommended:** as stated; the RFC leaves both open and they only need to be fixed once.
- **Q-T054-8: alias merge and collusion flags (F5).** (a) Keep them in the RFC phase 3 ticket, as RFC 11 says; T-054 keeps A7 to show the split risk and prints no flag column. (b) Pull both into phase C. **Recommended: (a)**, with the phase 3 ticket opened now with a release (section 12 item 5) so it is sequencing, not a cut. (b) adds about 120 lines and a registry format change to an already L ticket.

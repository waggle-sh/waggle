## 1. Goal

Build RFC-0006 phase 3 (RFC 11, `docs/RFC-0006-quorum.md:248`): "Area-scoped rounds, alias merge, collusion flags, optional commit-reveal." Each is a scale control the T-054 MVP leaves out on purpose, and each keeps weight `sqrt(Nectar)`, quadratic cost and the Head Keeper veto exactly as ruled (VISION core item 6).

- **Alias merge (RFC 7 item 4, `:193`).** The Head Keeper records that several `keeper_id`s are one person; their Nectar is summed before `sqrt`, and only one ballot chain counts for that person. This closes the split-identity gain that T-054 test A7 documents (`sqrt` is concave, so four ids with 100 each outweigh one with 400).
- **Area rounds (RFC 9, `:215`).** A round may carry a `scope` of directories; only items whose work sits under it are in the round. This serves companies with many teams on one repo (VISION "Who it is for").
- **Collusion flags (RFC 7 item 7, `:196`).** `waggle quorum status` flags, without penalty, voters whose ballots are identical and new registry entries whose first ballot lands in the round. The Head Keeper decides; the tool reports.
- **Commit-reveal (RFC 7, `:201`; RFC 13 question 6).** An optional round mode where ballots stay hidden as signed hashes until the commit deadline, then are revealed and counted.

Today none of this exists: `Tally` weighs each raw `keeper_id` on its own (`tally.go:65`), refuses two ballots with one `keeper_id` (`tally.go:51-60`), and `Round` has no scope or mode field (`record.go:27-37`).

## 2. Scope by phase

### 2.1 Phase A: alias merge and version 2 records (RFC 7 item 4)

1. **Version 2 records.** New types for `round.json` and `tally.json` at `version: 2`, separate from the version 1 types or added with `omitempty` so that a version 1 record encodes to the same bytes as before (F2). `Encode` (`record.go:102-123`) gains the v2 cases. The golden `testdata/tally-5.6.json` does not change by one byte. Every round opened by a T-069 build is version 2; a version 1 round is tallied, closed and verified by the version 1 rules forever, aliases or not (section 3).
2. **Alias file.** `layout.KeeperAliases = ControlDir + "/keeper-aliases"`: a Tier 3 sidecar to `.waggle/control/keepers` (Q-T069-2, F6). Grammar in section 5.4. Parsed by a pure function that returns groups and a malformed list with fixed reason codes: bad token, unknown decision form, an id in two groups, an alias that is also a primary, a group over 16 ids, a file over the cap (as `config.MaxFileSize` caps the config).
3. **Read at base.** The alias file is read from the round's base commit with `git cat-file`, never from the worktree, through the T-054 phase B base reader. An absent file means no groups.
4. **Decision check.** A group counts only if its `D-<n>` exists in `DECISIONS.md` at the round's base commit (`internal/decisions.Parse`). A group without its entry is ignored and listed (`alias_no_decision`), so a voter cannot be merged, or unmerged, without a recorded Head Keeper decision.
5. **Voter layer.** Between ballots and weights: each group is one voter named by its primary; every other `keeper_id` is a voter of its own. Voter Nectar is the sum of the group's milli-Nectar from the pinned snapshot (overflow checked with `bits.Add64`, an overflow is malformed, as `tally.go:71-79`), and voter weight is `isqrt(sum * 1000)` through the existing `weightMilli` (`nectar.go:121-127`). The formula does not change: weight is still `sqrt(Nectar)` of one person.
6. **Which ballot counts (Q-T069-3).** Only the primary's ballot chain counts, last ballot wins as in T-054. A ballot under an alias's ref is not counted and is listed with reason `alias_ballot` and the primary it belongs to. This is the deterministic reading of "only their latest ballot counts" (RFC 7 item 4): there is no trusted time across two ref chains (RFC 6.4, `cast_at` proves nothing).
7. **Tally v2.** A versioned entry point (suggested `TallyV2(round, ballots, nectar, groups, vetoes)`) beside `Tally`, which stays as it is for version 1. `tally.json` v2 adds `voters` (section 5.2) and keeps the raw per-`keeper_id` map, so a reader sees both the inputs and the merge.
8. **Verify by version.** `Verify` (T-054 phase C) reads `version` from `round.json` and recomputes with the matching rules. An unknown version is refused with a reason, never tallied by the wrong rules.

### 2.2 Phase B: area rounds and collusion flags (RFC 9, RFC 7 item 7)

1. **Scope fields.** `round.json` v2 carries `scope` (sorted, normalized directories, empty for a repo-wide round) and `item_dirs` (each item with its sorted directories). Normalizing reuses `comb.NormalizeDirectories` (`backend.go:268`); no looser copy.
2. **Under-scope rule.** In an area round every item must have at least one directory, and each of its directories must equal a scope directory or sit below one by whole path segments (the segment rule of `DirsOverlap`, `backend.go:388`: `internal` covers `internal/comb`, `internal/comb` does not cover `internal/combx`). Checked at open; an item that fails is refused with its id, or, with `--from-roadmap`, left out and listed in the open output, never silently dropped.
3. **Item directories source (Q-T069-6).** For a `T-` item, from the task file `.waggle/hive/tasks/T-<id>.md` at the base commit: the union of backticked paths on the `Lease (rw)` line and its nested bullets, up to the next top-level bullet. An explicit `item_dirs` input from the opener overrides it per item. An `issue-` item needs explicit directories. Whatever the source, the result is recorded in `round.json`, so the tally never reads a task file again.
4. **Weight in area rounds (Q-T069-5).** Repo-wide Nectar at `nectar_at`, as in any round. No change to `internal/nectar`.
5. **Ready list.** The T-054 ready list works unchanged on an area round's items; status prints the scope beside the order.
6. **Several open rounds.** Area rounds and repo-wide rounds may be open at once; round numbers stay global (T-054 create-only allocation). An item may sit in more than one open round; status lists the other open rounds that hold it. Each tally orders only its own items; the records PR that edits `ROADMAP.md` reconciles them, as today.
7. **Flag: identical ballots.** Two or more counted voters (after alias merge) whose canonical vote lists, with zero-vote entries dropped and at least one positive vote left, are byte-identical. Reported as one group per distinct list.
8. **Flag: new entries.** A voter is new in round `r` when its `keeper_id` has a line in the registry at round `r`'s base and none at the base of the highest-numbered round below `r` that has a close record. New voters with a counted ballot in round `r` are flagged as one group. With no earlier closed round, the flag is not computed and status says so.
9. **Flag: case variants (Q-T069-4).** `keeper_id`s in the registry or the pinned Nectar map that are equal under ASCII case folding and are not in one alias group (F9). Status names them so the Head Keeper can record an alias; nothing merges automatically.
10. **Where flags live (Q-T069-10).** Computed by `Status` and printed by `Verify`, never stored in `tally.json` and never compared by `Verify`. Flags carry no penalty and change no score, weight or order.

### 2.3 Phase C: commit-reveal rounds (RFC 7, RFC 13 question 6)

1. **Mode.** `round.json` v2 `mode`: `open` (default, T-054 behavior) or `commit_reveal`, plus `reveals_by` (RFC 3339) for a commit-reveal round. Set at open and fixed for the round (Q-T069-7).
2. **Commit record.** In a commit-reveal round, a cast writes onto the Keeper's ballot chain (same ref as T-054, `round-<r>/k-<sha256hex(keeper_id)>`) a commit whose tree holds `commit.json` and `commit.sig` (section 5.3). The full ballot is validated first (phase A item 3 of T-054) and only its commitment is published. Signed with a new namespace, `waggle-quorum-commit` (section 12 item 3). A recast before the seal writes a new commitment as a child, last one wins.
3. **Salt.** 32 bytes from a random source injected by the caller (the CLI passes `crypto/rand`; no randomness and no clock inside `internal/quorum`, as T-054 holds for the clock). The commitment is `sha256(ballot.json bytes || salt)`, lowercase hex.
4. **Salt store (Q-T069-8).** The exact `ballot.json` bytes and the salt are kept in `<git common dir>/waggle/quorum/round-<r>-<sha256hex(keeper_id)>.json`, file mode 0600, written before the commit ref so a crash cannot leave a commitment with no way to reveal it. Never a repo path, never pushed. `vote` prints that the file is needed to reveal.
5. **Seal (Q-T069-9, F4).** After `closes_at`, a listed approver (the T-054 round-signing rule) writes a signed `seal.json` onto the round chain naming every ballot chain tip it fetched, by ref hash and OID. Commitments written after the seal are not part of the round. Sealing twice is refused. Close of a commit-reveal round without a seal is refused.
6. **Reveal.** `Reveal(round, keeper_id)` reads the salt store, writes a child of the sealed commitment holding `ballot.json`, `ballot.sig` (the T-054 ballot namespace) and `salt`. It is refused before the seal and refused if the local bytes do not hash to the sealed commitment.
7. **Close.** For a commit-reveal round, close loads each sealed chain: counted when the tip is a reveal whose parent is the sealed commitment, whose bytes and salt hash to it, and whose ballot signature and content validate; `unrevealed` when the tip is still the sealed commitment; `reveal_mismatch`, `early_reveal` (the sealed tip was already a reveal) or `not_sealed` otherwise, each listed by ref and reason code and not counted. `tally.json` v2 records the seal OID and the unrevealed list. The closer's fetch is the reveal deadline, as RFC 6.4 makes it the ballot deadline today.
8. **Status and verify.** Before close, status shows for a commit-reveal round the committed and revealed voters and no provisional scores, raw votes or flags. Verify recomputes from the seal and the reveals and succeeds only on byte equality. `verify --receipt <oid>` also answers `sealed`, `revealed` and `not sealed` for commit and reveal OIDs.
9. **Registry namespaces.** T-054 phase B limits a registry line's `namespaces=` to three values (T-054 brief 2.2 item 4); phase C allows the fourth. If T-070's ballot export and import have merged, they also carry commit and reveal commits, verified before any write (F11).

### 2.4 Phase D: CLI and docs (RFC 10)

1. **Commands** (exit codes as T-054: 0 ok, 1 check or validation failed, 2 usage, 3 git or I/O):
   - `waggle quorum open ... [--scope <dirs>] [--item-dirs T-101=internal/pricing,issue-7=docs/pricing] [--commit-reveal] [--reveals <RFC3339>]`. `--reveals` defaults to `closes_at` plus 72 hours (Q-T069-7).

## 3. Must stay

- **Version 1 rounds replay byte for byte.** A round opened by a T-054 build closes and verifies to the same `tally.json` under every T-069 build, whatever the alias file, the task files or the registry say later. `testdata/tally-5.6.json` does not change.
- The T-054 rules for every round: one Nectar snapshot pinned at open, `C` credits at `v^2` cost, weight `sqrt(Nectar)` on the tally in milli units, no cap, no floor, no decay, the Head Keeper veto with its decision entry, signatures checked against the registry at base, determinism across clones.
- Alias merge changes only which ids form one voter. It never changes the weight formula, never transfers Nectar, never reads a group without its decision entry.
- The claim contract, the gate, `internal/comb`, `internal/nectar` and the RFC-0005 9.2 shape. Quorum still never writes a claim, and the gate never reads `refs/waggle/quorum/*`, the registry or the alias file.
- Quorum orders work; it does not assign, claim or merge it (RFC 4.3).
- VISION core items 3 to 6 as ruled. No phase drops, freezes or narrows any of them. A phase split moves work to a follow-up phase; it never removes it (vision guard 3). A builder or guard that finds a rule cannot be built as written stops and reports; the queen raises it, marked **CUT** if it would narrow items 3, 5 or 6.

## 5. Interfaces and data shapes

### 5.1 `round.json` version 2

Every version 1 field (`record.go:27-37`) plus every field T-054 phase C adds (dependencies per Q-T054-4), and:

```json
{
  "version": 2,
  "mode": "commit_reveal",
  "reveals_by": "2027-01-17T12:00:00Z",
  "scope": ["internal/pricing"],
  "item_dirs": [
    {"item": "T-101", "dirs": ["internal/pricing"]},
    {"item": "issue-7", "dirs": ["internal/pricing/rates"]}
  ]
}
```

`mode` is `open` or `commit_reveal`; `reveals_by` is empty for `open`. `scope` and `item_dirs` are empty lists in a repo-wide round. Lists sorted as T-054 sorts (Q-T054-7).

### 5.2 `tally.json` version 2

Every version 1 field (`record.go:84-96`) plus:

```json
{
  "version": 2,
  "voters": [
    {"voter": "ana", "keeper_ids": ["ana", "ana-work"], "nectar_milli": 500000, "weight_milli": 22360, "ballot": "<oid>"}
  ],
  "seal": "<oid or empty>",
  "unrevealed": ["ben"]
}
```

`nectar_milli` stays the raw per-`keeper_id` map. `voters` is sorted by `voter`; `keeper_ids` sorted with the primary first. Ignored alias groups and alias ballots go in `malformed` with reason codes. For Nectar 400 plus 100 merged, `isqrt(500000 * 1000) = 22360`, where the two ids apart would weigh `20000 + 10000`.

### 5.3 Commit, seal and reveal records

- `commit.json`: `{"version": 1, "round": <r>, "keeper_id": "<id>", "commitment": "<64 hex>", "prev": "<oid or empty>"}`, with `commit.sig` from `ssh-keygen -Y sign -n waggle-quorum-commit` over the exact bytes.
- `seal.json`: `{"version": 1, "round": <r>, "sealed_at": "<RFC 3339, author text>", "tips": [{"ref": "k-<hash>", "oid": "<oid>"}]}`, sorted by `ref`, signed with `waggle-quorum-round` by a listed approver, appended to `round-<r>/record`.
- Reveal commit tree: `ballot.json` and `ballot.sig` as T-054, plus `salt` (64 lowercase hex and a newline). Parent: the sealed commitment.

### 5.4 Alias file `.waggle/control/keeper-aliases`

```
# One person per line: primary, then aliases, then the decision that merged them.
ana ana-work Ana D-401
```

Lines split on runs of spaces or tabs. First token the primary, last token `D-<n>`, one to 15 aliases between; each id matches the D-016 pattern (`item.go:17`); `#` starts a comment line; blank lines ignored; ASCII only; capped in size. An id may appear in one line only.

### 5.5 Status flags (JSON)

`"flags": [{"kind": "identical_ballots" | "new_entries" | "case_variants", "keeper_ids": [...]}]`, plus `"flags_note"` when `new_entries` cannot be computed. Not part of `tally.json`.

### 5.6 Exports between phases

- A: v2 record types, `ParseAliases`, `LoadAliases` (base read and decision check), `TallyV2`, versioned `Verify`.
- B: scope validation, `ItemDirs` (task file reader), `Flags`.
- C: `CommitCast`, `Seal`, `Reveal`, the salt store, commit-reveal close and verify.
- D: no exported API.

## 7. Threat model (D-203)

**Boundary.** As T-054: anyone who can push `refs/waggle/*` can write, rewind or delete Quorum refs; authenticity comes from signatures against the registry at the round's base. New inputs: the alias file at base (Tier 3, Head Keeper approved, a PR cannot change an open round), task files at base (reviewed hive files, read once at open), the seal (an approver's signature), and the salt file (a local secret on the voter's machine).

**What is defended.**
- *Split identities:* recorded aliases sum to one `sqrt`; ballots under an alias's ref are not counted, so a merged person cannot vote twice. A group without its decision entry is ignored.
- *Quiet merges:* a merge needs a Tier 3 file change and a decision entry at base; both are visible and append-only or Head Keeper gated.
- *Area stuffing:* every item's directories are checked against the scope at open and recorded, so the tally never trusts a later file.
- *Mid-round tactics in commit-reveal rounds:* votes are hidden until the seal; provisional scores are not shown.
- *Late re-commit after seeing reveals:* the seal fixes the set of commitments before any reveal is accepted; reveals must hash to a sealed commitment.
- *Forged reveal:* the reveal must match the sealed hash and carry a valid ballot signature from the registered key.
- *Replay drift:* version 1 rounds keep version 1 rules; an unknown version is refused.

**What is not defended (note, not must-fix).**
- *Vote buying.* Commit-reveal does not make it harder (F5): a voter can hand a buyer the salt during the round, and every revealed ballot is signed and public after it. RFC 7 (`:201`) overstates this; section 12 item 4 corrects it.
- *Selective reveal.* A voter can watch other reveals and then choose not to reveal. The cost is their own ballot; unrevealed voters are listed.
- *Seal rewind.* A pusher can rewind the round chain to drop a seal; a second seal could then admit later commitments. Mitigations: close and verify name the seal OID, the records PR cites it, the T-054 forge protection of the namespace (T-054 section 12 item 7) where available, and a disputed close is a Head Keeper call with `waggle decide`.
- *Lost salt.* A voter who loses the salt file cannot reveal; the ballot is not counted.
- *Unrecorded aliases and evasive collusion.* Flags see only identical ballots, new entries and case variants; a near-identical ballot passes. They are signals, by design without penalty (RFC 7 item 7).
- *Opener judgment in area rounds.* An approver chooses scope and item directories; both are recorded and shown.

**Must-fix:** any change to a version 1 record's bytes or a version 1 tally's result; an alias group applied without its decision entry at base, or read from the worktree; a merged voter whose alias ballot counts; voter Nectar summed through a float or without an overflow check; a weight formula other than `isqrt(sum_milli * 1000)`; an area item counted whose directories are not under the scope, or whose directories are not recorded in `round.json`; a commitment, seal or reveal accepted with a bad or missing signature or the wrong namespace; a reveal counted that does not hash to the sealed commitment; a commitment written after the seal counted; a commit-reveal close without a seal; provisional scores shown for an unsealed commit-reveal round; the salt file written inside the worktree, pushed, or created after the commit ref; randomness or the wall clock read inside `internal/quorum`; a git or `ssh-keygen` call before input validation; flags stored in `tally.json` or changing any score; free text from a ballot, alias file or task file echoed in output; any change in `internal/comb`, `internal/nectar` or the gate; a help line that fails `checkPlain`; files outside the phase lease; any em or en dash added.

## 11. Findings and questions for the ruling

Findings from reading the RFC, the T-054 brief and the open phase A code together:

- **F1: the tally has no voter layer.** `Tally` weighs `nectar[b.KeeperID]` per ballot (`tally.go:65`) and marks every ballot of a `keeper_id` seen twice as malformed (`tally.go:51-60`). Alias merge needs a layer that maps ids to voters before weights. Adding it inside `Tally` would change version 1 results, so 2.1 item 7 adds a versioned entry point instead.
- **F2: records have no version switch.** `Round` (`record.go:27-37`) and `TallyRecord` (`record.go:84-96`) encode every field, and `Encode` (`record.go:102-123`) has one path. A new field on those structs would change version 1 bytes and break replay. Separately, an older build must refuse a version 2 round rather than tally it by version 1 rules. **Recommended:** the queen asks the T-054 phase C brief owner to make close and verify refuse a `round.json` or `tally.json` version they do not know, before T-054 C dispatches. One line now, and older CLIs fail loudly later.
- **F3: `Counted` holds `keeper_id`s, not ballot OIDs.** `tally.go:82` appends `b.KeeperID` and `record.go:90` names the field `counted`, while RFC 6.4 (`:177`) and the T-054 brief 2.3 item 3 say the close lists every counted ballot OID, which `verify --receipt` needs. `Tally` is pure and cannot know OIDs; T-054 B or C must add them. No real round exists yet, so the version 1 shape is still free to change. **Recommended:** raise to the T-054 owner now (not this ticket's lease); T-069's seal and `verify --receipt` for reveals rely on OIDs in the tally.
- **F4: commit-reveal needs a commit deadline someone signs.** In an open round the closer's fetch is the deadline (RFC 6.4, `:178`). With reveals, that is not enough: a voter who sees others' reveals could write a new commitment and reveal it at once. RFC 11 does not say how the two phases are separated. **Recommended:** the seal record (2.3 item 5, Q-T069-9).
- **F5: commit-reveal does not make vote buying harder.** RFC 7 (`:201`) says it "would make that harder". It does not: a voter can give a buyer the salt to prove a hidden vote, and every revealed ballot is signed and public afterward. What it gives is hidden votes while the round is open (no bandwagon, no tactical replies to provisional scores). Receipt-free voting needs cryptography beyond a git-only design. **Recommended:** build commit-reveal as RFC 11 lists it, correct the RFC sentence (section 12 item 4), and leave receipt-freeness as a note, not a ticket.
- **F6: the alias mark cannot live in `allowed_signers` lines.** OpenSSH defines a fixed option set for `allowed_signers` (`cert-authority`, `namespaces`, `valid-after`, `valid-before`), and to the scout's reading `ssh-keygen -Y verify` refuses a line with an unknown option, so a `waggle-alias=` option would break every signature check. Phase A confirms this against the `ssh-keygen` the CI runner has. A multi-principal line (`ana,ana-work ...`) shares a key, but it cannot merge an id that has Nectar and no key. Hence the sidecar file (Q-T069-2).
- **F7: no reliable directory source for area items.** Task file lease lines are free text in several shapes (`.waggle/hive/tasks/T-002.md:8`, `T-006.md:8`, the phased bullets of `T-054.md:18-22`), and some task files have none (`T-015.md`, `T-019.md`). Repos without a hive have no task files at all. Nectar units carry a task and commits but no directories (`internal/nectar/report.go:142-167`), so area-earned Nectar is not computable without a T-051 change. See Q-T069-5 and Q-T069-6.
- **F8: a new key inside `quorum:` breaks older builds.** `config.Parse` rejects an unknown key inside a known section (`internal/config/config.go:164`, `:185`, `:218`), and T-054 phase D gives `quorum:` the same rule. The gate parses the base config (`cmd/waggle/gate_verify.go:298`). So a `quorum.reveal_days` key in this repo's config would fail the gate and every CLI built between T-054 D and T-069 D. **Recommended:** no new config keys in T-069 (Q-T069-7 (a)). If keys are wanted, the gate pin and `waggle.pin` must move past phase D before any repo adds them.
- **F9: case variants of one login are separate voters.** `keeperIDPattern` allows upper case (`item.go:17`) and `ParseNectar` treats ids as exact (`nectar.go:47`), while approvers and the relay compare logins case folded (`docs/multi-keeper.md:16`; `internal/relay/policy.go:117` on `origin/t-065a`). `Ana` and `ana` would each get their own `sqrt`. Q-T069-4.
- **F10: RFC-0006 status lines are stale.** `docs/RFC-0006-quorum.md:4-6` still say "NOT IMPLEMENTED ... the decision in the last section is not recorded" after D-372 (T-054 F4 flagged it before the ruling). RFC 13 questions 2, 3, 5, 8, 9 and 10 have no ticket; they are open questions, not ruled scope, so leaving them is not a cut, but nothing tracks them.
- **F11: T-070 and commit-reveal touch the same objects.** RFC 9 (`:219-221`) moves "the signed ballot commit" by bundle and relay. In a commit-reveal round that is a commitment and then a reveal. Whichever of T-070 and T-069 phase C lands second carries the extension (2.3 item 9).

Questions, each with a recommendation:

- **Q-T069-1: when phase A dispatches** (RFC 11, `:243`: "Each phase ships and is evaluated before the next"). (a) After T-054 phases A to D merge and T-054 AC4 (one real round replayed) is done; T-069 does not wait for T-070 to finish, but T-070 goes first on any shared lease. (b) After T-070 also merges and is evaluated. (c) As soon as T-054 D merges. **Recommended: (a).** It honors "evaluated before the next" for the round machinery T-069 builds on, and T-069 needs nothing from export, import or relay. (b) holds a later release behind relay work it does not use; (c) builds on a round format no real round has tested.
- **Q-T069-2: alias record. Head Keeper decision (security; Tier 3 file).** (a) Sidecar `.waggle/control/keeper-aliases`, one line per person ending in the `D-<n>` that merged them, read at base. (b) A comment convention inside `.waggle/control/keepers`. (c) Parse alias lists from `DECISIONS.md` text. **Recommended: (a).** It follows RFC 7 item 4 (a decision plus a registry mark), keeps `ssh-keygen` reading the registry unchanged (F6), and is machine-checked against the decision. (b) hides weight-changing data in comments; (c) parses prose.
- **Q-T069-3: which ballot counts for a merged person.** (a) The primary's chain only; alias ballots listed and not counted. (b) The ballot with the latest `cast_at` or commit date. (c) Any one chain if only one exists in the group, malformed if several. **Recommended: (a).** Deterministic and simple to explain; (b) trusts author text RFC 6.4 says proves nothing; (c) lets the result depend on which id a person happened to use.
- **Q-T069-4: case variants.** (a) A status flag; merging still needs an alias line. (b) Merge ASCII case-folded ids automatically. **Recommended: (a).** Weight changes only through a recorded decision, and D-016 ids are not always forge logins. About 15 lines in phase B.
- **Q-T069-5: weight in area rounds** (RFC 13 question 7). (a) Repo-wide Nectar at `nectar_at`, as every round. (b) Nectar earned in the area. **Recommended: (a).** It is the literal "weight `sqrt(Nectar)`" of VISION item 6 and needs no Nectar change. (b) needs per-directory units from T-051 (F7) and changes what the weight measures; as a departure from item 6's wording it would need a Head Keeper typed reason (**CUT? needs Head Keeper typed reason** if read as narrowing a Keeper's earned say to one area).
- **Q-T069-6: where an item's directories come from.** (a) Explicit `--item-dirs` only. (b) The task file's `Lease (rw)` paths at base only. (c) (b) by default, (a) overrides, `issue-` items explicit, recorded in `round.json` either way. **Recommended: (c).** It works for this hive without typing every lease, works for repos without task files, and the record makes it deterministic.
- **Q-T069-7: how a round becomes commit-reveal.** (a) Opt in per round with `open --commit-reveal`, reveal deadline `--reveals` defaulting to `closes_at` plus 72 hours, no config keys. (b) `quorum.commit_reveal` and `quorum.reveal_days` config keys. **Recommended: (a).** RFC 11 calls it optional, and (b) breaks older gates and CLIs (F8) unless every pin moves first.
- **Q-T069-8: salt storage.** (a) Random salt and ballot bytes in a 0600 file under the git common dir, written before the commit ref. (b) Salt derived from an SSH signature over a fixed message, so any machine with the key can reveal. **Recommended: (a).** (b) is only repeatable for key types with deterministic signatures (ed25519), not ECDSA or hardware keys with counters, so it fails silently for some voters. Cost of (a): a voter who loses the file cannot reveal, which `vote` states.
- **Q-T069-9: commit deadline. Head Keeper decision (security).** (a) A listed approver signs a seal record after `closes_at` naming every commitment counted. (b) No seal; reveals are accepted against whatever commitment is the tip at close. **Recommended: (a).** (b) lets a voter change a hidden vote after seeing others' reveals (F4), which defeats the mode. Cost: one more approver step per commit-reveal round.
- **Q-T069-10: where flags live.** (a) Computed by status and printed by verify, never in `tally.json`. (b) Stored in `tally.json` v2. **Recommended: (a).** The new-entry flag depends on earlier rounds' records, which a pusher can delete, so storing it would let anyone break `verify`. Flags carry no penalty (RFC 7 item 7), so the tally does not need them.
- **Q-T069-11: delegated area veto** (RFC 13 question 8, RFC 9 `:215`). (a) Leave it an open RFC question; a design card later if a company repo asks. (b) Add it to phase B. **Recommended: (a).** It is not in the RFC phase 3 list, and it changes who holds veto authority, which today is the one Head Keeper the gate knows (`docs/gate.md` section 6). Leaving it out narrows nothing ruled.
- **Q-T069-12: live trial in this hive. Head Keeper decision (public-facing).** Ballots and reveals in this public repo are visible to everyone. (a) One commit-reveal round with the Head Keeper as the only voter, for the replay check (AC5); alias merge and flags stay fixture-tested until a second Keeper registers. (b) No live round. **Recommended: (a).** It proves the seal and reveal path on real refs at no cost; alias merge needs a second identity this hive does not have.

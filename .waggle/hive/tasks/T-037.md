### 3.1 README.md

Order: pitch; the checks; "What it does not do"; install; writing a claim; recipes; status; Documentation; License. About 95 lines with blanks.

**Pitch.** One or two sentences. It may be shorter than the repositioning note's sentence, never stronger, and it carries its conditions: the gate fails a PR whose commits change paths outside the claim of the task each commit names, on a repo where the gate is a required check and PRs are required. It does not say a PR "touched only what its task was given" without naming that the task is the one each commit names (3.2 limit L1).

**The checks** (one or two lines each, each linking its `docs/gate.md` section; this list replaces the note's section 2 wording, which overstates items 3 to 5):

1. *Each commit names its task.* By a `T-<id>: ` subject, a `Waggle-Ticket:` trailer, or a `waggle/T-<id>` or `t-<id>` branch; a commit naming none, or two different tasks, fails. The task is author-chosen (L1).
2. *Each commit stays inside its task's lease.* The lease is the directory list in the task's claim, written before the work by someone other than the agent; every commit, not only the final diff, is checked, exact case, with no new symlink or submodule; only a merge from the base branch is accepted.
3. *Protected paths.* Hardcoded control paths (workflows, CI, devcontainer, Waggle's own config, Go dependency files) fail whatever the claim says and pass only by an admin bypass, even with an approval (D-261). Paths the repo lists in `gate.protected_paths` fail too, unless a listed approver approved the PR at its exact head commit (D-233, D-262, D-267), or an admin bypasses.
4. *Intent Packet trailers.* `Waggle-Ticket`, `Waggle-Risk-Tier` and `Waggle-Verdict` in the last paragraph of the PR description are checked against the commits and changed paths, as warnings only; they never fail the gate (D-263). They reach `git log` only when the repo's merge message includes the PR description (T-035 2.7 item 5).
5. *Decisions log.* `.waggle/hive/DECISIONS.md` accepts only appended, well-formed entries, judged on the PR's net change; because `.waggle/` can never be leased, every append also needs an admin merge in any repo (L9).

**What it does not do.** It does not schedule or run agents; it is not a sandbox; it binds only on PRs that must pass it as a required check (L2); and one line each for L1 (an agent can name another task's live claim), L3 (whoever can push claim refs can write a lease, the agent included if it has your git credentials), L5 (a PR that edits the gate workflow runs its own copy, mitigated, not fixed), L6 (admin bypass) and L11 (any app with write access can post a status named like the required check). Each links its `docs/gate.md` limit.

**Install.** `<<G4: init --gate-only>>`, then require `verify-leases-and-tiers` (and PRs) on the default branch, then the link to the full workflow (`<<G4: calling workflow>>`). One line: run `waggle init` and `waggle upgrade` from a pushed or released build (T-036 2.4 rule 1). One line: the install PR fails its own gate and needs an admin merge (T-036 2.11 item 8).

**Writing a claim.** `waggle claim T-<id> --dirs a,b --gate light|full --owner <id>` and `waggle release T-<id>` (`cmd/waggle/claim.go:159, 220`). `--owner` is required in a gate-only repo, which has no `.waggle/local.yaml` (D-240, T-036 2.5). After a squash or rebase merge, `waggle release` needs `--unmerged` (D-242, D-265). Claims must stay until merge (`gate_commits.go:320-321`).

**Status** (pre-1.0, what is stable), **Documentation** (gate spec, recipes, CONTRIBUTING; RFC-0003 is linked only from CONTRIBUTING as design history), **License:** today's section with exactly one edit, dropping "and the `waggled` daemon" (no daemon ships; D-229 ships dispatch second and none is built). Everything else stays word for word: the MIT-0 sentence about `internal/scaffold/templates/` is true for `--gate-only` too, which renders from the same directory.

**Limits and known bypasses.** The spec states each, with its condition and source; the README names those 3.1 lists; AC9 checks both.

- **L1, author-chosen task.** A commit's task is whatever its subject, trailer or branch names (`gate_commits.go:259-334`), so a commit can ride another task's live claim and pass for that claim's directories. The PR-body `Waggle-Ticket` trailer only warns on a mismatch (D-263). Mitigation, stated as such: reviewers check that the named task is the one assigned; keep one live claim per agent where possible. (The queen has taken the product question to the Head Keeper separately; the docs describe today's behavior.)
- **L2, required check.** The gate binds only on PRs that must pass `verify-leases-and-tiers` on a branch that requires PRs (section 4 row G5; ruleset plan availability, row G6).
- **L3, who writes leases.** Anyone who can push `refs/waggle/claims/*` can write a lease, an agent running with your git credentials included (D-232). Contributors without push access to the base repository, fork PRs included, cannot write claims; a maintainer or the orchestrator writes the claim for them, and the gate reads the base repository's claim refs for every PR (template step that fetches claim refs from `origin`, `internal/scaffold/templates/waggle-gate.yml.tmpl:47-48`; `gate/action.yml` claim-ref fetch, T-036 2.2 step 3).
- **L4, expired claims pass** with a warning (`gate_commits.go:327-331`).
- **L5, workflow self-edit.** A PR that edits the gate workflow runs its own copy under `pull_request`. D-276's mitigation: code-owner review on `.github/workflows/**`, which binds only with the ruleset's "Require review from Code Owners" on (`.github/CODEOWNERS` header), or an organization ruleset that requires the workflow. A `pull_request_target` spike is pending, so this is a mitigation, not a fix.
- **L6, admin bypass** merges skip the gate.
- **L7, trailers** are author text and prove nothing (D-263).
- **L8, approvers.** An agent holding a listed approver's token can approve; a renamed and re-registered login counts (D-266); off Actions the approver check never runs (`gate_approve.go:172-185`).
- **L9, decisions log** is judged on net change only, and every append needs an admin merge because `.waggle/` cannot be leased (`gate.go:150-157`, `backend.go:455-458`).
- **L10, version skew.** A hand-written workflow pinned to an older Action that meets a newer config key exits 3 (D-239); a newer CLI can write claims an older Action reads (`internal/comb/backend.go:113`, the lease `version` field). Run `init` and `upgrade` from a pushed or released build: an unpushed commit renders an Action ref that fails at job setup, and a module build pins by tag and warns (T-036 2.4 rules 1 and 2).
- **L11, required-context spoofing.** Any app or status with write access can satisfy a required context that has no integration binding (T-036 section 5 note).
- **L12, merge queues.** The gate workflow has no `merge_group` trigger (template at the dispatch base), so a repo that merges through GitHub's merge queue is untested (T-036 2.9 reports `merge-queue` as not checked).

## 7. Threat model (D-203, scaled to docs)

**Harm:** a reader who believes the gate enforces something it does not, and lets agents loose on that belief. Secondary: copy-paste YAML or commands that weaken the reader's repo, and claims about other tools that are false or read as endorsement.

**Attacker:** none in the usual sense; the "attacker" is the error a reader will copy. The PR author of this ticket controls only the docs; the docs control no code.

**Must-fix:** an enforcement claim without a citation, or stronger than its code (for example "prevents", "blocks agents from", "guarantees", "only what its task was given", where the code fails a check on a PR that must pass it for the task each commit names); a check stated other than as 3.1 and the claim map state it (approval passing a hardcoded path, trailers that fail, a decisions check on every commit); a missing precondition (required check, PRs required, `fetch-depth: 0`, claim refs fetched, the review trigger, `pull-requests: read` and the token in the gate step, code-owner review with its ruleset setting); an L1 to L12 limit left out of `docs/gate.md`, or a 3.1 limit left out of the README; a recipe telling the agent to write its own claim, handing it approver credentials, or advising `pull_request_target`, a write permission, or `${{ }}` interpolation of PR-controlled fields into `run:`; any YAML not copied from merged files; an invented SHA, tag, flag, input or output line; a claim about another tool not backed by a verified section 4 row; another project's branding, or wording that implies endorsement; a bee name or decision ID in README, `docs/gate.md` or `docs/recipes/**` outside a literal code span, path or config key; files outside the lease rule.

**Note, not must-fix:** style, ordering, length within budget, a citation off by a few lines that still names the right function.

**Guard prompt sentence (repeat verbatim):** "Threat bar (D-203), docs: must-fix is any statement a reader could rely on that the cited code does not do, any check stated other than as the brief's section 3.1 and claim map state it, any missing precondition or known bypass of section 3.2, any copied command or YAML that weakens a repo or is not from merged files, any claim about another tool not backed by a verified section 4 row, any bee name in user-facing docs outside a literal code span, path or config key, and files outside the lease rule; style and wording choices are notes."

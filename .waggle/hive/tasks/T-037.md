### 3.1 README.md

Order: pitch; the checks; "What it does not do"; install; writing a claim; recipes; status; Documentation; License. About 105 lines with blanks.

**Pitch.** One or two sentences, naming the product Waggle Gate (D-287). It may be shorter than the repositioning note's sentence, never stronger, and it carries its conditions: the gate fails a PR whose commits change paths outside the claim of the task each commit names, or whose task's claim does not name the PR's branch, on a repo where the gate is a required check and PRs are required. It does not say a PR "touched only what its task was given" without naming that the task is the one each commit names (L1).

**The checks** (one or two lines each, each linking its `docs/gate.md` section; this list replaces the note's section 2 wording, which overstates items 3 to 5):

1. *Each commit names its task, and the task's claim names this PR's branch.* A commit names its task by a `T-<id>: ` subject, a `Waggle-Ticket:` trailer, or a `waggle/T-<id>` or `t-<id>` branch; a commit naming none, or two different tasks, fails. The task is author-chosen, so the claim's branch list is what ties it to the PR: a bound commit fails unless its task's claim lists the PR's head branch (forks only through an `<owner>/<repo>:<branch>` entry, D-293) (T-039 2.4; L1).
2. *Each commit stays inside its task's lease.* The lease is the directory list in the task's claim; every commit, not only the final diff, is checked, exact case, with no new symlink or submodule; only a merge from the base branch is accepted. Then, as a requirement on the user and not as a check: the gate does not check who wrote the claim or when (`gate_commits.go:312-335`), so a human or the orchestrator writes it, with its branch list, before the work, never from the agent's credentials (L3).
3. *Protected paths.* Hardcoded control paths (`.github/workflows/`, `.gitlab-ci.yml`, `.devcontainer/`, `.waggle/`, and Go dependency inputs `go.mod`, `go.sum`, `go.work`, `go.work.sum` and `vendor/`, `internal/comb/backend.go:29-39`) fail whatever the claim says and pass only by an admin bypass, even with an approval (D-261). Paths the repo lists in `gate.protected_paths` fail too, unless a listed approver approved the PR at its exact head commit (D-233, D-262, D-267), or an admin bypasses.
4. *Intent Packet trailers.* `Waggle-Ticket`, `Waggle-Risk-Tier` and `Waggle-Verdict` in the last paragraph of the PR description are checked against the commits and changed paths, as warnings only; they never fail the gate (D-263). They reach `git log` only when the repo's merge message includes the PR description (T-035 2.7 item 5).
5. *Decisions log.* `.waggle/hive/DECISIONS.md` accepts only appended, well-formed entries, judged on the PR's net change; because `.waggle/` can never be leased, every append also needs an admin merge in any repo (L9).

**What it does not do.** It does not schedule or run agents; it is not a sandbox; it binds only on PRs that must pass it as a required check (L2); and one line each for L1 (anyone who can push to a branch a claim names can add commits under that claim), L3 (whoever can push claim refs can write a lease and its branch list, the agent included if it has your git credentials), L5 (a PR that edits the gate workflow runs its own copy, mitigated, not fixed), L6 (admin bypass) and L11 (any app with write access can post a status named like the required check). Each links its `docs/gate.md` limit.

**Install.** `waggle init --gate-only` with its three files and next-step line (section 2), then require `verify-leases-and-tiers` (and PRs) on the default branch, then `waggle doctor` to check claim-ref push access and the required check, with one line on what it does not check (section 2), then the link to the full workflow in `docs/gate.md`. One line: build `waggle` from source at a pinned, pushed commit (section 2, release assets), and run `waggle init` and `waggle upgrade` from that build (T-036 2.4 rule 1). One line: the install PR fails its own gate and needs an admin merge (T-036 2.11 item 8).

**Writing a claim.** `waggle claim T-<id> --dirs a,b --gate light|full --owner <id> [--branch <name>]...` and `waggle release T-<id>`, with the usage lines copied from `cmd/waggle/claim.go` at the dispatch base (`runClaim`, `runTaskRelease`). `--owner` is required in a gate-only repo, which has no `.waggle/local.yaml` (D-240, T-036 2.5). `--branch` names a PR branch the claim accepts, repeatable up to 4; with none, a fresh claim records `t-<nnn>` (D-292); given flags replace the stored list, and a renewal without flags keeps it; a re-claim after the claim expired starts a new list, so repeat every `--branch`; after the list changes, re-run the failed gate check (T-039 2.2, 2.5). After a squash or rebase merge, `waggle release` needs `--unmerged` (D-242, D-265). Claims must stay until merge (`gate_commits.go:319-320`).

**Status** (pre-1.0, what is stable), **Documentation** (gate spec, recipes, CONTRIBUTING; RFC-0003 is linked only from CONTRIBUTING as design history), **License:** today's section with exactly one edit, dropping "and the `waggled` daemon" (no daemon ships; D-229 ships dispatch second and none is built). ## 7. Threat model (D-203, scaled to docs)

**Harm:** a reader who believes the gate enforces something it does not, and lets agents loose on that belief. Secondary: copy-paste YAML or commands that weaken the reader's repo, and claims about other tools that are false or read as endorsement.

**Attacker:** none in the usual sense; the "attacker" is the error a reader will copy. The PR author of this ticket controls only the docs; the docs control no code.

**Must-fix:** an enforcement claim without a citation, or stronger than its code (for example "prevents", "blocks agents from", "guarantees", "only what its task was given", where the code fails a check on a PR that must pass it for the task each commit names and the branches its claim lists); a check stated other than as 3.1 and the claim map state it (approval passing a hardcoded path, trailers that fail, a decisions check on every commit, a branch check that runs on local runs without `--branch`); a missing precondition (required check, PRs required, `fetch-depth: 0`, claim refs fetched, the review trigger, `pull-requests: read` and the token in the gate step, code-owner review with its ruleset setting, a claim that names the PR branch); an L1 to L12 limit left out of `docs/gate.md`, or a 3.1 limit left out of the README; a recipe telling the agent to write its own claim or branch list, handing it approver credentials, or advising `pull_request_target`, a write permission, or `${{ }}` interpolation of PR-controlled fields into `run:`; any YAML not copied from merged files; an invented SHA, tag, flag, input, output line or release asset; a claim about another tool not backed by a verified section 4 row, or beyond a row's fallback wording; another project's branding, or wording that implies endorsement; a bee name or decision ID in README, `docs/gate.md` or `docs/recipes/**` outside a literal code span, path or config key; files outside the lease rule.

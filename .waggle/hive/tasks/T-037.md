### 3.1 README.md

Order: pitch; the checks; "What it does not do"; install; writing a claim; recipes; status; Documentation; License. About 105 lines with blanks.

**Pitch.** One or two sentences, naming the product Waggle Gate (D-287). It may be shorter than the repositioning note's sentence, never stronger, and it carries its conditions: the gate fails a PR whose commits change paths outside the claim of the task each commit names, or whose task's claim does not name the PR's branch, on a repo where the gate is a required check and PRs are required. It does not say a PR "touched only what its task was given" without naming that the task is the one each commit names (L1). The sentence is stated as the code at the dispatch base behaves, with one exception check 3 states: an approval by a listed approver at the head commit clears an `outside_lease` finding on a repo-listed path (`gate_commits.go:223-227`, `gate_approve.go:233-242`).

**The checks** (one or two lines each, each linking its `docs/gate.md` section; this list replaces the note's section 2 wording, which overstates items 3 to 5):

1. *Each commit names its task, and the task's claim names this PR's branch.* A commit names its task by a `T-<id>: ` subject, a `Waggle-Ticket:` trailer, or a `waggle/T-<id>` or `t-<id>` branch; a commit naming none, or two different tasks, fails (`gate_commits.go:260-310`). The task is author-chosen, so the claim's branch list is what ties it to the PR: a bound commit fails unless its task's claim lists the PR's head branch (forks only through an `<owner>/<repo>:<branch>` entry, D-293), and a claim that names no branch fails every bound commit (`gate_commits.go:343-369`; L1).
2. *Each commit stays inside its task's lease.* The lease is the directory list in the task's claim; every commit, not only the final diff, is checked, exact case, with no new symlink or submodule; only a merge from the base branch is accepted. Then, as a requirement on the user and not as a check: the gate does not check who wrote the claim or when (`gate_commits.go:315-338`), so a human or the orchestrator writes it, with its branch list, before the work, never from the agent's credentials (L3).
3. *Protected paths.* Hardcoded control paths (`.github/workflows/`, `.gitlab-ci.yml`, `.devcontainer/`, `.waggle/`, and Go dependency inputs `go.mod`, `go.sum`, `go.work`, `go.work.sum` and `vendor/`, `internal/comb/backend.go:29-39`) fail whatever the claim says and pass only by an admin bypass, even with an approval (D-261). Paths the repo lists in `gate.protected_paths` fail too, unless a listed approver approved the PR at its exact head commit (D-233, D-262, D-267), or an admin bypasses.
4. *Intent Packet trailers.* `Waggle-Ticket`, `Waggle-Risk-Tier` and `Waggle-Verdict` in the last paragraph of the PR description are checked against the commits and changed paths, as warnings only; they never fail the gate (D-263). They reach `git log` only when the repo's merge message includes the PR description (T-035 2.7 item 5).
5. *Decisions log.* `.waggle/hive/DECISIONS.md` accepts only appended, well-formed entries, judged on the PR's net change; because `.waggle/` can never be leased, every append also needs an admin merge in any repo (L9).

**What it does not do.** It does not schedule or run agents; it is not a sandbox; it binds only on PRs that must pass it as a required check (L2); and one line each for L1 (anyone who can push to a branch a claim names can add commits under that claim), L3 (whoever can push claim refs can write a lease and its branch list, the agent included if it has your git credentials), L5 (a PR that edits the gate workflow runs its own copy, mitigated, not fixed), L6 (admin bypass) and L11 (any app with write access can post a status named like the required check). Each links its `docs/gate.md` limit.

**Install.** `waggle init --gate-only` with its three files and next-step line (section 2), then require `verify-leases-and-tiers` (and PRs) on the default branch, then `waggle doctor` to check claim-ref push access and the required check, with one line on what it does not check (section 2), then the link to the full workflow in `docs/gate.md`. **Limits and known bypasses.** The spec states each, with its condition and source; the README names those 3.1 lists; AC9 checks both. L1 is written from the merged code (`gate_commits.go:260-310, 343-369`); no doc mentions a planned fix.

- **L1, who can use a claim.** A commit's task is whatever its subject, trailer or branch names, and the claim's branch list is the only tie to the PR. So anyone who can push to a branch a claim names can add commits under that claim (same-repo branches are writable by every repo writer unless protected); a claim with no list fails every bound commit with `<id>: claim names no branch; renew it with waggle claim --branch` until it is renewed and the check re-run (`gate_commits.go:355-358`); only ASCII branch names can be listed (`internal/comb/backend.go:524-544`), so a PR from another branch cannot pass for a claimed task; a re-claim after expiry resets the list (`internal/dispatch/claim.go:58-60`). The PR-body `Waggle-Ticket` trailer only warns on a mismatch (D-263). Mitigation, stated as such: protect claimed branches or keep one writer per branch; reviewers check that the named task is the one assigned.
- **L2, required check.** The gate binds only on PRs that must pass `verify-leases-and-tiers` on a branch that requires PRs (section 4 row G5; ruleset plan availability, row G6).
- **L3, who writes leases.** Anyone who can push `refs/waggle/claims/*` can write a lease and its branch list, an agent running with your git credentials included (D-232); an agent that can run `waggle claim` can name its own branch. Contributors without push access to the base repository, fork PRs included, cannot write claims; a maintainer or the orchestrator writes the claim for them, with an `<owner>/<repo>:<branch>` entry for the fork (D-293), and the gate reads the base repository's claim refs for every PR (template step that fetches claim refs from `origin`, `waggle-gate.yml.tmpl:29-30`; `gate/action.yml:37-41`).
- **L4, expired claims pass** with a warning (`gate_commits.go:330-333`), and keep their branch list until renewed or released, since the branch check still runs on them (`:334`); an expired claim with no list fails closed on a known head with the renew hint (`<id>: claim names no branch; renew it with waggle claim --branch`, `:355-358`).
- **L5, workflow self-edit.** A PR that edits the gate workflow runs its own copy under `pull_request`. D-276's mitigation: code-owner review on `.github/workflows/**`, which binds only with the ruleset's "Require review from Code Owners" on (`.github/CODEOWNERS` header), or an organization ruleset that requires the workflow. A `pull_request_target` spike is pending (T-039 section 4), so this is a mitigation, not a fix; today the gate under `pull_request_target` fails every bound commit (`gate_approve.go:39-42`, `gate_verify.go:148-155`, `gate_commits.go:343-369`), and the template's job condition does not run it there at all (`waggle-gate.yml.tmpl:16`).
- **L6, admin bypass** merges skip the gate.
- **L7, trailers** are author text and prove nothing (D-263).
- **L8, approvers.** An agent holding a listed approver's token can approve; a renamed and re-registered login counts (D-266); off Actions the approver check never runs (`gate_verify.go:130-132`, `gate_approve.go:203-205`).
- **L9, decisions log** is judged on net change only, and every append needs an admin merge because `.waggle/` cannot be leased (`gate.go:147-158`, `backend.go:458-462`).
- **L10, version skew.** A hand-written workflow pinned to an older Action that meets a newer config key exits 3 (D-239); a newer CLI writes claims with a branch list an older Action ignores (an optional field at lease version 2, `internal/comb/backend.go:88, 121-123`, D-294), and an older CLI that renews such a claim drops the list, as does any tool that writes a claim ref without `branches` (git plumbing, a future relay; D-304), so every bound commit then fails with `<id>: claim names no branch; renew it with waggle claim --branch` until a newer build renews it and the check is re-run (`gate_commits.go:355-358`). Run `init` and `upgrade` from a pushed or released build: an unpushed commit renders an Action ref that fails at job setup, and a module build pins by tag and warns (T-036 2.4 rules 1 and 2).
- **L11, required-context spoofing.** Any app or status with write access can satisfy a required context that has no integration binding (T-036 section 5 note); `waggle doctor` does not check the binding (section 2).
- **L12, merge queues.** The gate workflow has no `merge_group` trigger (`waggle-gate.yml.tmpl:5-9`, `:16`), and a gate run outside a PR event fails every bound commit (`gate_verify.go:130-155`, `gate_commits.go:343-369`), so a repo that merges through GitHub's merge queue is unsupported and untested. `waggle doctor` does not detect a merge queue; only with `forge.merge_strategy: native_queue` set does it skip the up-to-date check and print an informational `merge-queue` finding marked unknown, and that setting does not make the gate run in a merge queue (`internal/forge/probe_github.go:66-73`). Builder rule: the config reference either omits `forge.merge_strategy` or documents `native_queue` with that same sentence, and never presents it as merge-queue support.

## 7. Threat model (D-203, scaled to docs)

**Harm:** a reader who believes the gate enforces something it does not, and lets agents loose on that belief. Secondary: copy-paste YAML or commands that weaken the reader's repo, and claims about other tools that are false or read as endorsement.

**Attacker:** none in the usual sense; the "attacker" is the error a reader will copy. The PR author of this ticket controls only the docs; the docs control no code.

**Must-fix:** an enforcement claim without a citation, or stronger than its code (for example "prevents", "blocks agents from", "guarantees", "only what its task was given", where the code fails a check on a PR that must pass it for the task each commit names and the branches its claim lists); a check stated other than as 3.1 and the claim map state it (approval passing a hardcoded path, trailers that fail, a decisions check on every commit, a branch check that runs on local runs without `--branch`, a ticket-branch-name fallback for a claim with no branch list described as live (T-042 deleted it, D-303), or a listed-path finding quoted without its approval gloss); a missing precondition (required check, PRs required, `fetch-depth: 0`, claim refs fetched, the review trigger, `pull-requests: read` and the token in the gate step, code-owner review with its ruleset setting, a claim that names the PR branch); an L1 to L12 limit left out of `docs/gate.md`, or a 3.1 limit left out of the README; a recipe telling the agent to write its own claim or branch list, handing it approver credentials, or advising `pull_request_target`, a write permission, or `${{ }}` interpolation of PR-controlled fields into `run:`; any YAML not copied from merged files; an invented SHA, tag, flag, input, output line or release asset, or a release stated as published when none is (section 2); a claim about another tool not backed by a verified section 4 row, or beyond a row's fallback wording; another project's branding, or wording that implies endorsement; a bee name or decision ID in README, `docs/gate.md` or `docs/recipes/**` outside a literal code span, path or config key; files outside the lease rule.

**Note, not must-fix:** style, ordering, length within budget, a citation off by a few lines that still names the right function.

**Guard prompt sentence (repeat verbatim):** "Threat bar (D-203), docs: must-fix is any statement a reader could rely on that the cited code does not do, any check stated other than as the brief's section 3.1 and claim map state it, any missing precondition or known bypass of section 3.2, any copied command or YAML that weakens a repo or is not from merged files, any claim about another tool not backed by a verified section 4 row or beyond its fallback wording, any bee name in user-facing docs outside a literal code span, path or config key, and files outside the lease rule; style and wording choices are notes."

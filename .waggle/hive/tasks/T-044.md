## 1. Goal

When `waggle dispatch` renews its own live claim for a run on a branch the stored list does not name, the renewal adds that branch to the list, so the run's pull request passes the gate's branch check. A renewal on a branch already listed, a fresh claim, a takeover, `waggle claim` and the guard behave as they do today.

## 2. The bug and where it comes from

**Evidence.** Claim ref `refs/waggle/claims/ticket-25` on origin. Commit `501cfc3` claimed T-025 for phase C1 with `directories` `[cmd, internal]` and `branches` `[t-025c1]`. Commit `01608e6` (`waggle: renew T-025 by <keeper> (builder, full)`), written by the phase C2 dispatch on branch `t-025c2`, changed `directories` to `[internal/license]` and both timestamps, and left `branches` at `[t-025c1]`. The gate (`waggle gate verify`, job verify-leases-and-tiers) then failed PR #155 with `claim does not name this pull request's branch`, the T-039 2.4 mismatch failure. T-042 removed the no-list fallback, so every bound commit now needs a list that names its head.

**The path.** `waggle dispatch` passes `--branch` as `Request.Branch` (`cmd/waggle/dispatch.go:54`; default `t-<nnn>`, `internal/dispatch/request.go:120-122`) and never sets `Request.ClaimBranches`, which only `ClaimTask` fills (`internal/dispatch/task.go:52`). `Run` calls `AcquireClaim` for a builder or forager (`run.go:358-364`). In `AcquireClaim`:

- `:44-47`: with no `ClaimBranches`, the list defaults to `[req.Branch]`, so a fresh claim records the run's branch.
- `:63-67`: on a renewal (same keeper, active claim) with no `ClaimBranches` and a non-empty stored list, `want.Branches = old.Branches`. The run's branch is dropped.
- `:68-72`: the renewal note compares the lists, so with the stored list kept it prints only the directory change, which is what the C2 dispatch printed.

The keepalive (`run.go:404-416`) then repeats `claim.Lease.Branches`, the read-back of that write (`:411`), so the claim stays wrong for the whole run.

**This is the designed behavior, not a regression.** T-039 2.2 says so (`tasks/T-039.md:41`: "A dispatch renewal therefore never adds its own branch"), lists the change as out of scope (`:87`) and gives the queen a workaround (`:5`): before a later-phase dispatch, renew with `waggle claim T-<nnn> --dirs <same> --gate <same> --branch t-<nnn>b`, or release the earlier claim. The C2 dispatch skipped that step. Under T-039's fallback era the mistake was quieter; since T-042 it fails closed. A step the queen must remember on every later phase is the kind of rule the tool should carry.

**What D-292 rules and what it does not.** D-292 (Q-T039-2) rules `waggle claim`: with no `--branch`, a renewal keeps the stored list (a TTL extension must not drop `copilot/<slug>`). It does not rule dispatch, whose caller always names a branch. This ticket leaves `waggle claim` exactly as D-292 rules it.

## 3. Behavior change

### 3.1 Replace, append or keep (Q-T044-1)

Three cases decide it:

1. **Renewal for the same branch** (a fix round on `t-025c2` while the claim names `[t-025c2]`): every option keeps the list unchanged.
2. **A second branch while the first PR is still open** (a D-185 cut splits a build into `t-<nnn>` and `t-<nnn>b`, both open; or a fix round lands on phase C1's PR after phase C2 was dispatched). **Replace** drops the first branch, so the first PR fails the gate on its next push, review or re-run. It also drops a `copilot/<slug>` or `<owner>/<repo>:<branch>` entry a human set with `waggle claim --branch`. **Append** keeps both PRs passing. **Keep** fails the new PR (today).
3. **The guard.** The guard never writes a claim: `AcquireClaim` refuses the guard role (`claim.go:41-43`), `Run` skips the claim step for it (`run.go:359`), and its keepalive returns before any write (`run.go:407-409`). A guard dispatched on `t-025c2` reads the builder's claim and leaves it as it is under every option. No change for the guard.

**Recommended: append.** It is the only option that is right in all three cases. Its cost is that a finished phase's branch name stays accepted until the claim is released (section 5).

### 3.2 The rule (at the recommended options)

In `AcquireClaim`, `want.Branches` is, in order:

1. `req.ClaimBranches` when it is not empty (today, `:44`; only `ClaimTask` sets it).
2. On a renewal (same keeper, active claim, `:63`) whose stored list is not empty:
   - **from a dispatch run** (the new flag, 3.3): the stored list unchanged if it already holds `req.Branch` (exact, case-sensitive string match, as the gate matches); else the stored list with `req.Branch` appended at the end, stored order kept, built as a new slice (`slices.Concat` or a clone), never by `append` onto `old.Branches`;
   - **from any other caller** (`ClaimTask`): the stored list unchanged (today, D-292).
3. Otherwise `[]string{req.Branch}` (today, `:45-47`): a fresh claim, a takeover (expiry is checked before keeper, `:60-62`, so a same-keeper re-claim after expiry is a takeover and resets the list), or a renewal of a claim with no stored list.

**Full list (Q-T044-2).** When the stored list already has 4 entries and none is `req.Branch`, appending would make 5. `AcquireClaim` refuses before any write with `ExitClaim` and this message, which names no branch: `<id>: claim already names 4 branches and not this run's; set the list with waggle claim <id> --branch, or release the claim`, wrapping `comb.ErrInvalidLease`. Nothing is written, as with every claim refusal (`claim.go:38-39`), and `Run` creates no worktree (the claim step runs before `Provision`, `run.go:358-364`). Without this check `AcquireLease` would still refuse (`backend.go:494-495`) with the less helpful `branches: at most 4: invalid lease`; the check is the planned cut (section 8).

**The renewal note** (`:68-72`) is unchanged code: when the list grows, `old.Branches` and `want.Branches` differ and the existing note shows both lists, for example `renewal changes the claim: builder full [cmd internal] [t-025c1] -> builder full [internal/license] [t-025c1 t-025c2]`. A renewal on a listed branch with nothing else changed prints no note, as today.

**The keepalive** (`run.go:411`) needs no change: it repeats `claim.Lease.Branches`, the read-back of the write above, or `want` when the read-back fails (`claim.go:80-83`).

### 3.3 Telling a dispatch run from `waggle claim`

After `Validate`, a `ClaimTask` request and a dispatch request look alike: both have `ClaimBranches` empty when no list is given and `Branch` set (`Validate` always fills it, `request.go:120-122`). So `Request` gains one unexported field (suggested `addBranch bool`, with a comment saying a dispatch run sets it so a renewal adds the run's branch), and `Run` sets it on the request it passes to `AcquireClaim` at `run.go:360` only, for example on a local copy inside that step. Nothing else sets it: `ClaimTask` keeps the zero value, so `waggle claim` keeps D-292 behavior, and every existing direct `AcquireClaim` test keeps today's result. An unexported field cannot be set from `cmd/waggle/`, so no CLI flag can turn it on. `Validate` does not touch it.

The builder may choose a different name or an equivalent unexported mechanism inside the lease rule (for example an unexported variant of `AcquireClaim` that `Run` calls), provided `AcquireClaim`'s exported signature does not change and `ClaimTask`'s path cannot reach the append.

## 5. Threat model (D-203)

**Boundary.** The branch list is the only tie between a claim and a PR at the gate (`docs/gate.md` L1). Who can write a claim ref is L3 and does not change. The list a dispatch renewal adds to comes from `Request.Branch`, which the queen passes on the command line before the agent starts; `checkBranch` (`request.go:146-163`) accepts only `t-<nnn>` and `t-<nnn>` plus a non-digit suffix of `[A-Za-z0-9._-]`, so dispatch can add only a branch named for its own ticket. The agent runs after the claim is written and never chooses the list; the keepalive repeats the read-back.

**What widens.** After this change a claim can name every phase branch it was dispatched on, up to 4, until release. A repo writer who pushes to an older listed branch (for example `t-025c1` after C1 merged) can bind commits under that claim. That is L1 as it stands (any writer on a listed branch), now with up to 3 more ticket-named branches per claim. Note, not must-fix; the mitigation stays protected branches and releasing a claim when its ticket is done.

**Must-fix:** a dispatch renewal that drops, reorders or alters a stored entry, or adds anything other than `req.Branch`; a stored list of more than 4 entries, or a duplicate, written by any path; a write before the full-list refusal; `ClaimTask` or `waggle claim` with no `--branch` changing a stored list (D-292); a takeover that inherits the old list; a guard that writes, renews or changes a claim; a fresh claim recording anything but `[req.Branch]` when no list is given; the new flag settable from outside `internal/dispatch/` or by `Validate`; the refusal message echoing a branch name or list entry; the keepalive writing a list other than the read-back; any change to `claimError`'s mapping; a test that sends a signal, sets a session `Timeout` or cancels a session (D-193); files changed outside the lease rule; any em or en dash added.

**Note, not must-fix:** stale phase branches staying listed until release (above); two builder runs of one ticket by the same keeper alive at once on different branches flap the list through their keepalives (`run.go:411` repeats each run's own read-back), which is not a regression: the keepalive already flaps `Directories` and `Gate` the same way, and the post-run check (`check.go:220-221`, `own claim ref changed after the last renewal`) fails the run that did not write last; a re-dispatch after expiry resetting the list to the run's branch (a takeover, today's rule), which fails an earlier phase's open PR until `waggle claim --branch` adds it back; an older binary that renews the claim (the hive pin until it moves) keeping today's behavior.

## 9. Hive effect and the interim step (queen, not the builder)

This ticket changes no hive file and no claim ref. The hive keeps running `bin/waggle` at the pin, which has today's behavior, until a Head Keeper pin move past this merge. Until then, before every dispatch on a branch the ticket's live claim does not name (a later phase, or a cut's `b` branch), the queen runs, from the main checkout, with the same keeper as dispatch:

```
bin/waggle claim T-<nnn> --dirs <next run's dirs> --gate <gate> --branch <listed branch> --branch <new branch>
```

repeating every branch whose PR is still open, or releases the earlier claim when its PR has merged. Given flags replace the stored list (D-292), so a branch left off is dropped. A claim write does not trigger the gate workflow, so after a late renewal the failed check must be re-run. After the pin move this step is needed only to remove names or for a takeover after expiry.

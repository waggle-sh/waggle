## 1. Goal

Spend fewer tokens per merged ticket without weakening review, and show the Keeper what each ticket cost. Two parts (D-075):

1. **Always-on savings** (section 3). Built in, no setting, cannot be turned off.
2. **One setting,** `context.profile: lean | balanced | thorough`, with per-role overrides (sections 4 and 5). It tunes how much context and how many turns a role gets. It never changes models or levels (T-012 owns those) and never skips or weakens the guard on Tier 2 and above.

Plus per-ticket token and dollar reporting in `waggle status` (section 8).

Role names below are roster ids. The code hardcodes only `guard` (unchanged by T-020) and never another role name, so T-020's rename does not touch this ticket's logic.

## 2. Where tokens go today (why these levers)

- A long session re-reads its whole history every turn. Fresh sessions and handoffs cap that.
- Prompt caching only pays when the start of every request is byte-identical. Anything task-specific placed early (task ID, date, lease) breaks the cache for everything after it.
- Test and build output is the largest single source of junk context. One `go test -v` can add 50,000 tokens.
- Automatic compaction is a lossy summary written by the model under pressure. A handoff file with fixed sections is cheaper to read and easier to audit.

## 3. Always-on savings (no setting)

**S1. Fresh session per task.** Each launch is a new runtime session. `claudeArgs` never emits `--continue`, `--resume` or `--session-id`, and `Invocation` gains no field that could request one. Each guard review round is its own session. A session continued after a handoff (S5) is a new session seeded with the handoff file.

**S2. Lease-scoped context.** The launch prompt names the brief, the lease paths, and the brief's read-only context list. It never includes a repo tree listing, a file dump, or files outside those three lists. (Mount isolation is the Cell's job; this is about what the prompt hands the model.)

**S3. Cache-friendly order.** `AssemblePrompt` (section 6.2) produces, in order: role prompt, then `WAGGLE.md`, then the brief, then task-variable lines (task ID, lease, handoff file if any). The first two parts are byte-identical across all tasks for a role: no timestamps, task IDs, Keeper IDs, or random values. For Claude Code the runtime already loads the agent file (role prompt) and the `CLAUDE.md` import (`WAGGLE.md`) before the first user message; the requirement there is that the generated shim stays byte-stable across tasks, so T-012's `model:` line is the only per-role variable and it does not change per task.

**S4. Trimmed tool output.**
- The adapter sets the runtime's own output cap from the profile (Claude Code: env `BASH_MAX_OUTPUT_LENGTH`, section 4).
- Output from waggle's own commands that an agent reads (gate results, the test-run summary the launcher hands back) goes through `TrimOutput` (section 6.3): keep the head and tail, replace the middle with one marker line naming the full-output file. Lines that report failures (`--- FAIL`, `FAIL`, `panic:`, `error:` at line start, `DATA RACE`) are kept even from the trimmed middle, up to 50 such lines. Trimming never hides why something failed.
- The full output is always written to a file first. For the guard it goes into the task's evidence folder.

**S5. Handoff instead of compaction.** When a session's context reaches the profile's handoff threshold, the launcher asks the agent for a handoff (format in section 6.4), ends the session, and starts a fresh one seeded with it. The agent returns the handoff as its final message; the launcher, on the host, writes it to `.waggle/control/handoffs/T-<id>-<role>-<n>.md` (gitignored), so a Cell never needs write access outside its lease. The runtime's automatic compaction is disabled where the adapter can do so; where it cannot, the handoff threshold must sit below the runtime's compaction point, and the adapter documents which applies.

The queen (D-078) is an interactive session in v0.1, not launched by waggle, so S5 reaches it only through its role prompt (section 7.3). Long term `waggled` makes the queen stateless.

**S6. Bare runtime configuration (for the T-023 launcher).** Every worker session the launcher starts runs with `--strict-mcp-config`, no plugins, and no claude.ai connectors: the only MCP servers and tools a worker sees are the ones Waggle passes explicitly (none in v0.1). Measured in this repo on 2026-10-17: the queen session's fixed system prompt was about 55k tokens before any file was read, most of it connector tool names, plugin skill descriptions and MCP instruction blocks, while the files the session read came to about 6k. That overhead is paid again on every request and is the largest single cost in a session, ahead of anything the profiles in section 4 control. The adapter asserts the flag is present (test alongside test 9) and the launcher documents which Claude Code settings files it bypasses; a Keeper's own plugins and connectors belong to the Keeper's interactive sessions, never to a Cell.

## 4. Profiles mapped to settings

Starting values. Tune them from section 8's data after a few weeks; changing a number is a template edit, not a schema change.

| Setting | `lean` | `balanced` (default) | `thorough` | Claude Code mapping |
| :--- | :--- | :--- | :--- | :--- |
| `HandoffTokens`, as a share of the adapter's `nudge_tokens` | 50% | 75% | 100% | launcher (S5). With today's `nudge_tokens: 200000`: 100k, 150k, 200k |
| `MaxSessions` per task and role (fresh sessions after handoffs) | 3 | 5 | 8 | launcher; on reaching it, stop and escalate to the Keeper instead of spending more |
| `MaxTurns` per session | 40 | 80 | 150 | `--max-turns` |
| `ToolOutputChars` | 10,000 | 20,000 | 30,000 | env `BASH_MAX_OUTPUT_LENGTH` |
| `OutputLines` for waggle's own output (S4) | 80 | 200 | 400 | `TrimOutput` |
| `ReadOnlyContext` | paths | paths | inline | paths: the prompt lists read-only files and the agent opens what it needs. inline: their contents go into the brief part, capped at 1,500 lines total, then paths for the rest |
| `Thinking` | low | medium | high | adapter-defined. Claude Code candidate: env `MAX_THINKING_TOKENS` at 4,000 / 12,000 / 32,000. Verify against the pinned Claude Code version (Q-T021-6); if unsupported, the adapter ignores it and says so once per launch |

Not in any profile: model, level, gate class, review passes, Risk Tier. `max_tokens` stays the adapter's per-session hard stop, unchanged.

## 5. The guard floor (D-075)

For role `guard` on a task whose Risk Tier is 2, 3, or unknown, every setting is the more generous of the guard's profile value and the `balanced` value. So `lean` and a `context.roles.guard: lean` override still apply on Tier 0 and 1, and are lifted on Tier 2 and above. The resolved settings carry `Floored: true` so launch logs and `waggle status` show it.

Also:

- No setting, profile, or override can skip the guard. There is no knob for it.
- A guard session that ends on `MaxTurns`, `MaxSessions`, or `max_tokens` without a verdict line is **no verdict**: never `pass`. The launcher escalates to the Keeper.
- The guard's full tool output is always saved in the evidence folder, whatever was trimmed from its context.

## 6. Phase A: pure policy (`internal/runtime/`)

No file reads, no env reads, no `time.Now()`. Target under 250 non-test lines. Doc comments on every exported identifier.

### 6.1 Profiles (`profile.go`)

```go
type Profile int // ProfileLean = 1, ProfileBalanced = 2, ProfileThorough = 3; zero invalid
func ParseProfile(s string) (Profile, error) // exact lowercase words only

type ContextSettings struct {
    Profile         Profile // the profile the role asked for
    Floored         bool    // guard floor raised at least one value
    HandoffTokens   int
    MaxSessions     int
    MaxTurns        int
    ToolOutputChars int
    OutputLines     int
    InlineReadOnly  bool
    Thinking        Profile // low/medium/high reuse the three steps
}

type ContextPolicy struct {
    Default Profile            // zero means balanced
    Roles   map[string]Profile // per-role overrides, keys are roster ids
}

// Settings resolves one role's settings for one task. tier is T-012's task
// tier (nil = unknown). nudgeTokens comes from the adapter config.
func (p ContextPolicy) Settings(role string, tier *RiskTierLike, nudgeTokens int) (ContextSettings, error)
```

Use T-012's task context type for the tier instead of `RiskTierLike`; do not add an `internal/comb` import if T-012 avoided one. Errors: `ErrInvalidProfile` (bad word, unknown role key is phase B's job), `ErrNoModelRole` for `waggled` (reuse T-012's sentinel), nudge tokens below 1,000.

### 6.2 Prompt assembly (`prompt.go`)

```go
type PromptParts struct { RolePrompt, WaggleMD, Brief []byte; TaskLines []string; Handoff []byte; ReadOnly []ReadOnlyFile }
func AssemblePrompt(p PromptParts, s ContextSettings) (stable, variable []byte)
```

`stable` is role prompt then `WAGGLE.md`. `variable` is the brief, then inlined read-only files (only when `InlineReadOnly`, capped per section 4) or their paths, then task lines, then the handoff. The adapter decides how each half reaches the runtime.

### 6.3 Trimming (`trim.go`)

```go
func TrimOutput(out []byte, maxLines int, fullPath string) (kept []byte, trimmed int)
```

Head 40% and tail 60% of `maxLines`, failure lines from the middle kept (S4), one marker line `[waggle: <n> lines trimmed, full output in <fullPath>]`. Input under the cap is returned unchanged. Handles CRLF and a missing trailing newline.

### 6.4 Handoff format (`handoff.go`)

```go
type Handoff struct { Task, Role string; Seq int; Done, Next, FilesTouched, OpenQuestions, Verification []string }
func RenderHandoff(h Handoff) []byte
func ParseHandoff(b []byte) (Handoff, error) // strict; Render(Parse(b)) == b
```

Markdown with fixed headings in that order, bullets only, at most 150 lines and 16 KiB. A handoff over the cap or with a missing heading fails (`ErrBadHandoff`) and the launcher escalates instead of starting a blind session.

### 6.5 Adapter (`claude.go`, T-012's `claudeArgs`)

When settings are supplied: add `--max-turns <MaxTurns>` and the env values from section 4. Assert S1: no `--continue`, `--resume`, `--session-id`.

### 6.6 Phase A tests (pure, never skip)

1. `ParseProfile`: accepts the three words; rejects `Lean`, `""`, ` lean`, `max`.
2. Each profile resolves to exactly the section 4 values with `nudgeTokens = 200000`.
3. Per-role override beats the default; a role without an override gets the default; zero `Default` means balanced.
4. Guard floor: guard `lean` on Tier 2, Tier 3 and nil tier resolves every value to at least balanced with `Floored = true`; on Tier 0 and 1 it stays lean with `Floored = false`; guard `thorough` is never lowered.
5. `waggled` returns `ErrNoModelRole`.
6. `AssemblePrompt`: two tasks with different briefs, task lines and handoffs produce byte-identical `stable`; `stable` contains no task ID; inline cap respected at 1,500 lines.
7. `TrimOutput`: under cap unchanged; over cap keeps head and tail; a `--- FAIL` line in the middle survives; CRLF input; marker names the path.
8. Handoff round-trips; over-length, missing heading, and reordered headings fail.
9. `claudeArgs` with settings contains `--max-turns` and never any S1 flag; without settings, output equals T-012's.

## 8. Phase C: usage ledger and `waggle status` (blocked)

Specified here so the launcher and status tickets inherit it.

- **Ledger.** After each session the launcher appends one JSON line to `layout.Usage`: `ts`, `ticket`, `role`, `session`, `adapter`, `model`, `profile`, `floored`, `input_tokens`, `cache_write_tokens`, `cache_read_tokens`, `output_tokens`, `cost_usd` (number or null), `end` (`done`, `handoff`, `max_turns`, `max_sessions`, `max_tokens`, `error`). Append-only, one writer (the launcher), per Keeper machine.
- **Source for Claude Code.** Launch with `--output-format json`; read `usage` and `total_cost_usd` from the result. The dollar figure is the CLI's API-price estimate. Keepers on a subscription plan see it as notional; the label is `est. $`. No price table in waggle (prices go stale; T-012 rules out price lookup).
- **`waggle status` usage section,** one line per ticket, then totals:
  `T-012  builder 3 sess  guard 2 sess  in 1.84M (81% cached)  out 52k  est. $4.10  [guard floored]`
  The cached share checks S3: a role whose share stays low has a cache-breaking prefix.
- A footer states what is not counted: sessions the Keeper starts directly (today the queen and the planning role) and other Keepers' machines (Q-T021-4).

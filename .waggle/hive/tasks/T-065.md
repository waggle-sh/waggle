## 1. Goal

An outside contributor who cannot push to the base repository comments `/waggle claim T-123 --dirs internal/pricing --branch alice/shop:t-123` on an issue or PR. A maintainer approves with one comment. A workflow on the default branch, running only Waggle's own pinned build, writes `refs/waggle/claims/ticket-123` with `keeper_id: alice` and the fork branch listed, after every check `waggle claim` already makes. The gate then passes the fork PR exactly as it passes a maintainer-written claim today (gate spec L3), with no gate change (relay 3, "What the gate checks").

This serves VISION core item 3 ("how untrusted contributors claim without push access") and gives Nectar (core item 5) an authenticated `keeper_id` from GitHub's own event, which RFC 10 requires of relay.

## 2. Scope by phase

### 2.1 Phase A: request parser, policy, config, comb unblock

1. **Relay mode stops refusing.** In `internal/comb`, relay mode behaves as direct mode for every method: a Keeper with push access claims, releases and lists as today (Q-T065-1). `ErrRelayNotImplemented` (`backend.go:174-175`) is removed with its seven call sites, and `TestRelayMode` (`backend_test.go:301-318`), `TestReadClaimRelay` and `TestForceReleaseRelay` become tests that relay mode reads and writes claims like direct mode. `internal/dispatch/release_test.go:193-198` loses its relay row in phase B (dispatch lease). `CombModeRelay`'s comment (`git.go:29`) is corrected.
2. **Claim commit trailers.** A new `GitBackend` method (suggested `AcquireLeaseWithTrailers(ctx, lease, trailers []Trailer)`) appends validated `Key: value` lines after the existing message (`git.go:583`); `AcquireLease` calls it with none, so its output is byte-identical. Keys allowed: `Waggle-Relay-Request` (the request comment URL), `Waggle-Relay-Requester` (login), `Waggle-Relay-Approved-By` (login or `auto:<association>` or, in phase D, `auto:nectar`). Values are printable ASCII, no newline, at most 256 bytes; a login matches the keeper id pattern (`backend.go:192`). `lease.json` does not change (Q-T065-2). The fixed `waggle <waggle@localhost>` identity (`git.go:661-674`) does not change.
3. **`relay:` config block.** A new top-level section in `internal/config`, with keys and defaults:
   - `auto_approve_associations`: list from `OWNER`, `MEMBER`, `COLLABORATOR`, `CONTRIBUTOR`; default empty, so every request needs approval (the 2026-11-19 ruling). `FIRST_TIME_CONTRIBUTOR` and `NONE` are refused as values.
   - `max_active_claims_per_login`: default 2, range 1 to 20.
   - `max_ttl_minutes`: default 1440, range 1 to `leases` maximum (`config.MaxTTLMinutes`).
   - `allowed_directories`: list of leasable directory prefixes, default empty (no extra limit), validated like `gate.protected_paths` (`config.go`, `validProtectedPath`).
   - `release_on_close`: bool, default true (used by phase C; parsed now so the block does not change shape twice). Only if HK-4 is ruled yes; otherwise omitted.
   Unknown keys inside `relay:` are a load error with their line, as other blocks. An older build ignores the whole section (`config.go:8-9`), so the block is L10-safe for older gates and CLIs.
4. **Request grammar (`internal/relay`).** Pure, no I/O. A request is the first line of the comment body that starts with `/waggle ` after trimming spaces; other lines are ignored. The body is capped (suggested 4 KiB) and must be valid UTF-8; the command line must be printable ASCII. Tokens split on spaces only; no quotes, escapes or globbing. Commands:
   - `/waggle claim <task> --dirs <a,b> [--branch <owner>/<repo>:<branch>]... [--ttl <minutes>m] [--gate light|full]` (gate default `full`)
   - `/waggle release <task>`
   - `/waggle approve-claim <digest>`
   No `--owner`, `--base`, `--repo` or `--json`: a request that names them is refused (the owner is always the commenter). The parser reuses `comb.ParseTicketID`, `comb.ValidateBranches` and the directory normalizer, never a looser copy. The `waggle-approve <sha>` gate comment (`docs/gate.md` section 6) is not a relay command and never matches.
5. **Event decode.** From the `issue_comment` event JSON (read from the path in `GITHUB_EVENT_PATH` in phase B; a byte slice here): action `created` only (an edit or delete is ignored), comment id, URL, body, `user.login`, `user.type`, `author_association`, issue number, whether the issue is a PR, and repository full name. `user.type` `Bot` is ignored, which also stops reply loops.
6. **Policy (pure).** Given the request, the decoded identity, the config and the current active claims, decide `refuse(reason)`, `pending(digest)` or `write`:
   - every `--branch` entry is a fork entry whose owner equals the requester, ASCII case folded; a short branch name is refused (Q-T065-3). With no `--branch`, the relay refuses with a hint, since the default `t-<n>` names a base-repo branch the contributor cannot push.
   - TTL at most `max_ttl_minutes`; default is the lesser of `leases.default_ttl_minutes` and that cap.
   - active relay claims by this login, plus this one, at most `max_active_claims_per_login`. "Relay claim" means the newest commit in its chain that carries `Waggle-Relay-Requester` (item 2) names the current owner, so a later renewal by an older CLI does not hide it.
   - every directory under an `allowed_directories` prefix when the list is non-empty.
   - approval: `write` if the requester's association is in `auto_approve_associations`, or the request is a renewal by the same owner with identical directories, gate and branches before expiry (Q-T065-4); otherwise `pending`.
   - `release`: only the claim's `keeper_id` (case folded) may release it; that is already `ReleaseLease`'s owner check, repeated here only to refuse early with a reply.
   The checks `waggle claim` already makes (Tier 3, `.waggle/`, Tier 2 under `light`, protected paths from base, overlap, held by another owner) stay in `ClaimTask` and `AcquireLease` and are not duplicated.
7. **Approval digest.** `pending` replies carry a digest: the first 12 hex of SHA-256 over the canonical request (task, sorted normalized dirs, gate, branches in order, TTL, requester login, request comment id). `/waggle approve-claim <digest>` from an approver (Q-T065-5) re-reads the request comment, re-parses it, recomputes the digest and writes only on an exact match. An edit to the request after the reply changes the digest, so an approval never writes a widened request. The approver must not be the requester.

### 2.2 Phase B: entry point, forge replies, Action, workflow template

1. **`waggle relay --event <path>`** in `cmd/waggle` (help line in `printUsage`, plain-terms clean, `cmd/waggle/plain_terms_test.go`). It refuses with exit 3 unless `forge.comb_mode` is `relay` and `GITHUB_ACTIONS` is `true` and the event name is `issue_comment` (phase C adds `pull_request_target` with action `closed`). It reads the repo config from the checked-out default branch, never from a PR head. It never takes request fields from flags or environment other than the event file.
2. **Execution (`internal/relay`).** `write` calls `dispatch.ClaimTask` with `Owner` set to the requester, the request's dirs, gate, branches and TTL, `Base` the default branch on the remote, and the item 2.1.2 trailers. `release` calls `dispatch.ReleaseTask` with `Owner` the requester and `Unmerged: true`, since the merged check (`internal/dispatch/release.go:148-162`) only looks for base-repo branches; once T-051 phase A lands, the receipt resolver still finds a squash by its binding (T-051 draft section 3). `approve-claim` looks up the request by digest among the issue's comments, then runs the `write` path with `Waggle-Relay-Approved-By` set.
3. **Dispatch passthrough.** `ClaimTaskRequest` gains `Trailers`; `AcquireClaim` passes them to the new comb method when set. `ClaimBackend` (`claim.go:17-21`) gains the method; `AcquireLease` callers are unchanged.
4. **Forge.** `internal/forge` gains, for the GitHub adapter: list issue comments by issue number (REST, paginated, capped) and post one issue comment. `none` returns an error. Token from `GITHUB_TOKEN` only.
5. **Replies.** Exactly one reply per handled command: `claimed`, `pending approval, digest <d>; an approver comments /waggle approve-claim <d>`, or `refused: <reason>`. Replies never quote the request body; values from the request are passed through `clean` (`cmd/waggle/claim.go:96-103`) and any `@` is rendered so it does not mention anyone. A write that comes after the PR's gate run tells the contributor to push again or ask a maintainer to re-run the check, since the relay holds no `actions: write` (L11). If posting the reply fails, the claim result stands and the job log says so.
6. **Action `relay/action.yml`.** A composite Action like `gate/action.yml`: build `waggle` from the Action's own pinned tree with `GOPROXY=off`, `GOFLAGS=-mod=readonly`, `GOTOOLCHAIN=local` (`gate/action.yml:24-35`), then run `waggle relay --event "$GITHUB_EVENT_PATH"`. The event body reaches Go only through the file; no step interpolates `${{ github.event.* }}` text into a `run:` line.
7. **Workflow template.** `internal/scaffold/templates/waggle-relay.yml.tmpl`, rendered by `waggle init --comb-mode relay` and `waggle upgrade`, as a separate file from the gate workflow (the gate template test forbids `issue_comment`, `pull_request_target` and `: write` in the gate file, `internal/scaffold/gate_action_test.go:132`). Its shape: `on: issue_comment: types: [created]`; job `if:` the comment starts with `/waggle ` and the user type is not `Bot`; `permissions:` exactly the set ruled in HK-3, nothing else; `concurrency: waggle-relay`, `cancel-in-progress: false`; checkout of the default branch only, no `ref:` from the event; the Action pinned by SHA with a `waggle.pin` comment, as the gate template. `main.go:37`'s `--comb-mode` help stops saying "not implemented".

### 2.3 Phase C: release on PR close, docs, doctor

1. **Release on close (HK-4).** If ruled yes: the relay workflow template gains `pull_request_target: types: [closed]` with no checkout of the head, ever; the job checks out the default branch as in phase B. `waggle relay` on that event releases each active relay claim whose `branches` names the PR's head as `<head owner>/<head repo>:<head ref>` and whose owner is the PR author, through `ReleaseTask` as in 2.2 item 2. It never releases a claim without `Waggle-Relay-Requester`. `relay.release_on_close: false` turns it off.
2. **Receipts.** No receipt code in this ticket. Once T-051 phase A merges, a relay release writes a receipt through `ReleaseTask` like any release, with `keeper_id` the contributor and `released_by` the owner it resolves (the contributor). The claim chain, trailers included, stays reachable as the receipt's second parent (RFC 6.2), which is how Nectar can tell a relay claim apart (section 11, F2).
3. **Docs.** `docs/relay.md` (new, plain terms): what relay does, the three commands, the approval flow, the caps, the token and what it can do (HK-2 wording), the cost note (HK-9), and how to turn it on and off. `docs/gate.md` L3 (`:99`) gains the relay path, and a new limit entry (next free L number; T-051 proposes L13) states that the relay token can push any unprotected ref, not only claims (HK-2). `docs/multi-keeper.md` section 7 (`:96`) moves relay from "not built yet" to a link.
4. **Doctor finding.** In relay mode, `waggle doctor` reports whether `.github/workflows/waggle-relay.yml` exists and whether its `permissions:` block is exactly the ruled set. A warning, not a required finding.

### 2.4 Phase D: Nectar auto-approval (HK-10)

1. `relay.auto_approve_min_nectar` (number, default absent, meaning off). When set, a requester whose matured Nectar, read through T-051 phase B's API at the default branch, is at or above it skips approval, recorded as `Waggle-Relay-Approved-By: auto:nectar`.
2. The `pending` reply may state the requester's score and the threshold.
3. The relay never runs the scorer with network; a scorer error means `pending`, never `write`.

## 3. Request flow, end to end

1. Contributor comments `/waggle claim T-123 --dirs internal/pricing --branch alice/shop:t-123` on issue #40.
2. Relay job runs on the default branch's workflow, decodes the event, parses, checks policy and dry-runs nothing: if the policy says `pending`, it replies with the digest and writes nothing.
3. An approver comments `/waggle approve-claim 3f9a01c2b7de`. The relay finds the request, re-parses it, matches the digest, and calls `ClaimTask` with owner `alice`. `ClaimTask` reads protected paths from base, checks overlap and contention against the remote, and writes the claim with the three trailers.
4. The relay replies `claimed T-123 for alice until <time>`. Alice opens the fork PR; the gate reads the claim from the base side and matches the fork entry (D-232, gate spec section 3).
5. On merge or close (phase C), the relay releases the claim; after T-051 phase A, that release writes a receipt crediting `alice`.

## 6. Exit codes and output

`waggle relay` exits 0 when it handled or deliberately ignored the event (a refusal is a reply, not a job failure, so a contributor cannot turn the workflow red at will); 2 for a usage error; 3 for environment trouble (wrong mode, wrong event, unreadable config, git or forge failure). It prints one line per action to stdout and never prints the comment body. With `--json`, one object in the house shape of `cmd/waggle/claim.go:22-83` (`version`, `command: "relay"`, `ok`, `task`, `outcome`, `request`, `reply_posted`).

## 7. Threat model (D-203)

**Boundary.** The comment body, PR title, branch names and every field in the event other than GitHub's own identity fields (`user.login`, `user.type`, `author_association`, repository, ids) are attacker text. The job holds a token that can push refs (relay 2, "Ref scope"; HK-2). Who can write `refs/waggle/*` grows from repo writers to repo writers plus the relay acting on approved requests.

**What is defended.**
- *Injection:* the body reaches Go only from the event file; the template and Action never interpolate event text into shell (test B6). The parser accepts printable ASCII tokens only.
- *Spoofing:* the owner is the commenter as GitHub reports it; a request cannot name an owner; a fork entry must belong to the requester; an approval must come from an approver who is not the requester.
- *Approval swap:* the digest binds the approval to the exact request; an edited request needs a new approval.
- *Lease squatting:* per-login cap, TTL cap, optional allowlist, and the existing refusals. Approval on by default for everyone.
- *Sybil:* throwaway accounts all need approval unless the repo opts an association in; phase D's threshold is off by default.
- *Pwn request:* no checkout of a PR head in any relay job, including `pull_request_target`; the binary is built from the Action's pinned tree, not the repo or the PR.
- *Reply loops and mention spam:* bot comments are ignored; replies do not echo the body and do not mention anyone.
- *Forged check:* the relay has no `actions`, `checks` or `statuses` permission (L11 unchanged).

**What is not defended (note, not must-fix).** The relay token can push any ref a `contents: write` token can push, branches included, unless a ruleset blocks it (HK-2). An approver who approves a bad request gets a bad claim; the gate still holds the PR to it. A maintainer who can push can still hand-write any claim (L3, unchanged). The `waggle <waggle@localhost>` author on claim commits proves nothing about who wrote them (gate spec L3); the trailers are a record, not a signature.

**Must-fix:** any `${{ github.event.* }}` text in a `run:` line or an env value that reaches a shell; any checkout of a PR head; any permission beyond the ruled set; a write without approval when policy says `pending`; an approval that writes a request whose digest changed; a claim whose owner is not the commenter; a fork entry for another owner; a short branch name accepted; a cap or TTL bypass; a relay claim that skips any `ClaimTask` refusal; a reply that echoes the body or mentions a user; a relay that runs outside Actions or outside relay mode; a release of a non-relay claim on close; any change to the gate, `lease.json` or `comb.Backend`; a help or error line that fails the plain-terms check; files outside the phase lease; any em or en dash added.

## 8. Test plan

Fixture repos in `t.TempDir()`, a local bare origin, a fake forge `doer`, fixed `Now`, event JSON files in `internal/relay/testdata/`. No test reads the network. Each case is a named subtest.

**Phase A**
- A1: grammar: each command parses; `--owner`, `--base`, `--repo`, `--json`, unknown flags, quotes, tabs, non-ASCII, over-long body, no `/waggle ` line give a refusal reason; the gate's `waggle-approve <sha>` line is ignored.

## 11. Findings and open questions

Findings from reading the code against relay.md and RFC-0005.

- **F1: the relay identity is not the commit author.** relay 3 says "the claim commit's author is the relay identity". Every claim commit is authored and committed as `waggle <waggle@localhost>` (`internal/comb/git.go:661-674`), whoever writes it. The push identity shows only in GitHub's audit log. So the record of who asked and who approved must be in the message (2.1 item 2), and HK-1's "distinct commit author" benefit of an App does not apply to claim commits.
- **F2: T-051 and relay attribution.** The T-051 draft's `third_party` rule reads the receipt commit author (T-051 draft 2.2 item 6), which is also the fixed `waggle` identity, so it cannot tell a relay write from an owner's. Relay claims are recognizable from their trailers through the receipt's second parent. Recommendation for the T-051 brief owner: read `Waggle-Relay-*` trailers from the released claim chain. Raised to the queen; not in this ticket's lease.
- **F3: fork contributors rarely run `waggle release`.** Without release on close (HK-4), a relay claim usually expires. RFC 6.2 covers that with a post-merge gate-run receipt (`source: gate_run`), but the T-051 draft's phase A scope (2.1) does not list it. If HK-4 is ruled no **and** the gate-run receipt is not built, fork contributors' work is mostly `unattributed` in Nectar. **CUT? needs Head Keeper typed reason**, since that narrows core item 5 for the contributors core item 3 names. Recommendation: rule HK-4 yes, and keep the gate-run receipt on T-051's roadmap.
- **F4: relay mode today breaks every Keeper's CLI, not the gate.** All backend methods refuse in relay mode (`git.go:523-526` and the other call sites), but the gate builds its own direct backend (`cmd/waggle/gate_verify.go:236`). So flipping `forge.comb_mode` to `relay` before phase A's build is everyone's CLI and `waggle.pin` breaks `waggle claim`, `release`, `status` and `dispatch` with exit 3, while the gate keeps passing. Section 13 item 5 orders the flip.
- **F5: replies need a second permission.** relay 3 says the job has "`contents: write` and nothing else". Posting a reply on an issue or PR needs issue-comment write (`issues: write`; whether `pull-requests: write` is also needed on PR threads is to be confirmed in phase B against GitHub's docs). See HK-3.

Questions. Each has a recommended option the Head Keeper may simply adopt.

- **Q-T065-1: what `forge.comb_mode: relay` means.** (a) Relay mode is direct mode plus the relay entry point: Keepers with push access work as today, and `waggle relay` runs only in this mode. (b) A separate `relay.enabled` key, with `comb_mode` left as is. **Recommended: (a).** One switch, already parsed and scaffolded (`config.go:286-289`, `templates/config.yaml.tmpl:17`); (b) leaves a mode that refuses everything.
- **Q-T065-2: where the request is recorded** (relay 6, question 2). (a) Commit message trailers only. (b) An optional `lease.json` field. **Recommended: (a).** It keeps the D-232 contract and avoids L10: an older CLI that renews the claim would drop a field, but a renewal by an older CLI simply writes a new commit whose chain still holds the trailers.
- **Q-T065-3: short branch names in relay requests.** (a) Refuse; fork entries owned by the requester only. (b) Allow. **Recommended: (a).** A contributor without push access cannot push a base-repo branch, so a short name only names someone else's branch (L1).
- **Q-T065-4: renewal without approval.** (a) A renewal by the owner before expiry with identical directories, gate and branches skips approval; any change, and any takeover, needs it. (b) Every relay write needs approval. **Recommended: (a).** It keeps long work alive without maintainer effort and cannot widen a lease.
- **Q-T065-5: who approves** (security; see HK-5).
- **Q-T065-6: default caps.** `max_active_claims_per_login` 2, `max_ttl_minutes` 1440 (24 hours), `allowed_directories` empty. **Recommended:** adopt as starting values, tuned after the live trial (AC7).
- **Q-T065-7: where requests may be posted.** (a) Any issue or PR in the repo. (b) Only issues carrying a task label. **Recommended: (a).** The task id is in the request; (b) adds a label convention adopters do not have.

## 12. Head Keeper decisions

- **HK-1: relay write identity (security).** (a) The workflow's `GITHUB_TOKEN`. (b) A GitHub App token, input to the Action. **Recommended: (a) as the default, with (b) documented as an optional `token` input.** The job token is minted per run, expires with the job, needs no stored secret and no setup for adopters (core item 4, small footprint); pushes made with it do not trigger other workflows, so a claim write cannot start a loop. An App can be revoked alone and rate-limited separately, but F1 removes its main benefit for claim commits, and it costs every adopting repo an App install and a private key secret.
- **HK-2: token ref scope (security).** Whether a ruleset or permission can confine the relay token to `refs/waggle/claims/` is not verified (relay 2). Rulesets target branches and tags. **Recommended: treat the relay as a repo-writer credential for refs, say so in `docs/relay.md` and the new `docs/gate.md` limit, and have the queen run a one-off check on a scratch repo (can a `contents: write` job token push a branch that a ruleset protects? an unprotected branch? a tag?) before HK-7.** The relay's own code pushes only claim refs, but the threat is the token, not the code. Default-branch protection (L2) is the main limit on what a leaked token can merge.
- **HK-3: job permissions (security).** (a) `contents: write` only, no replies; the contributor reads the job log. (b) `contents: write` and `issues: write` (plus `pull-requests: write` only if phase B confirms GitHub needs it for PR threads). **Recommended: (b).** Without replies relay is unusable for the outsiders it serves; `issues: write` lets a leaked token edit issues and labels, which is visible and reversible, unlike refs. Never `actions`, `checks` or `statuses` (L11).
- **HK-4: release on PR close (security).** A `pull_request_target` job on `closed`, no checkout of the head, same permissions, releasing only relay claims naming that PR's fork head by its author. **Recommended: yes, in phase C, `relay.release_on_close` default true.** It adds a second write-token trigger, but one that runs no PR code and reads only the event; without it relay claims expire and Nectar loses attribution (F3).
- **HK-5: who may approve a relay claim (security).** (a) Logins in base `gate.approvers` (read from the default branch, case folded, D-233). (b) Any commenter with association `OWNER` or `MEMBER`. (c) Either. **Recommended: (a).** It is a git-held list a PR cannot change, already the repo's statement of who it trusts; (b) trusts every org member, which for a large org is wider than the maintainers. Repos with no `gate.approvers` then cannot approve, and `waggle relay` says so in the reply; maintainer pre-claims still work.
- **HK-6: new protected path (security).** Add `relay/` to this repo's `gate.protected_paths` beside `gate/` (`.waggle/control/config.yaml:53`) before phase B, so changes to the Action that runs with a write token need a listed approver at the head. **Recommended: yes.** It mirrors how `gate/` is held.
- **HK-7: turning relay on for this repo (public-facing, security).** It puts a bot that answers on public issues into the project's front door, and adds a write-token workflow. **Recommended: turn it on after phase B merges, the pins move past it (section 13 item 5), HK-2's check is run and `docs/relay.md` is merged (phase C), then run AC7 with a test account.** This is the "own honey" adopt for core item 3. Until then, maintainer pre-claims (Option C) stay the documented path, as ruled.
- **HK-8: reply wording (public-facing).** The three reply forms in 2.2 item 5 are the project's public voice to contributors. **Recommended:** approve the wording at phase B review; plain terms, no mentions, no echo.
- **HK-9: Actions cost (money).** Each `/waggle` comment runs one job that builds Waggle from source (setup-go plus `go build`, about a minute on a hosted runner); comments that are not commands are skipped by the job `if:` and cost nothing. **Recommended: accept.** Public repos on GitHub-hosted runners are not billed, so this repo pays nothing; private adopters pay minutes, which `docs/relay.md` states. No spend is needed from the Head Keeper.
- **HK-10: Nectar auto-approval (security, vision).** relay 6 question 3, the "earn a say" path. **Recommended: build it in phase D, off by default (no threshold), opt-in per repo.** Deferring it to phase D is sequencing behind T-051 phase B, not a cut; dropping it would narrow the "earn a say" path for open source maintainers (VISION "Who it is for") and is not proposed.
- **HK-11: F3 attribution gap.** **Recommended:** rule HK-4 yes, and confirm the RFC 6.2 gate-run receipt stays on T-051's roadmap. Any ruling that leaves fork contributors without a receipt path is **CUT? needs Head Keeper typed reason** (core item 5).

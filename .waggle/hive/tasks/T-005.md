# T-005: Head Keeper-only force-release of malformed or abandoned claims

- **Status:** Blocked on T-002 merge only. Head Keeper identity and audit design are resolved (D-009, D-010; see section 10). Team-mode claim integrity (D-015, implemented by D-068 as SSH-signed commits) is a design consideration, not a blocker (section 2.1).
- **Naming (D-031, T-013 section 7):** the code uses Head Keeper names from the start: `Options.HeadKeeper`, `HeadKeeperAuthorizer` with method `AuthorizeHeadKeeper`, `StaticHeadKeepers`, `ErrNotHeadKeeper`, `headKeeperID`, request field `HeadKeeperID`, audit JSON key `head_keeper_id`. Never introduce `Controller` or `Master Keeper` identifiers.
- **Gate:** `full`
- **Risk Tier:** Tier 3 (semantic). This defines who may override another Keeper's claim, which is authorization on the control plane. The path `internal/comb/` is not hardcoded Tier 3, but the change is classified Tier 3 by content and needs **Head Keeper approval** at merge.
- **Role:** `forager` (implementation), `guard` (Full-gate review)
- **Lease (rw):** `internal/comb/` (all files, including `internal/comb/testdata/`)
- **Read-only context:** this brief, `docs/tasks/T-002.md`, `WAGGLE.md`, `go.mod`
- **Depends on:** T-002 (merged). Prerequisite for the `waggle release` CLI wiring task (not yet written).
- **Commit subject prefix:** `T-005:`

## 1. Goal

Give the Head Keeper (formerly Master Keeper or Controller, D-031) a way to clear a claim that ordinary `ReleaseLease` cannot clear:

- **Malformed** claims (T-002 section 7.4): not a commit, no `lease.json`, bad JSON, `TicketID` mismatch, bad directories, or a non-canonical ref name such as `ticket-007`. T-002 refuses these with `ErrMalformedClaim`, and `AcquireLease` refuses a malformed target, so the ticket is stuck forever.
- **Abandoned** claims: active (not expired) but held by a Keeper who is gone. Today only the owner can release; others wait out the TTL.
- **Expired** claims the Head Keeper wants removed rather than taken over.

The operation must be fail-closed on identity, CAS-safe, and leave a durable audit record.

## 2. Background

- T-002 semantics this builds on: claim ref `refs/waggle/claims/ticket-<n>` points to a commit whose tree holds `lease.json`; release is a CAS delete against the OID read; local CAS is `git update-ref`, remote CAS is `fetch` then `push --atomic --force-with-lease`; lost races are classified, never surfaced as generic errors; `ErrConcurrentUpdate` means the claim changed under a release.
- **Important limitation, stated plainly:** Git refs have no per-ref ACL. In `direct` comb mode anyone with push access to the remote can already run `git push origin :refs/waggle/claims/ticket-1`. A Head Keeper check inside `waggle` therefore stops honest mistakes and agents acting through the CLI or `waggled`; it does **not** stop a Keeper with push access using raw git. Real enforcement for untrusted contributors is relay mode (the forge's CI shim checks the actor), forge permissions where the host offers them (T-018 reports which), and in team mode the gate's signature check (D-068). Document this on the exported API.
- RFC-0003 section 3.5: a force-release is a `delete` decision card. When the CLI and `queen` wiring arrive, it must never auto-apply a default. Not implemented here, but the API must make a blind delete impossible (see 5.2, expected OID is mandatory).
- The RFC does **not** define how Head Keeper identity is established in v0.1. D-009 decides it: an allow-list of keeper IDs in a Tier 3 file, checked against `.waggle/local.yaml` `keeper_id`. Per D-016 keeper IDs are GitHub logins.

### 2.1 Team mode and bot-signed commits (D-015, D-068), a consideration only

D-015: in team mode the hive's bot is the **sole claim writer**, the gate rejects claim chains containing commits the bot did not write, and `waggled` alerts on rewrites. D-068 implements this with **git's built-in SSH commit signing**, not GitHub's verified-commit badge and not commits written through the GitHub API:

- The bot signs claim and audit commits with its own SSH key (`gpg.format=ssh`, `user.signingKey`). The bot writes with plain `git push`, like everyone else.
- The gate verifies each commit with `git verify-commit` against an allowed-signers file in the Tier 3 control folder (`.waggle/control/`; exact filename set by the verification ticket), read from the base revision.
- The bot's private key lives where the bot runs (Actions secrets on GitHub). Keepers never hold it and Cells never see it (D-061).
- D-016's later Keeper signing uses the same mechanism: more lines in the same allowed-signers file.

None of this is built here; T-005 still ships the unsigned direct-mode path. Keep these constraints so nothing has to be redesigned:

- **Writer seam.** Keep the atomic "delete claim ref plus append audit commit" step in one unexported function. Team mode runs the same git operations from the bot's process; no API path is needed.
- **Signing seam.** Build every audit commit in one unexported function that today passes `--no-gpg-sign` to `git commit-tree`. Team mode swaps that one argument for `-S` plus `-c gpg.format=ssh -c user.signingKey=<path>`. Tree, parents, message, identity and dates must not depend on whether the commit is signed. Do not add signing fields to `Options` now.
- **What the verifier will walk.** Parent 2 of an audit commit is the released claim commit, which may predate team mode or be the malformed commit being cleared. The signature check therefore covers the audit chain's first-parent commits only, and claim chains under `refs/waggle/claims/` separately. Keep the audit ref outside `refs/waggle/claims/` (already required) so the two scopes stay distinct.
- **Raw-git limitation in team mode.** A claim commit pushed with raw git is unsigned, so the gate rejects any PR that relies on it, even where the forge cannot block pushes to `refs/waggle/**` (T-018 reports whether it can). A raw ref deletion still succeeds where the forge allows it; it leaves no commit to verify, and the PR then fails the gate for having no claim. That is a denial of service, not a forged claim. In solo and direct mode nothing is signed and section 2's limitation holds in full. Document both on the exported API.
- **Out of scope:** bot setup and key storage, signing, and signature verification.

## 4. Head Keeper identity (shape fixed here; v0.1 source per D-009)

The comb package does not decide who the Head Keeper is. It requires an authorizer and fails closed without one.

```go
// HeadKeeperAuthorizer decides whether headKeeperID may force-release claims.
// Implementations must be deterministic and must not prompt.
type HeadKeeperAuthorizer interface {
    AuthorizeHeadKeeper(ctx context.Context, headKeeperID string) error
}

// StaticHeadKeepers authorizes an explicit allow-list of Keeper IDs.
type StaticHeadKeepers []string
func (s StaticHeadKeepers) AuthorizeHeadKeeper(ctx context.Context, headKeeperID string) error
```

- Add `HeadKeeper HeadKeeperAuthorizer` to `Options`. **nil means no one is a Head Keeper**: every `ForceRelease` returns `ErrNotHeadKeeper`. Never default to allow.
- `StaticHeadKeepers` compares exactly (case-sensitive), rejects an empty `headKeeperID`, and returns `ErrNotHeadKeeper` wrapped with the ID on failure.
- `headKeeperID` must match the T-002 `KeeperID` pattern; otherwise `ErrInvalidForceRelease`.
- Per D-009 the allow-list lives in a Tier 3 file and is matched against `local.yaml` `keeper_id`. Loading it is wired by the CLI task, not here. This task ships the interface, `StaticHeadKeepers`, and tests only. The exported doc states that this check is advisory against humans with push access (D-009).

## 5. API

### 5.1 Sentinels (add to `backend.go`, same style as T-002)

```go
var (
    ErrNotHeadKeeper       = errors.New("comb: caller is not an authorized head keeper")
    ErrInvalidForceRelease = errors.New("comb: invalid force-release request")
)
```

Reuse T-002 sentinels where they fit: `ErrInvalidTicketID`, `ErrNotFound`, `ErrConcurrentUpdate`, `ErrRelayNotImplemented`.

### 5.2 Request and method

```go
type ForceRelease struct {
    Ref          string // full ref under refs/waggle/claims/, as reported by ListActiveLeases / MalformedClaimsError
    ExpectedOID  string // required: the exact OID the Head Keeper inspected
    HeadKeeperID string // required
    Reason       string // required, 1..512 bytes, no NUL, no control chars except '\n'
}

// ForceRelease deletes a claim ref regardless of owner, malformed or not,
// after authorizing HeadKeeperID, and records an audit entry atomically.
func (g *GitBackend) ForceRelease(ctx context.Context, req ForceRelease) error
```

Callers that start from a ticket ID build `Ref` with T-002 `RefName`.

Why a full ref and not a ticket ID: a non-canonical ref like `refs/waggle/claims/ticket-007` cannot be reached through `ParseTicketID` (it canonicalizes to `ticket-7`). Accepting the full ref lets the Head Keeper clear exactly what `MalformedClaimsError` reported.

**Ref validation** (before any git write, `ErrInvalidForceRelease` on failure):
- Starts with `refs/waggle/claims/`, suffix non-empty, suffix matches `^[A-Za-z0-9._-]{1,64}$`, contains no `..`, does not end with `.lock` or `.`, and never starts with `-`.
- Additionally passes `git check-ref-format` (run through the T-002 git helper).

**ExpectedOID** must match the T-002 OID regex at the repo's hash length. Empty is `ErrInvalidForceRelease`. There is no "delete whatever is there" mode.

### 5.3 Inspection helper (suggested)

If T-002 shipped `ClaimOID(ctx, ticketID)`, add `RefOID(ctx, ref string) (string, error)` with the same ref validation so a Head Keeper (and tests) can read the OID of a non-canonical ref. Keep the surface small.

## 6. Behavior

Order is fixed. Authorization happens before any read of claim content, so an unauthorized caller learns nothing beyond the error.

1. Relay mode: return `ErrRelayNotImplemented`.
2. Validate the request (5.2). Then `Options.HeadKeeper.AuthorizeHeadKeeper(ctx, req.HeadKeeperID)`; nil authorizer or failure returns `ErrNotHeadKeeper`.
3. Remote mode: sync claims exactly as T-002 7.2, plus fetch the audit ref (`+<auditRef>:<auditRef>`, a missing remote ref is not an error).
4. Read the current OID of `req.Ref`. Absent: `ErrNotFound`. Present and not equal to `req.ExpectedOID`: `ErrConcurrentUpdate` (the claim was renewed, taken over, or replaced since the Head Keeper looked; they must re-inspect).
5. Classify the target for the audit record: object type (`git cat-file -t`), and if it is a commit with a decodable `lease.json`, the decoded lease; otherwise the malformation reason using the same checks as T-002 7.4. Never fail the force-release because the target is malformed; that is the point.
6. Build the audit commit (section 7) and write **both** changes atomically:
   - Local: one `git update-ref --stdin` transaction: `start`, `delete <ref> <expectedOID>`, `update <auditRef> <newAudit> <oldAudit or zero OID>`, `prepare`, `commit`. Either both apply or neither.
   - Remote: one `git push --atomic --porcelain <remote> --force-with-lease=<ref>:<expectedOID> --force-with-lease=<auditRef>:<oldAudit or empty> :<ref> <newAudit>:<auditRef>`. On success mirror both locally.
7. Failure classification, consistent with T-002:
   - Claim ref rejected or changed: `ErrConcurrentUpdate`.
   - Only the audit ref lost its CAS (another force-release raced on the audit chain): re-sync and rebuild the audit commit on the new audit head, retry up to 5 times with 10 to 50 ms backoff, then `ErrConcurrentUpdate`.
   - Local lock contention: same retry rule as T-002 7.1 step 6.
   - Transport or auth failure with no porcelain status line: wrapped git error.
   - Never leave the claim deleted without its audit entry, or the audit entry written without the delete.

## 7. Audit trail (D-010)

Why a separate ref: a child commit on the claim ref is unreachable once the ref is deleted and is never pushed with the deletion, so the audit lives on a ref that survives.

**Design:**
- One audit chain ref: `refs/waggle/audit/force-releases`, append-only, written atomically with the delete. It is outside `refs/waggle/claims/`, so `ListActiveLeases` and T-002 sync (`refs/waggle/claims/*` with `--prune`) never see or prune it. Per D-010 `waggle-gate.yml` does not fetch it in v0.1; only `ForceRelease` fetches it.
- Each force-release appends one commit:
  - Parent 1: the previous audit head (absent for the first entry).
  - Parent 2: the force-released claim commit, **only if the target is a commit**. This keeps the whole claim chain (claim, renewals, takeovers) reachable and pushed with the audit.
  - Tree entries: `force-release.json` (always) and, if the target is a blob, `released-claim.raw` pointing at that blob so its content is retained.
- `force-release.json` (indented JSON, trailing newline, times UTC at whole seconds):

```json
{
  "version": 1,
  "ref": "refs/waggle/claims/ticket-7",
  "released_oid": "<oid>",
  "released_type": "commit",
  "lease": { "...": "decoded lease, or null" },
  "malformed_reason": "",
  "head_keeper_id": "paulternate",
  "reason": "keeper unreachable since 2026-10-12",
  "released_at": "2026-10-17T14:00:00Z"
}
```

- Commit message: `waggle: force-release <ref> by <head_keeper_id>` plus a blank line and the reason with control characters stripped.
- Same deterministic identity env and `--no-gpg-sign` as T-002 6.1, passed only from the signing seam (section 2.1); `GIT_*_DATE` from `Options.Now`.
- Audit review: `git log --first-parent refs/waggle/audit/force-releases`.
- A `DECISIONS.md` entry is **not** written by this code. Per RFC section 2.2, `waggled` logs approved decisions; it does not exist yet. When it does, it may mirror audit entries into `DECISIONS.md`, but the ref stays the source of truth because it is CAS-coupled to the deletion.

## 8. Tests

Same harness rules as T-002 9.1 (skip without git, isolated config, `t.TempDir()`, fake clock, no `t.Setenv` in parallel tests).

1. **Fail closed:** nil `HeadKeeper` returns `ErrNotHeadKeeper`; `StaticHeadKeepers{"alice"}` rejects `bob`, `""`, `Alice`; ref unchanged in every case; no audit ref created.
2. **Request validation (table, `ErrInvalidForceRelease`):** empty ref; `refs/heads/main`; `refs/waggle/claims/`; `refs/waggle/claims/../heads/x`; `refs/waggle/claims/-x`; suffix ending `.lock`; empty or malformed `ExpectedOID`; empty `Reason`; 513-byte reason; reason with NUL; bad `HeadKeeperID`.
3. **Active claim, local:** Alice holds `T-001`; Head Keeper force-releases with the read OID. Claim ref gone; audit ref exists; audit commit parent 2 equals the claim OID; `force-release.json` decodes and names Alice's lease; `git status --porcelain` and index unchanged.
4. **Expired claim with a renewal chain:** claim, renew, expire, force-release. `git rev-list` from the audit ref reaches all claim commits.
5. **Malformed targets (each from T-002 test 11):** blob instead of commit (audit tree has `released-claim.raw` with identical content; only one parent); commit with `{not json`; commit without `lease.json`; `TicketID` mismatch; non-canonical `refs/waggle/claims/ticket-007`. Each succeeds and records `malformed_reason`. Afterwards `ListActiveLeases` returns no `MalformedClaimsError` for that ref, and `AcquireLease` on the ticket succeeds.
6. **CAS:** wrong `ExpectedOID` returns `ErrConcurrentUpdate` and the ref is intact; missing ref returns `ErrNotFound`; owner renews between inspect and force-release, so `ErrConcurrentUpdate`.
7. **Audit chain:** three force-releases produce three first-parent commits in order.
8. **Atomicity, local:** simulate a stale audit head (write the audit ref behind the backend's back between read and write, using a test hook or a second backend). The claim must still exist if the transaction fails, and must be gone with exactly one new audit entry if a retry succeeds.
9. **Remote:** bare origin, clones A and B. A claims `T-020`; Head Keeper on B force-releases. Origin has no claim ref, has the audit ref, and the audit commit's parent 2 is A's claim commit (proves the claim chain was pushed). A's next `ListActiveLeases` no longer shows `T-020`. A's `ListActiveLeases` sync does not prune or fetch-fail on the audit ref.
10. **Remote race:** A renews `T-021` while B force-releases with the pre-renewal OID behind a barrier, repeated 5 times. Each round ends in exactly one of: renewal wins and force-release returns `ErrConcurrentUpdate`, or force-release wins and the renewal's `--force-with-lease` push is rejected, returning `ErrAlreadyClaimed` per T-002 7.2. Never both, never a generic error.
11. **Concurrent force-releases on different tickets** from two backends against one remote: both succeed (audit retry path), audit chain has both entries.
12. **Relay mode:** `ErrRelayNotImplemented`.
13. **Interface surface:** compile-time check that `Backend` is unchanged (a test-only type implementing exactly the three T-002 methods still satisfies `Backend`).

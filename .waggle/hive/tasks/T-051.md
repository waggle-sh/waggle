## 1. Goal

Compute each Keeper's Nectar from `main` history and receipts, as RFC-0005 rules it: one unit per merged task (RFC 3.2), weighted by `tier_factor * size_factor * review_factor` (RFC 3.3), credited to the claim owner's `keeper_id` (RFC 6.1), paid when the unit survives 30 days on `main` without a revert and with at least half its lines alive (RFC 4), and clawed back with no time limit when a revert lands later (RFC 5). The result is deterministic: two clones given the same repo name, `main` commit OID, receipts commit OID, rules version and `now` give byte-identical JSON, whatever either clone's live heads are, so Quorum (T-054) can replay a pinned snapshot (RFC 9.2, RFC-0006 5.4).

Today nothing durable records who owned a task once its claim is released (RFC 6.2). Phase A fixes that first, so owners and forge facts are kept from the day it lands.

## 2. Scope by phase

### 2.1 Phase A: receipt ref, resolver and backfill (RFC 6.2, 6.3, 11.1 T-051a)

1. **Receipt type and ref.** `internal/comb` gains `ReceiptRef = "refs/waggle/receipts/main"` and a `Receipt` struct matching RFC 6.2's `receipt.json`, version 1: `version`, `source` (`release`, `backfill`, or `gate_run` from phase D), `ticket_id`, `keeper_id`, `co_keepers`, `role`, `gate`, `claimed_at`, `branches`, `base_sha`, `merged_sha`, `merged_at`, `pr_number`, `pr_author`, `head_branch`, `approvers`, `released_by`. It adds the three fields RFC 6.2 names in prose but leaves out of the JSON example (Q-T051-1): `status` (`merged` or `unmerged`, RFC 6.2 step 4), `incomplete` (true when the forge fields could not be read, RFC 6.2 "Forge fields") and `merge_proof` (`forge`, `binding`, `merged_tip` or `none`: which RFC 6.2 resolver step found `merged_sha`). An unmerged receipt has `merged_sha`, `merged_at` and `base_sha` as JSON `null`; a receipt with no PR has `pr_number`, `pr_author` and `head_branch` as `null` and `approvers` as `[]`. Field validation reuses the lease rules: `keeper_id`, `released_by` and each `co_keepers` entry match the D-016 pattern (`internal/config/local.go:17`), at most 4 co-keepers, no duplicate, none equal to `keeper_id` (RFC 6.3); each `approvers` entry matches the GitHub login pattern (`internal/config/config.go:85`), at most 32; `branches` and `head_branch` pass `ValidateBranches`; every SHA is null or a full hex OID of the repo's length.
2. **Atomic release with receipt.** A new `GitBackend` method (suggested `ReleaseWithReceipt`) does what `ReleaseLease` does (owner check, compare-and-swap on the claim OID, the same errors) and in the same transaction appends one receipt commit: first parent the previous receipt head (none for the first), second parent the released claim commit, so the claim's full chain, renewals and takeovers included, stays reachable (RFC 6.2). Local mode uses one `git update-ref --stdin` transaction, as `refTransaction` does (`force.go:477-489`). Remote mode uses one `git push --atomic` with `--force-with-lease` on both refs, as `pushForceRelease` does (`force.go:492-502`), with the same bounded retry when only the receipt head moved. Either both refs move or neither does (RFC 6.2 "same CAS rules as claims").
3. **Receipt sync.** Reading receipts fetches `refs/waggle/receipts/*` without `+`, so a remote receipt head that is not a descendant of the local one fails the fetch and is reported as `receipts rewound`, never silently taken. The claim fetch (`git.go:287-292`) is unchanged.
4. **`waggle release` writes the receipt.** `ReleaseTask` calls the new method instead of `ReleaseLease` (`release.go:164`). It fills `merged_sha`, `merge_proof`, `status`, `base_sha`, `merged_at` and the forge fields by section 3, `released_by` from the owner it already resolves (`:112-117`), the claim fields from the released lease, and `co_keepers` from a new repeatable `--co <id>` flag (at most 4; only the owner can run release, so only the owner names co-keepers, RFC 6.3). `--unmerged` skips the merged check, not the receipt: resolver steps 1 and 2 still run (RFC 6.2 "`--unmerged` releases"). A forge failure never fails the release: the receipt is written `incomplete` and the release prints one warning. The release refusals, exit codes and plain output stay as they are; the JSON output (`releaseOKJSON`, `claim.go:73-83`) gains one field, `receipt` (the receipt commit OID). The `release -h` text stays plain-terms clean (`cmd/waggle/plain_terms_test.go`).
5. **`waggle nectar backfill [--repo <dir>] [--apply] [--owner <id>] [--json]`** (RFC 6.2 "Backfill", RFC 9.1; `--owner` only if Q-T051-4 is ruled (a)). Builds receipts for tasks with a credited merge on `main` and no receipt, marked `source: backfill`, from the three sources RFC 6.2 names, in this order: live claim refs; reachable claim history (claim commits reachable as second parents of the force-release audit chain `refs/waggle/audit/force-releases`, and of existing receipts); and `DECISIONS.md` references, read at the `main` head through `internal/decisions.Parse`, where an entry's `Tickets:` field names the task (owner per Q-T051-4). `released_by` is the running Keeper's `keeper_id`. Forge fields are read by section 3 step 1 when the forge is reachable, else the receipt is `incomplete`. Without `--apply` it prints the plan (task, owner, source, `merged_sha`, evidence) and writes nothing. With `--apply` it appends the planned receipts in one atomic update. A task no source names is listed as `unattributed` and gets no receipt (RFC 6.2 gap (a)). Backfill never overwrites or reorders an existing receipt.
6. **Docs.** `docs/gate.md` section 10 gains an entry (suggested L13) that says what the receipt ref is, who writes it (anyone who can push `refs/waggle/*`, as L3), that the gate never reads it, that its forge fields are read once at write time, and that a writer can rewind it (section 7). `docs/recipes/` gains the `--co` flag and the note that release now records the owner. RFC 11.3 question 6 asks for this mention.

### 2.2 Phase B: scorer core (RFC 3.1, 3.2, 3.3 tier and size factors, 4.1, 4.4, 4.5 orphans, 5.1 items 1 and 3 in squash and merge form, 5.2, 6.1 to 6.4, 7, 9.2)

1. **Module.** New `internal/nectar/` with one exported entry point, suggested `Score(ctx, Input) (Report, error)`. `Input` carries the repo directory, `Repo` (the `repo` string of RFC 9.2, supplied by the caller), `Main` (a full commit OID, not a ref name), `Receipts` (a full commit OID on the receipt chain, or the zero OID for "no receipts"), `RulesVersion`, `Now time.Time` and `Recompute bool` (RFC 9.1 `--recompute`, used by phase C's cache). `Score` never resolves a live ref: the caller (T-052's CLI, T-054's Nectar source) resolves `main` and `refs/waggle/receipts/main` to OIDs first, and `Score` reads only `Main`'s first-parent history and the receipt chain reachable from `Receipts`, so a receipt appended or a `main` commit landed after those OIDs never changes the result. An OID that is not in the repo, or a `Receipts` OID that is not a receipt commit, is an error naming it, not an empty score. The function never reads the wall clock or the network (RFC 7). `Report` (section 6) marshals to exactly the RFC 9.2 object with `schema_version: 1`, `rules_version` = `Input.RulesVersion`, `repo` = `Input.Repo`, `main_sha` = `Input.Main` and `computed_at` = `Input.Now` in RFC 3339 UTC, so `(Repo, Main, Receipts, RulesVersion, Now)` fixes every output byte (RFC 9.2 "so a ballot can be replayed"; RFC-0006 5.4 `nectar_at`). Every non-integer number is written as a plain decimal with exactly 3 decimals, never in exponent form.
2. **Task binding on `main`** (RFC 3.1). Walk the first-parent line of `main`. A commit binds to a task by `T-<id>:` subject prefix or `Waggle-Ticket:` trailer, parsed exactly as the gate parses them (`cmd/waggle/gate_commits.go:33-92`, `classify` at `:267-322`): a subject and trailer that name different tasks bind to none, and a commit whose subject starts `Head Keeper: ` is a maintainer commit and binds to none (`:277-280`). A commit that neither form binds takes the ticket-branch form (`ticketBranch`, `:38`) of the `head_branch` of a valid receipt that names it as `merged_sha` (RFC 3.1 "or ticket branch"; the branch is not in `main` history, so only a receipt can supply it). The gate's parser lives in `package main` and cannot be imported, so `internal/nectar` carries its own copy with a comment naming the source and a shared fixture table that both packages' tests read (section 8, B1). Never looser than the gate. A commit with no binding is counted `unbound`, never dropped silently. A bot commit follows the claim, not its author (RFC 3.1 "Bot commits"). A bound merge touching only `.waggle/hive/` is a unit like any other and weighs at the docs factor (item 4; RFC 3.1 "Hive-only merges"). A merge of `main` into a branch is not a unit.
3. **Units** (RFC 3.1, 3.2). Squash: the commit. Merge commit: the merge commit, task from its non-merge commits (the gate rejects mixed tasks). Rebase: the run of consecutive first-parent commits with one task. One unit per task, completed by its last credited merge; a task in several PRs is one unit. Units are built from `main` history alone, so phase C can cache them; RFC 3.1's "one task and one `pr_number`" for a rebase run never changes a unit, since all of a task's credited merges are one unit, and the per-commit share of a rebase-run revert (phase C) is by line.
4. **Weight** (RFC 3.3). `weight = tier_factor * size_factor * review_factor`, all in one versioned rules table (rules version 1). Phase B builds `tier_factor` and `size_factor`; `review_factor` is 1 until phase C builds it. `tier_factor` is 1, 2, 3 or 4 for the highest Risk Tier of any path the task changed, by `TierPolicy.RequiredMinTier` with `gate.protected_paths` read from the config at the unit's base (the first parent on `main` of its first commit, computed from history), as the gate reads config at the PR base (`cmd/waggle/gate_verify.go:265-301`). `size_factor = 1 + log2(1 + min(changed_lines, 400) / 25)`, 3 decimals, range 1 to 5.087 (F8). `changed_lines = code_lines + docs_factor * docs_lines` with `docs_factor` 0.5, never 0, where lines are added plus deleted from `git diff --numstat` over the unit's commits and docs lines are lines in Markdown files (`*.md`, `*.mdx`) and in `.waggle/hive/` (a rules-table entry). Binary files, lockfiles (`go.sum`, `package-lock.json` and the other names in the table) and files marked `linguist-generated` in `.gitattributes` are left out of the count and listed per unit (RFC 3.3). A `light` and a `full` claim weigh the same. A pure-deletion task (no added lines) weighs as a minimal unit: `size_factor` 1 (RFC 4.2). **Arithmetic** is in integer thousandths: `size_factor` is computed once per value and rounded half up to thousandths, written so no fused multiply-add can apply (explicit `float64` conversions, as the Go spec allows), and pinned by a golden of all 801 half-line values from 0 to 400; every later product, share and proportion is integer thousandths with half-up rounding, so no float reaches the output.
5. **Window** (RFC 4.1). `merged_at` is the committer time of the unit's completing merge. A unit is a **direct push** unless a valid receipt for it carries a `pr_number`; for a direct push the window starts at the later of `merged_at` and **first-seen**, the committer time of the earliest receipt commit on the chain that names its `merged_sha`. A receipt that is `incomplete` therefore delays a unit and never removes one. `matures_at = start + 720h`. A unit with `now < matures_at` is `pending`.
6. **Attribution** (RFC 6.1 to 6.4, 10). A receipt is **valid** for a unit when its `merged_sha` is the unit's completing commit or another credited merge of the task on `Main`'s first-parent line, its `ticket_id` is the unit's task, and, when its `head_branch` is set, `branches` names it (RFC 6.2 trust note). Credit goes to the `keeper_id` of the valid receipt whose `merged_sha` is the completing commit, else the newest valid receipt for the task (Q-T051-3). When more than one valid receipt names the completing commit (a release and a phase D gate-run receipt for the same merge), a `release` receipt wins over `gate_run` and `backfill`, then the newest by receipt order. An `unmerged` receipt credits nothing and a later receipt for the same ticket supersedes it, newest by receipt order (RFC 6.2). A receipt whose `merged_sha` is not on `Main`'s first-parent line is `orphaned`: its unit is suspended, neither paid nor clawed back, until a later valid receipt for the task resolves it, and the detail says `rewritten` when its `base_sha` is still on the line and `missing` when not (RFC 4.5). `co_keepers` split the weight equally with the owner; each share is the floor in thousandths and the remainder goes to the owner, so the shares sum to the weight (RFC 6.3). **`third_party`** (RFC 6.2 trust note, 10; reading in Q-T051-6): a receipt is shown `third_party`, never rejected, when its `released_by` is not its `keeper_id`, or its commit identity is not the fixed `waggle <waggle@localhost>` one every `internal/comb` commit uses (`commitTree`, `internal/comb/git.go:655-673`), which marks a receipt written by other tooling. The unit detail also says whether `released_by` is a `gate.approvers` login (`maintainer: true`). A **relay** claim (T-065) is recognized from the `Waggle-Relay-Requester` and `Waggle-Relay-Approved-By` trailers on the released claim commit, the receipt's second parent, and its unit carries `relay: true`; a relay receipt released by its `keeper_id` is not `third_party` by the first rule. A receipt whose `pr_author` is set and differs from `keeper_id` marks the unit `fork_mismatch`, reported, not blocked (RFC 8 "Fork mismatch", RFC 10). These are display signals over self-asserted fields, not a defense (section 7). A unit with no valid receipt is `unattributed`. `nectar.exclude_keepers` drops listed ids from `keepers`; the report lists each excluded id and its weight (RFC 3.1).
7. **Reverts, trailer and merge forms** (RFC 5.1 items 1 and 3, 5.2). A commit whose body has `This reverts commit <sha>.` reverts the unit that SHA belongs to; `git revert -m 1` of a merge commit names the unit directly; a revert of a squash names its one commit. A revert commit is `kind: revert` with weight 0. A revert before maturity: the unit never matures, nothing is paid or clawed back. After maturity: a full clawback, no time limit (a revert at day 400 still removes the credit), capped at the unit's own weight, floor 0. The reverter is neither credited nor penalised.
8. **Revert of a revert** (RFC 4.4). Restores the original unit at its **original weight**, with `merged_at` set to the re-landing commit's committer time; it is pending until it matures again. A new task that re-adds the same lines is a new unit for its own owner, and the original stays clawed back unless its revert is itself reverted.
9. **Output rules** (RFC 3.3, 9.2). `matured` is the weight of a Keeper's shares in units that have matured, whether clawed back later or not; `clawed_back` is the weight removed by reverts after maturity; `pending` is the weight of shares not yet matured (and, from phase C, carried-forward daily-cap excess); `nectar = max(0, matured - clawed_back)`. `pending` is never part of `nectar`. Every number has exactly 3 decimals; keepers are sorted by `keeper_id` and every `keeper_id` with a share in any attributed unit appears, so absent means 0 (RFC 9.2); `units` counts those units, whatever their state. Units are sorted by `(merged_at, sha)`. No map iteration order reaches the output.
10. **Config** (RFC 3.1, 3.3, 8). `internal/config` parses an optional `nectar:` block with the five keys RFC-0005 names: `exclude_keepers` (default empty), `min_changed_lines` (default 0, off), `daily_cap` (default 12), `self_merge_factor` (default 0.5) and `reciprocity_discount` (default 0.5). Phase B uses `exclude_keepers`; phase C uses the rest. `self_merge_factor` and `reciprocity_discount` must be over 0 and at most 1 and `daily_cap` over 0, so no config value zeroes a unit (RFC 3.3 "Never 0", RFC 8 "no control zeroes a unit"). `docs_factor`, `survive_ratio`, the tier factors, the size cap and divisor, the 720h window and the 60% reciprocity threshold are rules-table constants, not keys; changing one is a `rules_version` bump (RFC 3.3, 7). An absent block means the defaults. The scorer reads the block from the `Input.Main` commit, not the worktree, so two clones agree. A build from before phase B ignores a well-formed `nectar:` block (an unknown top-level section, `internal/config/config.go:8-9`, `config_test.go:255`); from phase B on, an unknown key under it is a load error.

### 2.3 Phase C: survival, partial and manual reverts, gameability, cache (RFC 3.3 review factor, 4.2, 4.3, 4.5 doctor, 5.1 items 2, 3 rebase form and 4, 7 cache, 8)

1. **Survival rule 2** (RFC 4.2). At maturity, the share of the unit's added lines still present on `main`, by `git blame -w -M -C` at the newest first-parent commit at or before `matures_at`, honoring `.git-blame-ignore-revs` when present. At or above `survive_ratio` (0.5) the unit survives; below it the unit is `dropped`. A move or rename keeps its blame. Docs and hive lines count like any added line (RFC 4.2); lockfiles and generated files are not in the count, as in 3.3. `Waggle-Supersedes: T-<id>` on a later bound commit exempts the named unit from rule 2, not from rule 1. A pure-deletion task uses rule 1 only.
2. **Manual reverts** (RFC 5.1 item 2). A commit with no trailer whose reversed patch-id matches a credited commit's patch-id reverts it.
3. **Partial reverts** (RFC 4.3, 5.1 item 3). A revert whose inverse diff covers only some of a unit's hunks claws back in proportion to the share of weighted lines reverted, 3 decimals. In a rebase run, each reverted commit claws back its share by line.
4. **Unconfirmed reverts** (RFC 5.1 item 4). A `Revert "..."` subject with no SHA and no patch-id match is reported as `unconfirmed_revert` and changes no score. Who confirms one is RFC 11.3 question 4, not built here.
5. **Gameability controls** (RFC 3.3, 8). No control zeroes a unit, and every one is reported per unit.
   - **Self-merge, `review_factor`.** A unit is a self-merge when its valid receipt's `approvers` holds no login other than `keeper_id` (the RFC 8 row reads the other way; F7). In a **multi-Keeper repo**, where `gate.approvers` in the config at the unit's base has more than one login, a self-merge weighs `nectar.self_merge_factor` (0.5). In a single-Keeper repo (at most one login), a self-merge counts at full weight with no opt-in (RFC 8 "the default solo case"). A unit whose receipt is `incomplete` follows Q-T051-2.
   - **Daily cap with carry-forward.** Per Keeper share, at most `nectar.daily_cap` (12) of weight matures per UTC day of `matures_at`. Excess is carried forward, not dropped: it matures on the next days with spare room, in `(merged_at, sha)` order, never on a day after `now`'s UTC day, and counts as `pending` until then (RFC 8, 9.2). Total credit is unchanged, only delayed. A clawback of a unit whose weight was partly carried removes the carried part from `pending` first.
   - **Reciprocity.** For each Keeper pair, the share of the pair's units (both owners' units on `Input.Main`) approved by the other member. Over 60%, every unit of the pair weighs `nectar.reciprocity_discount` (0.5); at 60% exactly, full weight. Pairs are shown, not banned (RFC 8).
   - **Minimum size.** `nectar.min_changed_lines` defaults to 0 (off). When set, a unit under it weighs as a minimal unit (`size_factor` 1), reported, never 0 (F9).
6. **Cache** (RFC 7). `<git-common-dir>/waggle/nectar/<rules_version>.json`, resolved with `git rev-parse --git-common-dir` so worktrees share it; in a plain clone that is RFC 7's `.git/waggle/nectar/<rules_version>.json`. Local, never committed, never authoritative. It stores the last scored `main` SHA and per-unit facts derived from `main` history alone (units, line counts, factors, survival, revert links); it never stores attribution, review factors, first-seen times or anything else read from receipts, which is recomputed from `Input.Receipts` on every run, so a receipt appended later or a pinned older `Receipts` OID cannot meet a stale owner. A rescore reads only history after the cached SHA when that SHA is an ancestor of `Input.Main` (equal counts); otherwise, including a pinned `Main` older than the cached SHA, or when the file is unreadable, stale or of another `rules_version`, it is ignored for that run, and rewritten unless `Input.Main` is a strict ancestor of the cached SHA (a pinned older replay never moves the cache back). `Input.Recompute` ignores it. Deleting it never changes the result (section 8, C10).
7. **Doctor finding** (RFC 4.5). `waggle doctor` reports a warning finding when the default branch allows force-push (classic protection `allow_force_pushes`, or no ruleset blocking non-fast-forward), worded as "the reputation score can be rewritten". It is not a required finding and does not change the exit code.

### 2.4 Phase D: post-merge gate-run receipt (RFC 6.2 "Claims that expire or are never released", 11.1 T-051a)

Fork contributors and anyone whose claim expires rarely run `waggle release`, so without this phase their merges are mostly `unattributed` (T-065 F3 and HK-11). RFC 6.2 closes that gap with a receipt the gate Action writes on each push to `main`, which also covers direct merges by admins.

1. **`waggle nectar gate-receipt --before <sha> --after <sha> [--repo <dir>] [--json]`.** For each first-parent commit in `before..after` on `main` that binds to a task (the binding parser phase A already carries, section 3 step 2, so phase D does not wait on phase B), and for which no receipt names that commit as `merged_sha`, it writes one receipt with `source: gate_run`, `merge_proof: binding`, `status: merged`, `keeper_id`, `co_keepers: []`, `role`, `gate`, `branches` and `claimed_at` from the live claim ref when it still exists, the live claim commit as second parent, `base_sha` and `merged_at` from history, `released_by` the push event's actor (`github.actor`, passed in by the Action), and the forge fields read once by commit (the PR whose merge commit is that SHA, its author, head branch and approvals at its merged head), else `incomplete`. It does not release or change the claim. A commit with no live claim gets no receipt and stays `unattributed` (RFC 6.2 gap (a)). All receipts for one push go in one atomic append with the phase A retry when only the receipt head moved; a retry re-checks which commits already have a receipt, so a release that lands first wins and nothing is written twice.
2. **Action mode.** `gate/action.yml` gains an input (suggested `mode`, default `verify`) so the same pinned build runs `gate-receipt` with `before` and `after` from the `push` event. The `verify` path, its inputs and its exit codes do not change.
3. **Workflow template.** `waggle-gate.yml.tmpl` gains a job on `push` to the default branch with job-level `permissions: contents: write, pull-requests: read`, checkout of the pushed `main` only (never PR code), and the Action in `gate-receipt` mode. The PR job's triggers and `contents: read` do not change. Repos that do not want it delete the job; the gate's required check is unaffected either way.
4. **Docs.** The `docs/gate.md` receipts entry from phase A gains the gate-run writer, its token and its trigger; `docs/recipes/` notes that the post-merge job needs push rights to `refs/waggle/receipts/*`.

## 3. Finding the merged SHA and forge facts (phases A and D, RFC 6.2 "How `merged_sha` is found")

Today `branchMerged` (`release.go:184-230`) proves a merge only when the branch head is a second or later parent of a first-parent merge on `main`. It returns the branch name, not the merge commit. This repo squash-merges (the last five commits on `main` are squashes), so every hive release today runs with `--unmerged` and would record no merged SHA (F1, section 11).

The receipt fills `merged_sha` in RFC 6.2's order, and records the step in `merge_proof`:

1. `forge`: when `forge.provider` is `github` and the adapter has auth (`gh` or `GITHUB_TOKEN`, `github_transport.go:49-62`), the newest merged PR whose head branch is in the claim's `branches` (a `<owner>/<repo>:<branch>` entry looks up that fork head), when its merge commit is on `main`'s first-parent line. This one call also fills `pr_number`, `pr_author`, `head_branch` and `approvers`: every login whose latest review is `APPROVED` at the PR's merged head commit and not dismissed, read through `ReviewReader` (`reviews.go:127`). This is a record change: the gate reads only listed approvers (`docs/gate.md` section 6, D-233) and does not hold this list today (RFC 6.2).
2. `binding`: otherwise, offline, the first first-parent commit on `main` after the claim's `claimed_at` that binds to this task by the unit rule of section 2.2 items 2 and 3 (a merge commit binds through its non-merge commits), extended to the last commit of its rebase run. If a later, separate run also binds to the task, the candidates differ in PR and the step takes none (RFC 6.2 step 2). The parser is placed in `internal/dispatch` for phase A and copied into `internal/nectar` in phase B, or kept as one copy in `internal/comb` if the builder prefers, inside the phase A lease.
3. `merged_tip`: otherwise, the merge commit `branchMerged` found, which it now returns alongside the branch (internal change only).
4. `none`: otherwise `merged_sha: null` and `status: unmerged`. It credits nothing now, and a later receipt for the ticket may supersede it.

`base_sha` is the first parent on `main` of the unit's first commit and `merged_at` the committer time of `merged_sha` (RFC 6.2, 4.1). The forge fields are read once, here, and never again (RFC 6.2, 7). When step 1 cannot run (provider `none`, no auth, a network or API error), the forge fields stay null or empty and the receipt is `incomplete`; the scorer reports it, and the release succeeds with one warning. Phase D uses the same resolver with the PR looked up by commit instead of by head branch.

The release refusal rule does not change: without `--unmerged`, only a merge `branchMerged` proves passes, as today. Changing what `waggle release` accepts is out of scope (section 5).

## 6. Output shape guarantees (phase B, used by T-052 and T-054)

`Report` has three parts:

- **`Summary`**, the RFC 9.2 object and nothing else: `schema_version`, `rules_version`, `repo`, `main_sha`, `computed_at`, `keepers` (each `keeper_id`, `nectar`, `matured`, `pending`, `clawed_back`, `units`), `unattributed`, `orphaned`. `json.Marshal(report)` gives exactly these bytes (a `MarshalJSON` on `Report` returns the summary), so T-052's `--json` and T-054's Nectar source read the same bytes. Phase B pins them with a golden file in `internal/nectar/testdata/`.
- **`Counts`**, every rule that gave a unit less than full credit or none (RFC 1 "Nothing is excluded silently"): `unbound`, `unattributed`, `orphaned`, `unmerged`, `incomplete`, `third_party`, `fork_mismatch`, `direct_push`, `self_merge`, `carried` (units with carried-forward excess), `unconfirmed_revert`, `excluded` (each excluded `keeper_id` and its weight) and `reciprocal_pairs` (each pair and its share). Phase B fills the ones it builds; phase C adds the rest. Counts not yet built are 0.
- **`Units`**, one entry per unit and per revert commit, sorted by `(merged_at, sha)`: `task`, `kind` (`unit` or `revert`), `commits`, `merged_sha`, `base_sha`, `merged_at`, `first_seen`, `matures_at`, `state` (`pending`, `matured`, `clawed_back`, `dropped`, `orphaned`, `unbound`, `unattributed`), `keeper_id`, `co_keepers` with each share, `weight`, `factors` (`tier`, `size`, `review`, `changed_lines`, `code_lines`, `docs_lines`, `excluded_files`), `alive_ratio`, `clawed_back`, `carried`, the chosen receipt (`oid`, `source`, `status`, `merge_proof`, `incomplete`, `released_by`, `pr_number`, `pr_author`, `head_branch`, `approvers`), the flags `third_party`, `maintainer`, `relay`, `fork_mismatch`, `direct_push`, `self_merge`, `rewritten` or `missing` for an orphan, and `reasons`, a list of stable reason codes (for example `revert_before_maturity`, `alive_below_ratio`, `self_merge_multi_keeper`, `daily_cap_carry`), one per rule that applied.

`Report.Detail()` marshals `Counts` and `Units` under `detail_version: 1`; it is T-052's `explain` source and is not part of the RFC 9.2 contract T-054 reads. The replay contract covers all three parts: `Score` with the same `Repo`, `Main`, `Receipts`, rules version and `Now` gives the same bytes in any clone, whatever its live heads (section 2.2 item 1), which is what T-054 needs to pin `nectar_at`. Numbers in all three parts follow section 2.2 item 9.

## 7. Threat model (D-203)

**Boundary.** Who can write `refs/waggle/*` does not change (`docs/gate.md` L3). The receipt ref adds a new record that any such writer can append to, rewind or delete (RFC 6.2 trust note). The scorer reads it for credit; phase D's job reads it only to skip commits that already have a receipt. Forge fields are what the forge said once, at write time, as read by whoever wrote the receipt.

**What is defended.** A forged receipt credits nothing unless its `merged_sha` is a credited merge of its own task on `main` and its `head_branch`, when set, is in its `branches` (section 2.2 item 6); a receipt not on `main` is `orphaned` and suspended. A receipt released by someone other than its `keeper_id`, or written by other tooling, is shown `third_party`. A rewound receipt head fails the non-forced fetch and is reported (section 2.1 item 3). A self-added co-keeper is not possible through `waggle release`, which only the owner can run (owner check in `ReleaseLease`). A hand-written receipt that adds one, or that lists approvers who never approved, shows as `third_party` only when it states a `released_by` other than `keeper_id` or carries a commit identity other than the fixed `waggle` one; a writer who copies both passes unflagged, since the git author of every Waggle commit is the same fixed identity (`git.go:655-673`) and proves nothing (note, not must-fix; signed receipts would close it with team mode's signing seam). Self-merge and reciprocity controls trust `approvers` for the same reason. The phase D job holds a `contents: write` token on pushes to `main`, runs only the pinned Action on the pushed `main` (never PR code) and appends receipts only from live claim refs, so it credits nothing a claim writer could not already claim through `waggle release`.

**What is not defended (note, not must-fix).** A writer with push rights who deletes the receipt ref on the remote loses attribution for clones that fetch afterwards; clones that already hold receipts keep them and report the rewind. A protected-ref rule on `refs/waggle/receipts/**`, where the forge plan allows it, is the mitigation (section 12, item 6). A direct push to `main` that skips the gate can bind any task subject; the gate's L2 and L6 already cover that, the direct-push window rule delays it (RFC 4.1, weak by RFC 8's own account) and RFC 4.5's doctor warning covers force-push. Splitting one person's work across several `keeper_id`s raises their Quorum weight under `sqrt` (F6); Nectar has no control that removes that gain, and Quorum's alias merge is the answer (RFC-0006 7).

**Must-fix:** a release that deletes the claim without writing the receipt, or writes the receipt and keeps the claim, in either mode; a release that fails because the forge is unreachable; a receipt that rewrites or reorders an earlier one; backfill that writes without `--apply`; any change to the claim contract, the gate or the force-release path; `Score` reading the wall clock, the network, the worktree config, map order or a live ref head instead of `Input.Main` and `Input.Receipts`; a float reaching the output, a number in exponent form or without exactly 3 decimals; a phase D job that checks out or runs PR code, changes the PR job's permissions, or writes a receipt for a commit that already has one; output that differs across clones or across cache states; `pending` inside `nectar`; a negative `nectar`; a clawback above a unit's weight; a control or config value that zeroes a unit; a daily cap that drops excess instead of carrying it; docs or hive-only units at weight 0; a revert that credits or penalises the reverter; a co-keeper list over 4 or with the owner in it; co-keeper shares that do not sum to the weight; a help or error line that fails the plain-terms check; files outside the phase lease; any em or en dash added.

## 8. Test plan (RFC 11.2)

Fixture repos are built with `git` in `t.TempDir()`, with fixed author and committer dates through `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE`, and a fixed `Now`. Forge answers come from an `httptest` server. No test reads the wall clock or reaches the network. Each case is a named subtest.

**Phase A**

- A1: release of a merge-commit task with a fixture forge that reports the PR writes one receipt with `merge_proof: forge`, the merge SHA, `merged_at` its committer time, `base_sha` its first parent, `pr_number`, `pr_author`, `head_branch`, `approvers` (a login whose latest review is APPROVED at the merged head; a dismissed approval and an approval at an older head are left out), `status: merged`, `incomplete: false`, second parent the released claim OID; the claim ref is gone.
- A2: release with `--unmerged` after a squash bound to the task: with the forge, `merge_proof: forge`; with provider `none`, `merge_proof: binding`, the squash SHA and `incomplete: true`; two separate bound runs after `claimed_at` give `none`; no bound commit gives `none`, `merged_sha: null`, `status: unmerged`. A plain merge with the forge down gives `merged_tip` when no earlier step finds it (RFC 6.2 order).
- A3: a forge error (HTTP 500, timeout) during release still releases, writes an `incomplete` receipt and prints one warning; exit code unchanged.
- A4: atomicity, local and remote: an injected CAS loss on the claim (the `hookBeforeWrite` seam `ForceRelease` uses, `force.go:320-321`, called by the new method too) leaves both refs unmoved; a concurrent receipt append retries and both receipts land in order.
- A5: refusals unchanged: not merged, not owner, busy worktree, no claim (`no_claim`, no receipt) give today's codes and write no receipt.
- A6: `--co`: one, four, five (usage error), duplicate, owner listed (usage error); shares recorded in the receipt.
- A7: a rewound remote receipt head fails the fetch with `receipts rewound` and changes no local ref.
- A8: backfill dry-run writes nothing; `--apply` appends receipts for live merged claims, for audit-chain claims and for a `DECISIONS.md`-only task (owner per Q-T051-4), each `source: backfill`; a second `--apply` appends nothing; unnamed tasks are listed `unattributed`.
- A9: receipt validation rejects a bad `keeper_id`, a bad approver login, a short SHA and over 32 approvers.
- A10: `release -h` and `nectar backfill -h` pass `checkPlain`.

**Phase B**

- B1: binding parity: a shared table of subjects and trailers, including a subject and trailer that conflict and a `Head Keeper: ` subject, gives the same tasks through the gate parser and the `internal/nectar` copy.
- B2: squash, merge and rebase merges of one task each give one unit; a task in two PRs is one unit completed by the later; a commit bound only through a receipt's `head_branch` binds.
- B3: no binding, a maintainer commit and a commit with no receipt-supplied branch give `unbound`; a bot commit under a Keeper's claim credits that Keeper; a bot `keeper_id` in `exclude_keepers` is dropped and listed with its weight; a docs-only unit and a hive-only unit earn credit at `docs_factor` 0.5.
- B4: weight: tier from the config at the unit's base (a `protected_paths` entry added later does not change an older unit); `size_factor` golden for all 801 half-line values; a 1,000-line unit caps at 400; lockfile and `linguist-generated` lines are left out and listed; `light` and `full` weigh the same; a pure-deletion unit has `size_factor` 1.
- B5: window: `Now` at `start + 720h - 1s` is pending, at `+720h` matured; a committer clock that moves back between first-parent commits does not reorder units; a direct push (no receipt with `pr_number`) starts at the later of `merged_at` and first-seen; an `incomplete` receipt delays and never removes.
- B6: full trailer revert before maturity (never pays), after maturity (clawback), at day 400 (clawback), `-m 1` revert of a merge commit; floor 0; cap at unit weight; the reverter's own score is unchanged.
- B7: revert then revert of the revert: unit restored at original weight, window restarted from the re-landing commit; a new task re-adding the lines is a new unit and the original stays clawed back.
- B8: force-push orphan: a receipt whose `merged_sha` left `main` suspends the unit, counts `orphaned`, says `rewritten` or `missing` by `base_sha`, and a later valid receipt resolves it.
- B9: takeover owner (receipt names the later owner), `co_keepers` equal split summing to the weight (three shares of 1.000), fork contributor receipt (`released_by` a maintainer) flagged `third_party` with `maintainer: true` and credited to `keeper_id`; a receipt committed with an identity other than `waggle <waggle@localhost>` flagged `third_party`; a relay claim (fixture `Waggle-Relay-*` trailers on the second parent) released by its `keeper_id` not flagged and marked `relay: true`; a `pr_author` other than `keeper_id` marks `fork_mismatch`; a `release` and a `gate_run` receipt for the same merge credit the `release` one; an `unmerged` receipt superseded by a later merged one.
- B10: a receipt whose `merged_sha` is not on `main`, or whose `head_branch` is not in its `branches`, or whose `ticket_id` differs, is not valid attribution.
- B11: determinism: the same fixture scored with receipts and commits read in shuffled order gives byte-identical JSON. Pinned replay: score at `Main` = M1 and `Receipts` = R1, then land a commit on `main`, append a receipt and move both live heads; scoring again at M1 and R1 with the same `Repo` and `Now` gives byte-identical JSON, in the same clone and in a second clone that has the later heads; `main_sha` is M1, `repo` is `Input.Repo` and `computed_at` is `Now`. An unknown `Main` OID and a `Receipts` OID that is not a receipt commit are errors naming the OID; the zero `Receipts` OID scores with no receipts.
- B12: Quorum shape: golden file; `json.Marshal(report)` has exactly the 9.2 fields; `nectar` non-negative and finite; `pending` excluded; keepers sorted, a Keeper with only pending units present with `nectar` `0.000`; every non-integer number matches `^[0-9]+\.[0-9]{3}$`, including a fixture whose values are large (over 1e6) and small (0.001). `Report.Detail()` golden with every count and unit field.
- B13: config: an unknown key under `nectar:` is a load error with its line, as other blocks are; `self_merge_factor: 0`, `reciprocity_discount: 0` and `daily_cap: 0` are load errors; an absent block gives the defaults; the scorer reads the block from `Input.Main`, not the worktree.

**Phase C**

- C1: a later task rewrites over 50% of a unit's lines within 30 days: dropped; exactly 50% alive: kept; a move, a rename and a whitespace reformat: kept; a rev in `.git-blame-ignore-revs`: ignored; docs and hive lines count in the ratio.
- C2: `Waggle-Supersedes: T-<id>` exempts the earlier unit from rule 2 but not from a revert.
- C3: a manual revert by patch-id; a partial revert of 30% of weighted lines claws back 0.3 of the weight; a rebase-run revert of one commit claws back its share by line.
- C4: `Revert "..."` with no SHA is `unconfirmed_revert` and changes nothing.
- C5: daily cap: 20 units maturing on one UTC day give 12 matured that day and the rest pending, maturing on the next days with room in `(merged_at, sha)` order; total credit after enough days equals the uncapped total; nothing carries onto a day after `now`; a clawback of a partly carried unit removes the carried part from pending first.
- C6: self-merge: in a fixture with two `gate.approvers`, approvals only by `keeper_id` or none give half weight, an approval by another login gives full; with one `gate.approvers` login, a self-merge gives full weight; an `incomplete` receipt follows Q-T051-2.
- C7: reciprocal pair over 60% weighs 50%; at 60% exactly, full weight; the pair is listed.
- C8: `min_changed_lines: 5`: a 3-line unit weighs as a minimal unit, not 0; default 0 changes nothing.
- C9: pure-deletion task: rule 1 only, minimal weight.
- C10: cache: cold, warm, deleted, corrupt, other `rules_version`, and a `main` that no longer contains the cached SHA all give byte-identical JSON; `Recompute` gives the same. A warm cache built at a later `main` and later receipts, then a pinned replay at older `Main` and `Receipts` OIDs, gives the same bytes as a cold run at those OIDs and leaves the cache file unchanged.

## 11. Findings and questions for the ruling

These came up reading the code against RFC-0005. F1 to F5 are earlier findings, updated; F6 to F9 are RFC wording defects for the Head Keeper; the questions each carry a recommendation the Head Keeper may adopt.

- **F1: release cannot prove a squash merge today.** `branchMerged` only recognizes a merge commit (`release.go:184-230`), and this repo squash-merges. The accepted RFC 6.2 now says so and adds the forge-first resolver; section 3 builds it in RFC order and records the step in `merge_proof`, without changing the release refusal rule. Resolved by the accepted text.
- **F2: approvals are not in git.** RFC 8's self-merge and reciprocity controls need who approved each PR, and RFC 7 forbids network in the scorer. The accepted RFC 6.2 answers it: `approvers` is read from the forge once, at receipt write, and `incomplete` marks a receipt written without it. Built in section 3; what the scorer does with an `incomplete` receipt is Q-T051-2.
- **F3: tier factor is almost always 1.** By the gate's path rules nearly all leasable product code is Tier 0 (`backend.go:72-85`). Tier 3 paths (`backend.go:31-41`: `.waggle/`, `.github/workflows/`, `go.mod` and the other dependency inputs) cannot be leased and reach `main` only through an admin merge, and Tier 2 is `.waggle/hive/`, `CLAUDE.md` and `AGENTS.md` (`:51-55`). Since hive-only units now earn credit at the docs factor (RFC 3.1, 3.3), a records batch weighs `3 * size_factor(0.5 * lines)`, more than most product tasks of the same size. So RFC 3.3's tier factor mostly varies with repo-listed `protected_paths` and rewards hive edits. Phase B builds it as accepted; the tuning pass (section 12 item 9) may want a content tier source instead (for example a `Waggle-Tier:` trailer the gate validates, if one is added later). Not a blocker.
- **F4: the receipt commit author proves nothing.** Every commit `internal/comb` writes, claim, audit and so receipt, uses the fixed `waggle <waggle@localhost>` identity (`git.go:655-673`), so an author test could never fire, and relay writes (T-065 F2) look like owner writes. Section 2.2 item 6 flags on `released_by` and on a non-`waggle` identity, and recognizes relay claims from their trailers on the receipt's second parent. Signed receipts, through team mode's signing seam, would make the writer provable; that is a follow-up candidate, not in this ticket.
- **F5: the post-merge gate-run receipt.** RFC 6.2 and 11.1 put a `source: "gate_run"` receipt written on push to `main` in T-051a; it is phase D (section 2.4), with forge fields read by commit.
- **F6 (Head Keeper): RFC 8 says identity splitting loses weight; under `sqrt` it gains.** RFC-0005 line 230 (RFC 8, Sybil row): "Quorum weight is `sqrt(Nectar)` (T-053), so splitting loses weight." `sqrt` is concave, so the reverse holds: Nectar 400 as one id weighs 20, as four ids of 100 it weighs 40. RFC-0006 7 (`docs/RFC-0006-quorum.md:188`) already says so and answers it with alias merge. Nectar adds a second gain: the daily cap (RFC 8) is per `keeper_id`, so split ids also share a higher combined rate. **Recommended RFC wording** for the Sybil row: "Per `keeper_id`; a new id starts at 0, and Nectar never transfers. Quorum weight is `sqrt(Nectar)` (T-053), which is concave, so splitting one person's Nectar across several ids raises their total weight, and each id has its own daily cap. The controls make splitting costly and visible, not unprofitable: each id earns its own units through claims, review and the 30-day window; claims need push rights or a maintainer; and Quorum's alias merge sums one person's ids before `sqrt` (RFC-0006 section 7)." The brief needs no change for this: Nectar is per `keeper_id` either way.
- **F7 (Head Keeper): the RFC 8 self-merge row is inverted.** RFC-0005 line 226 says the factor applies when "The `approvers` list (6.2) has no login equal to `keeper_id`". Read literally, a PR approved by another Keeper is halved and one approved only by its owner is not; GitHub does not let a PR author approve their own PR, so in a multi-Keeper repo almost every reviewed unit would be halved. RFC 3.3 ("for a self-merge") and RFC 11.3 question 7 show the intent. **Recommended RFC wording:** "The `approvers` list (6.2) has no login other than `keeper_id`, and the repo has more than one Keeper: weight is multiplied by `nectar.self_merge_factor` (0.5), reported." Section 2.3 item 5 builds this reading.
- **F8 (Head Keeper): the stated `size_factor` range is wrong.** RFC-0005 line 68 says "Range 1 to 5.17". The formula gives `1 + log2(17) = 5.087` at the 400-line cap. **Recommended RFC wording:** "Range 1 to 5.087." The brief follows the formula.
- **F9 (Head Keeper): `third_party` and `min_changed_lines` are stated two ways.** RFC 6.2's trust note (line 191) flags a receipt "written by someone other than `keeper_id` or a listed maintainer", which exempts maintainers, while RFC 10 (line 276) says "`third_party` flags the maintainer write" for a fork contributor. Q-T051-6 asks which. Separately, RFC 8 says "no control zeroes a unit" but does not say what `nectar.min_changed_lines` does when set; the brief makes a unit under it weigh as a minimal unit (`size_factor` 1), never 0. **Recommended RFC wording** for RFC 8's farming row: "`nectar.min_changed_lines` defaults to 0 (off); when set, a smaller unit weighs as a minimal unit."
- **F10: the RFC header still says not ruled.** At `f1e0908` the RFC banner (line 4) says "The decision in 'Decision requested' is not recorded" and the status (line 6) says "Proposed. ... Not ruled", while line 331 records the acceptance. The "fix" in "Accepted pending fix" is not named anywhere, and `DECISIONS.md` has no T-050 ruling entry. Section 12 item 1.
- **Q-T051-1: receipt fields beyond the RFC 6.2 example.** RFC 6.2 names `status: "unmerged"` and an `incomplete` mark in prose but not in its JSON example, and has no field for which resolver step found `merged_sha`. (a) Receipt version 1 adds `status` (`merged` or `unmerged`), `incomplete` (bool; a receipt can be both unmerged and incomplete, so they are separate fields) and `merge_proof` (`forge`, `binding`, `merged_tip`, `none`). (b) Add only `status` and `incomplete`, and bump to version 2 if the step is wanted later. **Recommended: (a).** A version bump later leaves early receipts without the field forever, and `explain` (T-052) uses `merge_proof` to say why a merge was found. Neither option changes any RFC field. The earlier draft's `approved_by` is gone: RFC 6.2's `approvers` replaces it.
- **Q-T051-2: how the scorer weighs a unit whose receipt is `incomplete`.** RFC 6.2 marks it and RFC 8 does not say how self-merge treats an unknown approver list. (a) Approval unknown: `review_factor` 1, counted under `incomplete` and listed. (b) Treat it as a self-merge in a multi-Keeper repo (`self_merge_factor`). (c) Suspend the unit until a later receipt has the forge fields. **Recommended: (a).** It does not punish offline releases or forge outages, and the report shows every such unit; (b) halves every receipt written without a token; (c) leaves units unpaid with no way to fill them, since forge data missing at write time cannot be recovered offline (RFC 6.2 gap (c)). The direct-push window rule (section 2.2 item 5) already delays an `incomplete` unit.

(a) Credit the owner of the valid receipt for the completing commit, else the newest valid receipt. (b) Split by each receipt's share of the task's changed lines. **Recommended: (a).** It matches RFC 6.3 ("Credit follows the owner when the PR merged") for the completing merge and stays simple; (b) is a later rules version if needed.
- **Q-T051-4: how a `DECISIONS.md` reference names an owner (RFC 6.2 Backfill, RFC 11.3 question 8).** The accepted RFC 6.2 lists `DECISIONS.md` references as a backfill source, and the brief builds it. (c) A `DECISIONS.md` reference is evidence only, never an owner. **Recommended: (a).** It builds the source as accepted, keeps an explicit human choice for an owner the file cannot state, and works for multi-Keeper repos; (b) silently assumes ownership; (c) narrows RFC 6.2's source list and would be **CUT? needs Head Keeper typed reason**. How far back backfill reaches (the rest of question 8): every task with a credited merge on `main`, no cutoff.
- **Q-T051-5: how the gate-run receipt runs (phase D).** (a) A second job in the gate workflow on `push` to the default branch, same pinned Action in a `gate-receipt` mode, job-level `contents: write` and `pull-requests: read`, checkout of the pushed `main` only. (b) A `workflow_run` job after the gate workflow completes. (c) No workflow change; the subcommand only, run by each repo as it likes. **Recommended: (a).** It is what RFC 6.2 describes ("The gate action, on a push to `main`"), runs no PR code, needs no second workflow and keeps one pinned build; (b) adds a trigger that is easy to misconfigure into running with PR context; (c) leaves most repos without the receipt, which is the gap HK-11 names. Under (a) the job's token can push any unprotected ref, as T-065 HK-2 notes for the relay token; item 6's ruleset on `refs/waggle/receipts/**` should allow appends from the Actions identity and block deletion and non-fast-forward.
- **Q-T051-6: when a receipt is `third_party` (F9).** (a) When `released_by` is not `keeper_id`, maintainers included, with `maintainer: true` in the detail when `released_by` is a `gate.approvers` login (RFC 10's reading). (b) Only when `released_by` is neither `keeper_id` nor a `gate.approvers` login (RFC 6.2's reading). Either way a non-`waggle` commit identity also flags. **Recommended: (a).** The flag is shown, never rejects, so over-flagging costs a line while under-flagging hides a maintainer crediting someone else; `maintainer: true` keeps the common fork case readable. Under (a), every `gate_run` receipt where a maintainer merged a contributor's PR shows `third_party`.

## 1. Goal

Make `waggle doctor` say which enforcement the forge can hold, and whether a `hold` hive is ready. Today `doctor` asks one thing: is `verify-leases-and-tiers` a required check (`probe_github.go:163-180`). On a private repo of a free plan the rules read answers 403 with an upgrade message (`T-047.md` Step 1 row), so `required-gate` comes back `unknown (GitHub answered 403)`, `doctor` exits 1, and nothing tells the Head Keeper that no setting can fix it. With `hold` merged (T-113), there is now a mode for exactly that forge. This ticket adds:

1. **A capability finding.** Probe what the forge can do, never the plan name (an org plan is readable only by org owners, RFC 5.5): `required_check`, `none` or `unknown`.
2. **A mode fit finding.** Recommend `guard` where a required check is possible, flag a `hold` hive that could be stronger, recommend `hold` where none is possible. Never change the mode (D-382).
3. **The `hold` parts.** Merge identity, audit workflow present and pinned, audit refs pushable, Write-holder count, last breach. Only the last-named count can ship now; the rest need code that T-114 and T-115 define (section 3).

## 2. Scope

1. **Capability probe (forge package).** `Probe` reads `private` from the repo answer it already fetches. A new `capability` decision, taken after `readRules`:
   - rules read returned 2xx: `required_check`;
   - rules read returned 403, the repo is `private`, and the answer's message holds the word `upgrade` (case insensitive): `none`. This is the 403 noted in `T-047.md`. The classic protection read is not tried, since it answers 403 for the same plan reason and the existing code already falls through to it only when the rules read succeeded (`probe_github.go:58-63`);
   - any other outcome (a 403 on a public repo, a 403 with no upgrade word, a 404, a transport failure, a body over the cap, more than 10 pages): `unknown`.
   The message text is read only to find the word; it is never printed (`failWhy`, `probe_github.go:21-32`).
2. **Capability finding.** Not `Required`, so it cannot change the exit code. Exact lines in section 4.
3. **Write-holder count.** One read of `GET /repos/{o}/{r}/collaborators?per_page=100&page=N`, at most 5 pages. It counts entries whose `permissions.push` is true (this includes maintain and admin and is true for owners). It prints a number, never a login. A 403 or 404 (the token cannot list collaborators) is `unknown`, with the words "needs push access to list who can write". Not `Required`. Cut candidate (section 9).
4. **Mode fit (cmd package).** `modeFit(mode, capability string) forge.Finding`, a pure function, nine cases (three modes against three capabilities), exact lines in section 4. It runs when `Report.Capability` is not empty, which means the GitHub forge. The none forge and the local-only path print nothing new.
5. **Hold skip (Q-T116-2).** On `hold` with capability `none`, `required-gate` and `up-to-date` cannot be met by any setting, so `doctor` rewrites them to `skipped` with `Not used: gate.mode is hold and this repo cannot require a check.` and `Required` false. Everything else keeps its exit behavior. The rewrite is in `doctor_hold.go`, after the probe, so `probe_github.go` keeps reporting the raw facts.
6. **`hold` part probes (phase `t-116b`).** See section 3. Each is one finding, `Required` false in `t-116` terms; Q-T116-5 asks whether they become required on a `hold` hive.
7. **Never change anything.** No mode write, no ruleset write, no workflow write, no new ref. The only writes `doctor` makes stay the two `refs/waggle/probe/` refs of `claim-refs`, behind `--no-write`.
8. **Docs.** `docs/gate.md` section 12 and `docs/troubleshooting.md`, as listed in the lease justification. No new section.

## 4. Exact `waggle doctor` output

Findings render through `forge.Render` (`report.go:79-119`): `  <status> <id> <summary>` with the id padded to 15 columns, then `Not enforced:` and `Fix:` continuation lines for a `missing` or `unknown` finding, folded at 99 columns. New findings go after the existing four (`claim-refs`, `required-gate`, `up-to-date`, `force-push`), in this order: `capability`, `write-holders`, `mode-fit`. `Probe` (forge package) appends `capability` then `write-holders`; `doctor.go` appends `mode-fit` after `Probe` returns, since `modeFit` needs `gate.mode`. All are `Required` false. A `missing` or `unknown` one prints in the `Not enforced on this repo` list like `force-push` does. `{mode}` is the value of `gate.mode`.

**`capability`** (always, GitHub forge):

- `ok`: `Forge capability: required_check. GitHub lets a rule require the gate check on {branch}.`
- `ok`: `Forge capability: none. GitHub offers no required check on this private repo (rules answered 403 with an upgrade message).`
- `unknown`: `Forge capability: unknown. Could not tell whether a rule can require a check ({why}).`
  Not enforced: `this run could not tell whether a required check is possible here, so it cannot say which mode fits.` Fix: `run waggle doctor with a token that can read branch rules, or check the repo settings by hand.` `{why}` is `failWhy` text (`GitHub answered 403`, `the request failed`, and so on), or `a 403 that is not an upgrade answer`.

**`mode-fit`** (when `capability` is not empty; printed after `write-holders`). Rows are capability by mode:

| Capability | Mode | Status and summary | Not enforced / Fix |
| :--- | :--- | :--- | :--- |
| `required_check` | `guard` | `ok`: `gate.mode guard fits: a rule can require the gate check here.` | none |
| `required_check` | `hold` | `missing`: `gate.mode hold works, but a stronger mode is available: this repo can require the gate check.` | Not enforced: `a manual merge click lands first and is detected after, where a required check would block it.` Fix: `ask the Head Keeper to move gate.mode to guard and add a ruleset that requires verify-leases-and-tiers. waggle doctor never changes the mode.` |
| `required_check` | `open` | `ok`: `gate.mode open is the staging mode. guard is available here when you are ready.` | none |
| `none` | `hold` | `ok`: `gate.mode hold fits: no rule can require a check here, so waggle merge holds the merge.` | none (`t-116b` adds the part findings) |
| `none` | `guard` | `missing`: `gate.mode guard cannot be enforced here: no rule can require the gate check. Recommended: hold.` | Not enforced: `a pull request can merge without the gate passing.` Fix: `ask the Head Keeper to consider gate.mode hold. waggle merge and the audit workflow are not in this build yet. waggle doctor never changes the mode.` |
| `none` | `open` | `missing`: `gate.mode open records findings and holds nothing, and no rule can require a check here. Recommended: hold.` | Not enforced: `a pull request can merge whatever the gate finds.` Fix: as the row above. |
| `unknown` | any | `unknown`: `Could not tell which mode fits (capability unknown).` | Not enforced: `this run cannot say whether gate.mode {mode} can be enforced.` Fix: `fix the capability line above, then run waggle doctor again.` |

**`write-holders`** (cut candidate):

- `ok`: `{n} people can write to the repository (count only; see the write access pattern in the gate spec).` With `n` of 1: `1 person can write ...`.
- `unknown`: `Could not count who can write (needs push access to list collaborators).` Not enforced: `this run cannot say how many people could merge by hand.` Fix: `run waggle doctor with a token that can list collaborators.`

**Hold skip** (hold with capability `none`): `required-gate` prints as `skipped  required-gate   Not used: gate.mode is hold and this repo cannot require a check.` and `up-to-date` the same. The `Enforcement:` header line (`report.go:55-73`) says `advisory (required-gate is skipped)` today for a skipped finding. Under Q-T116-3 (a) `t-116` prints that line unchanged; under (c), the recommended ruling, it prints `Enforcement: advisory (hold parts not checked)` on a `hold` hive with capability `none`; under (b) it would print `held` only once `t-116b` can check every part, so `t-116` prints (c)'s line until then.

**Phase `t-116b` lines** (only when `gate.mode` is `hold`; on other modes they are not printed):

- `merge-identity`: `ok`: `A merge identity is configured: {kind}.` / `missing`: `No merge identity is configured for waggle merge.` Not enforced: `no account can merge through waggle merge, so agents have no allowed way to land a change.` Fix: set per T-114 (a GitHub App, or the documented bot account).
- `audit-workflow`: `ok`: `The audit workflow is present at the base commit and pinned to a commit.` / `missing`: `The audit workflow is missing at the base commit.` or `... is not pinned to a commit.` Not enforced: `a merge by hand would not be detected.` Fix: `run waggle upgrade --apply and merge the PR it opens.` (T-115 may change this text.)
- `audit-refs`: `ok`: `Pushes to refs/waggle/audit/* on {remote} work.` / `missing`: `This remote does not accept pushes to refs/waggle/audit/*.` Not enforced: `merge records and breaches cannot be written, so the audit has nothing to compare.`
- `last-breach`: `ok`: `No breach is recorded in the fetched refs/waggle/audit/breaches.` / `ok`: `Last breach recorded {date}: {commit12}.` / `skipped`: `refs/waggle/audit/breaches is not fetched here; run git fetch {remote} refs/waggle/audit/*:refs/waggle/audit/*.`

Exit code: unchanged (0 when every required finding is ok or skipped, 1 when one is missing or unknown, 2 usage, 3 unreadable config, forge or default branch). Q-T116-5 asks whether `hold` readiness findings become required.

## 5. Flow, end to end

1. A Head Keeper runs `waggle doctor` in a hive on a free plan, private repo, `gate.mode: guard`.
2. Before: `required-gate unknown (GitHub answered 403)`, `up-to-date unknown`, exit 1. Nothing says no setting can fix it.
3. After: `capability` reads `none`; `mode-fit` reads `missing ... guard cannot be enforced here ... Recommended: hold.`; `required-gate` and `up-to-date` still print their raw `unknown`, since the mode is `guard` and the truthful result is that `guard` binds nothing. Exit stays 1.
4. The Head Keeper moves the mode (a Tier 3 change, D-382) after the pin carries T-114 and T-115. Now `gate.mode: hold`, capability `none`: `mode-fit ok`, `required-gate` and `up-to-date` print `skipped`, exit 0 if `claim-refs` is ok (Q-T116-2 option (c)).
5. On a Team plan with `hold` set early: `capability required_check`, `mode-fit missing ... a stronger mode is available`, exit unchanged (never required).

## 8. Test plan

## 10. Threat model (D-203)

**Boundary.** `doctor` runs on the operator's machine with the operator's forge credentials (`gh` login or `GITHUB_TOKEN`, D-061). Its inputs are GitHub's API answers and the local config and clone. Contributors and agents do not control those: rulesets, collaborators and `private` are set by repo admins. It prints advice and writes nothing new.

**Defended.**
- *A wrong `none` steers the Head Keeper to a weaker mode.* `none` needs `private` true, a 403 and the upgrade word together (C2, C3). Anything else is `unknown`, which recommends nothing. Even a wrong `none` only prints advice; the mode change is Tier 3 (D-382) and needs the Head Keeper.
- *A hold skip hides a real gap.* The skip applies only to `hold` with capability `none`, where no setting could make those two findings ok. On `guard` they stay raw (M3). A `hold` hive that loses its capability to a changed plan is flagged by `mode-fit` going `required_check` next run.
- *Leaks.* GitHub's message text, tokens and logins are never printed (C6, W1). The transport already redacts the token from `apiError` messages (`github_transport.go:187-190`). Write holders are a count.
- *Hostile or huge answers.* The body cap (`maxBody`), the 10 page rules cap and a 5 page collaborator cap bound every read (C5, W2). A failed read is `unknown`, never a crash and never `ok`.
- *Timeouts.* The existing `doctorTimeout` of 2 minutes covers the new calls.

**Notes, not must-fix (D-203).** An attacker who can forge GitHub's TLS answers, edit the local config or the `doctor` binary, or already holds repo admin can do more damage directly. A writer who edits the audit workflow on main (`t-116b`) is L3 and RFC 5.6: `doctor` reads the base commit, so it reports the change after the fact, it does not prevent it. `write-holders` counts users GitHub lists; teams, apps and org owners may be counted differently (section 11).

## 13. Open questions

- **Q-T116-1: What does `doctor` say to a hive that sets `hold` where `guard` is possible?** (RFC open question 6, ruled "yes, `hold` only where `guard` is impossible" under D-389.)
  Options: (a) flag it as `missing mode-fit` ("a stronger mode is available") with the Fix naming `guard`, never required, exit unchanged. (b) Print it as `ok` with an informational note, so a Team plan user who wants Waggle-owned merges is not nagged. (c) Treat it as required, so `doctor` exits 1 on `hold` where `guard` is possible, enforcing open question 6 as a rule.
  Recommended: (a). It is the RFC text ("flag a `hold` hive that could be stronger") and narrows nothing. (c) would make `hold` a CUT of core item 2 for that hive, which open question 6 reserves for a Head Keeper typed reason.

- **Q-T116-2: On a `hold` hive that cannot hold a required check, how does `doctor` treat `required-gate` and `up-to-date`, and what exits 1?**
  Options: (a) leave them as they are: a `hold` hive on a free private repo keeps exiting 1 forever on two findings it can never fix. (b) On `hold`, always `skipped`, for either capability. (c) On `hold` with capability `none` only, `skipped` with a fixed reason; on `required_check` they stay raw, and `mode-fit` flags the stronger mode.
  Recommended: (c). (a) makes the first `hold` pilot fail its own `doctor`. (b) hides that a Team plan could have held the check. Whether the `hold` part findings become required is a separate ruling (Q-T116-5), so this one does not decide it.

- **Q-T116-3: Does the `Enforcement:` header line change for a `hold` hive?**
  Options: (a) no: it keeps reading `advisory (required-gate is skipped)` on a `hold` hive, which is false (the merge is held by Waggle). (b) it reads `held` when the mode is `hold`, capability is `none` and, in `t-116b`, every part finding is ok; else the first part not ok. (c) it reads `advisory (hold parts not checked)` until `t-116b`, then (b).
  Recommended: (c). It changes `Render` text in `report.go` (a line some docs and tests may quote; the build greps `Enforcement:` in `docs/` and `cmd/waggle` tests and lists every hit), and it does not claim `held` before the parts that make it true can be checked. (a) is the do-nothing option and leaves a misleading word on the pilot's first `doctor` run.

- **Q-T116-4: Sequencing of the dependent probes.**
  Options: (a) split: `t-116` now (capability, mode fit, hold skip, write holders), `t-116b` after T-115 merges (merge identity, audit workflow, audit refs, last breach). (b) one build after T-115, one branch, no phase A. (c) `t-116` now with the four dependent lines present as `skipped` and the words `not in this build`, so the output shape does not change later.
  Recommended: (a). The pilots need the capability line now (RFC open question 11 puts `hold` second), and T-114 and T-115 define the facts the dependent probes read. (c) prints four lines that can only say "not built", which is noise for pilots and a stale doc risk.

- **Q-T116-7: How is an upgrade answer recognized?**

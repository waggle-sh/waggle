## 1. Goal

Two gate features from D-229 and D-233, for users of the gate in any repo:

1. **Named approver.** Today a change to a repo-listed protected path (`gate.protected_paths`, T-031) fails `tiers` (`protected path (listed in .waggle/control/config.yaml); needs an admin bypass to merge`) and, because G2 refuses any lease that covers a listed path (T-032, D-243), also fails `leases` with `path is outside the claim directories`. The only way through is an admin bypass. After this ticket the same change passes when a GitHub account listed in the base config's `gate.approvers` has an approving review on the PR at exactly the head SHA being gated (D-233), submitted after the PR's last base change (Q-T035-7 (a)). With no approval, no list, no token or any lookup failure, it fails exactly as today, and the admin bypass stays.
2. **Intent Packet trailers.** D-017 puts ticket, risk tier and verdict trailers in the merge commit; nothing checks them. The gate reads the PR body and warns (never fails, Q-T035-3) when the trailers are missing, malformed, or disagree with what the commits bind and what the diff touches.

Product and hive stay apart: everything above is product code any repo gets. What this hive does with it (trailers in its PR bodies, pin move, workflow rewrite, its own approver list) is section 2.7, done by the queen and the Head Keeper, not by the builder.

## 2. Design

### 2.1 Config: `gate.approvers`

`GateConfig` gains `Approvers []string`, parsed like `protected_paths` (D-238): one comma-separated scalar, entries trimmed of spaces, `""` meaning none. Each entry is a GitHub login without `@`: 1 to 39 bytes of `[A-Za-z0-9-]`, not starting with `-`. Rejected (ErrInvalidConfig, line-numbered like the others): `@` anywhere, `/` (teams need `read:org`, which the Actions token lacks; out of scope), control bytes, empty entries, a trailing comma, more than 32 entries, a nested mapping. Duplicates are accepted, as `protected_paths` accepts them. Approvers are compared to review logins with ASCII case folding (GitHub logins are case-insensitive), never by prefix or substring.

**Version skew.** The key is additive to the schema but not backward compatible for readers: a binary built before this ticket treats `gate.approvers` as an unknown key and exits 3 (D-239 for the gate, D-246 for dispatch). Inside a repo that builds the gate from base source, as this one does, the gate cannot meet the key early: the key can land only after T-035 is on main, and base config and base source are one revision. The real skew is dispatch's pinned binary and any installed CLI (section 2.7 item 3), and, after G4, a released Action pinned by tag that reads a newer config. G4 and the G5 recipes carry that rule.

### 2.2 PR context

The approver check and the trailer check need the PR number, its head SHA, its head branch and its body. Under GitHub Actions they come from the event payload file, read through the injected `getenv` only (`GITHUB_ACTIONS`, `GITHUB_EVENT_NAME`, `GITHUB_EVENT_PATH`, `GITHUB_REPOSITORY`, `GITHUB_TOKEN`). No new command-line flag: the workflow keeps calling `gate verify --base "$BASE_SHA" --head "$HEAD_SHA"`, so a binary built before this ticket ignores the new inputs instead of exiting 2 on an unknown flag.

- **Event file.** Read only when `GITHUB_ACTIONS` is `true` and `GITHUB_EVENT_NAME` is `pull_request` or `pull_request_review`. It is opened, read through a 2 MiB cap and decoded into `pull_request.number`, `pull_request.head.sha`, `pull_request.head.ref` and `pull_request.body`. Unreadable, over the cap, malformed, number not positive, or `head.sha` not 40 lowercase hex: the file did not parse, with a reason the approver check may print.
- **Context.** The PR context exists when the file parsed and `pull_request.head.sha` equals the OID `--head` resolved to (otherwise the reason is `event head differs from --head`). The binding ties the PR number, and so its reviews and body, to the commit being gated. In CI both sides come from the same payload, so it always holds there; it guards manual runs.
- **Branch default.** GitHub sets `GITHUB_HEAD_REF` only for `pull_request` and `pull_request_target` events, not for `pull_request_review`, so a review-triggered run would lose the D-237 branch binding and fail `leases` for commits bound only by branch name. When `--branch` is not given, `GITHUB_HEAD_REF` is empty and the event file parsed (the head binding is not required: the branch name is author-chosen anyway, as `--branch` and `GITHUB_HEAD_REF` are today), the branch name comes from `pull_request.head.ref` and goes through `branchTicket` as today (length and control-byte checks, never echoed). So it needs no head OID and `runGateRange` keeps its order (branch, then `scanRange`). When `GITHUB_HEAD_REF` is set, it wins, as today. The template must not interpolate `github.event.pull_request.head.ref` (`guard_template_test.go:69` forbids it); reading it in Go from the file is safe. Accepted: a review-triggered run whose event file does not parse loses the branch default and fails closed for branch-only commits.
- **What prints when.** Outside a parsed file the gate behaves as today, with one exception: when the base config lists approvers and the scan hit a listed path (2.3), a missing context under `GITHUB_ACTIONS=true` warns `approver check skipped: no pull request context (<reason>)`. With approvers absent or no listed hit, a missing context prints nothing. The trailer check prints only when the context exists (2.4).

### 2.3 Approver check

**Approvable path.** A path is approvable when the base `TierPolicy` lists it (`policy.RequiredMinTier(p) == Tier3ControlPlane`) and no entry of `comb.HardcodedTier3Prefixes` matches it by comb's equal-or-prefix rule. `matchesPrefix` is unexported, so `gate_approve.go` repeats its six lines over the exported list, on the path normalized exactly as `TierPolicy.listed` does (`filepath.ToSlash(filepath.Clean(p))`, then lowercase); paths from `git diff-tree` are already clean, so this changes nothing for them, but the two matchers must not drift. The filter uses the prefix list, not `comb.RequiredMinTier`: under `RequiredMinTier` the `.waggle/hive/` carve-out is Tier 2, so a listed hive path (a supported config, `gate_bind_test.go:175-183`) would move from bypass-only to approver-passable, the one case where adding a `protected_paths` entry would lower the bar. With the prefix filter all of `.waggle/` stays bypass-only and a listing stays raise-only.

**When it runs.** Only when all of these hold: the first `scanRange` returned nil (an `errTooLarge` first scan, reported as a failure at `gate_verify.go:138-141`, or a git error, never triggers a lookup or a rerun); the base config lists at least one approver; the scan found at least one `tier3` violation on an approvable path; and the PR context exists. With no approvers, or no approvable hit, no forge call is made and no approver warning prints. Approvers and protected paths are read from the base config only (`baseTierPolicy`, extended to return both); a list edited in the PR's own head never applies.

**Reading reviews (section 2.5).** `GITHUB_REPOSITORY` gives `owner/repo` and `GITHUB_TOKEN` the token. One reader call returns every review and the time of the PR's last base change. The decision is a pure function in `gate_approve.go` over the reviews, the last base change time, the approver list and the head OID.

**The rule.** Reviews are ordered by `fullDatabaseId` ascending (not response order, not `submittedAt`). IDs are unique (2.5 makes a duplicate a read error), so the order has no ties. Times compare strictly: an approval counts only when its `submittedAt` is after the base change (`Submitted.After(LastBaseChange)`, never `!Before`), so an approval in the same second as a retarget (both times have one-second resolution) does not count, which fails closed. For each listed approver, the counted state is the state of that login's last review whose state is `APPROVED`, `CHANGES_REQUESTED` or `DISMISSED`; `COMMENTED` and `PENDING` reviews do not change it. GitHub dismisses a review in place (same ID, state becomes `DISMISSED`), so a dismissed approval reads back as `DISMISSED`. The PR is approved when at least one listed approver's counted state is `APPROVED` with `commit_id` equal to the head OID (full 40-hex compare) and, under Q-T035-7 (a), a `submittedAt` after the last base change (an approval with no time, or a base change time that does not parse, does not count), and, under Q-T035-2 (a), no listed approver's counted state is `CHANGES_REQUESTED`, at any commit. So: approved at an older head is stale; approved at old head then again at head counts; approved then dismissed does not; approved then changes requested by the same approver does not; a dismissed change request followed by an approval at head counts; approved then commented still counts; approved and then the base retargeted does not; an account not on the list never counts.

**Effect.** When approved, `scanRange` runs a second time with a filter, and the second report is the one printed. It is a full rerun, `caseCollisions` included, so expired-claim warnings regenerate; warnings that `runGateRange` adds before `scanRange` (`branch name ignored`, `gate_verify.go:131-134`) are carried into the second report. The filter drops exactly two kinds of violation, and only on approvable paths: `tier3` and `outside_lease`. Every other finding stays: hardcoded Tier 3 paths, unbound commits, `Head Keeper:` commits, merge commits that are not base updates, `link_mode`, `case_differs`, `tier2_light`, case collisions, the size caps, missing or malformed claims, and `decisions`. The rerun, rather than editing the first report, keeps the unapproved path identical to today and avoids the dedup trap in `gateReport.fail` (key `check + path`): a filtered `outside_lease` must not leave a `link_mode` on the same path hidden, and in the rerun it is no longer shadowed. If the rerun returns any error, the first report is printed unchanged with the warning `approver check skipped: rescan failed`, so the approver path never turns into exit 3. The approved run adds one warning under `tiers` (under `leases` for `gate leases`): `protected paths approved by <config entry> at <short head>` (the config entry, never the API login, is echoed).

**Degrade, never exit 3.** Every failure of this path leaves the findings as they are (exit 1, as today). Under `GITHUB_ACTIONS=true` it adds one warning under the same check: `approver check skipped: <reason>`; with `GITHUB_ACTIONS` unset (a developer machine) it adds nothing (2.2). The reason is one fixed phrase: `no pull request context (<context reason>)`, where the context reason is `event is not a pull request event` (any `GITHUB_EVENT_NAME` but `pull_request` or `pull_request_review`; the name itself is not echoed), `no GITHUB_EVENT_PATH`, `event file unreadable`, `event file over 2 MiB`, `event file malformed` (bad JSON, number not positive, or `head.sha` not 40 lowercase hex) or `event head differs from --head`; or `no GITHUB_TOKEN`, `invalid GITHUB_REPOSITORY`, `GitHub answered <status>`, `GitHub reviews unavailable` (transport, timeout, decode, GraphQL errors, body cap, page cap, and the 2.5 node rules), `rescan failed`. A run that read reviews and found no qualifying approval warns `no approving review from a listed approver at <short head>`. No GitHub message text, review body or unlisted login is printed. The lookup has its own 60 second context inside the gate's 5 minutes. Nothing in this path returns exit 2 or 3, and nothing turns an exit 1 into 0 except a qualifying approval.

### 2.4 Trailer check

Runs in `gate verify` only, when the PR context exists, whatever the approver config. Warnings only, under `leases`; it never changes an exit code (Q-T035-3 (a)). Its warnings are the one intended output change on every PR with a context; the "no change" rules of sections 5 and 8 apply to the approver path.

- **Parse.** Body capped at 64 KiB (over: one warning `Intent Packet: PR body over 64 KiB; trailers not checked`). CRLF becomes LF, trailing blank lines are dropped, and the trailer block is the last paragraph. It counts as a trailer block only when every line matches `^([A-Za-z][A-Za-z0-9-]{0,63}):[ \t]*(.*)$`. Keys compare case-insensitively; only `Waggle-Ticket`, `Waggle-Risk-Tier` and `Waggle-Verdict` are read (Q-T035-4 (a)); other keys such as `Signed-off-by` are ignored. A Waggle key given twice is malformed.
- **Values.** `Waggle-Ticket` goes through `trailerTickets` (the commit-trailer parser, unchanged). `Waggle-Risk-Tier` is one digit 0 to 3. `Waggle-Verdict` is `pass` or `must-fix`. Values over 256 bytes are malformed.
- **Warnings** (prefix `Intent Packet: `; only canonical ticket IDs and digits are echoed): no Waggle trailer at all; each missing key; a malformed key (named, value not echoed); the trailer ticket set differs from the set of tickets the commits bind (`Waggle-Ticket names T-x; commits bind T-y`); the risk tier is below the highest `TierPolicy.RequiredMinTier` over the PR's changed paths (`Waggle-Risk-Tier 1 is below the Tier 3 the changed paths require`); verdict `must-fix`.

`commitScan` collects the bound ticket set (it already has `bound`) and the highest required tier of the changed paths for this. With `edited` in the trigger list (2.6), a body edit reruns the gate, so warnings follow the current body.

### 2.5 Forge: reading reviews

A new `internal/forge/reviews.go`, with no change to the `Forge` interface, `github`, `none` or the transports:

- `type Review struct { ID int64; Login, State, CommitID string; Submitted time.Time }` and a result holding the reviews and `LastBaseChange time.Time` (zero when the base never changed).
- `NewReviewReader(repository, token string)` returns a reader bound to `api.github.com` through `tokenTransport` and `tokenClient` (token only in the Authorization header, the existing redirect rule, the existing redaction). `repository` must be `owner/repo` with `ownerPattern` and `repoPattern`, else an error wrapping `ErrForgeRemote`; an empty token wraps `ErrNoForgeAuth`. An unexported constructor takes the API base for tests, as `newGitHub` does. **D-061 deviation, stated:** D-061 says forge calls use `gh` when it is logged in, else `GITHUB_TOKEN`. The gate reader is token-only and never runs `gh`, so auth in the merge gate is predictable; in CI the token is what exists, and on a developer machine the check skips with `no GITHUB_TOKEN`, losing no protection.
- **One GraphQL query, no bodies.** REST `/pulls/<n>/reviews` returns review bodies of up to 65536 characters each, so 100 reviews per page can pass the 1 MiB `maxBody` cap, and any account that can post a review could force `GitHub reviews unavailable` (fail closed, but a denial of the approval route, and on a public repo after G5 anyone can post). The reader therefore sends `POST /graphql`, as `autoMerge` does, with `repository(owner: $owner, name: $name) { pullRequest(number: $n) { ... } }` selecting `timelineItems(last: 1, itemTypes: [BASE_REF_CHANGED_EVENT]) { nodes { ... on BaseRefChangedEvent { createdAt } } }` and `reviews(first: 100, after: $cursor) { pageInfo { hasNextPage endCursor } nodes { fullDatabaseId state submittedAt commit { oid } author { login } } }`. It pages while `hasNextPage`, at most 10 pages; an 11th page is an error (the gate skips). A response with a non-empty `errors` array, a missing `repository` or `pullRequest`, or a cursor that is not a non-empty string under 256 bytes is an error.
- **Review IDs.** `PullRequestReview.databaseId` (Int) is deprecated in GitHub's GraphQL reference because it cannot hold 64-bit IDs, and REST review IDs passed 2^31 in 2024; the reader never selects it. `fullDatabaseId` is a `BigInt`, which arrives as a JSON string: it is decoded as a decimal string of 1 to 19 digits into a positive `int64` (`strconv.ParseInt`, base 10), never through a float. The all-digits check runs before `ParseInt`, which on its own accepts a leading `+` or `-`.
- **Node rules.** A node whose `author` is null or whose `author.login` fails `ownerPattern` (a deleted account) is dropped: it can never be a listed approver. For every other node, a missing, null or unparseable `fullDatabaseId`, two nodes with the same ID, or a `state` outside `APPROVED`, `CHANGES_REQUESTED`, `COMMENTED`, `DISMISSED`, `PENDING` makes the whole read an error (`GitHub reviews unavailable`, gate exit 1 as for every read error, never exit 3, never a pass), because dropping or misordering such a node could hide a listed approver's later change request. A `commit.oid` that is null or not 40 lowercase hex becomes `""` and so never matches a head; a `submittedAt` that is null or does not parse as RFC 3339 becomes zero, which never counts (2.3). The builder confirms these names against GitHub's GraphQL reference (`docs.github.com/en/graphql/reference`) and cites it in the PR body. A token with `pull-requests: read` can run this query.

The package doc comment says gate logic never imports `forge`. It changes to say what holds after this ticket: core packages (comb, decisions, dispatch's claim and lease code) never import `forge`; the gate command in `cmd/waggle` reads PR reviews through `ReviewReader` for the approver check, and the lease and tier decisions stay plain git. `cmd/waggle` reaches the reader through an unexported package variable (`newReviewSource`) that tests replace with a fake returning fixed results or errors; no `cmd/waggle` test talks HTTP. No test in `cmd/waggle` uses `t.Parallel` today, so the swap is safe; new tests keep it that way.

**Environment.** Every environment read in new code goes through the injected `getenv`. product-ci runs on GitHub Actions, where `GITHUB_EVENT_PATH` and `GITHUB_TOKEN` are real; an `os.Getenv` in this path would make the test suite read the CI run's own event.

### 2.6 Workflow template: lands in G3, not G4

Decision: the template change is part of this ticket. Without it the approver check is dead code until G4, G4 would carry Tier 3 behavior it does not test, and D-258 chose a public launch with named approvers and rejected the option where G4 carries the trigger, permission and token. It is about 14 YAML lines in `internal/scaffold/templates/waggle-gate.yml.tmpl`, a product file inside this lease. The hive's own `.github/workflows/waggle-gate.yml` is not touched here; it takes the render at the next pin move as a Head Keeper commit (the D-249 and D-250 pattern). G4 keeps the release binary and the composite Action, and must carry the same triggers, permission and token input into the Action.

Changes, all inside `on:` and the `verify-leases-and-tiers` job:

- `pull_request` types become `[opened, synchronize, reopened, labeled, edited]`. `edited` fires when the base branch, title or body changes. Without it a base retarget never reruns the gate, so a green check computed against the old base (its merge-base, its base config, its protected paths) stays on the head: an author opens the PR against a branch where the gate passes, retargets to `main`, and merges with no approver. With it the check reruns against the new base, and Q-T035-7 (a) makes an approval from before the change stale. Cost: a title or body edit also reruns the job (about one runner minute, check pending meanwhile), which also keeps trailer warnings current. - `on:` gains `pull_request_review: types: [submitted, dismissed]`, so an approval reruns the check and a dismissal fails it again.

## 5. Threat model (D-203)

**Attacker:** the PR author, an agent or a person who is not a listed approver. They control the PR title and body (trailers included), the branch name and head ref, every commit (trees, messages, `Waggle-Ticket` trailers, push timing, force-pushes back to an older SHA), the PR's base branch (retargeting), extra PRs with the same head, review requests, and reviews from any account they own that is not on the list. They do not control the base config, a listed approver's account or review actions, the token's scope (`contents: read`, `pull-requests: read`; read-only for forks in any case), the event fields and timeline times GitHub writes (number, head SHA, base change time), or the runner. A write-access collaborator can also dismiss reviews or request changes; both only make the gate fail.

**Trusted:** the base config and its approver list (Tier 3, read from base), listed approvers, the Head Keeper, GitHub's API answers and event payload, the runner environment.

**Must-fix:** an approvable-path change that passes without a listed approver's counted state being `APPROVED` at exactly the gated head OID: a stale approval at an older head, a dismissed approval, an approval followed by changes requested, an unlisted account, a login matched by prefix, substring or anything but ASCII case folding, reviews ordered by response order instead of ID, or an approver list read from the head, the merge-base or the working tree; under Q-T035-7 (a), an approval submitted before the last base change, or one with no time, that counts; under Q-T035-2 (a), a change request from a listed approver that does not block; reviews of a PR whose event head SHA differs from `--head`; an approval that removes any finding other than `tier3` and `outside_lease` on an approvable path, or removes those on a path matching `HardcodedTier3Prefixes` (`.waggle/hive/` included), unbound or `Head Keeper:` commits, crafted merges, `link_mode`, `case_differs`, `tier2_light`, case collisions, size caps, claims or decisions; a filtered finding that hides another finding on the same path; a pre-scan warning dropped from the second report; any approver-path failure that exits 2 or 3 (a rescan error included), or exits 0 where today's code exits 1; any approver warning, forge call or output change from the approver path when `gate.approvers` is absent or empty, or when no approvable path is hit; any trailer warning that changes an exit code; the token in argv, output, errors or files, sent to any host but `api.github.com`, or present in a template step other than the gate step; any environment read outside the injected `getenv`; PR body text, trailer values, review bodies, API logins or GitHub error text echoed in output, or any way they start a workflow command; an unbounded read of the event file, the body or review pages; review bodies or the deprecated `databaseId` requested from the API; a node from a valid login with a missing, unparseable or duplicate ID, or an unknown state, dropped or ordered instead of failing the read; an ID decoded through a float; a time compare that counts an approval in the same second as the base change; a write permission, `pull_request_target`, a missing `edited` type, or PR-field interpolation in the template; a change to the `Forge` interface, `none`, the transports, or `comb` importing `forge`; files changed outside the lease rule.

**Note, not must-fix:** an agent holding a listed approver's credentials can approve another PR (equal capability to that approver; G5 recipe says keep approver tokens away from agents); GitHub forbids self-approval, but an approver who pushed commits to the PR can still approve it (GitHub's "approval of the most recent reviewable push" is not replicated); a renamed then re-registered login counts (Q-T035-6); under Q-T035-7 (b) an approval survives a base retarget; a PR that edits the gate workflow gets its own edited workflow run for `pull_request` and `pull_request_review` events, a GitHub behavior that predates this ticket and that the gate catches only while the edited workflow still runs it (carried to G4: required workflows or rulesets); trailer values are author text and gate nothing; intermediate runs in the concurrency group can end `cancelled` while the newest event runs last; a review-triggered run whose event file does not parse loses the branch default and fails closed (2.2); a PR with over 1000 reviews skips the approver check, which only its own participants can cause; an invalid `gate.approvers` in the base config exits 3, as D-239 already rules for every base config fault; until the hive pin move, the hive's own workflow lacks `edited`, so the pre-existing retarget hole stays open there.

**Guard prompt sentence (repeat verbatim):** "Threat bar (D-203): a finding whose attacker needs to edit the base config, act as a listed approver, widen the workflow token, or control the runner or GitHub's event payload is a note, not a must-fix; must-fix is for what a PR author can do through the PR body, branch, commits, pushes, retargeting and reviews from unlisted accounts, and for any path where a protected-path change passes without a listed approval at the exact head, or where the approver path changes today's exit code or output when it should not."

## 1. Goal

Two gate features from D-229 and D-233, for users of the gate in any repo:

1. **Named approver.** Today a change to a repo-listed protected path (`gate.protected_paths`, T-031) fails `tiers` (`protected path (listed in .waggle/control/config.yaml); needs an admin bypass to merge`) and, because G2 refuses any lease that covers a listed path (T-032, D-243), also fails `leases` with `path is outside the claim directories`. The only way through is an admin bypass. After this ticket the same change passes when a GitHub account listed in the base config's `gate.approvers` has an approving review on the PR at exactly the head SHA being gated (D-233). With no approval, no list, no token or any lookup failure, it fails exactly as today, and the admin bypass stays.
2. **Intent Packet trailers.** D-017 puts ticket, risk tier and verdict trailers in the merge commit; nothing checks them. The gate reads the PR body and warns (never fails, Q-T035-3) when the trailers are missing, malformed, or disagree with what the commits bind and what the diff touches.

Product and hive stay apart: everything above is product code any repo gets. What this hive does with it (pin move, workflow rewrite, its own approver list, the queen's PR bodies) is section 2.7, done by the queen and the Head Keeper after merge, not by the builder.

## 2. Design

### 2.1 Config: `gate.approvers`

`GateConfig` gains `Approvers []string`, parsed like `protected_paths` (D-238): one comma-separated scalar, entries trimmed of spaces, `""` meaning none. Each entry is a GitHub login without `@`: 1 to 39 bytes of `[A-Za-z0-9-]`, not starting with `-`. Rejected (ErrInvalidConfig, line-numbered like the others): `@` anywhere, `/` (teams need `read:org`, which the Actions token lacks; out of scope), control bytes, empty entries, a trailing comma, more than 32 entries, a nested mapping. Duplicates are accepted, as `protected_paths` accepts them. Approvers are compared to review logins with ASCII case folding (GitHub logins are case-insensitive), never by prefix or substring.

The key is additive to the schema but not backward compatible for readers: a binary built before this ticket treats `gate.approvers` as an unknown key, and the gate (D-239) and dispatch (D-246) both exit 3 on an invalid base config. Section 2.7 states the order this forces.

### 2.2 PR context

The approver check and the trailer check need the PR number, its head SHA, its head branch and its body. Under GitHub Actions they come from the event payload file, read through the injected `getenv` only (`GITHUB_ACTIONS`, `GITHUB_EVENT_NAME`, `GITHUB_EVENT_PATH`, `GITHUB_REPOSITORY`, `GITHUB_TOKEN`). No new command-line flag: the workflow keeps calling `gate verify --base "$BASE_SHA" --head "$HEAD_SHA"`, so a binary built before this ticket ignores the new inputs instead of exiting 2 on an unknown flag.

- The context exists only when `GITHUB_ACTIONS` is `true` and `GITHUB_EVENT_NAME` is `pull_request` or `pull_request_review`. Outside that the gate behaves as today, with no warning.
- The event file is opened, read through a 2 MiB cap and decoded into `pull_request.number`, `pull_request.head.sha`, `pull_request.head.ref` and `pull_request.body`. Unreadable, over the cap, malformed, number not positive, or `head.sha` not 40 lowercase hex: no context, with a reason the two checks may print.
- **Binding:** the context is used only when `pull_request.head.sha` equals the OID `--head` resolved to. Otherwise there is no context (reason: `event head differs from --head`). This ties the PR number, and so its reviews, to the commit being gated.
- **Branch default (found while writing this brief):** GitHub sets `GITHUB_HEAD_REF` only for `pull_request` and `pull_request_target` events, not for `pull_request_review`. A review-triggered run would therefore lose the D-237 branch binding and fail `leases` for commits bound only by branch name, which the push-triggered run passed. When `--branch` is not given, `GITHUB_HEAD_REF` is empty and the context exists, the branch name comes from `pull_request.head.ref` and goes through `branchTicket` as today (length and control-byte checks, never echoed). When `GITHUB_HEAD_REF` is set, it wins, as today. The template must not interpolate `github.event.pull_request.head.ref` (`guard_template_test.go:69` forbids it); reading it in Go from the file is safe.

### 2.3 Approver check

**When it runs.** Only when all of these hold: the base config lists at least one approver; the scan found at least one `tier3` violation on a path that is listed in the base `gate.protected_paths` and is not hardcoded Tier 3 (`comb.RequiredMinTier(path) != comb.Tier3ControlPlane`; Q-T035-1 (a)); and the PR context exists. With no approvers, or no listed-path hit, no forge call is made and output is byte for byte today's. Approvers and protected paths are read from the base config only (`baseTierPolicy`, extended to return both); a list edited in the PR's own head never applies.

**Reading reviews (section 2.5).** `GITHUB_REPOSITORY` gives `owner/repo` and `GITHUB_TOKEN` the token. The gate lists every review of the PR and decides on data, in a pure function in `gate_approve.go` that takes the reviews, the approver list and the head OID.

**The rule.** Reviews are ordered by review ID ascending (not response order). For each listed approver, the counted state is the state of that login's last review whose state is `APPROVED`, `CHANGES_REQUESTED` or `DISMISSED`; `COMMENTED` and `PENDING` reviews do not change it (GitHub's own semantics; a dismissed approval reads back with state `DISMISSED`). The PR is approved when at least one listed approver's counted state is `APPROVED` with `commit_id` equal to the head OID (full 40-hex compare), and, under Q-T035-2 (a), no listed approver's counted state is `CHANGES_REQUESTED`, at any commit. So: approved at an older head is stale and does not count; approved at old head then again at head counts; approved then dismissed does not; approved then changes requested by the same approver does not; approved then commented still counts; an account not on the list never counts, whatever its state.

**Effect.** When approved, `scanRange` runs the scan a second time with a filter, and that second report is the one printed. The filter drops exactly two kinds of violation, and only on listed, not hardcoded, paths: `tier3`, and `outside_lease`. Every other finding stays: hardcoded Tier 3 paths, unbound commits, `Head Keeper:` commits, merge commits that are not base updates, `link_mode`, `case_differs`, `tier2_light`, case collisions, the size caps, missing or malformed claims, and `decisions`. The second scan, rather than editing the first report, keeps the unapproved path identical to today and avoids the dedup trap in `gateReport.fail` (key `check + path`): a filtered `outside_lease` must not leave a `link_mode` on the same path hidden, and in the second scan it is no longer shadowed. The approved run adds one warning under `tiers` (under `leases` for `gate leases`): `protected paths approved by <config entry> at <short head>` (the config entry, never the API login, is echoed).

**Degrade, never exit 3.** Every failure of this path leaves the findings as they are (exit 1, as today) and adds one warning under the same check: `approver check skipped: <reason>`, where the reason is one fixed phrase: `no pull request context` plus the 2.2 reason, `no GITHUB_TOKEN`, `invalid GITHUB_REPOSITORY`, `GitHub answered <status>`, `GitHub reviews unavailable` (transport, timeout, decode, body cap, page cap). A run that read reviews and found no qualifying approval warns `no approving review from a listed approver at <short head>`. No GitHub message text, review body or unlisted login is printed. The lookup has its own 60 second context inside the gate's 5 minutes. Nothing in this path returns exit 2 or 3, and nothing turns an exit 1 into 0 except a qualifying approval.

### 2.4 Trailer check

Runs in `gate verify` only, when the PR context exists. Warnings only, under `leases`; it never changes an exit code (Q-T035-3 (a)).

- **Parse.** Body capped at 64 KiB (over: one warning `Intent Packet: PR body over 64 KiB; trailers not checked`). CRLF becomes LF, trailing blank lines are dropped, and the trailer block is the last paragraph. It counts as a trailer block only when every line matches `^([A-Za-z][A-Za-z0-9-]{0,63}):[ \t]*(.*)$`. Keys compare case-insensitively; only `Waggle-Ticket`, `Waggle-Risk-Tier` and `Waggle-Verdict` are read (Q-T035-4 (a)); other keys such as `Signed-off-by` are ignored. A Waggle key given twice is malformed.
- **Values.** `Waggle-Ticket` goes through `trailerTickets` (the commit-trailer parser, unchanged). `Waggle-Risk-Tier` is one digit 0 to 3. `Waggle-Verdict` is `pass` or `must-fix`. Values over 256 bytes are malformed.
- **Warnings** (prefix `Intent Packet: `; only canonical ticket IDs and digits are echoed): no Waggle trailer at all; each missing key; a malformed key (named, value not echoed); the trailer ticket set differs from the set of tickets the commits bind (`Waggle-Ticket names T-x; commits bind T-y`); the risk tier is below the highest `TierPolicy.RequiredMinTier` over the PR's changed paths (`Waggle-Risk-Tier 1 is below the Tier 3 the changed paths require`); verdict `must-fix`.

`commitScan` collects the bound ticket set (it already has `bound`) and the highest required tier of the changed paths for this.

### 2.5 Forge: reading reviews

A new `internal/forge/reviews.go`, with no change to the `Forge` interface, `github`, `none` or the transports:

- `type Review struct { ID int64; Login, State, CommitID string }`.
- `NewReviewReader(repository, token string)` returns a reader bound to `api.github.com` through `tokenTransport` and `tokenClient` (token only in the Authorization header, the existing redirect rule, the existing redaction). `repository` must be `owner/repo` with `ownerPattern` and `repoPattern`, else an error wrapping `ErrForgeRemote`; an empty token wraps `ErrNoForgeAuth`. The gate never runs `gh`: in CI the token is what exists, and it keeps auth predictable. An unexported constructor takes the API base for tests, as `newGitHub` does.
- `Reviews(ctx, number)` sends `GET /repos/<owner>/<repo>/pulls/<n>/reviews?per_page=100&page=<k>` from page 1 until a page holds fewer than 100 entries, at most 10 pages; an 11th full page is an error (the gate skips). Each body is capped by `maxBody` as today. Entries whose `user.login` fails `ownerPattern` are dropped; a `commit_id` that is not 40 lowercase hex becomes `""` and so never matches a head.

The package doc comment says gate logic never imports `forge`. It changes to say what holds after this ticket: core packages (comb, decisions, dispatch's claim and lease code) never import `forge`; the gate command in `cmd/waggle` reads PR reviews through `ReviewReader` for the approver check, and the lease and tier decisions stay plain git. `cmd/waggle` reaches the reader through an unexported package variable (`newReviewSource`) that tests replace with a fake returning fixed reviews or errors; no `cmd/waggle` test talks HTTP. No test in `cmd/waggle` uses `t.Parallel` today, so the swap is safe; new tests keep it that way.

**Environment.** Every environment read in new code goes through the injected `getenv`. product-ci runs on GitHub Actions, where `GITHUB_EVENT_PATH` and `GITHUB_TOKEN` are real; an `os.Getenv` in this path would make the test suite read the CI run's own event.

- The job's `if:` becomes `github.event_name == 'pull_request' || github.event_name == 'pull_request_review'`.

## 3. Questions for the Head Keeper (open)

- **Q-T035-1: which paths can a listed approver pass?** (a) Only repo-listed `gate.protected_paths`; every hardcoded Tier 3 path (`.waggle/`, `.github/workflows/`, `.gitlab-ci.yml`, `.devcontainer/`, `go.mod`, `go.sum`, `go.work*`, `vendor/`) stays Head Keeper commit plus admin bypass. (b) Also the hardcoded dependency paths (`go.mod`, `go.sum`, `go.work*`, `vendor/`), with control and CI paths still bypass only. (c) Every Tier 3 path. **Recommended: (a).** Matches T-031's split between protected paths and Tier 3 paths, keeps CI and control files (which can rewrite the gate itself) behind the bypass, and is the smallest surface. Cost: an outside user's agent PR that bumps `go.mod` still needs an admin merge, and this hive gains nothing until it lists paths. (b) is about 5 more lines and a new tier distinction; (c) lets an approval pass a PR that edits the gate workflow. Reversible: widening later is additive.
- **Q-T035-2: does a change request from another listed approver block an approval?** (a) Yes: any listed approver whose counted state is `CHANGES_REQUESTED` blocks, at any commit, until they approve or the request is dismissed. (b) No: one listed approval at head is enough. **Recommended: (a).** It matches GitHub's branch protection, and one approver cannot overrule another by racing a click. Cost: about 3 lines; a stale change request needs a dismissal. Reversible.
- **Q-T035-3: how strong is the trailer check?** (a) Warnings only, no config key. (b) Warnings by default, plus an opt-in `gate.require_trailers` that makes them failures. (c) A hard failure for every repo. **Recommended: (a).** The repositioning risk list warns against day-one strictness; trailer values are author-controlled and prove nothing, so a failure adds friction without security. Cost of (b): about 15 lines, a schema key and the version-skew rule of 2.1 again. Reversible: (b) can come later.
- **Q-T035-4: what are the trailer keys?** (a) `Waggle-Ticket`, `Waggle-Risk-Tier`, `Waggle-Verdict`. (b) Unprefixed `Ticket`, `Risk-Tier`, `Verdict`. **Recommended: (a).** It matches D-234's `Waggle-Ticket` commit trailer, which `trailerTickets` already parses, and avoids clashing with other tools' trailers. Cost: none. Hard to reverse once public (G5): the key names become user habit.
- **Q-T035-5: does G3 also read PR merged state for `waggle release` (Q-T032-3, D-242) and bind the merged check to a PR (fable N4 on the T-032 brief)?** (a) No; both stay open for G4 or a later polish ticket, and `release` keeps needing `--unmerged` after a squash or rebase merge. (b) Yes, adding `internal/dispatch/` to the lease and a PR lookup by branch to the reader. **Recommended: (a).** `release` runs on a developer machine where the token is a `gh` login, not the CI token, so it needs its own auth design; it adds a fifth leased directory and about 40 doubled lines past this budget; and the N4 hole has the same capability as the existing one (a note under T-032's threat model). Reversible.
- **Q-T035-6: how does the config name an approver?** (a) GitHub login, compared with ASCII case folding. (b) Numeric GitHub user ID. **Recommended: (a).** Readable in review and matches what users see. Cost: a listed login that is renamed and then re-registered by someone else would count (section 5 note); (b) closes that but is opaque in a Tier 3 file. Reversible before G5; afterwards a format change.

## 5. Threat model (D-203)

**Attacker:** the PR author, an agent or a person who is not a listed approver. They control the PR title and body (trailers included), the branch name and head ref, every commit (trees, messages, `Waggle-Ticket` trailers, push timing, force-pushes back to an older SHA), the PR's base branch (retargeting), extra PRs with the same head, review requests, and reviews from any account they own that is not on the list. They do not control the base config, a listed approver's account or review actions, the token's scope (`contents: read`, `pull-requests: read`; read-only for forks in any case), the event fields GitHub writes (number, head SHA), or the runner. A write-access collaborator can also dismiss reviews or request changes; both only make the gate fail.

**Trusted:** the base config and its approver list (Tier 3, read from base), listed approvers, the Head Keeper, GitHub's API answers and event payload, the runner environment.

**Must-fix:** a listed protected-path change that passes without a listed approver's counted state being `APPROVED` at exactly the gated head OID: a stale approval at an older head, a dismissed approval, an approval followed by changes requested, an unlisted account, a login matched by prefix, substring or anything but ASCII case folding, reviews ordered by response order instead of ID, or an approver list read from the head, the merge-base or the working tree; under Q-T035-2 (a), a change request from a listed approver that does not block; reviews of a PR whose event head SHA differs from `--head`; an approval that removes any finding other than `tier3` and `outside_lease` on a listed, non-hardcoded path (hardcoded Tier 3, unbound or `Head Keeper:` commits, crafted merges, `link_mode`, `case_differs`, `tier2_light`, case collisions, size caps, claims, decisions); a filtered finding that hides another finding on the same path; any approver or trailer failure that exits 2 or 3, or exits 0 where today's code exits 1; any output or exit change when `gate.approvers` is absent or empty, or when no listed path is hit; any forge call in those cases; the token in argv, output, errors or files, sent to any host but `api.github.com`, or present in a template step other than the gate step; any environment read outside the injected `getenv`; PR body text, trailer values, review bodies, API logins or GitHub error text echoed in output, or any way they start a workflow command; an unbounded read of the event file, the body or review pages; a write permission, `pull_request_target`, or PR-field interpolation in the template; a change to the `Forge` interface, `none`, the transports, or `comb` importing `forge`; files changed outside the lease rule.

**Note, not must-fix:** an agent holding a listed approver's credentials can approve another PR (equal capability to that approver; G5 recipe says keep approver tokens away from agents); GitHub forbids self-approval, but an approver who pushed commits to the PR can still approve it (GitHub's "approval of the most recent reviewable push" is not replicated); a renamed then re-registered login counts (Q-T035-6); an approval survives a base retarget at the same head (the approver approved that head tree); a PR that edits the gate workflow gets its own edited workflow run for `pull_request` and `pull_request_review` events, a GitHub behavior that predates this ticket and that the gate catches only while the edited workflow still runs it (carried to G4: required workflows or rulesets); a PR body edit does not rerun the gate, so trailer warnings can be stale; trailer values are author text and gate nothing; GitHub's ordering of check runs between concurrent events (the concurrency group serializes them); an invalid `gate.approvers` in the base config exits 3, as D-239 already rules for every base config fault.

## 5. The Expo dashboard and roles (answers to item 2, Q-T144-4)

`dash.ts auto` runs on a two minute timer and reads `TODO.md` by position. Three one-PR options, and the fourth the brief asked about:

- **(a) `TODO.md` stays the dashboard source and is generated from `backlog/tasks/`.** Needs a generator file, a "do not edit" header, a writer rule that dev-mgr edits Backlog.md and never `TODO.md`, and a timer or commit hook to regenerate. Every status change then exists in two places for a while, which is exactly the drift T-124 section 4.4 warns about (`next` must not hand out finished work). It adds a converter, which the stub rules out, and a second file that looks editable.
- **(b) `dash.ts` reads `backlog/tasks/` in the same PR.** Recommended, in its smallest form: one new function in `dash.ts` that reads each task file's front matter and returns **legacy-shaped row lines** (`- [ ] T-198 · title · size · status · release · kind: x`), appended to the text `syncTodo` and `parseTodoLines` already parse. `syncTodo`, `mapStatus`, `parseKind`, `itemTitle` and the title cell do not change; the "Backlog" detail shows the rebuilt line (front matter plus the `## Row fields` lines, in order). The front matter reader is a dozen lines of `key: value` and `- item` parsing; `dash.ts` has no dependencies (`package.json` is `{ "type": "module" }`) and the reader adds none. A `section-` label yields no row, so the 25 rows the dashboard hides today stay hidden. About 45 non-test lines bottom-up (section 9).
- **(c) A pointer `TODO.md` plus a dashboard change in a separate Expo PR first.** Safest for the dashboard: the parser change lands alone and is checked green before any row moves, so a parser bug and a bad move cannot hide each other. It costs a second Expo PR, a second review round and a second `TODO.md` freeze window. The queen's scout prompt asked for exactly one Expo PR; that is a queen constraint, not a recorded ruling, and the Head Keeper can override it (Q-T144-4). It is also the fallback if Expo's dev-mgr will not take a parser change and a backlog move in one diff.
- **(a') Do nothing to the dashboard and delete the rows.** Not an option: `syncTodo` would drop 72 visible features and the dashboard would go quiet while still green.

Recommendation (b): it changes the fewest files that must change together, keeps one source of truth for open rows, and rollback is one revert.

**Threat model (D-203).**

- **Boundary.** `TODO.md` rows, task files and any issue text are data. Row text is written by Expo's team and workers and may hold backticks, `$(...)`, `---`, `<!--`, quotes, instructions to an agent or very long lines. Nothing in the move or the reader executes, evaluates or follows it. The builder passes row text to the CLI as an argument, never through a shell string. The reader parses front matter as `key: value` and `- item` lines only, with caps (a title over 120 bytes is cut; a file over 64 KiB is skipped with a log line), and never `eval`s or imports it.
- **The move must not drop or reorder an open row.** The how-to and the Expo PR body run the same checks, before and after, and paste the output: (1) `git show <base>:TODO.md | grep -c '^- \[ \]'` is 98 before; after, `TODO.md` has 1 (the unchecked-done row, T-198) and `backlog/tasks/` has 97 files, 98 in all; (2) the sorted `T-` ids of the 97 moved rows equal the sorted title prefixes of the 97 files, with no id twice; (3) each moved row appears verbatim, once, in exactly one file's `## Moved from TODO.md` block (`grep -Fx -- "$row"` per row, row read from the base copy); (4) the `ordinal` values, read in file order of the original `TODO.md` (not `T-` id order), are strictly increasing within each heading; (5) `dash.ts auto` with the fixture options (`--workers-file`, `--tasks-file`) run on the base and on the PR head gives the same `features` and `releases` in the state file, except the title cell detail. A failed check stops the PR.
- **Front matter injection.** A title with a newline, a `---` line or a leading `#`/`:` must not break the file or add a key: the builder reads each created file back (`backlog task view EXPO-n --plain` or the file's front matter) and compares id, title, status, priority and labels with what it sent.
- **Stale snapshot.** Rows edited while the PR is open: the freeze and the re-check at the merge base (section 6 item 3). A merged PR on a changed `TODO.md` would silently resurrect or drop a row; the checks fail then.
- **Id confusion.** Two id schemes: a title prefix that does not parse (`T-198`) or a claim keyed on `EXPO-n` for a row the team calls `T-198`. The prefix `expo` makes the schemes look different on purpose; the check in (2) catches a missing or doubled prefix.
- **Not defended (stated in the how-to).** Anyone with push access can edit a task file or `TODO.md` by hand. A claim is cooperative (T-124 section 10). Expo's two queens are trusted.

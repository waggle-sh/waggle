# T-119: Speed up product-ci with Go build and test caches

- **Status:** Proposed on 2026-11-23. Not claimed, not dispatched.
- **Release:** after v0.1.2; not required in the v0.1.2 cut.
- **Kind:** product. **Size:** S.
- **Layer:** `product`. **Hive effect at merge:** none. Product CI is not scaffolded into other hives (T-019, D-072).
- **Gate:** `full`.
- **Risk Tier:** Tier 3 (`.github/workflows/**` is hardcoded Tier 3). Merge needs Head Keeper approval.
- **Role:** `builder` (draft the workflow change), Head Keeper (signature at merge), `guard` (review).
- **Lease (rw):** none. `.github/workflows/ci.yml` is Tier 3, and `AcquireLease` refuses a lease that touches a Tier 3 path (T-002, T-019).
- **Depends on:** none. Origin is T-019 and current product-ci runs of about 8 minutes, spent mostly in `go test -race ./...`.
- **Commit subject prefix:** `T-119:`

## 1. Goal

Cut product-ci time on PRs and on `main` by restoring Go's build cache and test cache so unchanged packages skip work. Keep `go test -race ./...` on every pull request and every push to `main`. Do not move the race run to a nightly job.

## 2. Scope

Edit only `.github/workflows/ci.yml`.

- Restore `GOCACHE` (and the test cache, which lives under it unless `GOTESTCACHE` is set) across runs with `actions/cache` or an equivalent, so `go build` and `go test -race` reuse object files and passing test results for packages whose inputs have not changed.
- Cache key material: runner OS, Go version from `go.mod`, `go.mod`, and `go.sum` when that file exists. Do not put a hash of the whole source tree in the only restore key. A primary key that includes a source hash is fine if restore-keys fall back to the Go version and `go.mod` / `go.sum` keys, so a typical PR still restores the previous cache and Go skips unchanged packages. A key that only hits when every file is identical would make every PR a cold cache and miss the goal.
- `actions/setup-go` still has `cache: false` today because the module is stdlib only and there is no `go.sum` (T-019). Keep that, or turn setup-go's module cache on only if it can be done without a warning on every run. The speed win is the build and test cache, not module download.
- Leave `go test -race ./...` in the `product-ci` job on `pull_request` and on `push` to `main`. Do not add a nightly-only race job as a substitute. Do not rename the `product-ci` check (the main ruleset requires that name).
- Keep `contents: read`, `persist-credentials: false`, the gofmt tracked-files check, vet, and the 15 minute timeout unless a measured need to raise the timeout is recorded in the PR.
- Comment in `ci.yml` why the caches exist and that race stays on every PR, citing T-119 and the T-019 `cache: false` note.

## 3. Out of scope

- Sharding `go test` across jobs. If product-ci is still slow after a cache hit, file a follow-up rather than sharding in this ticket.
- Changes to `waggle-gate.yml`, other workflows, the main ruleset, or Go source.
- Adding a third-party module only to create a `go.sum` for setup-go.

## 4. Checks

- `go test -race ./...` still runs on every PR. A PR that changes no Go packages should be clearly faster on a cache hit than the current cold run of about 8 minutes. A PR that changes a package still race-tests that package.
- `dco`, `docs-impact`, and `verify-leases-and-tiers` follow the usual rules. The implementation PR is Tier 3 and stays open until the Head Keeper signs the head.

## 5. Stop

- Do not drop `-race` from the PR or `main` path.
- Do not use an admin bypass to merge.
- Do not edit `.waggle/control` or hive records in the implementation PR.

## 6. Origin

Head Keeper request on 2026-11-23 after signed T-102 (#303) product-ci runs of about 8 minutes, spent mostly in `Test (race)`. T-019 turned off setup-go's module cache because there was no `go.sum`; this ticket caches compile and test results instead.

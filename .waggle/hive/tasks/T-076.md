## 1. Goal

Add `gate.mode`, with the values `open` and `guard` in this ticket, parse it from the base config, and make `waggle gate verify` honor it.

- `guard` is today's behavior, byte for byte, and is what a missing key, a missing `gate:` section and a missing config file mean.
- `open` runs every check, reports each would-be finding as a warning, and exits 0.
- Exit 2 (usage) and exit 3 (git or I/O error, broken base config) are not findings and do not change in any mode. D-382 (open question 3) rules that exit 3 stays a failure in `open`.

The check always runs. Only what happens to a finding changes (RFC section 2).

## 2. Scope

### 2.1 `internal/config`

1. **Field and constants.** `GateConfig` gains `Mode string`. Exported constants `GateModeGuard = "guard"` and `GateModeOpen = "open"` sit with the other defaults (`config.go:33-36`).
2. **Default.** `Parse` starts with `Gate: GateConfig{Mode: GateModeGuard}` (`config.go:161`), so a config with no `gate:` section, or no `mode` key, reads as `guard`.
3. **Parse.** A `case "mode":` in the gate loop (before the default at `config.go:258`) reads the scalar with `stringValue`. A mapping value fails the way `stringValue` already fails it.
4. **Validate.** In `validate` (after the approvers check, `config.go:388`): any value other than `open` or `guard` is invalid, with the line number and the message `must be "open" or "guard", got %q`, the same form as `forge.merge_strategy` (`config.go:362-364`). The match is exact and case sensitive. An empty value is invalid, not a default. `watch` is invalid here; T-077 adds it (Q-T076-3).
5. **No other key, no other file.** The `forge`, `leases` and `relay` sections do not change.

### 2.2 `cmd/waggle`

1. **Read the mode from the base config only.** `baseTierPolicy` (`gate_verify.go:280`) returns the mode as well. Today it returns early with zero values when the config file is missing (`:282-284`); that path must return `guard`, never an empty string. `scanOutcome` gets a `mode` field set where the outcome is built (`:249`), before the commit scan, so it is set even when the scan stops on `errTooLarge`. One rule everywhere: only the exact value `open` loosens anything; every other value, including empty, is `guard`.
2. **Verify honors the mode.** In `runGateRange` (`gate_verify.go:101-185`), when the check is `verify` and the mode is `open`:
   - `leases` and `tiers` findings (`gateReport.print`, `:67-96`) print as warnings that say they would have failed, and their exit code is 0.
   - The decisions check (`runGateDecisions`, `gate.go:86-134`) does the same: a failure that would exit 1 prints as a would-be finding and exits 0. A git or I/O error in it stays exit 3.
   - Exit 3 from `scanRange` (`gate_verify.go:167-169`), and every usage error before it, are untouched.
   - Findings keep their existing text and go through the same workflow-command encoders (`annotData`, `annotProp`, `:30-33`), so attacker-chosen paths and subjects cannot start a new line or a new command.
3. **Output in `open`.**
   - One line to stderr on every open run, before the checks: `gate: mode open: findings are reported, not enforced`. Under GitHub Actions it is a `::notice::` line.
   - Each would-be finding: `<check>: would fail (mode open): <path>: <msg>` locally, and `::warning file=<path>::<check>: would fail (mode open): <msg>` under Actions.
   - A check with no findings still prints `<check>: ok` on stdout, as today.
   - Warnings that exist today (branch name ignored, approver check skipped, trailer warnings, signature notices) stay as they are.
4. **Output in `guard`.** Unchanged. A missing key and `mode: guard` give the same bytes on stdout and stderr and the same exit code as main today (test G1).
5. **Usage text.** `gate.go:53-82` gets one short paragraph: the mode is read from the base config, `guard` is the default and fails on a finding, `open` reports each finding as a warning and exits 0, and exit codes 2 and 3 do not change. It passes `checkPlain` (`cmd/waggle/plain_terms_test.go:19-37`): no `Keeper`, no `hive` outside `.waggle/hive/`, no dashes.
6. **No flag, no env var, no label.** `waggle gate verify` gets no `--mode` flag and reads no environment variable for the mode (RFC section 4, "Mode is never per PR"). An unknown flag stays exit 2.

## 3. Flow, end to end

1. A project adopts Waggle. Its base config has `gate:` with `mode: open`, written by a Head Keeper approved change in a later ticket (T-079 or T-080). A person on the team opens a PR that edits `src/api.go` while the claim for its ticket leases only `docs`.
2. The workflow runs `waggle gate verify --base <sha> --head <sha>` (`gate/action.yml:65`). The gate reads `.waggle/control/config.yaml` at the base commit, finds `open`, and runs the lease, tier and decisions checks.
3. The lease check finds `src/api.go` outside the claim. Under `open` it prints `::warning file=src/api.go::leases: would fail (mode open): ...` and the run exits 0. The required check, if the repo has one, is green; the annotation is on the run.
4. Later, the project moves to `guard` through a Head Keeper approved change that sets `mode: guard`. The PR that changes the config is itself checked against its base, which says `open`, so it reports and passes. From the next PR on, the base says `guard` and the same finding exits 1.
5. In the other direction: a PR on a `guard` repo that sets `mode: open` is checked against its base, `guard`, so the config change is a Tier 3 finding and fails. Only an admin merge lets it in (RFC section 4; D-382, open question 2).
6. On any mode, a broken base config (a typo, `mode: watch` on this build, a symlink) exits 3 and blocks the PR, as `TestBaseConfigFaultsExit3` pins today (`cmd/waggle/gate_bind_test.go:257`).

## 4. Must stay

- `guard` output and exit codes are byte for byte today's, for a missing key, a missing `gate:` section, a missing config file and `mode: guard`.
- The mode comes from the base config only (`baseTierPolicy`, `gate_verify.go:276-280`). A PR cannot select its own mode through its head tree, a flag, an environment variable, a label, a trailer or a commit message.
- Only the exact value `open` loosens. Every other state reads as `guard`. No value is guessed or case folded.
- Exit 2 and exit 3 are the same in every mode (`gate.go:25-30`). A failing `git` call, an unresolvable revision, a missing merge-base and a broken base config all stay exit 3 in `open`.
- Claims are read, never written. `waggle claim` and its refusals do not change; `open` does not touch claim-time checks (RFC section 2, notes).
- `verify-leases-and-tiers` stays the one check name. The gate action (`gate/`) and the workflows (`.github/`) do not change.
- The approver and trailer logic (`gate_approve.go`) runs exactly as today in every mode.
- `.waggle/control` is not edited. Lowering the Tier 3 status of `config.yaml` is out of scope (T-060).
- Every existing test passes unchanged, except where this ticket adds a case to a table.
- No step narrows core item 1 or 2. A builder or guard that finds a rule cannot be built as written stops and reports; the queen raises it, marked **CUT** with the quoted core item if it would narrow one.

## 7. Threat model (D-203)

**Boundary.** The mode is a security setting: `open` turns a required check into a recorder. The mode is read from the base commit, like `gate.protected_paths` and `gate.approvers`, and `.waggle/control/config.yaml` is under the hardcoded Tier 3 prefix.

**Defended.**
- *A PR sets its own mode to `open` to pass its own violation:* the head config is never read for the mode. Test G5 runs it with a violation in the same PR.
- *A flag, environment variable, label or trailer selects the mode:* none exists. Test G7.
- *A typo or an unknown value loosens the gate:* an unknown value is a parse error and exit 3 (the gate fails closed), and only the exact string `open` loosens.
- *A missing or unreadable config loosens the gate:* a missing config file or key reads as `guard`; an unreadable or invalid one is exit 3.
- *Attacker-chosen paths or subjects in a would-be finding start a workflow command:* findings go through the existing encoders in `open` as in `guard`. Test G9.
- *An old pin meets `gate.mode`:* the old build exits 3 on the unknown key (`config.go:259`), which blocks every PR and does not loosen. This ticket writes the key nowhere, and the pin must move to a build with this parser before any hive writes the key (RFC section 3, rollout order; Head Keeper action in section 12).

**Not defended (docs say so in T-080).**
- `open` records and reports and does not protect. A repo in `open` can edit its own config, including `gate.mode`, without an admin merge, because the check passes. That is what `open` means, and it is why D-382 keeps the raise from `open` to `guard` as an ordinary change with no carve-out.
- Admin bypass (L6 in `docs/gate.md`) and the ruleset (L11) are not involved; there is nothing to bypass in `open`.
- Findings in `open` live in the run log. They are not an audit log.

## 11. Open questions

Each carries a recommended default. None may auto-apply. The test plan and the budget follow the default; a different ruling changes only the tests named.

- **Q-T076-1: In `open`, does a PR too large for the gate (`errTooLarge`, over 500 commits or 5000 paths, `gate_commits.go:18-25`) still fail?**
  Options: (a) it stays exit 1, as a gate that could not check anything is not a pass; (b) it becomes a would-be finding and exits 0.
  Recommended: (a). D-382 rules that a gate that cannot run is not a pass for exit 3, and `errTooLarge` is the same case with exit 1. The cost is that a very large PR on an open repo is blocked until it is split. Test G8 pins (a).

- **Q-T076-2: Does `gate.mode` apply to the single checks `waggle gate leases`, `tiers` and `decisions`, or only to `verify`?**
  Options: (a) `verify` only; the single checks stay strict; (b) all four honor the mode.
  Recommended: (a). The action runs only `verify` (`gate/action.yml:65`), the ticket title and D-382 name `verify`, and the single checks are tools a person runs to see a hard answer. (b) is a small follow-up if wanted. Test G10 pins (a).

- **Q-T076-3: What does this build do with `gate.mode: watch`?**
  Options: (a) reject it as an invalid value (exit 3) until T-077 adds it; (b) accept it and treat it as `guard`; (c) accept it and treat it as `open`.
  Recommended: (a). Accepting a mode that behaves differently from its name (the RFC says `watch` adds a PR comment) would mislead, and (b) or (c) would make this build quietly disagree with the build T-077 ships. Nothing writes `watch` before T-077, and any hive that does so early fails closed. Tests C3 and G6 pin (a).

- **Q-T076-4: Does this ticket write the job summary (`GITHUB_STEP_SUMMARY`) for `open`, or only warnings and the notice line?**
  Options: (a) warnings and the notice line now; the summary for `open` and `watch` in T-077; (b) the summary file here, about 25 more non-test lines.
  Recommended: (a). T-077 is named "watch summary and comment", the summary writer serves both modes and should exist once, and (b) would pass the target. The RFC table lists a job summary for `open`, so `open` is not complete on the RFC's terms until T-077 merges; the queen records that and does not call `open` done before then. The summary needs no new workflow permission, so this does not touch RFC open question 4.

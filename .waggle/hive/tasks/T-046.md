## 1. The question

D-276 asks whether the gate can run under `pull_request_target` without losing the review trigger. Stated so it has a yes or no answer:

> **Can a gate workflow that a PR cannot change for its own run produce the required check on the PR head SHA, re-evaluate it when a listed approver submits or dismisses a review, and do so without running any PR-controlled code in a context that holds a write token or secrets?**

The answer is **yes** only if all four parts below are yes. Each part is answered `yes`, `no` or `unknown`, with a source for each `yes` or `no` (a docs URL with the quoted sentence, or a probe run ID).

- **(a) Head evaluation.** Under `pull_request_target`, the job can name the PR's base and head SHAs from GitHub-written payload fields, has both commits and the claim refs in its clone (including a fork PR's head), and the check run it creates is attached to the PR head SHA so it satisfies the ruleset's required check there. Today's template takes base and head from `github.event.pull_request.base.sha` and `.head.sha` (`.github/workflows/waggle-gate.yml:35, 56-57`), which `pull_request_target` payloads also carry. Since 2025-12-08 the workflow file and `GITHUB_SHA` for this event come from the repository's **default branch**, not the PR's base branch (GitHub changelog, 2025-11-07, "Actions: pull_request_target and environment branch protections changes"; the forager quotes it). The open parts are the clone contents and where the check run attaches, since `GITHUB_SHA` is then a default branch commit, not the PR head or merge commit.
- **(b) Review trigger.** A listed approver's review **submission and dismissal both** cause a run of a copy the PR cannot change, which updates the required check on the head SHA. `pull_request_target` has no review activity type, and `pull_request_review` runs the workflow from the PR's merge ref (the PR's own copy, as today's review run does: `.waggle/hive/reviews/hive-control-d269-opus.md:30`). Candidate paths, each answered separately:
  - **Chained:** a `workflow_run` workflow on the default branch, triggered by the review workflow's completion, posts a check run on the head SHA. The triggering `pull_request_review` workflow file is the PR's own copy, so a PR can delete or rename it and the chained run never starts. The path therefore counts only if the required check starts red on every new head and only the chained run turns it green.
  - **Label:** `pull_request_target` with `labeled`; the approver adds a label after approving. Fires on a manual step, not on submit or dismiss.
  - **Re-run:** a re-run of the `pull_request_target` run; the gate reads reviews live through the API at run time (`cmd/waggle/gate_approve.go:96-160`). The re-run docs say a re-run keeps the original `GITHUB_SHA` and `GITHUB_REF` and the original actor's privileges; the repository roles table gives "re-run" of Actions workflows to Write, Maintain and Admin only, so the person re-running needs write access (the forager quotes the roles table for this row). Manual, after every approval and dismissal.
  
  A path is a **full review path** only if both submitted and dismissed re-evaluate the head check with no manual step. A label or re-run path is recorded with its cost to the approver but is not a full review path: a dismissal with no new push would leave a green check, because `approvedBy` drops a dismissed approval only when the job runs (`cmd/waggle/gate_approve.go:130-160`), where today's `pull_request_review: [submitted, dismissed]` reruns on dismissal.
- **(c) Safety.** Under `pull_request_target` the job holds a token and secrets. Yes means: no step builds, runs or sources PR content (the gate binary builds from the base revision, `.github/workflows/waggle-gate.yml:62-63`, or from the pinned Action tree, `gate/action.yml:34-35`); head commits are only read as git objects; the job `permissions:` block still limits the token to `contents: read` and `pull-requests: read` under this event; and no cache, credential or artifact written by the job can carry PR content into a later privileged run. Section 3 lists the specific checks.
- **(d) Spoof resistance.** The required check cannot be satisfied by a same-named check run that the PR's own workflows create. Under `pull_request` a same-repo PR can add a workflow whose job is named `verify-leases-and-tiers`, or create a check run with that name through the Checks API if its token has `checks: write`; both come from the GitHub Actions app, so binding the rule to that integration does not separate them (`docs/gate.md:84`, L11). If GitHub evaluates a required check by the latest run of that name, a passing spoof can override a failing protected run, and moving to `pull_request_target` closes nothing. If any failing run of that name blocks, the protected run decides. The published docs say both a check and a commit status of one name must pass, but say nothing about two check runs of one name from one app, so (d) is expected to need the probe (P4).

## 2. What the code does today (cites at `648ddc8`)

1. **Triggers.** The template and the hive workflow are identical except the Action pin line (`:68`, placeholder against a rendered SHA). Both run on `pull_request` types `[opened, synchronize, reopened, labeled, edited]` and `pull_request_review` types `[submitted, dismissed]` (`internal/scaffold/templates/waggle-gate.yml.tmpl:5-9`), and the job condition admits only those two events (`:16`). Both run the YAML from the PR's merge ref. That is the L5 hole (`docs/gate.md:78`), and the review event inherits it.
2. **The gate refuses a `pull_request_target` event.** `readPREvent` accepts only `pull_request` and `pull_request_review` (`cmd/waggle/gate_approve.go:42`). Under any other event it returns no event, so the approver check never reads reviews, `prh.sameRepo` is false (`cmd/waggle/gate_verify.go:156`), and although `GITHUB_HEAD_REF` is set (`:137`), every bound commit fails with `claim does not name this pull request's branch` (`cmd/waggle/gate_commits.go:370`). `cmd/waggle/branches_test.go:152-155` pins that exit 1. Adopting `pull_request_target` therefore needs a product change in `cmd/waggle/`, not only in the template. The spike does not make it; it records the size in the follow-up (section 6, O1).
3. **Tests that ban the event.** `internal/scaffold/guard_template_test.go:68` fails if the template contains `pull_request_target`; `internal/scaffold/gate_action_test.go:66` and `:132` ban it in the Action text and the rendered workflow. T-035 section 2.6 and T-036 section 5 list it as a must-fix. A follow-up must lift these with its own threat model, as D-276 says.
4. **The build is base-only already.** The gate source comes from `$BASE_SHA` (the payload's PR base) in a separate worktree (`.github/workflows/waggle-gate.yml:41, 62-63`), or from the Action's pinned tree with `GOPROXY=off` and `GOFLAGS=-mod=readonly` (`gate/action.yml:24-35`). The workspace checkout under `pull_request` is the merge commit; under `pull_request_target` it is the default branch commit in `GITHUB_SHA`, which differs from `$BASE_SHA` for a PR into another branch. `actions/setup-go` reads `go-version-file: go.mod` from the workspace (`.github/workflows/waggle-gate.yml:48-51`) with its default cache on; under `pull_request_target` that cache is the default branch's, shared with other privileged runs (section 3, C4).
5. **What already covers L5 here.** `.github/CODEOWNERS:11` names `/.github/workflows/` (D-140), binding only with "Require review from Code Owners" on in the main ruleset. The gate itself fails any change under `.github/workflows/` as a hardcoded control path that only an admin bypass merges (`docs/gate.md:49`), but only when the honest copy runs. The recipes require code-owner review on `.github/workflows/**` (`docs/recipes/README.md:14`).
6. **Review-triggered run on the head, still unverified.** T-035 section 2.7 item 2 asked the queen to confirm, after pin `97127fc` (D-269), that a review-triggered run updates the required check at the head SHA; the queen summary still carries it as open (`.waggle/hive/handoff/queen.md:60`). The spike answers where that check attaches from this repo's own check runs (section 4.2, R1), because it is the `pull_request` baseline that every outcome is compared with.

## 3. Safety checks for part (c)

Each is answered from docs, and from the probe where docs are silent.

- **C1, token scope.** Does a job-level `permissions:` block bound the `GITHUB_TOKEN` under `pull_request_target` for same-repo and fork PRs, and does the workflow-level `contents: read` still apply? Probe: one step attempts a harmless write (create a label) and must get 403.
- **C2, secrets.** Which secrets (repository, environment, organization) a `pull_request_target` job from a fork PR can read. The gate needs none; record whether adopting the event exposes any secret an adopter's repo holds, since the template would run there.
- **C3, which workflow copy and which source runs.** Default-branch sourcing is a fact since 2025-12-08 (section 1 (a)); the forager quotes the changelog and the events page and records the consequences. A PR into a non-default branch is gated by the default branch's workflow, while the gate binary (present=true) builds from the payload's `$BASE_SHA`, the PR's base. A writer who controls a non-default branch could then have its code built in a job that holds secrets reachable from fork PRs. Under D-203 that is a note (it needs push rights, and a same-repo `pull_request` run already has that exposure), but the findings record it for adopters and say whether the follow-up should build from `GITHUB_SHA` or refuse non-default bases. P10 probes it.
- **C4, cache.** `actions/setup-go` caches by default; privileged runs share the default branch cache. Today only base modules are downloaded, but the follow-up must set `cache: false` (as the Action already does, `gate/action.yml:22`) unless the docs show the scope cannot be written from this event.
- **C5, persisted credentials.** `actions/checkout` writes the token into `.git/config` by default. No PR code runs, but the follow-up should set `persist-credentials: false`; record whether the later `git fetch` of claim refs (`.github/workflows/waggle-gate.yml:30`) then still works on a private repo.
- **C6, reading head objects.** Fetching the PR head (for a fork, `refs/pull/<n>/head`) brings objects only. Confirm nothing the gate runs reads attributes, hooks or config from the head tree in a way that executes code: git filter and diff drivers need config, which the clone does not take from the tree; `lfs` is off in `actions/checkout` by default.
- **C7, expressions.** The template interpolates only GitHub-written fields into `env:`, never into `run:` (`.github/workflows/waggle-gate.yml:34-35, 55-58`; `guard_template_test.go:68` forbids `head.ref`). Record that the same rule holds unchanged under `pull_request_target`.

## 8. Threat model (D-203)

**Attacker, for the question itself:** a same-repo PR author (an agent with push rights to its own branch, the case the gate exists for) and a fork PR author. Either controls every file in the head tree, including `.github/workflows/**`, and may add workflows and check runs that its event's token allows. **Trusted:** the default and base branches, the base config and claim refs, the ruleset, listed approvers, the Head Keeper.

**For this ticket's own work:** the forager reads public docs and this repo, and writes nothing. The probe repo is throwaway, holds no secret and no Waggle code, and is deleted after.

**Must-fix in the findings:** an answer of `yes` or `no` without a quoted docs sentence or a probe run ID; a forum post or blog used as the only source of an answer; any row of section 1 or section 3 left out; a label or re-run path counted as a full review path; a probe step written as a forager or queen step instead of a card item; a probe workflow that uses a third-party action other than the two named in 4.1, uses a tag instead of a full SHA, interpolates `${{ }}` into `run:`, or stores a secret; an outcome other than the one the section 6 rule selects from the table's answers; a `gh` call that is not a GET on this repo.

**Note, not must-fix:** GitHub changing the documented behavior after the retrieval date (the date column records it); behavior that differs between GitHub plans the probe cannot test; the C3 non-default-base build exposure (needs push rights to that branch).

**Guard prompt sentence (repeat verbatim):** "Threat bar (D-203): this is a findings note. Must-fix is an answer with no quoted docs sentence or probe run ID, a missing row, a manual path counted as a full review path, an outcome other than the one the brief's section 6 rule selects, a probe step assigned to anyone but the Head Keeper, or a probe workflow that runs PR content, stores a secret, or uses an unpinned or third-party action; a doubt about GitHub's future behavior is a note."

# Guard review: T-023 phase C (PR #50), fable

Verdict: must-fix
Risk-Tier: 3

PR #50, branch `t-023c`, head `05343b4`, base `23bdf75`. Second independent guard (fable); no coordination with the other model.

## Intent Summary

Phase C is the first slice that launches a real agent. `dispatch.Run` claims the ticket, provisions the worktree, snapshots host state, starts headless `claude -p` in its own process group through the `CellRuntime` seam (`hostCell`), streams into `Collect` while renewing the claim, runs the 7.2 checks under a pinned git environment, pushes from the host only on a clean pass, writes `result.json`, and `waggle dispatch` exposes it with the section 4 exit codes. Three commits, 1186 added non-test lines (matches the PR description; D-169 accepted this count and set the phase C stop at 1350 including fix rounds). Every file is inside the phase C lease (`internal/dispatch/`, `internal/config/local.go`, `cmd/waggle/`: only the `dispatch` case and one usage line in `main.go`, only the keeper-id pattern in `local.go`). Stdlib only, `go.mod` unchanged, sign-off present on all three commits under the Keeper's git identity, no en or em dash in output. `product-ci` is green on ubuntu 24.04 / go 1.23.12 with both the plain and symlinked repo path variants.

Blast radius: Tier 3 by content. The file-first, git-second check design is sound against an agent that writes files and refs: every host-state probe I ran (admin dir files, `HEAD` detach, hooks, `info/exclude`, `info/attributes`, a common-config filter, `.git` rewrite to a planted gitdir, new refs, tags, main-checkout writes, another ticket's claim ref, `pushurl`) ended exit 1, nothing pushed, worktree tainted, and no planted filter ran through a pinned check. The admin-dir pin, the canonical-path precondition, the sign-off rule, the tainted marker, the dispatch lock, the two-fetch claim accounting and the `redirectVars`/`scrubbedGitEnv` tie-out all hold up.

What the branch misses is a single class of defect: dispatch runs git against the agent-controlled repository in places that are not pinned and not gated on the config check, and the push re-resolves the branch ref after the checks instead of pushing the exact commit it validated. Four concrete instances follow. All fixes are small (about 20 added non-test lines total) and fit inside the remaining D-169 budget.

## Blocking Issues

Ranked most to least severe. Estimated added non-test lines in brackets. If the Keeper caps the fix round, keep B1 and B2 (they let unchecked content or withheld credentials escape); B3 and B4 are narrower and could defer to a follow-up, but all four fit.

**B1. The push re-resolves the branch ref after the checks, so a surviving background process can substitute an unchecked commit** [about 3 lines]. `run.go` line 290 runs the checks against `refs/heads/<branch>` inside `ck.run`; line 291 reads `HeadOID` with a second `rev-parse`; line 302 pushes `refs/heads/<branch>:refs/heads/<branch>`, which git resolves yet again at push time. Each read is a separate resolution. The process-group kill (`cell_unix.go`) reaps only the worker's group; a process that leaves the group (setsid or double fork) survives, which `TestProbeSetsidSurvivor` confirmed acts after `Run` returns. A survivor that flips the branch between the check and the push makes dispatch push a commit the checks never saw. My `TestProbePushRace` (12 runs, a survivor alternating the branch between a checked good tip and an unchecked child) pushed the unchecked child to the remote in 1 of 12 runs, exit 0, `pushed=true`, no violation recorded. This violates AC5 ("Nothing is pushed unless every check passed") and section 5 step 8. The merge gate would re-check the commit later, but the guard and `result.json` present the pushed head as the validated one. Fix: have `ck.run` resolve the branch OID once, validate that OID, and return it; push `<validatedOID>:refs/heads/<branch>` (a literal object id, not the ref), so a later ref move cannot change what is pushed. Set `HeadOID` from the same OID.

**B2. The pre-check claim sync (remote mode) runs git under the agent's repo config with the Keeper's full environment, defeating the env allowlist** [about 10 lines]. `run.go` lines 284 to 288 call `backend.ClaimOID` (which runs `git fetch` against the remote) before the file-hash step in `ck.run` has verified the repo config. The Comb backend builds its child env from `os.Environ()` (section 8's dropped variables, `GITHUB_TOKEN`, `GH_TOKEN`, `SSH_AUTH_SOCK` and the rest, are present for the host, only the worker env is scrubbed), and it does not pass dispatch's pinned `-c` flags, so an agent-written repo-config value that names a program runs it. `TestProbeFinalSyncUnderPlantedConfig` planted `remote.origin.uploadpack` pointing at a wrapper; the wrapper ran during the post-session sync, after the worker had exited, with the Keeper's full environment. The same reaches execution through `core.sshCommand`, `credential.helper = !cmd`, `url.<base>.insteadOf` plus `protocol.ext`, or `core.fsmonitor` for the relevant remote type (the `fable-git-exec-paths.txt` experiment shows the unpinned fetch runs the repo `core.fsmonitor` command; that is also how the `fsmonitor` admin probe's canary fired). The run then reports the config change and blocks the push, so no bad commit escapes, but the command has already executed with credentials the section 8 allowlist explicitly claims to withhold from the worker. This is remote-mode only and so does not bite our local-only hive before phase F (D-119), but the code ships remote mode and phase C's own fixtures exercise it. Fix: run the file-hash comparison before the final sync and skip the sync (with a `claim_sync_skipped: host config changed` warning) when it found any change to `config`, `config.worktree`, `info/`, the admin dir or the global config. The tampered-mirror case the sync exists for is moot when the config is clean, and a dirty config fails the run regardless.

**B3. The post-run `git log` honors the repo's `log.showSignature` and `gpg.program`, executing an agent-named program** [about 1 line]. `check.go` line 219's commit walk runs `git log` through `RunIn`, whose pinned argv (`worktree.go` line 52) sets `core.hooksPath=/dev/null` and `core.fsmonitor=false` but not `log.showSignature`. An agent that writes `log.showSignature=true` and `gpg.program=<script>` to the repo config and commits a blob with a `gpgsig` header makes the post-run log spawn the script. `TestProbeLogShowSignature` confirmed the canary fired, and the wrapper captured dispatch's own pinned `git log --reverse -z -n 501 --format=... <checkBase>..refs/heads/t-023` as the caller. As with B2 the config change is later flagged and the push blocked, so this is an execution-under-Keeper-env escalation rather than a bad push. Fix: add `-c log.showSignature=false` to the pinned argv in `RunIn`. Verified: with that flag the probe canary no longer fires and the suite stays green.

**B4. The post-run `git status` descends into a staged nested repository and runs its clean filter** [about 3 lines]. `check.go` lines 66 and 210 (and the reuse check at `worktree.go` line 402) run `git status --porcelain` with no `--ignore-submodules`. An agent that `git init`s a directory inside the lease, gives it a `.gitattributes` and a `filter.<x>.clean` command, and stages the gitlink makes the pinned host `status` enter that nested repository and run the filter. `TestProbeSubmoduleStatusSpawn` confirmed the canary fired from the pinned status call. Fix: add `--ignore-submodules=dirty` to the three `status` calls; the experiment (`fable-git-exec-paths.txt`) shows this stops the descent while still reporting the staged gitlink (so the dirty rule still fires), and a committed gitlink is caught by `CheckChanges` as mode `160000`. `git worktree remove` without `--force` already refuses a worktree holding a gitlink, so the success path cannot delete one. Verified: with the flag the probe canary no longer fires and the suite stays green.

## Rulings on the builder interpretations

- **Budget stop `end: "max_budget"`, exit 5:** exit code sound (`outcome` maps `error_max_budget_usd` to `cut="max_budget"`, exit 5, the right "needs the Keeper" bucket). But `max_budget` is not in section 9.1's `end` value list or its T-022 ledger mapping, so `result.json` now carries an undocumented `end`. The ledger writer is phase D, so nothing breaks yet. See N1.
- **A limit stop with only a dirty tree stays exit 5:** sound. `outcome` treats a dirty-only tree under a limit as `cut` (exit 5), and a non-dirty violation under a limit as `lease_violation` (exit 1). The ordering is correct and `TestWaggleCommandsAndOutcome` covers both.
- **Post-run checks use the in-memory lease from `AcquireClaim`; the own claim ref excluded from rule 4 and not otherwise verified:** sound per section 7.2 (the spec excludes this ticket's claim ref from rule 4, for keepalive moves) and safe, because `CheckChanges` runs against the in-memory lease, so rewriting the claim ref cannot widen the check. See N2 for the local-mode residue.
- **`dispatch.lock` taken before fetch and claim:** sound. The lock is acquired (line 189) before the `seq` that fetches and claims; `refuseDirs`, config load and `Verify` run before it but write nothing. Test 24 confirms a held lock exits 3 with no ref write.
- **`refuseDirs` uses `comb.HardcodedTier3Prefixes` plus `comb.DirsOverlap`:** sound and matches section 5 step 1 (pre-refuse only Tier 3 and `.waggle/`, before any fetch; the Comb stays the authority). Test 23 confirms zero fetches for a refused dir.
- **Shell-script `claude` fixtures, unix-only tests:** acceptable. Section 11 names the `GO_WANT_HELPER_PROCESS` pattern; the builder used a shell `claude` script instead, which achieves the same (canned stream-json plus scripted git) and is consistent with dispatch being unix-only at runtime, with test 27 guarding the Windows cross-compile.
- **No per-turn usage event:** a deviation from section 9.2, which lists `usage` (per assistant turn) among the events. Emitting it would need the phase A `Collect` to surface per-turn usage, which its signature does not, and `internal/runtime/` is outside this lease, so the omission is forced. See N3.
- **New `Git.Remote`/`Git.Pinned`:** sound, within the carry-item edits; `pinned()` is used for every post-run call. Test `TestPinnedEnv` covers it.
- **New `waggleCommands` WAGGLE.md parser:** sound. It reads `WAGGLE.md` from base (not the working tree), takes the first backtick span of each section 3 bullet and skips `<placeholder>` entries. See N4 on its coupling to the `## 3.` heading.
- **A repo without a `.waggle/worktrees/` entry: a planted new admin entry fails rule 4:** sound. `hostFiles` records the set of `worktrees/` entry names, so a new entry is a diff key and a `host_state` violation; test 20's "new admin entry" plants a valid-looking gitdir so git does not prune it first.
- **Kill test assumes a reaping init; "new admin entry" plants a valid gitdir:** both sound for the unix CI target. The group kill reaps the in-group grandchild and the ESRCH check then holds; the planted gitdir keeps the entry from being pruned so the snapshot diff is what is asserted.

## Notes

- **N1 (scout):** section 9.1's `end` list and T-022 ledger mapping predate the C0 `--max-budget-usd` allowlist and omit `max_budget`. Reconcile before phase D wires `usage.Append`: add `max_budget` (mapped to itself or to the limit category) or map the subtype to an existing `end`.
- **N2 (scout, low):** in local mode there is no post-session claim re-write (the final sync is remote-only), so an agent's last-act rewrite of its own claim ref persists undetected (rule 4 excludes the own claim ref by design). Content is still lease-validated; the corrupt claim is healed by the next claim op or a force-release. The CI gate cannot see local claims anyway (which is why `verify-leases-and-tiers` is red on this PR, the expected D-168/Q-T023-19 gap, not a code defect; `product-ci` is the relevant check and it is green).
- **N3 (scout):** either drop `usage` from section 9.2's phase C event list or schedule the per-turn event for when the stream surfaces per-turn usage (phase E), since the phase A `Collect` surface does not provide it and `internal/runtime/` is outside the phase C lease.
- **N4 (builder, low):** `waggleCommands` keys on the `## 3.` heading; if WAGGLE.md section 3 is renumbered the worker silently gets no build or test commands. Consider matching the section by title as well.
- **N5 (builder, low):** the dirty-tree `status` honors the Keeper's XDG global ignore file even under the pinned env, because `core.excludesFile` defaults to `$XDG_CONFIG_HOME/git/ignore` independently of `GIT_CONFIG_GLOBAL`. `TestProbeGlobalIgnore` showed an agent that writes that file can hide an untracked file from the dirty rule. No content escapes (untracked files are never committed or pushed), so this is not a blocker, but adding `-c core.excludesFile=/dev/null` to the `status` calls (alongside the B4 flag) closes it cheaply.
- **N6 (limitation):** the keepalive claim renewal runs during the session through the Comb backend with the Keeper's full environment and the agent-controlled repo config, so a planted `core.sshCommand` or `url.insteadOf`+`protocol.ext` can execute during the session with withheld credentials. The post-run config hash is the backstop (it blocks the push and taints). Fully fixing it would mean re-verifying the repo config before each renewal; at minimum, state in `not_enforced` that claim pushes during a session run under the repo config the live worker controls.

## Findings

Blocking issues: none.

Non-blocking notes:

- **N1 (security, low): raw control bytes from the ledger reach the terminal.** `Render` prints `Role` verbatim. A ledger line with `"role":"\u001b]0;pwned\u0007\u001b[2Jx"` makes `waggle status` emit OSC title-set and clear-screen sequences (confirmed with the built binary and `od -c`); a `\n` or `\t` in a role breaks the tabwriter rows. Phase A escaped stored values with `%q` for the same reason. The ledger is 0600 and launcher-written, so the live vector is a hostile clone that commits `.waggle/control/usage.jsonl` (this repo's own ignore block does not list it yet; the scaffold template does after T-021 phase B). Follow-up: quote any role that is not plain printable (`strconv.Quote` or a `[^[:print:]]` check) in `Render`, or have `Read` reject such roles as a `BadLine`. Two lines.
- **N2 (security, low, for T-023 phase D): `Append` and `Read` follow symlinks.** `Append` on a symlink writes through it, and on a dangling symlink creates the target (mode 0600). `Read` on a symlink to a FIFO blocks forever (confirmed: status hung until a writer opened the pipe). With a committed symlink in a hostile repo, `Append` would write a JSON line whose `model` string is repo-controlled into any file the Keeper can write (for example a shell rc file, where `"$(...)"` inside a JSON string is live). No code calls `Append` yet, and dispatching agents in a hostile repo already runs its code, so this does not block. Before T-023 phase D wires the writer: open with `O_NOFOLLOW` (or `Lstat` and require a regular file) in both `Append` and `Read`.
- **N3: misleading totals from out-of-range numbers.** The reader trusts the writer, as the brief says. Probed results: negative tokens print `in 5k (200% cached)  out -2000000`; two `int64` max inputs overflow to `in -2 (-0% cached)`; two `1e308` costs print `est. $+Inf`; `1e12` tokens prints `1000000.00M`. No panic in any case. Cheap hardening if wanted: `Read` reports negative counts as a `BadLine`. Not required by the brief.
- **N4: a line of 1 MiB or more makes `waggle status` exit 3 and hides the claims block.** A 1,048,575 byte line loads; 1,048,576 (exactly 1 MiB, before the newline) and over fail with `bufio.Scanner: token too long`. The doc comment says "a line over 1 MiB", which is off by one, and the brief says malformed lines are "never fatal". The 1 MiB buffer is what the brief specifies and only corruption produces such a line (records are small; 3,200 concurrent 200 KB appends never produced one), so this is a Keeper call, not a defect. If the Keeper wants status to degrade instead, `Read` can switch to `bufio.Reader.ReadLine` and record oversized lines as `BadLine`.
- **N5: `Append` keeps looser permissions on an existing file** (a 0644 ledger stays 0644). The brief only asks for 0600 on create. T-023 may want a one-time `Chmod`. Nit.
- **N6: an empty or all-bad ledger prints `Usage: none recorded (<path> absent)` although the file exists.** This is the brief's literal wording for "absent or empty", so accepted; the stderr warning covers the all-bad case.
- **N7: a missing `cost_usd` key and an explicit `null` both read as unknown** (`est. $ n/a`). Conservative and correct for the writer the brief describes.

Judgment calls:

1. `renderStatus` gained a `usageBlock []byte` parameter instead of reading the ledger itself: accepted. It keeps the render pure and the phase A golden test only changes one call.
2. `Summarize` canonicalizes with `comb.ParseTicketID` and falls back to the raw id (sorting as 0) for direct callers that skip `Read`: accepted. `T-9`, `T-009` and `9` group as `T-009`; `T-0`, `t-1`, ` T-1`, `T-1000000`, `""` and `null` tickets are `BadLine`s with the right line numbers.
3. Roles with an empty name print as ` 1 sess`: accepted, the writer validates roles.

### TOCTOU and O_NONBLOCK analysis

The `Lstat` precheck is advisory. On unix the guarantee comes from `O_NOFOLLOW` (a symlink swapped in after `Lstat` makes `open` fail with `ELOOP`, including with `O_CREAT`) plus the post-open `fstat` on the descriptor (a FIFO or device swapped in is refused after open, and `O_NONBLOCK` keeps that open from blocking). Both checks act on the inode the write then uses, so there is no window between check and use. The only residual effect of a swap is that `open(2)` runs on a device node before the `fstat` refusal; on a ledger path that is harmless in practice.

`O_NONBLOCK` on a regular file is harmless for the append. POSIX gives it no effect on regular-file reads and writes, and Go does not register regular files with the poller (kqueue is skipped for `S_IFREG` on darwin and the BSDs; epoll refuses them on linux), so `Write` stays a plain blocking `write(2)` with `O_APPEND`. The 4 MiB probe and the existing 16 goroutine and 8 process append tests confirm one intact line per record.

## Intent Summary

Phase B lands the config half of D-075. `internal/config/context.go` adds `ParseContext(cfg, roster)` and `LoadContext(repoDir)`, which read the optional `context:` block (`profile` plus per-role `roles`) with T-004's subset parser into T-021 phase A's `runtime.ContextPolicy`; an absent block is `balanced` with no overrides, and every unknown key, wrong shape, bad profile word, non-roster role id or `waggled` key fails with `ErrInvalidConfig`, key path and line. The shared `policy()` body behind `LoadPolicy` and `ParsePolicy` now runs `ParseContext` after the roster loads, so a bad block refuses `waggle init` (claude-code) and `waggle upgrade --runtime claude-code` at plan time, before any write. `internal/layout` gains `Handoffs` and `Usage`, and both join the `.gitignore` marked block that `init`, `init --force` and `upgrade` write. The Head Keeper commit (written by the builder under D-154) adds the `context:` block with its one comment line to `config.yaml.tmpl` and a `## Handoff` section to `roles/queen.md`. Blast radius: every hive's ignore block gains two lines on its next upgrade, every claude-code hive with a `context:` block must keep it valid against the roster the upgrade is about to write (a stale role key after T-020 refuses the upgrade, by design), and every queen session in every hive now carries the handoff instruction. No guard setting can be lowered from config: the floor stays in `ContextPolicy.Settings`, which phase B does not touch. `go.mod` unchanged, stdlib only.

4. The parser. T-004's `Parse` looks up only `version`, `forge` and `leases` and ignores other top-level keys, so `context` coexists with it the way `runtimes` and `cell` already do; `ParseContext` runs `parseTree` a third time on the same bytes, which cannot fail once `Parse` has passed. Live, through `waggle upgrade --apply` on a scratch hive, every bad shape was refused with nothing written (`git status --porcelain` empty each time) and the message carried the line and key path: `line 41: context.roles.architect: unknown role; keys must be roster role ids`, `line 39: context.profile: must be lean, balanced or thorough, got "Lean"`, `line 40: context.roles.waggled: waggled is the daemon, not a roster role`, `line 40: context.budget: unknown key`, `line 38: context: must be a mapping`, `line 39: context.roles: must be a mapping of roster role id to profile`, `line 39: context.profile: must be a scalar, not a mapping`, `got ""` for an empty value, and `line 49: context: duplicate key` from `parseTree`. Quoted values (`"balanced"`, `'thorough'`), trailing spaces and trailing comments are accepted, matching the rest of the config grammar. Keys are visited in lexical order (`sortedKeys`), so with two errors in one block the lexically first is reported, not the first in the file; the T-004 sections behave the same. A nil or empty roster map rejects every `roles` key, so a missing roster fails closed. `ParseProfile`'s `ErrInvalidProfile` is replaced by `ErrInvalidConfig` at the config boundary, which is what section 7.1 asks for; nothing in the tree relies on the runtime sentinel from config.

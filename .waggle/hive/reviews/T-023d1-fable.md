## Blocking Issues

**B1. `host-files.json` records the state after the push and the worktree removal, not the snapshot the checks verified** [about 2 lines]. `run.go` line 376 calls `saveHostRecord(dir, common, ...)`, which hashes `hostFiles(common, "")` fresh at that moment. The 7.2 checks ran on `ck.before.files` against a compare taken at `ck.run`; between that compare and the save come the push (remote mode) and `git worktree remove`, several hundred milliseconds that a survivor can target. My `TestProbeSurvivorAfterCheck` (run B in `media/T-023d1/fable-probe-output.txt`) starts a child in its own process group that polls the git wrapper log for `worktree remove`, then writes `hooks/post-checkout` and appends a `[remote "evil"]` section to the common `config`. Run 1 ended exit 0 with no violation (correct: the writes came after the compare), and the record it saved holds a hash for `hooks/post-checkout` and the modified `config`. Run 2 then passed the record check and ran clean, exit 0, no violation: the planted hook and config line are now the baseline, and nothing will ever name them. Item 1 exists for exactly this process ("the next run compares it with fresh hashes ... a difference is exit 3 naming the earlier run"), and `not_enforced` concedes only a survivor that also rewrites the record; here it did not have to. Fix: save `hostBase(ck.before.files)`, the map the checks verified (the run was clean, so it equals the state at the compare), and keep the compare side as it is. With that, the probe's run 2 is exit 3 naming run 1.

**B2. `TestStdoutHolder` calls `t.Skip` when `perl` is absent** [about 10 test lines]. `d1_test.go` line 110. Section 11 opens with "Never `t.Skip`" and AC13 repeats it; this is the only skip in `internal/dispatch/`. CI and this Mac both have perl, so the test runs today, but a skip is a silent miss on exactly the machine where the holder behavior would differ. Fix: spawn the setsid child through the helper-process pattern section 11 names (`GO_WANT_HELPER_PROCESS` on the test binary, `SysProcAttr{Setsid: true}`), or through `python3 -c 'import os; os.setsid(); ...'` with no fallback, and fail rather than skip when the helper cannot start.

## Notes

- **N1 (D-176 facts, for the Keeper ruling; facts, not a design).** Measured with the pinned Claude Code 2.1.304 on this Mac, started exactly as the host cell does (Setpgid, stdout on a pipe, allowlisted env, haiku, one Bash call `perl -e 'sleep 40'`), and with a stdlib probe on darwin and in a linux container (Debian 12, kernel 6.8, under Colima):
  1. The Bash tool's shell is a **session leader**: `/bin/zsh` pid 65633 has pgid 65633 and sid 65633, its perl child the same, while the worker (`claude`) has sid equal to dispatch's. Claude Code spawns the tool shell with its own session (node `detached`), not only its own process group. A sweep that kills every process in the worker's session therefore finds nothing: in the probe it killed 0 and the perl survived the group SIGKILL. `SysProcAttr{Setsid: true}` on the worker does not change this: the stdlib probe shows a session sweep catches a `setpgid(0,0)` child (same session) on both OSes but never a `setsid()` child, and the tool shell is the latter.
  2. The tool child's fds 0, 1 and 2 are `/dev/null` and a regular output file under Claude Code's temp dir, not dispatch's pipe. Tool children do not hold the worker's stdout, so the item 5 holder path (`stdout_held`) is not triggered by them; the pipe hit EOF as soon as the leader was reaped.
  3. After the leader dies the orphaned tool shell is reparented to pid 1 on both OSes, so a parent-chain walk works only before the kill (snapshot the descendants, kill them, then the leader). Linux offers `prctl(PR_SET_CHILD_SUBREAPER)` so orphans reparent to dispatch instead; macOS has no subreaper. The builder's probe also shows SIGTERM lets Claude Code clean its own children up, so the `stop()` path that sends SIGTERM first loses them only when the grace expires; the path that always loses them is a leader that exits (or is SIGKILLed) with a tool child still running, since the group kill after `Wait` cannot reach another session.
  4. With the fake adapter (`TestProbeSurvivorHoldsStdoutLeaderExits` and `TestProbeSameGroupChildDies`): a plain `&` child dies with the group on leader exit and its late write never lands; an own-group child that inherits stdout survives `Run`, its write at 2 s is reported as `dirty`, and `Run` takes timeout plus 1 s (N2). A survivor that writes after the compare is B1.
  Darwin detail for whoever writes the fix: the stdlib has no `syscall.Getsid` on darwin or linux; `syscall.Syscall(syscall.SYS_GETSID, ...)` works on both (310 and 124).
- **N2 (builder, low; part of the D-176 round):** once the leader is reaped the group is already killed, so only an out-of-group process can still hold the pipe; waiting for the timeout before closing it (item 5's wording) turns a session that already delivered a success result into `end: timeout`, exit 5, after the full 120 minutes. Probe 1b: leader exit 0 with a result event, own-group child holding stdout, 4 s timeout, `Run` returned after 5.6 s as `timeout` with `stdout_held`. Closing the read end a grace period after `exited`, regardless of the timeout, would keep the result the leader produced.

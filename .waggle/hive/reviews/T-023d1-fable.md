### 1. The `037ba4f` hardening, and the hunt for a stray signal

Read against the diff `32b9812..037ba4f`: `newTracker(root<=1)` returns `&tracker{blind: true}` with a nil `seen` and root 0, and `observe` drops the table whenever `err != nil || t.root <= 1`, so an inert tracker never writes `seen` (the nil map is only read) and `sweep` on it breaks at the first empty `live`; `observe` skips `p.pid <= 1 || p.ppid <= 1` in the grow loop and `live` keeps `p.pid > 1` only; the old `poll` returned early on a `procTable` error and left the previous `live` for the sweep (the incident path), the new one empties it and sets `blind`; `sweep` kills by pid only when `p.pid > 1 && p.pid != t.self`; the pgid guard `p.pgid > 1 && p.pgid != syscall.Getpgrp()` is unchanged; `runSession` warns `survivors_unchecked` when `tr.blind`. The builder's seven-mutation run on linux (`builder-verify4-linux-fixremoval.txt.txt`) shows the four new `TestObserve*` data tests catch each `observe` and `newTracker` guard; the sweep pid guard is the one they cannot reach (fix-removal results below). The four data tests pass on darwin here (`fable-confirm2-host-suite-darwin.txt`, whole suite ok, dispatch 151 s).

Paths I looked for, with the facts (`fable-confirm2-darwin-output.txt`, `TestFableC2SessionFacts` and `TestFableC2LiveIsTheTargetList`):

- **Which session and group the worker is in.** The worker is `Setpgid`, so its group is its own pid and its session is inherited from dispatch: run from the queen's Bash tool it is the tool shell's session (here sid 6123, a `zsh` that Claude Code started with `setsid`); run from the terminal it is the Keeper's login session. The table lists exactly three groups in that session: dispatch's own (skipped by the guard), the worker's, and pid 0's.
- **A tracked process in a Keeper group.** `setpgid(0, G)` needs G in the caller's session. From the queen's Bash tool the Keeper's interactive shell (sid 39729 here) is in another session and cannot be joined. From the terminal it can: a descendant that joins the interactive `zsh`'s group would make the sweep send `SIGKILL` to `-G`, and the guard skips only `Getpgrp()`. The data probe shows it: a fabricated tracked process with `pgid 7000` (the Keeper's shell) is in `live` with "group kill would be sent true", one with `pgid 4242` (dispatch) is "false". No program does this by accident (Claude Code's tool shells `setsid`, which puts their whole subtree in a session the Keeper's shell is not in); it takes code in the worker's tree that calls `setpgid` on purpose, and that code can already `kill -9` the same group itself. No new capability, so a note (N15), not a blocker.
- **A group the worker joined via `setpgid`.** Same analysis: the group id is a pid in the same session, and the only groups there are dispatch's (skipped), the worker's own and whatever the Keeper's shell has in that session.
- **Pid reuse between observe and kill.** The identity in `seen` is pid plus start (microseconds on darwin, clock ticks on linux); a reused pid with another start is not in `live` (data probe: pid 502 reappearing with start 99 is dropped; `TestSweepSkipsReusedPid` in the suite). The remaining window is the one between the sweep's poll and its `kill`, about 25 ms plus one table read; a wrong victim there needs the pid space (99998 on darwin, 4194304 in this container) to wrap inside that window. No practical path.
- **`kill(-pgid)` of a group whose leader is dead.** XNU does not hand out a pid while a group or session with that id exists, so a tracked process's pgid names a group whose members all joined it; on linux `setsid` and `setpgid(0,0)` refuse an id that is a live group, so a reused pid cannot become that group's leader either. The members are the worker's descendants or deliberate joiners.
- **The darwin path.** `subreaper` is false, `startedAfter` is always false and `kids[t.self]` is always false, so dispatch's own children are never tracked on darwin; a tracked process is reached only by the ppid chain from the live root or by its own recorded identity. A failed `sysctl` after five tries is `blind`.
- **A failed read during the sweep.** `observe` empties `live`, `sweep` breaks, `survivors_unchecked` is reported, nothing is signalled. Fail-safe in the right direction; the survivors are then alive and only named by the warning (N18).

### 6. Darwin catch rate and the recommendation

Measured without `sweep` (`TestFableC2CatchRate`): the leader is `Setpgid` like the worker, lives 200 ms, and runs a tool shell under `setsid` like Claude Code's Bash tool; the tool shell backgrounds a child that records its pid and sleeps, then exits after a hold; "caught" means the child's pid is in `seen` when the leader is reaped, which is exactly the set the sweep would kill. Tool shell exiting at once after `cmd &` (its remaining life is one `fork`/`exec` of `sleep 0`, a few ms): 25 ms 7/20, 10 ms 0/20, 5 ms 4/20, 2 ms 20/20, 1 ms 20/20. At 25 ms with the tool shell held 10 ms: 8/10; 30 ms: 10/10; 100 ms: 10/10. The builder's shape (a perl parent that exits with no further work, a sub-millisecond window) gave 0/65 at 50, 25 and 10 ms, 15/40 at 5, 20/40 at 2 and 61/65 at 1 ms. The two series agree on the rule: the catch rate is set by how long the child's parent lives after the fork, not by the interval, and the common tool-shell shape lives a few milliseconds at most. The non-monotonic 25 ms figure is phase: the fork lands at a nearly fixed offset from the tracker's start, so the 25 ms ticks either straddle it or not.

Cost (`TestFableC2PollCost`): one `sysctl kern.proc.all` read is 272 us for 596 processes on this Mac, 1.1% of a core at 25 ms, 5% at 5 ms, 27% at 1 ms, for the whole session.

Recommendation: **keep the tracker at 25 ms (D-191) and state the gap plainly.** Dropping the darwin tracker would lose the shapes it does catch (a `setsid` child of a live parent, which is the foreground `go test` case of the D-176 proof, and anything whose parent lives 25 ms or more), and changing the interval buys nothing that closes the gap: 2 ms catches my shape but half of the builder's, 1 ms costs a quarter of a core and still misses 4 of 65. What is not honest today is the implied width. D-191 says the sysctl read "narrows the macOS window about tenfold", which is true of the window and not of the outcome: for a tool command that backgrounds a child and returns, the catch rate at 25 ms is between zero and about a third, where at 250 ms it was zero. The `NotEnforced` line ("one that daemonizes between two polls escapes") reads as if only a deliberate daemon escapes. I would change it to name the shape: "on macOS a background child whose parent exits before the next 25 ms read, which is the usual `cmd &` from a tool shell, escapes until T-024", and have the phase F trial report carry the same sentence. The rest of the line is honest: the hook and config writes of an escaped child are named by the next dispatch's host record (confirmed at `d95aa72`), its ref and main-checkout writes are not. For T-024, if the Cell does not cover process tracking: `kqueue` `EVFILT_PROC` with `NOTE_TRACK` on the worker delivers a `NOTE_CHILD` event for every fork in the tree, so there is no window at all; about 40 lines of stdlib `syscall.Kevent`, darwin only.

### Notes

- **N15 (scout, zero lines).** When dispatch runs from the terminal, the worker's tree shares the Keeper's login session, and a descendant that calls `setpgid` into the interactive shell's group turns the sweep's `kill(-pgid)` on that shell. Only deliberate code can do it and such code can kill the shell directly, so this is a fact for the phase F runbook (run dispatch from the queen's Bash tool, whose `setsid` session the Keeper's shell is not in), not a gap in the product.
- **N16 (builder, test only, with the item 5 helpers).** Lengthen the helpers' fixed sleeps so the sweep tests do not depend on a session finishing in under 4 s on a loaded runner.
- **N17 (zero lines).** `observe` keeps refreshing `rootStart` whenever a process with the root's pid is listed, including after the leader is reaped; on linux a reused root pid during the 3 s sweep would move the adoption threshold. Needs a pid wrap inside the sweep; noted for whoever extends the tracker (my N14 restated for the new code).
- **N18 (queen, docs).** Once `blind` is set it stays set, and a transient read failure during the sweep ends the sweep after that poll with the survivors alive and `survivors_unchecked` in the warnings. The warning text ("the process table could not be read") covers it. A retry of a failed poll inside the 40-round bound would be two lines, for D2.
- **N19 (builder, low, one changed line).** `syscall.Getpgrp` does not exist in Go's `syscall` for `solaris` and `illumos`, so `internal/dispatch` stopped cross-compiling there with `e0d3b61` (the merge-base builds on both). `syscall.Getpgid(0)` is the portable spelling if that matters; the product supports darwin and linux hosts, and item 7 pins only the Windows cross-compile, so this is a note.
- **N20 (zero lines).** The `cell_other.go` stub's `tracker{ blind bool }` is only there so `runSession` compiles on Windows; it is never set, and `ownGroup` refuses before `newTracker` runs. Fine as is.
- **N22 (builder, D2, about 6 lines moved, 0 added).** The two `sweep` guards (M1, M2) can only be tested by signalling, which D-193 keeps off the host. Factoring the target selection out of `sweep` into a pure `targets(live []proc, self, group int) (pids, pgids []int)` lets a data test pin both guards (pid 1, self, pgid 0 and 1, dispatch's group, a Keeper group) with no process started and no signal sent, and `sweep` becomes the kill loop only. For D2, since D1 is at its stop.
- **N21 (builder, test only, D2).** No test pins the `tctx.Err()` check before a renewal (M4). A stalling backend that counts calls after the session's end, with a keepalive shorter than the renewal, would.

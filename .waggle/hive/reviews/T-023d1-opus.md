## D-176 and the exit path today (known open item, not blocking)

`signalGroup` sends SIGTERM or SIGKILL to `-pid` of the worker, the group `Setpgid` created. `stop()` (timeout, cancel, token cap, stream end while running) sends SIGTERM, then SIGKILL after `killGrace` (10 s). The exit goroutine sends SIGKILL to the group right after `cmd.Wait()` returns. The probe shows that Bash tool children lead their own groups, so neither signal reaches them. They die on the SIGTERM path only because Claude Code reaps its own children when it handles SIGTERM. They survive when:

- Claude Code exits on its own while a tool child still runs.
- Claude Code ignores SIGTERM past the grace and gets SIGKILL.
- Claude Code crashes.

`Run`'s promise that "the process group is gone" stays literally true and covers less than it reads. `dispatch.lock` is released while a survivor runs, so the next dispatch can start beside it, and that run's snapshot absorbs whatever the survivor has done so far.

What the post-run check can catch from a survivor:

- Caught: anything written before the files step and the git step, which is every hash, ref, admin entry and status the snapshot covers.
- Caught at the next dispatch, with limits: writes to the hashed host files after the check. The host record catches them only if this run was clean, the survivor wrote after `saveHostRecord` (N2), and it did not rewrite `host-files.json`.
- Caught or erased on reuse: worktree writes. A builder's reuse fails `checkClean` (exit 3). A guard's reuse is reset, except for B1.
- Not caught: ref moves after the check. The push sends the checked OID, but nothing compares refs across runs, so a survivor that moves `refs/heads/main` or a claim ref after the run goes unseen.
- Not caught: main checkout writes after the check. The record holds no status.
- Not caught: writes outside the repo.

On linux, the narrowest fix is `PR_SET_CHILD_SUBREAPER` on dispatch, then killing every remaining descendant after the leader exits. macOS has no subreaper, so there the option is a descendant walk (by `ppid`) while the leader is still alive.

### Blocking Issues (Must-Fix Only)

**CB1. A blank command name hides a process and its whole subtree from the darwin tracker (D-187)** [1 line plus a test]. `reap_ps.go` asks for `pid=,ppid=,lstart=,stat=,comm=` and skips any line with fewer than 9 fields. A process whose argv0 is empty or blank prints no `comm`, so its line has 8 fields and is dropped. Nothing that descends from it is found either, because its children's ppid is a pid the table does not list. C1: a setsid perl with `$0 = ""` or `" "` is never killed and writes its marker; the same child named `probe` is killed. C1b, through `Run`: the blank-named child is alive when `Run` returns exit 0 with no violation and no survivor, and then writes `hooks/post-checkout` into the main checkout. In the Bash tool's own shell this is one word: `ARGV0=' ' cmd` (zsh) prints the same 8-field line. The D-176 probe passes only because Claude Code names its children. A newline in argv0 is printed as `\012`, so there is no line injection; linux reads `comm` between parentheses and is not affected. Fix: accept 8 fields and take `comm` from `f[8:]` when present (an empty name is fine, the identity is pid and start). Worth adding while there: the sweep kills by pid only; also sending SIGKILL to each tracked process group (`-pgid`) would catch an unseen child that stayed in a tracked tool shell's group.

**CB2. `product-ci` is red on linux since `a78dd68`** [about 3 lines]. `gh pr checks 57`: `product-ci` fails on ubuntu-24.04 at `a78dd68`, `ab64571` and `d95aa72` (`d48deaf` was green) with `TestRunLimitsKillTheGroup/max_tokens` and `/timeout`: "grandchild survived". Cause (C7): with `PR_SET_CHILD_SUBREAPER`, the worker group's `sleep` grandchild, killed by the group SIGKILL after the leader exits, is reparented to dispatch and stays a zombie of dispatch (`/proc/<pid>/stat` state `Z`, ppid the test pid), so `kill(pid, 0)` keeps succeeding. `sweep` reaps only what it killed itself and `poll` skips zombies, so a tracked process that is already a zombie at the sweep's first poll is never reaped. Whether the test passes depends on that timing (it passed once in my container and fails every time in CI). Fix: at the end of `sweep`, `Wait4(pid, WNOHANG)` every tracked pid whose entry shows ppid equal to self (zombie or killed), not only the killed ones. The product effect is zombies under the CLI until it exits, so the blocker is the red check and the false "survived" signal, not a leak.

**CB3. `d95aa72` makes a stalled renewal unbounded, lets renewals start after the session, and on linux puts a renewal in the sweep's path** [about 5 lines]. The intent (do not kill a renewal mid-write) is right, and a renewal still cannot outlive `Run` or write after the checks: `wg.Wait()` precedes the return and the checks. But: (a) `renew(context.WithoutCancel(tctx))` has no deadline at all, and a remote-mode `AcquireLease` is a push to origin, so a stalled network now holds `Run` and `dispatch.lock` forever; before, the session timeout bounded it. C5: a renewal that stalls 8 s, session timeout 1 s: `Run` takes 24.9 s at `d95aa72` and 1.7 s with `renew(tctx)`. (b) The 24.9 s is three stalls: after a renewal returns, the loop's `select` sees both `tctx.Done()` and a buffered tick and picks at random, so new renewals start after the session ended. (c) The renewal loop keeps running after the leader exits, concurrently with the sweep. On linux the sweep adopts any child of dispatch younger than the worker (`ppid == self` and `startedAfter`): C4 shows dispatch's own `sleep` child, started 300 ms after the worker, killed and recorded as a survivor. The only such child in production is the renewal's git, so a renewal in flight at the sweep is SIGKILLed mid-transaction, which can leave a ref `.lock`. Fix: end the renewal loop on `exited` as well as `tctx`, check `tctx.Err()` before starting a renewal, run each renewal under `context.WithTimeout(context.WithoutCancel(tctx), <bound>)`, and have the sweep goroutine wait for the renewal loop to finish before it sweeps.

### Answers to the queen's questions

- **darwin `ps`:** pinned to `/bin/ps`, `exec.CommandContext` with a 5 s timeout, env exactly `LC_ALL=C` and `TZ=UTC`, so `lstart` is the fixed English five-field form in UTC (C1 output). One-second resolution: the identity check and the kill are a few ms apart, and a pid wrap inside that window on darwin's sequential pids cannot be steered onto a chosen victim; `TestSweepSkipsReusedPid` covers the mismatch case. A name change is harmless (identity is pid and start), except a change to a blank name, which is CB1. Cost: one `ps` sample is about 46 ms on this Mac (about 1000 processes), every 250 ms for the whole session.
- **Double fork gap:** measured (C2, poll 250 ms, staggered phase): intermediate lifetime 0 ms escapes 10/10, 50 ms 10/10, 125 ms 7/10, 200 ms 3/10, 300 ms 0/10, about `1 - d/250` as expected. On darwin a deliberate `daemon()` therefore escapes almost always; this is D-187's documented gap and is correctly in `not_enforced`. On linux the subreaper catches every case (0/10 at every d).
- **Sweep bound and respawn:** 40 rounds of poll plus 25 ms, under 3 s on darwin. ### Rulings on the seven questions

**1. The 037ba4f hardening holds. No remaining path is a D1 must-fix; two are notes (N15, N16).**
- Every guard named in the brief is in place. The builder's fix-removal run shows the `observe` and `newTracker` guards pinned by `fix4_test.go`. The two sweep guards are not pinned, but my container mutants show both are load-bearing. G1: with `p.pid > 1 && p.pid != t.self` removed, a tracker whose `seen` holds dispatch's own identity SIGKILLs the test process (`signal: killed`). G2: with the pgid guard replaced by `true`, a tracked child left in dispatch's own group makes the sweep send `kill(-Getpgrp())`, which killed the test binary and the `go test` and `timeout` processes above it (exit 137). With both guards in place, G1 kills nothing and G2 kills only the child by pid.
- Pid reuse between sample and kill (G4): on linux a table read is about 0.9 ms, and the 20 targets were signalled 31 µs after the read finished. Pids are assigned in sequence on both systems, so reuse inside that window would need a full wrap of the pid space within a millisecond. Not reachable. The start-time identity still guards `seen` across polls.
- Sessions and groups: dispatch starts the worker with `Setpgid`, not `Setsid`, so the worker stays in dispatch's session (the Keeper's terminal session when run by hand). Claude Code's Bash tool shells are session leaders: this guard's own tool shell shows `Ss`, pgid equal to its pid, and no tty. So a tool command's descendants can only join groups the worker tree created. A worker descendant that is not under a tool shell can still call `setpgid(0, G)` for any group G in the Keeper's session. See N15 (G3).
- darwin: the same guards apply. Without a subreaper, `kids[self]` is always false, and an orphan reparented to launchd has ppid 1 and is never adopted, so the sweep reaches only identities it saw while their parent was tracked. `TestProcTableLayout` passes here (pid, ppid, pgid, zombie state, start, name).
- Fail-closed paths: when `Sysctl` fails five times, the table comes back empty with the error, and `observe` drops it and sets `blind`. A table returned with an error is never used (`TestObserveErrorClearsLive`).

**2. `TestSweepKillsTrackedGroup`: a test bug, and the assertion is not weakened.** The check is still `!gone(orphan.pid)` (`kill(pid, 0)` keeps failing for 5 s). The fix gives the tracker its real root (the spawned `sh`, in place of the `newTracker(0)` that was the incident's shape) and sets `rootStart`. With `rootStart` set, the sweep reaps the killed orphan when an earlier test has made the process a subreaper. Before, the orphan stayed a zombie that answered `kill 0`. `product-ci` is green at `037ba4f` (linux, `internal/dispatch` ok in 66.9 s), and the test passed 10 of 10 in my container repeats.

**3. `reap_other.go` fails closed, and the NotEnforced clause for it is accurate.** `procTable` always returns an error, so `observe` empties `live` and sets `blind`. The sweep sees `live` empty and signals nothing, and every run warns `survivors_unchecked`. `GOOS` freebsd, openbsd, netbsd, linux and windows each pass `go vet ./internal/dispatch/`. The clause "on other unix systems no tracker runs and only the worker's own group is killed" is accurate. The darwin clause understates how often the escape happens; see 6 and N17.

**4. The `case <-exited` renewal branch: a D2 carry, not a D1 must-fix.** No test names it, but `TestStdoutHolder` should catch its removal. Without the case, the loop ends only on `tctx`. `tctx` is cancelled only after `Collect` returns, and `Collect` returns only when the pipe closes. The sweep waits on `<-renewed`, and the pipe cut runs after the sweep. So a setsid child holding stdout holds `Run` until the session timeout (120 minutes in the fixture), and `TestStdoutHolder`'s 8 s bound fails on both systems. I could not confirm this by mutant: every container build of that mutant was OOM-killed (the 2 GB VM was shared with the fable container and two local database stacks, which restarted under the pressure), and D-193 rules the host out. The sibling `tctx.Err()` check is pinned by nothing: its mutant passed `TestRenewalBounded`, `TestSweepWaitsForRenewal` and `TestRunKeepalive`. That check only stops a renewal starting on a tick that races the cancel. Carry a direct test for both to D2: a renewal stub that records starts after the leader exits.

**5. The linux flakes come from load, not a product race.** The container VM has 2 CPUs and 2 GB and was shared during my runs. `TestSurvivorKilledAndRecorded` gives its helper a fixed 4 s life. Every failure is a `Run` that took longer than that, so the helper exited on its own before the sweep (`survivors []`), or wrote its marker just before the kill. With the helper's life raised to 12 s, it passed 19 of 20. The one failure was a 67 s run that outlived even 12 s, and it was never `survivors []`. Unmodified, it passed 15 of 20 in each of two runs, every failure at 6 s or more. The builder's debug run also shows the helper in `seen` at the sweep, so it was tracked. It had already exited. `TestRunKeepalive` asks for 3 leases in a 1 s worker. Since `case <-exited` stops renewals once the leader is gone, a slow renewal under load leaves 2. That is a test margin. `TestRunLimitsKillTheGroup/max_tokens` without `--init` is an environment artifact: the builder ran a cross-built test binary as the container's pid 1, so orphans and zombies landed on a process that never waits for them, and `kill(pid, 0)` sees a zombie as alive. With `--init` and in CI it passes. The same load also explains the other container-only failures in my full suite run: `TestStdoutHolder` took 14.8 s but killed the holder, a `claude --help` hit its `WaitDelay`, and the 10 min package timeout fired. The git 2.39 failures (`guard3_test.go`) are the image's git version, as the builder also found. Note N18 on hardening the tests.

**6. Darwin catch rate: keep the tracker at 25 ms, state the gap plainly, and leave the real fix to a later phase.** My data-only probe used Claude Code's shape: the worker forks a setsid tool shell, which runs a 100 ms step, backgrounds `sleep 2`, and exits. Over 20 runs per interval:

| interval | tool shell seen | background child seen | background child alive in the tool shell's group after the worker exits |
|---|---|---|---|
| 25 ms | 20 | 0 | 20 |
| 5 ms | 20 | 6 | 20 |
| 1 ms | 20 | 13 | 20 |

One table read costs about 0.25 ms here (about 590 processes), so 25 ms is 1% of a core, 5 ms 5% and 1 ms 25%. That agrees with the builder (0 of 65 at 10 to 50 ms). A shorter interval costs CPU on every dispatch and still loses most cases, so do not change it. Do not drop the tracker either: it catches every tool shell and any setsid child alive at the worker's exit, the shapes in fable's table and CB1, and with it gone only the worker's own group would be killed. The cheap lever is in the third column. A `cmd &` or `nohup cmd &` child stays in the tool shell's process group after the shell exits, and the tool shell was seen 20 of 20. A sweep that also signals the group of every seen group leader (pgid equal to a seen pid) would kill all 20, and only a child that calls setsid again would escape. This needs care because it is the incident's class: a group id can be reused once the group empties. Signal group G only when G > 1, G is not `Getpgrp()`, and the table shows either no process with pid G or one whose start matches the seen identity. That is about 6 lines and over D1's budget (see 7), so it is a Keeper choice for D2 or T-024, not D1.

The text needs one change now (N17). "One that daemonizes between two polls escapes" reads as a narrow race. In practice, a background child of a tool command whose shell exits at once almost always escapes on macOS. The phase F trial report owed by D-191 should quote that.

### Notes (non-blocking)

- **N15 (D2, 1 line; Keeper should know).** G3 in the container: a worker descendant that calls `setpgid(0, G)` into an existing group of the same session (a stand-in for the Keeper's shell group) was tracked, and the sweep's `kill(-pgid)` killed the stand-in, which is not a descendant. It takes a deliberate call, and a host-cell worker can already signal anything the Keeper owns, so this adds no new power over the Keeper's processes. It does mean the sweep's "only the worker's tree" property relies on the worker not joining a foreign group. Starting the worker with `Setsid: true` in place of `Setpgid` in `cell_unix.go` closes it structurally: `setpgid` cannot cross sessions, and `kill(-pid)` still names the worker's group. A narrower alternative is to signal only groups whose id is the root or a seen pid.

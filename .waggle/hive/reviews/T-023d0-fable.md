### N1 closed: whitespace and control identity (P2, 25 cases, real commits for the ones that pass)

- `strings.TrimSpace` uses `unicode.IsSpace`, so U+00A0, U+2003, U+3000, U+0085, U+2028 and U+2029 count as blank. A name of only U+00A0 with an email set is refused as half-blank; U+00A0 in both fields, U+00A0 or U+3000 with an empty email, and em space with a space email all become the zero identity with no `GIT_AUTHOR_*` or `GIT_COMMITTER_*` in the env. A U+0085-only or U+2029-only name with an empty email is refused (the control check runs on the untrimmed value), which is the conservative side.
- Git accepts U+00A0 in a name: with an inner or padding U+00A0 and a real email the identity passes `check` and git 2.54 stores the bytes unchanged (its crud stripping covers bytes at or below 32 and a short punctuation list). Harmless; the only reach is cosmetic.
- Refused as claimed: NEL in the email, tab-padded name, DEL, overlong NUL, an encoded surrogate, a raw 0xff with a blank email, form feed, vertical tab. Accepted and stripped by git: ASCII space padding (`" A "` is stored as `A`).
- What still passes `check` with a visually empty or deceptive name: U+200B, U+FEFF and U+202E (category Cf, neither space nor control), which git stores; `.` (git 2.54 stores it); `<>` (git refuses at commit with "name consists only of disallowed characters"). Not blocking: the identity comes from the Keeper's git config, and refusing all of Cf would also refuse ZWJ sequences in real names. Phase D should trim what it reads from `git config` and treat a blank result as exit 3, as noted before.
- `workerEnv` now gates on `strings.TrimSpace(id.Name) != ""`; `Prepare` calls `check` (line 231) before `workerEnv` (line 242), so the "both set or both blank" comment on that line is true at every call site. The values are passed untrimmed, which is fine since git strips ASCII whitespace.

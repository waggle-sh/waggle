## Blocking issues

### 1. `held2.pl` proves the pid path only on the runs where the tracker happens to list it before `setpgrp`; on the others it is a group-path kill that `result.json` cannot tell apart

Runbook 2.2 makes `setpgrp(0, 0);` the first statement of `held2.pl` and says it "stays tracked by pid only, so it proves sweep's pid path"; 2.5 (the D-199 paragraph), the Pid path gate bullet and 7.3 build on that. The product does not guarantee it. `observe` in `reap_unix.go` records a process in `leaders` only at first sight, when its pgid equals its pid (lines 87 to 93). `targets` then names every tracked leader's group that has a live member (lines 129 to 138), and `sweep()` kills groups before pids (lines 169 to 182). So:

- If the first table read that lists `held2.pl` comes before `setpgrp`, its pgid is the tool shell's, it is not a leader, and after `setpgrp` it is outside every tracked group: the sweep reaches it only through the pid loop. That is the pid path the runbook claims.
- If that first read comes after `setpgrp`, its pgid is its own pid, it is recorded as a leader of a one-process group, `targets` names that group (`member` is itself, `same` is true), and the sweep kills it with `kill(-pgid)` on the group path; the pid loop then finds it already noted. `result.json` shows the same `Survivor` either way, and `ps-0a-during.txt` is taken after `held2.pid` exists, which is after `setpgrp`, so no capture can tell the two apart.

The darwin poll is 25 ms (`reap_darwin.go` line 19). On this Mac a fresh `perl` reaches `setpgrp` 8 to 22 ms after exec (ten samples through a tiny timing script in my scratchpad, measured from a timestamp taken just before the exec, so an upper bound). The first sighting therefore lands on either side of `setpgrp` with similar odds. On roughly half the runs the report and the cutover card would say "held2 proves the pid path" when the group path fired, and D-217's second half ("proves the pid path") rests on a coin flip nobody can inspect. This is a defect against D-217 and against the D-203 case of cutover evidence that does not show what it claims; it is not the cutover gate itself (Pass rests on `held`), but it is the evidence the card cites.

Fix, in 2.2 only (D-217's design is unchanged, the pid file is still written after `setpgrp`, and the during-capture pgid check still holds):

- `probe/held2.pl` starts with a pause longer than a few polls, then `setpgrp`: its first two statements are `select(undef, undef, undef, 0.2); setpgrp(0, 0);`, then the pid file and `sleep 300;`. With `hold2.sh`'s shell alive for 1 s, the tracker's first sighting (about eight reads inside those 200 ms) records `held2.pl` in the tool shell's group, not as a leader; after `setpgrp` it is outside every tracked group and only the pid loop can reach it. Change "its first statement is `setpgrp(0, 0);`" to "its first statements pause 200 ms (several 25 ms tracker reads, so it is first listed inside the tool shell's group, never as a group leader) and then call `setpgrp(0, 0);`". One clause in the D-199 paragraph, "only `held2`, outside every tracked group, proves the pid path", can then stay as written.

Nothing else in the round needs to move for this.

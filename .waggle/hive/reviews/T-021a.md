## Non-blocking findings

1. **Resume guard is token-exact, so some resume paths pass** (probes.txt). Refused: `--continue`, `-c`, `--resume`, `-r`, `--session-id`, and each with `=value`; `--resumed`, `--RESUME` and `--session-ids` are correctly not refused. Not refused: `-rabc` (attached short value, which Claude Code's parser very likely reads as `-r abc`), `--from-pr`, `--teleport`, `--fork-session`. The brief's S1 names only the three flags, so AC6 holds, but the intent (fresh session per task) is weaker than the comment claims. Also over-refuses a value that equals a flag (`--append-system-prompt -r`), harmless. Suggest a follow-up that also rejects `-r*`/`-c*` clusters, `--from-pr`, `--teleport`.
2. **`default_args` can override what the adapter sets** because it is appended last: `--max-turns 9999` (wins over the profile), `--model evil` (pre-existing from T-012), `--mcp-config x.json` (defeats S6), and a duplicate `--strict-mcp-config` (harmless). The values come from the Keeper's own config, not an attacker, but phase B or the launcher should reject `--max-turns`, `--model` and `--mcp-config` there.
3. **Overflow in `Settings`.** Brief only requires nudge >= 1000. `nudge_tokens` above about 1.2e17 overflows `nudge*75/100` to a negative `HandoffTokens`, and the guard floor does not rescue it (floor overflows the same way). Unreachable with sane config; phase B should cap `nudge_tokens` (for example 10,000,000).
4. **Does a config string reach argv or env unescaped?** Env: no. `BASH_MAX_OUTPUT_LENGTH` and `MAX_THINKING_TOKENS` come from `strconv.Itoa` of ints and a fixed map; no string from config enters the environment. Argv: `default_args` entries go verbatim into the argv slice (no shell), so a config author can add flags, see 1 and 2. A hand-built zero `ContextSettings` gives `--max-turns 0` and `BASH_MAX_OUTPUT_LENGTH=0`; `Settings()` never returns zeros without an error, so only a caller that skips it is exposed.
5. **Q-T021-6 (builder judgment call 3).** The installed Claude Code 2.1.302 has `MAX_THINKING_TOKENS`, `BASH_MAX_OUTPUT_LENGTH`, `--max-turns` and `--strict-mcp-config`. `--max-turns` is hidden from `--help` and, per Claude Code docs, applies to non-interactive (`-p`) runs: the launcher must use print mode. The binary also contains `DISABLE_AUTO_COMPACT`, so S5's "disabled where the adapter can" may be achievable with one more env entry; I did not test its behaviour. The builder documents the alternative path (handoff below compaction point), which satisfies the brief's fallback. Head Keeper to decide whether to add `DISABLE_AUTO_COMPACT=1` in phase C.
6. **Prompt assembly bounds are line-based only.** A read-only file of lone-CR line endings, or a few very long lines, counts as 1 line each and bypasses the 1,500-line cap; there is no byte cap. A read-only `Path` containing a newline can forge a prompt line. File content and paths come from the Keeper's own brief and repo, so this is low risk. CRLF and NUL bytes pass through verbatim and are counted correctly (CRLF counts per `\n`).
7. **`TrimOutput` is line-based.** A single 5 MiB line is returned whole (0 trimmed). Output can exceed `maxLines` by the marker plus up to 50 rescued lines (61 lines for cap 10 with 200 failure lines); the doc says "about". A `fullPath` containing a newline can forge a marker line; the launcher chooses that path. Failure lines at the head/tail boundary are not lost (probes: line 4 of 11 kept and counted, boundary lines stay in head or tail).
8. **Handoff.** A body containing the handoff's own markers (`## Next`, `# Handoff: T-2 guard 9`, blank bullet) round-trips byte for byte because every body line is prefixed `- `. `RenderHandoff` does not validate its input: an item with an embedded newline renders structure that `ParseHandoff` then rejects (`ErrBadHandoff`), so it fails closed. CRLF, spaces in task or role, and sequence 0 are rejected.

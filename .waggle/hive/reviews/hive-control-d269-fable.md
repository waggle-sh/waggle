## Workflow security review (D-203 threat model)

- Token scope: workflow-level `permissions` stays `contents: read`; the verify job declares `contents: read` and `pull-requests: read` only; `relay-claim` keeps its write permissions but is gated to `issue_comment` plus the `/waggle claim` prefix, unchanged. GitHub gives `pull_request_review` runs from forks a read-only token and no secrets, the same as `pull_request`; for same-repo branches the job's own declaration caps it at read. The token appears once, in the `Waggle gate` step env, where it is also in the environment of `go build` from base source (trusted) and of `git` subprocesses (git does not read `GITHUB_TOKEN`; the reader never runs `gh`). Logs mask it.
- Base vs head: `actions/checkout@v4` with `fetch-depth: 0` checks out the merge ref for both events and fetches every branch, so `base.sha` and `head.sha` are reachable; the checker is built from `BASE_SHA`, never from the head or the merge commit, and `setup-go` reads `go.mod` from the merge checkout (the accepted note from D-250).
- Injection: no PR-controlled field (head ref, title, body, labels) is interpolated into any `run:`; PR SHAs reach the gate through `env:`. The `${{ }}` in the verify job are `pull_request.number` and `pull_request.head.sha`, both GitHub-written, both present in `pull_request` and `pull_request_review` payloads. The pre-existing `relay-claim` interpolations (`comment.user.login`, `issue.number`) are unchanged and out of scope (G4 removes the job).
- Concurrency: only the verify job carries the group, and its `if:` excludes `issue_comment`; even if the expression were evaluated for a non-PR event, missing properties resolve to empty strings and cannot error or inject. The group keys on head SHA, so a run for one head cannot cancel a pending run for another; `cancel-in-progress: false` lets the running job finish and the newest event's run always executes last with the full review list.
- Can `edited` or a review turn a failing required check green without a valid approval? No. The ruleset on `main` requires `product-ci` and `verify-leases-and-tiers` (strict) plus one approving review with code owner review; the hive merges Tier 3 PRs through the admin bypass as before. The gate's result is a function of base, head and the base config, not of the event type: hardcoded Tier 3 paths (`.waggle/`, `.github/workflows/`, `.gitlab-ci.yml`, `.devcontainer/`, `go.mod`, `go.sum`, `go.work*`, `vendor/`) are never approvable (`approvablePath` rejects every `HardcodedTier3Prefixes` match); with no approvers listed there is no approval path at all; a review from an unlisted account, a stale approval at an older head, a dismissed one, or one before the last base change does not count (`approvedBy` at `97127fc`, read in ID order from `api.github.com` with no bodies). `edited` closes the pre-existing retarget hole in the hive: a base change now reruns the gate against the new base and, under D-267, invalidates earlier approvals.
- `issue_comment` and `relay-claim`: unaffected; the new triggers add events that `relay-claim`'s `if:` rejects.
- Fork PR with an author-controlled head: the head only affects the diff being scanned and the workflow file of the merge commit (the pre-existing GitHub behavior that a PR editing the workflow runs its edited copy for `pull_request` and `pull_request_review` alike, noted in the brief and carried to G4); the gate source, the approver list and the protected-path policy come from base.
